# 開発ツールのテスト

（テストの一覧は [`tests/README.md`](../../../tests/README.md#何をテストしているか)）

## CI 完了待ち

**`CiWaitScriptTests`** … `scripts/ci-common.sh`（待機の土台）と `scripts/ci-wait.sh`
（PR ／ブランチ ／コミットの CI 完了待ち）を、フェイクの `curl` を `PATH` の先頭に置いて
検証します（`tests/ci-wait.test.sh`）。プラグインのコードではなく開発ツールですが、
守っている性質——**待機は必ず有限時間で終わる**・「まだチェックが登録されていない」や
「新しい push で古い run がキャンセルされた」を green と取り違えない——が 2 度壊れ、
そのたびに「CI は終わっているのにセッションが気付かない」という事故になったため、
回帰テストを ctest ／CI に組み込んであります。締切・ウォッチドッグ・API 連続失敗の
打ち切りといった歯止めは、フェイクの probe で直接動かして確認します。

## clang-tidy の結果キャッシュ

**`TidyCacheScriptTests`** … `scripts/tidy-cache-key.py`（翻訳単位ごとの鍵）と
`scripts/clang-tidy-sdk.sh -c`（その鍵で解析を省略する側）を、**合成のリポジトリ**と
スタブの clang-tidy に対して検証します（`tests/tidy-cache.test.sh`）。これも開発ツール
ですが、間違えたときの現れ方が最も深刻——**鍵に漏れがあると、直した翻訳単位を解析しないまま
CI が緑になる**——なので回帰テストで押さえてあります。

**スタブは本物と同じ「成功時の余分な出力」を出します**（`72231 warnings generated.` など）。
これが要点です——控える条件を「出力が空なら」と書いていたせいで実機では**1 件も控えられて
おらず**、それでも CI は緑でした（結果は正しく、ただ何も速くならない）。何も出力しないスタブでは
その欠陥がテストで検出されません。

確認しているのは「診断を変えうるものは、すべてキャッシュを無効にする」ことです: 翻訳単位そのもの・
**推移的に include されたヘッダ**（`.cpp` は名前すら知らない孫ヘッダ。素朴な鍵が
取りこぼす場所）・`.clang-tidy`・コンパイル指令・`VW_SDK_CACHE_KEY`・**ランナーイメージ**
（`ImageOS` / `ImageVersion`。コンパイラの既定の検索パスから来る標準ヘッダの代表）。裏返しの性質も
同じだけ確認しています——**診断の出た翻訳単位を「きれい」として控えない**こと、入力を
突き止められない翻訳単位（compile database に無い・綴りがマクロで決まる `#include`）は
必ず解析されること、そして `-c` を渡さなければ従来どおり全部を解析すること。

逆向きに、**診断を変えないものでキャッシュを無効にしない**ことも確認しています
（`clang-tidy --version` に混ざる `Host CPU:` のような実行機ごとに変わる行で鍵が変わらない
こと）。この仕組みの壊れ方はいつも「緑のまま速くならない」なので、テストの側で押さえる
しかありません。

本物の clang-tidy は要らず（スタブが「どれを解析させられたか」を記録します）、bash と
python3 だけで走ります。
