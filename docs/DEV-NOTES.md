## 設計の考え方

### 2 フェーズ分離が全ての土台

処理を **IFC 解析（`src/parse/`）** と **VW 描画（`src/draw/`）** に完全分離し、両者を
**命令セット（`src/core/Document.h`）だけ**でつなぐ。`parse/` と `core/` は SDK を一切
include しないので、SDK 無し（約 800MB のダウンロード無し）で**コンパイルも単体テストも
できる**——これがこのリポジトリの生産性のほぼ全てを支えている。

- 解析ロジックは**実 IFC に対して CI で常時テストできる**（`tests/`）。
- 描画は実機でしか確かめられないが、**そこへ持ち込む値は先に固められる**。だから実機での
  切り分けが「命令セットの値が違うのか／SDK の呼び方が違うのか」の 2 択に絞れる。
- 依存の向きは CI が担保する（`core/` `parse/` を無 SDK でビルド・テストするジョブがある）。

**この分離を崩さないこと。** 「ここだけ SDK の型を使えれば楽」という誘惑は、無 SDK
テストの土台ごと壊す。SDK の幾何型が要る計算は `core/Geometry.h` の自前 `Vec2` / `Vec3` /
`Mat4` で書き、`draw/` の入口で変換する。

### 命令セット（Document）の設計則

- **フェーズ間で運べないものを載せない。** SDK ハンドル・STEP エンティティポインタは
  Document に入れない。描画中に必要なハンドルの受け渡しは「命令インデックス → ハンドル」の
  対応表（`draw/ObjectHandles`）で行う（立上り → 壁結合、横架材 → データタグ、柱 → 記号）。
- **同型が並ぶところは 1 つの構造体へ畳む。** アンカーボルト・床束・火打・仕口は中身が
  同じなので `core::SymbolCommand` 1 つで受け、要素の区別は「Document のどのリストか」が
  担う（描画も `draw/Symbol` ただ 1 本）。
- **突き合わせが要る関係は入れ子で持つ。** データタグは `ViewportCommand::tags`、
  グラフィック凡例は `SheetCommand` の中。平らに並べて番号で突き合わせる形にすると、
  突き合わせ自体がバグの温床になる。
- **振り分けは解析側でやり切る。** 「このタグはどのビューポートに載るか」のような判断は
  `parse/` が決め、`draw/` は「渡されたものを置く」だけにする。伏図と軸組図で**描画実装を
  1 つ**にできるのはこのため。
- スキーマを変えるときは、構造体定義・`validateDocument`・テストを**同時に**更新する。

### 描いた結果に対する 5 つの方針

1. **空のものを先に作らない。** 描画対象の無いレベル・レイヤ・凡例は作らない（空レイヤが
   図面に溜まると、利用者はそれが失敗なのか仕様なのか判断できない）。ストーリのレベルは
   「その要素の命令が実際にあるか」で足す。
2. **図面の既存リソースを書き換えない・増やさない。** スラブ／ウォールスタイルも
   データタグスタイルも**作らず**、構成層・基準面・タグレイアウトをオブジェクトへ直接
   与える（スタイルを作る形は、取り込みのたびに名前付きリソースが増え、しかも undo で
   消えないため、どちらも一度採用してから撤回した）。
3. **決定性を守る。** エンティティの列挙順に依存しない結果を出す。ソート・集約は明示的に
   行い、同値のときの順序も決めておく（`#id` 昇順など）。テストは全要素で決定性を見ている。
4. **1 要素の欠損で全体を止めない。** 想定外のエンティティ・解決できない幾何はスキップして
   次へ進む。例外は `parse/` 内部の局所処理に留め、フェーズ境界は値で返す。SDK
   コールバック（`plugin_module_main` / `DoInterface`）へ例外を漏らさない。
5. **診断は「異常だけ」を出す。** 平常時に鳴る診断は外す（後述「[診断・完了報告の方針]
   (#診断完了報告の方針m15m19)」）。完了ダイアログに出るのは、件数の一覧と**起きては
   いけないこと**だけ。

### 形状を先に確定し、支持部材を合わせる

床（床版）・屋根（屋根版）は建物の外形そのものを表す一次情報で、位置決めの基準になる。
そこで**床・屋根面を先に確定**してから、横架材・柱という支持部材をそこへ合わせる。

- 垂木・野地板は**屋根版から導出**される（IFC に垂木は出力されない）。面が形を決める。
- **登り梁はホームズ君の入力位置が不正確**（軸勾配が屋根版より急・端部が受け材へ食い込む）
  なので、天端中央線を屋根面へスナップし、端部を受け材（横架材・柱）の面まで詰める。
- 床版は IFC の位置を尊重し、スキップフロアの段差を絶対 Z で表す。

### 部材の端点は接合点（芯線の交点）に置く

構造材ツールの芯線は断面基準点を通る——横架材は**天端中央**、柱は**断面中心**。したがって
「柱が受ける梁の芯線」は梁の**天端**にあり、「勝ち梁の芯線」は勝ち梁の**天端中央線**にある。

命令の端点を「材が実際に止まる位置」（梁の下端・勝ち梁の側面）に置くと、その座標は
**どの部材の芯線にも乗らない**。すると図面からも命令セットからも「どの部材とどの部材が
接合しているか」を座標だけで言えない。そこで:

- **端点は接合相手の芯線上に置く**（柱・束の上端＝受ける横架材の天端、負け梁の端＝勝ち梁の
  天端中央線、柱に取り付く横架材の端＝柱芯の軸位置）。
- **材が実際に止まる位置は端部オフセット**（構造材ツールの「始端オフセット」「終端
  オフセット」。符号つきで、負が短く・正が長くする）で戻す。上に乗る梁のせいが 150mm なら
  −150、直交する 105mm の梁に負けるなら −52.5。柱に取り付く端は「端点から柱芯までの軸方向の
  距離」の符号を反転した値で、**柱の向こうの面まで来ていた端（外周の桁が隅柱の外面まで
  伸びている取り合い）は正値**になる。

**描かれる形は従来と同じ**で、変わるのは命令が持つ端点の意味だけ。フレーム解析モデル
（節点と部材）を取り込んで組み立てるときの土台になる。実装は `core/Document.h`
「端部オフセット」・`parse/Member` の `resolveMemberInterferences`・`parse/Column` の
`beamSeatAbove` / `memberOnTop`、柱に取り付く端は `parse/Member` の
`resolveMemberColumnJoints`（柱命令は横架材の後に組み上がるので別の関門）。

**端点と「材の端」は使い分ける。** 仕口シンボルを置く位置・登り梁が受け材の面まで詰める
判定・図に映るものの広がりは**材の端**が要るので、`core::memberDrawnStart` /
`memberDrawnEnd` / `columnDrawnTop` / `columnDrawnBottom` を通す（この 4 つが唯一の定義）。

### レイヤ・クラス・レベルの規約は 1 か所に置く

同じ定数・述語を 2 か所に書かない。IFC 属性インデックスは `parse/IfcAttr.h`、レベル種別名は
`parse/Story.h`、基礎のレイヤ名・許容値は `parse/Footing.h`、レイヤ名の組み立ては
`storyLayerName` / `spanLayerName`、記号レイヤ名は `parse/ColumnMark`、構造クラス名は
`parse/StructuralClass.h`。**要素を足すときに触る場所が 1 行で済む**形を保つ
（完了ダイアログの要素一覧が `parse/Summary.cpp` の `kElements` 表 1 つなのが典型）。

### 用紙の割り付けの決め事（M18）

用紙と建物の大きさから縮尺・配置を自動で決める。用紙の読み取り（単位の癖・印刷可能
領域）と「置いた後に測って動かす」作法は SDK リファレンスの
[用紙（シートレイヤ）と割り付け](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Sheet%20Layers%20and%20Page%20Layout.md)
にある。このプラグインとしての決め事は次のとおり。

- **縮尺は「印刷可能領域に収まる中で最も大きい図」を階梯から選ぶ**（`core::fitScale`）。
  階梯は 1/200・1/175・1/150・1/125・1/100・1/75・1/50・1/30・1/25・1/20・1/15・1/10・1/5
  のキリの良い値だけで、どれにも収まらなければ**いちばん小さい図**へ倒す
  （はみ出すくらいなら小さく描く）。
- **伏図は全図が同じ縮尺・同じ位置**（用紙をめくっても図が動かないため）。位置は
  「外形の中心を用紙の中心へ」ではなく、**建物の中心が常に同じ点へ来る**ように置く
  ——伏図ごとに映すレイヤが違えば図の中身の広がりも違うので、外形の中心で揃えると
  ページごとに建物がずれる。ずらす量は「その伏図に映る範囲の中心 − 文書全体の中心」を
  縮尺で割ったもの。
- **縮尺は凡例の幅を引いてから決める。** 用紙いっぱいで縮尺を決めて凡例は置き場所だけで
  避ける、という形も一度試したが、建物がギリギリの大きさだと凡例を置くスペースが
  残らない（凡例も図面の一部で、重なると読めない）。置けなくなるくらいなら図を 1 段階
  小さく描く、が決まりごと。引く幅は定数ではなく**実測した凡例の幅**——凡例の大きさは
  中身が流し込まれるまで確定しないので、`draw/Sheet` は **2 巡**する（1 巡目は仮の縮尺で
  図と凡例を作って幅を測り、2 巡目で確定した縮尺を当て直す。`ApplyViewportScale` は
  縮尺が実際に変わったときだけ——更新は重い）。
- **縮尺を決めた 3 つの値（印刷可能領域・凡例の幅・建物の広がり）は結果として残す。**
  ローカル確認の場で分かるのは結果の縮尺だけなので、これが無いとどれが効いたのか
  切り分けられない（実際に「1/50 のはずが 1/75 になる」で足止めされ、建物が
  18.07 × 13.52m あって当時の割り付けでは 1/50 が入らない——実装も測り方も正しい——と
  分かるまで往復した）。`draw/Sheet` は「伏図の割り付け（mm）: 用紙 … / 印刷可能 … /
  凡例 … / 建物 … → 用紙上 … / 縮尺 1/N」の 1 行を完了ダイアログへ出す。命令の座標に
  現れないもの（通り芯の丸など）のぶん実際の図は見積もりより大きくなりうるので、
  **はみ出し・重なりは描画側が実測して診断へ残す**。
- **軸組図は上下 2 段**になる縮尺を選び、1 段の枚数は用紙の幅から決める。入りきらない
  ぶんはシートレイヤを足し、タイトルを "軸組図(1)" … と連番にする。**何枚に分かれるかは
  用紙が分からないと決まらない**ので、命令セットが持つのは「番号の始まり（伏図の続き）と
  タイトルの基」だけにした（`core::SectionSheetCommand`）。用紙の大きさを読むには 1 枚目の
  シートレイヤが要るので、**先に 1 枚用意してから**割り付けを決め、タイトルは本番の
  ループで付け直している。
- **余白の解釈は `core::resolvePageMargins`（無 SDK）に置いてある。** 読むのは SDK の
  仕事だが、**読めた数字をどう解釈するか**——インチか mm かの突き合わせ・0 の扱い・
  負値の棄却——は算数でしかないので、描画側から切り離して `CoreLayoutTests` で
  テストする（CLAUDE.md「描画側から切り離せる純計算」）。

### 診断・完了報告の方針（M15/M19）

進捗ダイアログ・診断ログ・例外境界の SDK 作法は SDK リファレンスの
[進捗・診断](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Progress%20and%20Diagnostics.md)
にある。このプラグインとしての決め事は次のとおり。

- **進捗バーの重みは実測で按分する**（`core::drawWeight`）。1 件あたりの重さは要素で
  **3 桁**違った——仕口 0.1ms/件・アンカーボルト 0.1ms/件に対し、底盤 670ms/件・軸組図
  520ms/枚・伏図 480ms/枚・横架材 130ms/本。件数比で配分すると、シンボル 472 件（全命令の
  4 割超）が 0.05 秒でバーを 4 割進め、17 秒かかる軸組図 33 枚が 3% しか進まない**嘘の
  進捗**になる。
- **完了ダイアログは読まれない前提で組む（M19）。** ダイアログは「どのファイルを・
  成功したか・問題はあったか」の 3 つに絞り、内訳・注意・記録はログへ移す。残すのは
  **その場で操作が要ること**だけ——伏図・軸組図の「1 回更新」と、「取り消し」が普通には
  効かないときの断り。**描けた件数も所要時間も出さない**（うまくいっているときには読む
  必要が無く、うまくいっていないときはその数だけでは足りない。どちらもログにある）。
  **当たり前のことは書かない**（1 回で戻せるときは何も出さない）。
- **「問題あり」の判定には、平常でも出る説明を混ぜない（M19）。** 異常＝
  `DrawCounts::diagnostics`（完了ダイアログの「問題あり」の根拠）／平常の記録＝
  `DrawCounts::notes`（ログにだけ出る）と行き先を分け、前者だけを結末の判断
  （`parse::importOutcome`）に使う。
- **ログは取り込みのたびに必ず開く（M19）。** 「困ったらログを貼る」を運用の柱にした
  以上、要るときに限って無いのでは意味がない。ログは**ファイルと同時にメモリにも溜める**
  （`core::trace::text`）——一時ディレクトリへ書けない環境でもダイアログのログ欄には
  出せるし、表示のために読み直さずに済む。置き場所はログ自身の見出しに書き、書けなかった
  ときは黙らず「ファイルは無い」と出す。
- **ログの見出しは「どのリビジョンを・いつ・どのファイルに対して動かしたか」（M19）。**
  dev ビルドは PR ごとに中身が違うので、これが無いと「直したはずの不具合」の報告を古い
  ビルドと取り違える。ビルドの素性を詰めるのは SDK 側（`Extensions/ExtMenu`）——
  `BuildConfig.h` を見られるのはあちらだけで、`parse/Summary` は受け取った文字列を並べる
  だけ。（VW 本体のバージョンは C++ SDK から取れないため、見出しに無い。）
- **診断ログへの書き出し口は 2 か所だけ**（`core/Progress` の `beginPhase` と
  `Extensions/ExtMenu`）。各要素へ `trace::log` を撒かない。

### 取り込み設定の決め事（M20）

IFC を選んだ直後に**設定ダイアログ**を 1 枚出し、「どの要素を図面のどのシンボルで置くか」を
決めてもらう（`draw/SettingsDialog`）。レイアウトダイアログ・シンボル表示コントロール・
図面のリソース一覧の SDK 作法は SDK リファレンスの
[レイアウトダイアログ](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layout%20Dialogs.md)
と [シンボル](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Symbols.md)
にある（この機能で使った呼び出しの具体は `draw/SettingsDialog.cpp` の冒頭コメント）。
このプラグインとしての決め事は次のとおり。

- **設定は「フェーズ間で運ぶ値」**（`core::ImportOptions`）。決めるのは描画側——図面に
  どんなシンボルがあるかは VectorWorks にしか訊けない——で、使うのは解析側（命令へ名前を
  書き込むのは解析）。したがって Document と同じく `core/` に置く。**役割の表（表示名・
  既定名）は `core::symbolRoles()` ただ 1 つ**で、解析側はシンボル名の固定値を持たない。
- **既定は従来の固定名のまま。** 設定を触らなければ取り込みの結果は変わらない——設定を
  足したことで既定の振る舞いが動いてはいけない（`ParseImportOptionsTests` が全フィクスチャで
  担保する）。
- **名前ではなく絵で選べることが要点。** "床束" と "床束2" のどちらが要る絵かは名前からは
  決まらないので、選択は**サムネイル付きのポップアップ**（VectorWorks 自身の「鋼材断面を
  選択」などと同じコントロール）にする。絵は VW がリソースに対して持っているサムネイル
  そのもので、こちらで描画モードやビューを決める必要が無い。
- **行は縦に積まず 2 列に折る。** 1 行の高さはサムネイルの高さで決まり、**その大きさは
  選べない**（`kStandardSize` と、線種用の細長い `kLineTypeSize` の 2 つだけ。上記
  レイアウトダイアログ）。役割の数ぶんそのまま縦に並べると画面に対して細長くなりすぎるので、
  列の頭を「前の列の先頭行の右」へ置いて折る（`kColumnCount` / `RowTail`）。役割を増やす
  ときに触るのはこの定数だけで、割り切れない分は最後の列が短くなる。
- **行ごとに「取り込むか」のチェックを持つ。** 置きたいシンボルが図面に無いことは普通に
  ある（テンプレート未適用・その要素を使わない案件）。そのとき**名前だけを持たせて
  「あるつもり」で置きに行っても必ず失敗する**ので、はじめから「取り込まない」と言える
  ようにした——解析側はその役割の命令を 1 つも作らない（描画側で失敗させて診断に出すのでは
  なく、そもそも指示を出さない）。アンカーボルトは座金の有無、伏図記号は柱と小屋束で
  役割が分かれるので、片方だけ取り込むこともできる。
- **候補は図面にある「置けるシンボル」だけ。** サムネイルのポップアップは項目が
  **実在するリソース**なので名前だけの項目を作れないが、チェックがあるおかげでそれで足りる
  （置くものが図面に無いなら取り込まない）。**いまの対応先が図面に無い行は、チェックの
  外れた状態で開く**——勝手に別のシンボルへ差し替わらないことがここの肝で、黙って違う絵が
  置かれるくらいなら何も置かない方がよい。図面にシンボルが 1 つも無いなら、その旨を
  ダイアログの頭で言う。
  なお**シンボル定義の一覧をそのまま出さない**——VectorWorks 自身がプラグインオブジェクト
  のスタイルとして持つ定義（図面枠・データタグ・図面ラベル・グラフィック凡例・木質構造材…）
  が混ざるので、`GetSymbolDefSubType == 0`（＝普通のシンボル定義）だけを候補にする
  （切り分けの根拠は SDK リファレンスの
  [シンボル](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Symbols.md)）。
- **設定を出せなくても取り込みは止めない。** ダイアログを組めなかったときは既定の対応で
  そのまま進み、その旨をログへ 1 行残す（結果ダイアログの逃げ道と同じ考え方）。
- **選んだ対応はログの見出しの次に必ず記録する**（`parse::formatImportOptions`）。
  「シンボルが 1 つも置かれない」という報告の切り分けは、まず対応表を読むところから始まる。
- **選択は VectorWorks を起動している間だけ覚え、図面には書かない。** 名前付きリソースを
  増やさないのと同じ考え方で、取り込みの設定を図面へ書き戻さない。

## IFC / STEP 側の癖

ホームズ君構造EX が出す IFC（IFC2X3）に固有の性質。**汎用 IFC 対応は非目標**で、この
既知サブセット前提に最小 STEP リーダ（`parse/Step`）を組んでいる。

- **日本語の `Name` は ISO 10303-21 の拡張文字エスケープで出る**（`\X2\…\X0\` / `\X\HH` /
  `\S\c` / `\P?\`）。**デコードしないと名前による要素判別が一切通らない**（`床版` /
  `木梁:床大梁` など、ホームズ君の命名規約に全面的に依存している）。
- **IFC2X3 のファイルに IFC4 専用エンティティが混入する**（`IFCFOOTINGTYPE`）。スキーマ検証を
  する読み取り系はここで止まるが、**自前リーダは非正規エンティティもそのまま読める**ので
  除去は不要（本プラグインはそれらの型を参照しないので、グラフ上に残っていても無害）。
  `parse/Loader` はファイル読み込みだけを担い、サニタイズを持たない。
- **要素配置は `RelativePlacement` のみを使い、親を合成しない。** 親を合成すると階高が
  二重計上される。
- **開口付き断面（`IfcArbitraryProfileDefWithVoids`）がある。** 階段の吹抜けを持つ床版がこの型
  で出力され、未対応だと**床が丸ごと落ちる**（実データ 2 件で 2 階・3 階の床が入っていなかった）。
  現状は外形（`OuterCurve`）だけを読み、開口（`InnerCurves`）は無視する＝**床は開口を塞いだ
  形で入る**。
- **差演算（`IfcBooleanResult` / `IfcBooleanClippingResult`）の第 1 オペランドを再帰で辿る。**
  第 2 オペランド（削り取る側）は人通口の抽出に使う。
- **ロフト（小屋裏収納）の床版は出力されない。** 一方で小屋伏図には床梁が出るので、屋根階に
  床版が無いときに限り**床梁が囲む領域**を床の外形とみなす（`core/Region`）。近似であること
  ——床梁で囲まれた吹抜けは塞がり、骨組みが閉じていない部分は床にならない。
- **小屋束の断面は当てにならない。** 直上に乗る母屋・棟木・登り梁の幅に合わせた正方形へ
  置き換える。
- **登り梁の入力位置が不正確**（軸勾配が屋根版より急・端部が受け材へ食い込む）。天端中央線を
  屋根面へスナップし、端部を受け材の面まで詰める。また端部が直切り（鉛直面）なので、
  天端は XY ずらし無しで **せい/(2·cosθ)** 持ち上げる（矩形前提の軸直交持ち上げだと天端が
  垂木下面に届かない）。
- **基礎梁は底盤の底面までの全高でモデリングされている。** 立上りの下端をさらに下げる必要は
  無い（下げると底盤の下へ突き出すだけで意図と逆になる）。深さの差（スキップフロアなど）は
  IFC の実形状のまま残す。
- **地中梁の断面は立上りの外面に片側の垂直面が付き、内側へ広がる逆台形**（ハンチ。例:
  `(0,0) (-200,0) (-380,150) (0,150)` で配置原点が立上りの外面）。壁芯に対して中心を
  合わせたいなら、それは IFC の実形状から意図的に変える話になる。
- **人通口は実寸法でモデル化されている**（長さ補正しない）。立上りソリッドから天端の下方へ
  削り取った別ソリッドとして出るので、「天端まで届き底面には届かない」削りだけを拾う
  （端部が他材で削られた全高の差演算を人通口と誤認しないため）。
- **床束は IFC に出力されない。** 大引の下へ 910mm 間隔で決め打ち配置する（継手で分断された
  大引は 1 連へ統合し、端部は受けている支持材の芯にする）。

## 打ち切った調査（もう一度やらないこと）

**同じ道を再探索しないための記録。** どれも実機まで行って確かめた結論なので、状況
（VW のバージョン・SDK の版）が変わらない限り再挑戦の価値は無い。

**SDK そのものの「できない」**——スラブへ「足す」噛み合わせ（`ModifySlab`）・断面
ビューポートの範囲「無限」・ビューポート単位のレイヤ重ね順上書き・`VWNURBSCurve` の
制御点構築・凡例のイメージの縮率・データタグの相対配置——は、SDK リファレンスの各
トピックの「打ち切った調査」へ移動した（上の表から辿れる）。ここには**このプラグインの
方針・実装として打ち切ったもの**だけを残す。

### 標準のグラフィック凡例をこれ以上いじらない（将来 独自 PIO へ置き換える）

VW 標準のグラフィック凡例は、中身（ソース定義）も縮率も外から十分に制御できない
（SDK リファレンス「[Graphic Legends](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Graphic%20Legends.md)」）。
縮率は当てず PIO 既定の 1:50 のままにし、合わせたい利用者には OIP の「イメージの縮率」を
手で変える案内をする（README「既知の制限」——手で変えれば枠も中身も正しく変わる）。
**この凡例は将来 独自 PIO へ置き換える方針**で、標準凡例の追加調査はしない。

### 地中梁のずれを端部の延長で直す

「地中梁の角が底盤の角と合わない」に対して 3 リビジョン続けて延長規則を足して外した
（① 底盤の外形へレイを飛ばして縁まで伸ばす ② ＋「別の地中梁が続いている端は伸ばさない」
③ 端が直交する立上りの壁芯上にあるときだけ半壁厚伸ばす）。**真因は `VWExtrudeObj` の
平行移動**（SDK リファレンス「[Slabs and Extrudes](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Slabs%20and%20Extrudes.md)」）で、
伸ばす必要のないところに延長を足していた。

> **教訓**: 症状が同じまま 3 リビジョン続いたら、対処の方向ではなく**前提**（＝命令と図面の
> どちらがずれているか）を実測で確かめる。今回は「梁 1 本の両端の座標と長さ」を測った時点で
> 確定した（長さが一致して位置だけ違えば描画側、長さも違えば解析側）。

### 結合の成否を壁芯の端点で測る／レイヤ上の壁を数える

いずれも切り分けには役立ったが、**平常時から鳴る**（結合は壁芯の端点を動かしうるし、
X 結合は仕様で壁を 1 本増やす）ので外した（「[診断・完了報告の方針]
(#診断完了報告の方針m15m19)」。当時の実装は PR の履歴にある）。

## 実機確認の作法

**CI が全て緑でも、実描画（高さ・傾き・スタイル・PIO の挙動）は検証できない。** このリポジトリの
`draw/` に自動テストが無いのはそのためで、代わりに実機（ローカルの VectorWorks）で確かめる。
調査の一般的な作法（読み戻す・測る・正解と差分を取る・setter の戻り値を信じない）は
SDK リファレンスの
「[Investigation Techniques](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Investigation%20Techniques.md)」
にまとめてある。このプラグインでの進め方は次のとおり。

- **切り分けは「完了ダイアログの診断行」と「OIP の値」の読み合わせで進む。** 例えば柱の高さは、
  「鉛直パスが 2 点にならなかった件数」と OIP の 高さ／始端・終端オフセット／スパン・長さの
  組み合わせで、原因が解析側（命令の値）か描画側（パス・パラメータ）かを 1 周ごとに絞り込めた。
- **API の無い設定は「UI で手作業したもの」と見比べて突き止める。** 読み取り専用の
  ダンプを設定の前と後で 2 回取り、diff を見る（選択オブジェクトのパラメトリック
  レコード・付いているレコード・オブジェクト変数・文書内のビューポート一覧を
  [`scripts/vw-dump-pio-fields.py`](../scripts/vw-dump-pio-fields.py) が書き出す）。
- **実機の出力にはビルドを添える。** M19 以降、診断ログの先頭に `CurrentBuildInfo()` が
  ブランチとコミットを書くので、報告に貼られたログを見ればどのビルドか分かる。
- **役目を終えた計装は消す。** 規約を詰めるための実測コード・一時診断コマンドは、確定と同時に
  外す（履歴に残っているので必要なら作り直せる）。
- **往復そのものはプラグインに回させる（M23）。** dev ビルドは取り込みの結果を PR へ
  投稿し、修正版のビルドが出たら**自分で入れ替えて同じ条件で取り込み直す**。人がするのは
  「絵を見て一言書く」だけで、ビルドの入れ直し・ファイルの選び直し・ログの貼り付けは
  無くなった（[`docs/DEVELOPMENT.md`](DEVELOPMENT.md)「実機フィードバックの往復」）。
  **数字で分かることは向こうが見る**ので、所見に書くのは**絵でしか分からないこと**
  （浮いている・傾いている・重なっている）にする。M24 でその往復を**モードレスのパレット**が
  回すようになり、push のあとは人が何もしなくても次の周が来る（下記 M24）。
- **描画に触れる変更は、実機で確認できるまでマージしない**（[`CLAUDE.md`](../CLAUDE.md)
  「開発プロセス: PR とマージ」）。未確認の描画が積み上がると、不具合が出たときにどの変更が
  原因か切り分けられなくなる。
- **実機で SDK の挙動として新しく分かったことは、SDK リファレンスの `Findings/` へ足す**
  （本ファイルではなく）。このプラグインの方針・入力データの癖は本ファイルへ。

## 実装の経緯（M0〜M24）

機能は「IFC 解析 → 命令セット → VW 描画 → 実機で目視確認」の 1 周が回る**縦切り**で、
1 マイルストーン＝1 要素ずつ積み上げた。**ソースコードのコメントにある `M<数字>` はこの
番号**を指す。番号は振り直さない（既存のコメント・PR 本文が参照している）。新しい区切りが
要るときは末尾に足すか非整数（M9.5 等）にする。

| # | 要素 | 主な中身と、そこで分かったこと |
| --- | --- | --- |
| **M0** | 基盤整備 | 2 フェーズの骨組み・CMake 分割（無 SDK `MinNanoStructureCore` ＋ SDK 依存の本体）・最小 STEP リーダ・無 SDK テスト土台。手動ディスパッチ専用の CI デバッグ（`ci-debug`）もここで整備 |
| **M1** | 通り芯 | 最初の縦切り。`IfcGridAxis` → 区間ごとに 1 本・重複除去・センタリング・X/Y 判定 → `GridAxis` PIO |
| **M2** | 幾何の土台 | 配置行列（Gram-Schmidt で正規直交化）・押し出しソリッド・断面・boolean 辿り。描画なし＝テストのみ |
| **M3** | ストーリ | 階・ストーリレベル・デザインレイヤ。**レイヤ重ね順**の決定箇所（当初 per-viewport 上書きに委ねたが M13 で並べ替えへ差し替え。上書きは 2 度目の挑戦でも書けず打ち切り） |

| **M6** | 屋根面・屋根組 | 形状先行②。屋根版から垂木・野地板を導出。`VWRoofFaceObj` と配置行列の作法がここで確定 |

### 基礎の床付け（捨てコン・砕石）は 3 通りに分かれる（M17）

M9 の当初は底盤スラブの構成層を「コンクリート / 捨てコン / 砕石」の 3 層にしていたが、
実際の施工は**底盤の下と地中梁の下で違う**。M17 で次のように描き分けた。

| どこ | 何を敷くか | どう表すか |
| --- | --- | --- |
| 底盤の下 | **砕石のみ**（厚みは捨てコン + 砕石ぶん＝130mm） | 底盤スラブの構成層（コンクリート + 砕石の 2 層） |
| 地中梁の下 | 捨てコン 30 + 砕石 100 | 地中梁と同じ押し出しのソリッド（`core::BeddingCommand`） |
| 地中梁の傾斜部 | **砕石のみ**で、法線方向に 130mm | 同上（傾斜に沿った帯になる） |
| 外周部 | 上記が地中梁の外側へ 50mm 張り出す | 同上（側面を回り込まず張り出しで終わる） |

**なぜ構成層で表せないか。** VW スラブの構成層は「一様な厚みの水平な層」しか表せない。
床付けは地中梁の下で深さが変わり、傾斜部では**法線方向**に厚みを持つので、層では表現できない
——地中梁のコンクリート自身を台形プリズムで描いているのと同じ理由で、押し出しソリッドにするしかない。

**断面の作り方**は「地中梁の**下面**（側面 → 下端 → 側面 と続く折れ線。天端の辺は含まない）を
外向き法線へ 130mm オフセットし、隣り合うオフセット線の交点（マイター）を頂点にする」。
これで傾斜部の法線方向の厚みが自動的に保たれる（真下へ 130mm 下げる素朴なやり方だと、
45 度の傾斜部で法線方向の厚みが 92mm に痩せる）。捨てコンはそのうち**下端の平らな面の
直下 30mm だけ**で、残りが砕石になる。

**外周部の判定は「底盤の外形の外か」**で行う。地中梁の側面のすぐ外側（1mm）を押し出し方向の
3 か所で突き、**すべてが底盤の外形の外**なら外周部とみなす。側面が鉛直かどうかは見ない
——外周の地中梁は外面が鉛直で底盤の外形とちょうど一致するが、**わずかに傾いていても
「外に回り込ませない」ほうが安全**（回り込ませると建物の外に砕石の壁が立つ）。この判定に
底盤の外形が要るので、床付けは**地中梁を底盤へ振り分けた後**でなければ求められない。

**砕石の帯は「立ち上げすぎない」のが要点で、上端を 2 段階で切る。** 素直に組むと帯は地中梁の
天端（＝底盤の底面）まで立ち上がるが、それだと**直交する地中梁と取り合うところで相手の
コンクリートへ食い込む**（実機で判明。実データを測ると最大 200mm、床付けの体積の 2〜9%）。

1. **底盤の砕石の底まで切る。** 底盤は地中梁の台形プリズムでしか削り取られないので、傾斜部の
   すぐ外側には底盤の砕石（130mm の水平な層）が残っている。**帯のうちその層と重なる部分は
   切っても和が変わらない**——同じ砕石が同じ場所を埋めているため。これだけで外周の取り合い
   （建物の四隅・T 字）は全て解消する。
2. **取り合う地中梁の下端まで切る。** それでも内部どうしの直交（互いに同じ深さ）が残るので、
   相手の平面外形が掛かる区間だけ更に切り下げる。区間ごとに切る高さが違うので、床付けの命令は
   押し出し方向の区間（`BeddingCommand` の `start` / `depth`）を持ち、**切る高さの同じ区間は
   1 本へ繋いで**無用な継目を作らない（取り合いの無い地中梁では区間は 1 つ＝全長）。

区間が掛かるかどうかは、相手のコンクリートの平面外形の 4 隅をこちらの (押し出し方向, 幅) 座標へ
写した外接矩形で見る。**直交・平行な取り合いでは厳密**で（実データはこの 2 通りしか無い）、
斜めでは安全側（広めに切る）に倒れる。

床付けのソリッドには**呑み込み（bite）を掛けない**——呑み込みは同じ素材どうしの coplanar
対策で、床付けの天端が接する相手（地中梁のコンクリート・捨てコン）は別素材なので、
そこに線が出るのはむしろ正しい。

**回帰は「食い込まないこと」で押さえてある**（`tests/ParseFootingTests.cpp` の
`ground_beam_bedding_never_bites_into_a_crossing_beam`）: 実フィクスチャ全件で床付けを格子状に
標本化し、どの点も他の地中梁のコンクリートに入らないことを確かめる。

### 共通化で寄せたもの（M19.5）

寄せ先の一覧は `CLAUDE.md`「重複を作らない置き場所」が正で、ここには**迷った判断と、
再調査しないための記録**だけを残す。

- **ローカル配置原点の 4 段の鎖**（ObjectPlacement → IFCLOCALPLACEMENT → RelativePlacement →
  IFCAXIS2PLACEMENT3D → Location）は `parse/IfcGeometry` の `resolveLocalPlacementOrigin` に
  統一した。かつて柱・横架材・ストーリが各々書いており、**Location の型チェック
  （IFCCARTESIANPOINT）はストーリだけが持っていた**。統一では**厳格側（型チェックあり）に
  揃えた**——IfcDirection も同じ属性位置に実数リストを持つため、型を見ないと方向比を座標
  として誤読する（`ParseStoryTests` の `get_local_placement_z_false_when_location_not_cartesian`
  が守っている仕様）。柱・横架材はこの統一で従来より厳格になったが、ホームズ君 IFC の
  実データでは挙動は同一（全フィクスチャで確認）。
- **同一直線マージの平行許容は要素間で意図的に違うまま**にしてある: 大引の継手統合
  （`parse/FloorPost.h` の `kCollinearAngleTol` = 1e-6）と立上りの統合（`parse/Footing.h` の
  `kWallMergeAngleTol` = 1e-3）で 1000 倍違う。共通化したのは骨格（`core/UnionFind` の
  `connectedComponents` と `core/Geometry` の `collinearSpan`）だけで、**許容値は統合していない**
  ——値を揃えると片方のチューニングがもう片方を巻き添えにする。1e-3 が意図的な緩さか単なる
  歴史かは未確認（フィクスチャではどちらでも結果が変わらない）。揃えたくなったら、先に
  実データで立上りの向きの分布を測ること。
- **Z 重なり判定・平行判定などの許容値も統合していない**（`kJointZOverlapTol` /
  `kNoboribariZOverlapTol` / `Member.cpp` の `kZOverlapTol` はいずれも今たまたま 1.0）。
  式は `core/Document.h` の `zRangesOverlap` に 1 つだが、**tol は呼び出し側の定数のまま**。
  意味が違う（取り付き・受け・食い込み）ので、片方だけ調整できる形を保つ。
- **Member.cpp のローカル `MemberGeom` と `parse/Joint.h` の公開 `MemberGeom` は敢えて
  統合しなかった**。同名・同形に見えるが関門が違う——食い込み調整側（`geomOf`）は傾斜梁を
  弾き長さ 0 だけ拒否、仕口側（`memberGeom`）は傾斜梁を受け入れ長さ < 1mm を拒否。統合すると
  この差分がポリシー引数になって読みにくくなるうえ、閾値の差で挙動が変わる。

### 耐力壁は「柱に紐付く線分 PIO」で描く（M19）

耐力壁（筋かい・面材）は、伏図では**記号**・軸組図では**形状**という、図によって別物を
見せる要素で、しかも**両端の柱に紐付いて伸縮**してほしい。素のジオメトリでは
「柱を動かすと間違った耐力壁が残る」という、記号（M12）とまったく同じ問題が起きるので、
**自作 PIO**（`Extensions/ExtShearWall`）で描く。線分 PIO（`kParametricSubType_Linear`）に
してあるので、両端のハンドルがそのまま「どの柱とどの柱の間か」を表す。

**追随の限界は M12 と同じ。** 柱を動かした瞬間には動かず、リセット・再オープン・
書き出し前（`kObjXPropResetBeforeExport`）に描き直される（上記「自作 PIO を足すときの 3 点」）。

解析（`parse/ShearWall`）で分かったこと:

- **壁の軸は押し出し方向から取る。** 筋かいも面材も「壁面内の断面を壁面に直交する向きへ
  押し出した」ソリッドなので、押し出し方向がそのまま平面の法線になり、それに直交する向きが
  壁の軸になる。平面 footprint の外接矩形や「最も離れた 2 点」から向きを推し量ると、
  厚み 45mm の帯では**対角線を軸と取り違える**（実際に一度そう書いて、見付け幅が 2 倍近くに
  化けた）。
- **見付け幅は回転キャリパの最小幅で測る。** 壁面座標 (軸方向, 高さ) へ落とした断面外形は
  IFC のプロファイルを回転しただけの形になるので、その最小幅がそのまま見付け幅（45×90 の
  90）になる。
- **たすき掛けは「同じ Name の 2 要素」。** ホームズ君は `筋かいダブル:1FL_18` を、互いに
  逆向きに傾く `IfcMember` 2 本として**同じ Name で**出す。Name でまとめて 1 枚にする。
- **大壁の表裏は「同じ軸・同じ区間」の面材 2 枚。** ただし軸と区間だけでまとめると、
  同じ通りに並ぶ**別の部屋の壁**まで 1 枚になる（間口が同じなら軸も区間も一致する）。
  法線方向の近さ（柱幅＋板厚ぶん）も条件に入れて初めて正しく分かれた。
- **表と裏に実世界の意味は無い。** IFC には内外の区別が無いので、「軸（始点→終点）を見て
  左手側が表」という幾何の約束で決める。始点は (x, y) の辞書順で小さい方に固定してあり、
  列挙順で軸が反転して表裏が入れ替わることはない。用途は**ハッチングの向きで 2 枚を
  見分ける**ことだけなので、決定的でありさえすればよい。
- **柱の無い端も軸の線に載せる。** 面材は壁芯から板厚ぶん外れた位置にあるので、片端だけ
  柱に吸着させると軸が斜めになる。柱芯を通る線を先に決めて、柱の見つからない端はその線へ
  射影する。

描画（`Extensions/ExtShearWall`）の要点:

- **軸組内法は毎回実物の柱から引く。** 対象レイヤ（`";"` 区切りの span 柱レイヤ。管柱と
  通し柱が別レイヤに分かれるので 1 つでは片端を取り逃がす）を走査し、構造用途 4 の
  構造材の外接矩形を PIO ローカルへ落として、両端の柱の**内側面**を内法とする。
  柱が見つからない図面では解析時に測った控え（`ClearSpan`）を両端の中央へ置く——柱が
  無いだけで耐力壁が消えるのは、図面として黙って欠ける最悪の形。
- **筋かいの帯は内法の矩形で切る。** 対角線に沿った幅 90 の帯は角が内法の外へ出るので、
  4 隅がそれぞれ別の辺で落ちて八角形になる。この計算は SDK に依らないので
  `core::shearWallBracePolygon`（＋`core::clipPolygonToRect`）に置いて無 SDK でテストしてある。
- **表裏の描き分けはクラスに委ねる。** ハッチングの向きはクラス属性なので、面材の面ごとに
  クラス（`…-01壁-01表` / `…-01壁-02裏`）を与えるだけでよい。プラグインは図面リソース
  （ハッチング定義）を作らない。

実機（ローカルの VW）でしか出なかったこと:

- **`SetLinearObjectPos` が効かない。** `CreateCustomObject` で置いた直後に
  `VWParametricObj::SetLinearObjectPos` で両端を与えても例外は出ないのに、
  `Recalculate` の中で `GetLinearObjectPos` を読むと **(0,0), (0,0) が返る**（＝線分として
  置けていない）。同じ症状は 53 枚すべてで再現した。中身は `GS_SetEndPoints` /
  `GS_GetEndPoints` そのもの（`SDKLib/Source/VWSDK/VWFC/VWObjects/VWParametricObj.cpp`）で
  戻り値が無いので、失敗しても呼び出し側からは分からない。原因は追えていないが、
  **「両端が取れない」前提で描けるようにしてある**ので実害は出ていない:
  `CreateCustomObject` に**始端→終端の角度**を与えてあるのでローカル +X は壁の向きに
  揃っており、控えの内法（`ClearSpan`）から軸を組み直して柱を探せば、内法は実物の柱から
  引き直せる。**PIO の絵は正しく、柱の移動にも（±300mm の探索窓の中なら）追随する**が、
  両端のハンドルで伸ばす操作はできない。診断ログの
  `shearwall: 線分の両端を読めない` / `軸を控えの内法から組み直す` がこの経路の目印。
- **伏図の記号は壁芯に置くと必ず横架材の下へ潜る。** 壁芯には土台・胴差が幅 105 前後で
  載っているので、面材の実物の離れ（半柱幅＋板厚の半分＝58.5 程度）では足りない。
  記号は `MarkOffset`（既定 200mm）だけ壁芯から離し、**面材ならその面材のある側**へ寄せる。
  実物の離れ（`PanelOffset`）は軸組図の面の位置にだけ使う。
- **耐力壁レイヤは最前面群へ回す。** 記号は「材の絵の上に重ねて読む注記」なので、
  背面に回ると意味が無い。`core::desiredStoryLayerOrder` が床（FL）・野地板を背面へ集める
  のと対称に、耐力壁レベルを `"共通"`／`topLayers` の直後へ集める。
- **伏図はその階自身の耐力壁を映す。** 当初は伏図記号レイヤ（M12）に倣って「切断の直下の
  階」を映していたが、図面の読み方は「n 階の耐力壁は n 階の伏図」だった（1 階の耐力壁は
  土台伏図＝1 階床伏図）。**重ね順の面でもこちらが正しい**——下の階のレイヤを載せると、
  上の階の横架材レイヤより必ず後ろに積まれる（順は最上階→最下階）ので、記号が隠れる。
- **伏図記号の大きさを内法で割らない。** 当初は内法の 1/3 を上限にしていたが、455mm 幅の
  壁（内法 350）だけ記号が 1/3 に縮んで図が不揃いに見えた。記号は実物の大きさを表さない
  **表記**なので、内法にも縮尺にも依らない一定の大きさにする。
- **`VWPolygon2DObj` を閉じ忘れると斜辺が 1 本消える。** 直角三角形にしたら斜辺だけが
  出なかった（`SetClosed(true)` を呼んでいなかった。SDK 側の挙動は [SDK リファレンス「Parametric Objects」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)）。
- **軸組図は壁芯で切っているので、面材を実物の位置へ置くと消える。** 断面ビューポートは
  通り芯（＝壁芯）で切ってあり、**切断面より奥は表示しない**設定（draw/Section の 1064）。
  実物どおり壁芯から 58.5mm 外した面は、表側が手前で切り落とされ裏側は奥に隠れて、
  **両方とも図に出ない**。筋かいの帯が出ていたのは offset 0＝切断面の上に載っていたから。
  面材の面も**壁芯の鉛直面へ置く**（両面のときは 2 枚が重なるので、表裏はハッチングが
  重なって見えるかどうかに委ねる）。実物の離れ（`panelOffset`）と材厚（`thickness`）は
  命令セットに残すが、作図には使わない**測った値の記録**になる。
- **見た目に効く値は書き手（`draw/`）から毎回明示的に書く。** PIO のパラメータの既定値は
  **図面に記録される**ので、コード側で既定を変えても、その PIO を一度使った図面では古い
  既定のままになる（M19: `MarkOffset` の既定を 4 → 200 にしたのに実機のログはずっと
  `記号の離れ 4.0mm` で、記号が横架材の下へ潜って見えなかった。SDK 側の挙動は [SDK リファレンス「Parametric Objects」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)）。
- **伏図記号は用紙基準（縮尺非追従）のシンボルで、大きさは用紙 mm。** 紙の上で
  三角 6×3mm・丸 直径 3mm に固定し、伏図の縮尺が変わっても変えない。絵をシンボル定義
  （`耐力壁記号_筋かい` / `耐力壁記号_面材`）にしておくと、図面の側で 1 か所を編集する
  だけで**すべての耐力壁の記号を一括で差し替えられる**（ご要望。定義を作るのは
  `draw/ShearWall` の `EnsureMarkSymbols`、置くのは PIO 本体）。**このプラグインが図面へ
  作る唯一の名前付きリソース**で、例外の作法は `CLAUDE.md` の 4 にある。

  **用紙基準は 3 つで 1 組。** どれが欠けても記号が桁違いに大きく／小さく出る。

  1. 定義を `SetPageBased(true)` にする。
  2. 定義の図形を**用紙 mm** で作る。
  3. **`n-耐力壁` レイヤの縮尺を伏図の縮尺へ揃える**（`applyShearWallLayerScale`）。

  3 が要るのは、用紙基準の大きさが「定義の図形 × **そのレイヤの縮尺**」で決まるから
  （SDK 側の挙動は [SDK リファレンス「Symbols」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Symbols.md)）。プラグインはレイヤの縮尺を設定していないので、
  作ったデザインレイヤは図面の既定のままになる。伏図はビューポート越しに見るため、
  レイヤ縮尺を伏図の縮尺に揃えて初めて紙の上で一定になる。**伏図の縮尺は用紙を読まないと
  決まらない**（`core::planLayout`）ので、レイヤを作るときではなく**シートを組む側から**
  呼ぶ（`draw/Sheet`）。

  **離れ（`MarkOffset`）だけは図面 mm のまま。** 記号が避ける相手（壁芯に載る土台・胴差の
  幅 105mm）が実物の寸法なので、紙ではなく図面の寸法で決めるのが正しい。
- **筋かいの記号のシンボル定義は 1 つでよい。** 向きは「斜辺の向き × 記号を寄せる側」で
  4 通りあるが、**軸ごとに反転すれば 1 つの定義から作れる**（反転は負の倍率で表す。
  SDK 側の挙動は [SDK リファレンス「Symbols」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Symbols.md)）。対応表は `Extensions/ExtShearWall.h`。
- **筋かいの三角は直角三角形にする。** 二等辺三角形では「どちら向きに傾いた筋かいか」が
  読めない。壁と平行な脚を底に、直角を材が高くなる側の端へ立てると、斜辺の傾きが
  そのまま筋かいの向きになる。たすき掛けは**同じ場所へ反転して重ねる**（斜辺が交差する）。


### 往復をモードレスのパレットで回す（M24）

**動機は M23 の結び目そのもの。** M23 は「投稿したら戻り、次の周は人がメニューを 1 回押して
始める」で落ち着いた。プラグインが自分で待つとモーダルのダイアログが図面を塞ぎ、絵を見る
ために回している往復で絵が見られなくなるからである（M23「ビルドを待つのをやめた」）。
そのとき残した選択肢が「モードレスなパレットへ載せ替える」で、**完全な無操作と図面の操作を
両立する道はこれしか無い**と書いてあった。M24 はそれを行い、あわせて**往復の終わり方を
Claude の合図にした**——「一度 PR ビルドを回したら、エージェントが要らないと言うまで
アップデートとフィードバックが続く」状態が目標である。

#### 何をどう割ったか

| | 中身 | どこ |
| --- | --- | --- |
| 駆動 | 合図を見る → 新しいビルドを見る → 入れて本体を降ろす → 取り込み（本体）→ 投稿、と止まる条件 | `src/FeedbackLoop`（**殻**・無 SDK・テストあり） |
| 殻の実物 | 本体への問い合わせ・同梱スクリプト・尋ねないアップデート（`PollDevBuildWith`）・パレットの表示 | `src/FeedbackLoopHost`（殻・SDK 依存） |
| パレット | 登録と JS の取り次ぎ。**判断は持たない**（JS のタイマーで `homeskz.tick()` を呼び、返った文言を並べる） | `src/Extensions/ExtFeedbackPalette` ＋ `resources/<vwr>/html/index.html`（殻） |
| 本体が殻へ見せるもの | 往復の記憶（`vw_payload_loop_status`）と「止めた」の受け口（`vw_payload_loop_end`） | `src/PayloadAbi.h` v3 / `draw/Feedback` |
| 合図 | PR が open か・自分の投稿より後に `control=stop` が付いたか | `scripts/vw-feedback.*` の `loop-control` |

**駆動が殻にあるのは、入れ替えが殻でしか起きないから**（本体は自分を降ろせない。M21）。
これは「殻に実処理を書かない」の例外ではなく、殻に残る唯一の実処理である自動アップデートの
一部——「新しいビルドが出たら入れて取り込みを頼む」という、往復のための顔である。取り込み
そのものは相変わらず本体が行う。UpdaterFlow と同じく副作用を host の後ろへ出したので、
状態機械は無 SDK でテストできる（`tests/FeedbackLoopTests.cpp`）。

#### なぜ Web パレットか（そして何が未確認か）

SDK でモードレスに出せる口は `IExtensionWebPalette` だけである（SDK リファレンス
[Findings「モードレス（非モーダル）なパレット」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layout%20Dialogs.md)。
`RunDialogLayout` はモーダル、`RegisterDialogForTimerEvents` はダイアログのタイマーで、
SDK に遅延実行の口は無い）。中身は HTML/JS で、**JS の `setInterval` がこのプラグインで
唯一の周期的な駆動源**になる。JS → C++ は `AddFunctionPromiseSync` で登録した関数が
`OnFunction` に届き、`Resolve` で Promise を返す（`Sync` はメインスレッド＝SDK と本体を
触ってよい）。

**この拡張種別は実機未確認である**（Findings はヘッダ根拠と構文チェックまで）。本リポジトリで
SDK の調査はしない決まりだが、Findings に載っている宣言を `ci-debug` の `sdk-ls` で写し取り、
その範囲で書いた。確かめること: (1) 開いて図面を操作しながら見えるか (2) タイマーからの
呼び出しが届き続けるか (3) `SetWebPaletteVisibility` で表示・非表示が切り替わるか (4)
取り込み中（進捗ダイアログの `DoYield`）に届く呼び出しが無視されるか（駆動は再入を弾く）
(5) `.vwr` の `html/index.html` が `GetStandardURL` の既定で読まれるか。**効かなくても手動の
周は壊れない**——メニューからの取り込みは M23 のまま動くので、この PR の往復自体でそれを
確かめられる。分かったことは Findings へ足す。

#### 止まる条件と、記憶を消さないこと

止まる入口は 3 つ——人がパレットで止める・Claude が PR に
`<!-- homeskz-ifc-feedback v1 control=stop -->` を投稿する・PR が閉じる（マージを含む）。
加えて入れられなかった・殻まで変わった・取り込めなかった・投稿できなかったときも止まる。
**確認そのものができなかった（オフライン等）ときは止めない**（次の周期にもう一度見る）。

**どれも記憶は消さない**（`FeedbackSession::loop` を下ろすだけ）。M23 で「送らない」が記憶を
消すのをやめたのと同じ理屈で、止めたことが「ファイルと設定を選び直し」に化けるのは割に
合わない。人がメニューから取り込みを実行すれば続きの周として走り、そこでまた回り出す。
だから止めるボタンは往復を止めるだけで、取り込みのダイアログには足していない。

**合図は「自分の投稿より後」だけを読む。** `post` が返す `created_at` を記憶し
（`lastPostedAt`）、`loop-control` の `since` に渡す。切らないと一度読んだ古い合図を毎回
読み直す。プラグイン自身が投稿する「終えました」（`control=ended`）を合図と読み違えない
よう、`control=stop` の直後が空白か `-->` のものだけを合図とする。

**Claude の合図には返事をしない。** 人が止めたときと入れ替えに失敗したときだけ PR へ
「終えました」を載せる（読む側が push しても周が来ないことを知るため）。

#### 合図は行であって、文中の引用ではない（実機 round 1 で判明）

**round 1 を投稿した直後、パレットが「往復を終えました（Claude が「もう要らない」と合図
しました）」になった。** 誰も合図していない。犯人は**プラグイン自身の投稿**だった——
コメントの末尾には「往復がもう要らなくなったら `<!-- … control=stop -->` を含むコメントを
投稿してください」という案内が入っており、合図を探す側は**本文のどこかにその目印があるか**
しか見ていなかった。しかも合図を探す範囲の起点（`since`）は自分が投稿した時刻なので、
**1 通目に読むのは自分のその投稿**である。つまりこの仕組みは、**始めた瞬間に自分の言葉で
自分を止めていた**。

**「書いてある」と「合図である」は別物である。** 目印を本文のどこかで拾う作りは、その
目印を説明・引用・転載した文章をすべて合図にしてしまう——案内文・PR 本文・レビューでの
言及・過去のコメントの引用、どれも同じ形をしている。**合図は「その行だけの行」**と定義し
直した（`scripts/vw-feedback.*` の `control_of_comment` / `Get-CommentControl`）:

1. **行がまるごと目印**であること（前後は空白だけ）。文中に引用したものは合図でない。
2. **``` で囲まれた中は読まない**（例として貼ったものを合図にしない）。
3. **プラグイン自身の投稿は合図にしない**（`round=` / `control=ended` の目印を持つ本文）。

3 は 1 と 2 があれば要らないが、**「自分の言葉で自分が止まる」を二度と起こさない**ための
歯止めとして重ねてある。書く側も直した——本文へ生の目印を置かず、`control=stop` と綴りだけ
書いて書き方は CLAUDE.md へ送る（`parse/Feedback.cpp`。読む側・書く側の二重の歯止め）。

**教訓は目印の設計そのものにある。** 機械可読な目印を人の読む文書へ埋めるなら、**その目印を
語れる場所**を必ず残すこと。「本文に含まれるか」で判定する目印は、自分について書けなくなる。

#### 実機で確かめられたこと（round 1）

上の誤検知と引き換えに、**実機未確認だった拡張種別がひととおり動くことは確かめられた**
（macOS / VW 2026）。パレットのスクリーンショットで確認:

| 確かめたこと | 結果 |
| --- | --- |
| `IExtensionWebPalette` がモードレスに開くか | **開いた。** 図面（軸組図のシート）を表示したまま、パレットが手前に浮いている |
| `SetWebPaletteVisibility` で表示できるか | **できた。** 投稿できた周の終わり（`ArmFeedbackLoop`）で自動的に開いた |
| JS のタイマーから C++ へ届くか | **届いた。** `homeskz.tick` が返した見え方（phase / message / branch / round / build）がそのまま描かれている |
| 見え方の JSON を JS が読めるか | **読めた。** 「ブランチ: … ／ round 1 (a618af6)」がパレットに出ている |
| ボタンの活殺 | **効いた。** 止まった状態なので「今すぐ確認」「往復を止める」が無効、「閉じる」だけ有効 |

**残っているのは「自動で次の周が走るか」だけ**（新しいビルドを見つけて入れ替え、取り込み、
投稿する一周）。これは合図の誤検知で止まっていたため、まだ 1 度も走っていない。
分かったことは SDK リファレンスの Findings「モードレス（非モーダル）なパレット」へ足し、
【実機未確認】の注記を外すこと。

#### 分かったこと・決めたこと

- **殻の sha を「いま動いている版」に使ってはいけない。** 本体だけを入れ替えたあと、殻に
  コンパイルされた sha は古いままである（殻は起動時にしか読み直されない）。それを基準に
  すると `q-dev` は毎回「新しいビルドがある」と言い、同じビルドを周ごとに入れ直す。
  `PollDevBuildWith` は `q-dev` の `installed=`（ディスク上の版）を基準にした。既存の
  `Auto` の経路（メニュー）は据え置いてある——そちらは人が押したときにしか走らないので、
  入れ直しは無駄だが害は無い。
- **GitHub を見る間隔は 1 分。** CI の dev ビルドは push から十数分かかるので十分に早く、
  同梱スクリプトの起動（1〜2 秒）でメインスレッドが止まる回数も許容できる。JS のタイマーは
  5 秒で、間隔に満たない tick は現在の見え方を返すだけ。
- **パレットの HTML は殻の ID に入れない。** `.vwr` の文字列と同じで、殻へコンパイル
  されるものではない。起動時に読み込まれた `.vwr` が入れ替えに追随するかは未確認だが、
  追随しなくても古い見た目のまま動くだけで、入れると HTML を直すたびに再起動を強いる。
- **前の周の図は自動では戻らない。** プログラムから取り消しを掛ける手立ては無い
  （Findings「Undo」。issue #23 で確定）。自動の周は前の周の上に重ねて描き、PR コメントの
  「図面の状態:」がそれを言う。読む側はそれを前提に数字を読む。

### 実機確認の往復をプラグインに回させる（M23）

**動機は M21 が開けた道。** アップデートに Vectorworks の再起動が要らなくなったことで、
「新しいビルドを、動かしたまま、その場で読み直す」が可能になった。すると実機確認の往復
——このリポジトリで**実装そのものより時間を食っていた**もの——を、プラグイン自身に
回させられる。

従来の 1 往復は、人が全部やっていた:

> 新しいビルドを入れる → **再起動** → 図面を戻す → IFC を選ぶ → 設定を選ぶ → 取り込む
> → ログを写して PR へ貼る

いまはこうなる:

> **絵を見て一言書く → 送る**（あとは待つだけ。次の周は無操作で走る）

#### 何をどう割ったか

| | 中身 | どこ |
| --- | --- | --- |
| 覚えておく値 | 1 周目の選択（IFC・設定・宛先 PR）・周回数・前の周の内訳 | `core/FeedbackSession`（無 SDK） |
| コメント本文 | 内訳・**前の周との差分**・注意・ログ・匿名化 | `parse/Feedback`（無 SDK） |
| 往復の運転 | **取り込みの前に**送るか決め、終わったら黙って投稿（**待たない**。下記） | `draw/Feedback`（SDK 依存） |
| 入れ替え | 次の取り込みの頭で、尋ねずにインストールして本体を読み直す | `src/UpdaterFlow.cpp`（`UpdateCheckKind::Auto`） |
| ネットワーク | トークンの保管・PR の特定・コメントの投稿 | `scripts/vw-feedback.*`（同梱） |

**ネットワークを C++ で書かない**のは自動アップデートと同じ分担（`src/Updater.h`）。
おかげでコメント本文の組み立て——いちばん頻繁に直るところ——が**丸ごと無 SDK で
テストできる**。

#### 入れ替えは必ず殻の側で起きる

新しい本体をその実行のまま効かせるには載っている本体を降ろす必要があり、それができるのは
**本体のコードがスタックに 1 つも無いとき**だけである（`src/PayloadSession.h`）。したがって
入れ替えは必ず「本体から戻ったあと」＝取り込みコマンドの頭になる。本体がするのは投稿まで
で、殻へ返すのは「**次は尋ねずに入れてよい**」という 1 ビットだけ。殻に足したのはそれを
1 回ぶん覚える `static bool` で、往復の中身はすべて本体側にある（＝往復のふるまいを
直しても再起動は要らない）。ABI は 2 へ上げ、**同梱スクリプトの実行**を貸すようにした
（本体が読まれるのは一時ディレクトリの複製なので、自分の在り処から同梱物へたどり着けない）。

#### インストールの経路は 1 本に保つ（#108 を取り込んで整理）

最初の実装では、本体が待ったうえで `do-install` まで自分で呼んでいた。**そこは間違いで、
インストールの経路が 2 本になっていた**（殻の更新の流れと、往復のためのもの）。「再起動が
要るか」の判定も、失敗したときの文言も、2 か所で同じことを書くことになる。

`#108` で更新の確認が**起動時から取り込みコマンドの頭へ移った**ので、往復はそれに乗れば
よくなった——本体は「出た」と見届けて戻るだけで、入れるのは**もともとそこにある**更新の
確認である。そのために `UpdateCheckKind` に `Auto`（尋ねない・報せない・再起動しない）を
足し、流れは「この実行のまま自動で続けてよいか」を `bool` で返すようにした。**本体から
`do-install` が消え**、往復のために増えた経路は 0 本になった。

`Auto` が**再起動を仕掛けない**のは、利用者が図面を開いたまま輪を回しているからである。
殻まで変わったら、伝えて輪を止め、再起動するかどうかはその人に委ねる。

#### 公開されることの扱い

PR コメントは公開なので、**既定で伏せる**: IFC のファイル名は仮名（`model-8f3a12.ifc`。
**同じ入力なら毎回同じ**なので周回どうしの同一性は保たれる）へ、パスのユーザー名は伏せ字へ。
残すのは要素ごとの命令数と描けた数・描画側の注意・所要時間で、これは**案件ではなく
プラグインの話**である。「フィクスチャに実案件データを使わない」という運用と合わせて、
公開でも困らない形にしてある。私有リポジトリへ向けることもできるが、その PR のイベントで
Claude が起きないので往復の自動性は落ちる。

#### 所見は別プロセスのダイアログで訊く（round 1〜4。**のちに丸ごと外した**）

**round 1 の所見がこうだった:**

> ダイアログを非モーダルで表示してもらわないと実行結果を確認できません。

そのとおりで、取り込み直後にモーダルのダイアログで所見を求めると、**その所見の材料である
図面が見られない**。「絵を見てから書く」が成り立たないと、この往復の価値はほとんど消える。

**SDK にモードレスの口はある。** `IExtensionWebPalette`（5 つ目の拡張種別。
[SDK リファレンス「モードレス（非モーダル）なパレット」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layout%20Dialogs.md)）。
ただし中身は HTML/JS で、登録は殻に置くしかなく（VW に vtable を握られる）、閉じる API も
見つかっていない。そして**全部が実機未確認**である。所見欄 1 つのために UI スタックを
もう 1 つ背負う判断は、まだできない。

**代わりに、既にある仕組みで足りた。** プラグインは同梱スクリプトを起動できる
（自動アップデートの経路）。**スクリプトが OS 標準のダイアログを出せば、それは別プロセス
なので Vectorworks を止めない。**

肝は**待たないこと**。プラグインはスクリプトの出力を読み終わるまでメインスレッドを止める
（`popen`）ので、ここで待つと結局図面が固まる。そこで `ask-note` は**自分自身を detached
で起こし直して即座に `ok` を返す**——プラグインはすぐ戻り、Vectorworks は完全に操作できる
状態になる。

**戻ってしまう以上、こちらへは返せない。** だから尋ねてから投稿するところまでスクリプトの
仕事にし、**所見は独立した 1 通**として PR に載せる（目印 `homeskz-ifc-feedback-note`）。
取り込み結果の本文へ差し込む形にしなかったのは、そうするとコメントの組み立てが C++ 側
（`parse/Feedback`）とスクリプト側の 2 か所に割れるため——差し込み位置の目印を置いて
awk で嵌める案も試したが、「所見の節をどう書くか」が二重定義になるので採らなかった。

分けたことで良くなった点もある: **投稿の成否がプラグインの手に残る**ので、記憶
（round / 内訳）の更新は従来どおり確実で、所見を書かなかった周も正しく数えられる。

この分離だけでは足りなかった——**待機のほうが残っていた**（下記「ビルドを待つのをやめた」）。

#### ビルドを待つのをやめた（round 3 の実機で判明）

**round 3 の所見がこうだった:**

> 所見ダイアログは非同期に開きましたが、次のアップデートと実行を自動にチェックを入れると
> 修正版のビルドを待っていますダイアログが表示されて、図面確認できません。

所見を外へ出しても、**その直後にプラグイン自身がビルドを待ち始めれば同じこと**だった。
待つ側は進捗ダイアログを出し続けるほかなく（出さなければ Vectorworks が固まって見える）、
モーダルである以上その間は図面が見られない。**絵を見るために回している往復で絵が見られ
ない**のでは本末転倒である。

**プラグインが自分で待つ限りこの症状は消せない。** レイアウトダイアログも進捗ダイアログも
モーダルで、待機はメインスレッドを握り続ける。逃げ道は 2 つしかなかった:

| | 得るもの | 払うもの |
| --- | --- | --- |
| 待つのを外のプロセスへ出す | 図面は常に操作できる | 周ごとにメニューを 1 回押す |
| モードレスなパレット（`IExtensionWebPalette`）へ載せ替える | 完全な無操作と図面の操作が両立 | 実機未確認の拡張種別。往復の入口ごと作り替え |

**選んだのは「待つのをやめる」**（後者は別途検討）。プラグインは投稿したら即座に戻り、
次の周は人が取り込みを 1 回実行して始まる。残る操作はそのメニュー 1 回だけで、**どの
ビルドを入れるか・何を取り込むか・どの設定で描くかは自動のまま**である。旧来の
「入れ直して再起動して図面を戻して選び直す」に比べれば無視できる手間で、しかも
**絵をいつでも見られる**という、この往復の前提そのものが戻ってくる。

その 1 回を押した瞬間に新しいビルドが**尋ねられずに**入るよう、本体は周の終わりに
「次は尋ねずに入れてよい」を戻り値で返し、殻が `static bool` で 1 回ぶん覚える
（`UpdateCheckKind::Auto`）。**覚えを殻に置くのは、本体が入れ替わっても残ってほしいから**
——本体側に置くと、入れ替えた次の周でまた尋ねることになる。

この判断で消えたコードのほうが多い: 本体から待機ループ・進捗ダイアログ・`do-install` の
呼び出しが消え、殻からは「もう 1 周」のループが消えた。**往復のために増えた経路は 0 本**
になり、インストールは殻の更新の流れ 1 本だけになっている。

#### 「送らない」周も見えるようにする（round 4 の実機で判明）

**round 4 の所見がこうだった:**

> 前回は送らないを選択しましたが、これにセッションは反応していないようでした。送らない
> 場合にも何かコメントを更新しないと、トリガーできないのはないでしょうか。

そのとおりで、**「送らない」を選んだ周は PR に何も残らず、読む側からは丸ごと消えていた**。
ところがそこで何を見て、なぜ送らないと判断したのかは、絵を見たその人にしか分からない
——往復でいちばん失ってはいけないものが、いちばん静かに落ちていた。

直し方は 2 つに割れる。

**1. 送らない周にも所見だけは訊く。** 結果（内訳）は投稿しないまま、所見のダイアログだけを
出す。文言も変える——「これがこの周の唯一の記録になります」と言われれば、書く気になる。
所見は `posted=no` を付けた 1 通として載る。**空のまま閉じれば何も投稿されない**ので、
本当に何も残したくないときの逃げ道は残る。トークンが未登録のときは訊かない——送らないと
決めた人の前に登録のモーダルを出すのは筋が違う。

**2. 「送らない」で記憶を消すのをやめた。** もともとは「送らない＝往復をやめる意思表示」と
して記憶を捨てていたが、これは**自動周回があった頃の理屈**である（勝手に次の周が始まると
驚くから）。待たなくなった今は、報告したくない周が 1 つあっただけでファイルと設定を選び
直す羽目になるだけで、割に合わない。

代わりに**やめる入口を、次の周の頭の確認（「取り込み前の状態に戻してから続ける」）の
「往復を終える」へ移した**。「この往復を続けますか」と訊いている当の場所であり、ボタンを増やさず
に済む（`AlertQuestion` の 3 つ目のボタンの戻り値は確かめていないので、増やすなら SDK の
調査が要る。CLAUDE.md）。

※ この確認そのものを後で外したので、やめる入口も併せて動いている（下記「戻したかどうかを
訊かない」「やめるボタンを置かずに済ませる」）。

#### 所見はプラグインの仕事ではなかった（実機の指摘）

所見を訊く仕組みは、round 3 の「モーダルで図面が見られない」から始まって、別プロセスの
OS ダイアログ・`posted=no` の周・ボタンの文言と、3 周かけて作り込んだ。**そして外した。**

外した理由は 1 行である——**所見を書くには、その人が実機を見ている必要がある。見ている
なら、チャットへ書くほうが速い**（スクリーンショットも貼れる）。プラグインが間に入る
価値が無い。

作っている間はこれが見えなかった。「往復をプラグインが回す」という枠に、**回さなくてよい
ものまで入れていた**のが原因である。**この往復でプラグインにしかできないのは「数字と
診断ログを機械的に集めて投げること」だけ**で、それ以外は人の側でやったほうが速いか、
そもそも人にしかできない。

消えたもの: `ask-note` / `ask-note-worker`（両スクリプト）、別プロセスを起こす仕掛け
（`spawn_self` / `Invoke-SelfDetached`）、OS ダイアログのラッパー 3 つ、`posted` の
受け渡し、それらのテスト。**足したものより消えたものが多い変更**になった。

#### 取り込みのあとに人の操作を残さない（実機の指摘）

同じ指摘の後半がこれである:

> 結果を送るかどうかはコマンド実行の最初に選択します。そうしないと、インポートを待って
> 操作しなければなりません。

**取り込みは 1 分以上かかる。** その終わりに確認が待っていると、その人は席を離れられない
——「実行して放っておく」が成立しない。ダイアログを 1 枚に減らしても、**終わりに置いて
ある限り同じこと**だった。

そこで**尋ねることを全部、取り込みが始まる前へ移した**: 送るかどうか・宛先の PR・伏せ字・
トークンの登録。取り込みが終わったあとにするのは投稿だけで、**結果ダイアログも出さない**
（投稿できたなら内訳もログも PR にあるので、見せる相手がいない）。

投稿に失敗したときだけ、いつもの結果ダイアログに理由を添えて出す。ここでアラートを重ねる
と、無操作で終わるはずの取り込みにボタンが 1 つ増えてしまう。

**「取り込みの前か、後か」は、この往復では機能そのものである。** ダイアログの枚数や文言
より先に、それを問うこと。

#### ボタンが何を指しているのか分からなかった（実機の指摘）

「送る／送らない」というボタンが**2 つの別々のダイアログ**（結果のダイアログと所見の
ダイアログ）に同じ文言で並んでいて、しかもどちらも**往復が続くのか終わるのかを何も
言っていなかった**。結果として「送らない＝往復が終わる」と読まれた。

**動詞だけのボタンは、対象が 1 つしか無い画面でしか成立しない。** ここは対象が 2 つある
（結果と所見）ので、ボタンに対象を持たせた:

| ダイアログ | いま |
| --- | --- |
| 送るかどうか（取り込みの前） | 「取り込み結果を送る」／「送らない」 |
| 続きの確認 | 「続ける」／「往復を終える」 |

（所見のダイアログはこのあと丸ごと外した。上記「所見はプラグインの仕事ではなかった」。）

**結末そのものをボタンに書く**のも同じ理由である——「やめる」では「この取り込みをやめる」
とも読めるが、「往復を終える」なら読み違えようがない。加えて結果のダイアログには、押した
あと何が起きるか（所見のダイアログが出る・往復は終わらない）を 2 行で書いた。**押す前に
結末が分かること**が、ここでの唯一の要件である。

（Windows の所見ダイアログは `InputBox` でボタン名を変えられないので、そちらは本文で
「OK で所見を送り、キャンセルなら書かずに閉じます」と名乗る。）

#### 同梱スクリプトは bash 3.2 で動かなければならない（round 1 の実機で判明）

**macOS が積んでいる `/bin/bash` は 3.2**（プラグインはこれで同梱スクリプトを起動する。
`src/Updater.cpp`）。3.2 には、`set -u` の下で**空の配列を展開すると "unbound variable" で
即死する**という古い不具合がある（bash 4.4 で修正済み）。

これに `vw-feedback.sh` の `find-pr` が当たった。トークンが未登録のときだけ

```bash
local auth=()
[ -n "$token" ] && auth=(-H "Authorization: Bearer ${token}")
curl … "${auth[@]}" …          # ← 空だとここで死ぬ（bash 3.2 のみ）
```

が空配列を展開して落ち、**PR 番号の自動取得だけが黙って失敗**した（トークンがある
`post` は配列が空にならないので動く——「認証済みなら動くのに未認証だと動かない」という
紛らわしい症状になった）。

**テストでは捕まらなかった。** ハーネスが走るのは Linux の bash 5 で、そこでは空配列の
展開が通る。だから対策は振る舞いではなく**構文の側**に置いた——同梱スクリプトでは
**配列を書かない**ことにし、`tests/vw-feedback.test.sh` が配列展開の不在を検査する。
`vw-update.sh` にも配列はあるが、そちらは対話モードだけで、しかも空でないことを
確かめてから展開している。

#### 同梱スクリプトを殻の ID から外した（＝スクリプトの修正に再起動が要らない）

上の bash 3.2 の不具合を直したとき、**スクリプト 1 行の修正なのに利用者へ再起動を
強いる**ことになった。`scripts/vw-*.{sh,ps1}` を `VW_SHELL_INPUTS`（殻の ID の材料）に
入れていたためである。往復から再起動を無くすのがこの仕組みの目的なのだから、これは
本末転倒だった。

**基準を言い直した——「起動のときにしか読まれないか」。** Vectorworks が読み込むのは殻の
モジュールだけで、そこへコンパイルされたものは次の起動まで入れ替わらない。同梱スクリプトは
**プロセスへ読み込まれず、呼ぶたびにパスからディスクを読む**（更新は `src/Updater.cpp`、
フィードバックの投稿は `src/draw/Feedback.cpp` が、その場でプロセスを起こす）。だから
置き換えれば次の呼び出しから効く＝再起動は要らない。M22.1 でプラグインのものが
プラグイン名のフォルダ 1 つに閉じ、インストーラがそのフォルダごと置き換えるように
なったので、**ディスク上のスクリプトは常に「いま入っているビルドのもの」**でもある。

**代わりに背負った前提**: これまでは「古いスクリプト × 新しい殻」だけを考えればよかったが、
**新しいスクリプト × 古い殻**（本体だけを入れ替えた直後）も起こる。機械可読な出力の形
（`installed=` / `build` 行 / `installed-shell=` / `ok` / `error=`）は、**新旧どちらの
組み合わせでも通るよう**に保つこと——列を足したり意味を変えたりしてはならない。

一覧は**最小限に保つ**。1 つ余計に入れるたびに、そこを直しただけで再起動を強いることに
なる。残っているのは、殻へコンパイルされるソースとヘッダ・`Info.plist` のテンプレート・
ビルド設定（`CMakeLists.txt`）だけである。

#### 戻したかどうかを訊かない（実機の指摘）

2 周目以降は同じ文書へもう一度描くので、前の周を「取り消し」で戻していないと図が二重に
なる。そこで当初は、次の周の頭に「取り込み前の状態に戻してから続ける」の確認を 1 枚
出していた。**これを外した。**

理由は 2 つある。

**1. 確認は嘘をつく。** 押したかどうかは戻したかどうかではない。「続ける」を押した人が
戻し忘れていても、プラグインにも読む側（Claude）にも区別が付かない——しかも**内訳の
数字は命令の数なので、戻したかどうかで 1 つも変わらない**。つまり確認を置いた分だけ
クリックが増え、得られる情報は 0 である。

**2. 訊くなら 1 周目に訊けばよい。** 2 周目は自動で走るわけではなく、人がメニューから
実行する。実行する前に「取り消し」を掛けるのは、その人がすでに図面の前でしていることで、
毎周ダイアログで念を押す相手ではない。頼むのは 1 周目のダイアログ（`draw/Feedback.cpp` の
静的テキスト）で 1 度だけにした。

**代わりに実測を載せた。** 描画側は「取り込み前から在ったレイヤへ描いたか」を
`DrawCounts::undoPartial` として既に持っている（`draw/DrawUtil.h` の `ImportUndoScope`。
取り消しがどこまで効くかの判断に使っていたもの）。これを PR コメントの「図面の状態:」
として毎回出す（`parse/Feedback.cpp`）。**押した／押さないではなく、実際に何が起きたか**
なので、読む側は絵の破綻が実装のせいか戻し忘れかを切り分けられる。

#### 基準は 1 周目に採る（実機の指摘）

上の「実測を載せた」には穴があった。**`undoPartial` は真偽 1 つ**で、意味は
「取り込み前から在ったレイヤへも描いたか」である。ところが**利用者のテンプレートには
「共通」等のレイヤが最初から在る**ので、**1 周目からこれは true になる**——「前の周を
戻し忘れた」と「もともと在った」を区別できない。実際、round 5 のコメントを読んで
「戻していない」と早合点した。

直し方は「基準を持つ」ことだった。描画側は**取り込み前から在ったレイヤの名前**を
控えるようにし（`DrawCounts::existingLayers`）、**1 周目のその顔ぶれを記憶へ採る**
（`FeedbackSession::baselineLayers`）。次の周からは引き比べて言う:

| 今回の顔ぶれ | 言うこと |
| --- | --- |
| 基準と同じ | 取り込み前の状態へ戻してから実行されている |
| 基準に無いものが増えている | **前の周の図が残ったまま重ねて描いた**（増えた枚数を出す） |
| 基準にあったものが無い | 別の図面か、テンプレートが変わった（**戻し忘れとは言わない**） |

`baselineRecorded` という真偽を別に持つのは、**「まっさらな図面で始めた 1 周目（基準は
0 枚）」と「古い版が書いた記憶（基準が無い）」を区別する**ため。これが無いと、基準を
採る前の周を「戻っています」と報告してしまう。

**レイヤ名そのものは PR へ出さない**（枚数と判定だけ）。レイヤ名は図面の側の言葉で、
公開の場へ置くものではない——伏せ字の方針と同じ。

**プログラムから戻すのが本筋**であることは変わらない（そうなれば人の手仕事が 1 つ消え、
読む側は「戻っている」を前提にできる）。ただし「取り消し」をプログラムから掛ける手立ても、
レイヤのハンドルを消して中身ごと消えるかも、**SDK の挙動なので本リポジトリでは調べない**
——リファレンス側で issue を立て、`Findings/` に載ってから実装する（`CLAUDE.md`）。
起票済み: [min-nano/vectorworks-developer-sdk-reference#23](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/23)。

#### やめるボタンを置かずに済ませる

上の確認を外すと、「往復を終える」の置き場所が無くなる。**置き直さなかった。**

続きの周が走る条件を「記憶した sha と動いているビルドが違うこと」に絞ったからである
（`draw/ImportCommand.cpp`）。同じビルドで取り込み直しても前の周と同じ数字が並ぶだけで、
そもそも周として意味が無い。この条件なら**push が止まれば往復も止まる**——Claude が
直すのをやめれば新しい dev ビルドは出ず、続きの周は二度と走らない。

（M24 で往復が自動になったので、止める口はパレットに 1 つある。取り込みのダイアログには
相変わらず無い。上記 M24「止まる条件と、記憶を消さないこと」。）

新しいビルドを待っている間に取り込みを実行したときだけ 1 周目のダイアログが出る（1 行目が
「新しいビルドはまだ出ていません」と名乗る）。**そこで「送らない」を選べば記憶ごと消える**
——このダイアログが出ているのは「続きの周ではない」ときだけなので、送らないと決めた人は
もう往復を回していない、と読んでよい。忘れたころの IFC が黙って取り込まれるのを防ぐ意味も
ある。

### 殻と本体に割ってホットリロードする（M21）

**動機はひとつ。** 「直した → 入れた → 再起動して開き直す」の最後の 2 手が、実機確認の
1 周のうちいちばん長かった。VectorWorks の起動は数十秒かかり、開いていた図面も開き直す
ことになる。**コンパイル済みプラグインは起動時にしか読み込まれない**という SDK の性質
そのものが原因なので、プラグインの側で受け止めるしかない。

**やったこと**は、成果物を 2 つに割って、VectorWorks に読み込ませるものを最小にした
（作法と決めごとは CLAUDE.md「アーキテクチャ: 殻と本体」）。

```
VectorWorks ──読み込む──▶ 殻（登録・更新・読み込み）  … 起動時に 1 度きり。滅多に変わらない
                              │ dlopen / LoadLibrary
                              ▼
                          本体（core / parse / draw）  … いつでも降ろして読み直せる
```

**この道が通ることは SDK リファレンス側で実測済み**だったので、本リポジトリでは調査を
していない（CLAUDE.md「SDK の調査はリファレンス側で行う」）。あちらの
[「プラグインモジュールの読み込みと入れ替え」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)
に、`dlopen` できること・`GS_InitializeVCOM` を自分で呼べば `gSDK` が埋まること・
`dlclose` で本当に消えること・置き換えて読み直すと走るコードが実際に入れ替わることが
実機の数字つきで載っている。**この節はその知見を本プラグインへ当てはめた記録**である。

#### 本プラグイン固有の判断

- **本体は載せっぱなしにする。** リファレンスの実機確認プラグインは「メニューを開くたびに
  読んで、終わったら降ろす」作りだが、本プラグインは**PIO のリセットが同じ本体を使う**。
  取り込み直後は記号・耐力壁が数百個リセットされるので、1 回 0.3〜0.4 秒の読み込みを毎回
  払うと現実的な速さにならない。そこで載せたままにし、**入れ替えの判定だけを入口ごとに
  行う**（`src/PayloadSession.cpp`）。判定は同梱ファイルの大きさ・更新時刻で、**中身の
  ハッシュは取らない**——入口のたびに数 MB を読む価値は無く、取りこぼしても次の入口で
  拾えるだけだからである。

- **PIO は「登録は殻・作図は本体」に割る。** `SParametricDef` とパラメータ定義は
  VectorWorks に番地を握られるので殻に残すほかないが、`Recalculate()` の中身は出せる。
  出したことで、**記号や耐力壁の描き方の直しも再起動なしで反映される**ようになった
  （`src/draw/ColumnMarkPio.cpp` / `src/draw/ShearWallPio.cpp`）。

- **PIO のリセットではダイアログを出さない。** 本体を読み込めなかったとき、メニュー
  コマンドは理由をダイアログで見せられるが、リセットは図面の記号の数だけ走るので黙って
  諦めるしかない。`kObjectEventHadError` も返さない——描けなかったことより、**既に描いて
  ある記号を消さずに残す**ほうが害が少ない。

- **殻の ID で再起動の要否を決める。** `CMakeLists.txt` の `VW_SHELL_INPUTS`（殻に入るもの
  だけ）のハッシュをビルドへ焼き、インストール物にも控える。`do-install` が入れたビルドの
  ID を返し、走っている殻の値と一致すれば**再起動を尋ねない**（`src/UpdaterFlow.cpp` の
  `FinishInstall`）。**この一覧に `draw/` や `parse/` を足してはいけない**——描画を直した
  だけで毎回再起動が要る仕様に化ける。判断できないときは必ず「要る」へ倒す。

- **`file(SHA256)` だけで ID を出す。** 外部スクリプトを噛ませると mac と Windows の CI で
  値が食い違いうる。食い違った瞬間に「毎回再起動が要る」へ化けるので、CMake 組み込みの
  ハッシュだけで完結させた。

#### 落とし穴（両方とも実機でしか出ない）

- **殻の記憶域を本体に持たせない。** 境界を越えて渡した構造体のポインタを受け取った側が
  持ち続けると、腐ったポインタから関数ポインタを読んで**VectorWorks ごと落ちる**。
  コンパイルもリンクも CI も通る。写す側（`src/PayloadHostHolder.h`）と渡す側
  （`Payload::fHost` をメンバに置く）の**両方**で止め、写していることは無 SDK テストで
  押さえてある（`tests/PayloadHostHolderTests.cpp`）。
- **mac は本体にも個別のアドホック署名が要る。** バンドルの外に置くので `codesign --deep`
  には含まれず、署名が無いと Apple Silicon の検証で `dlopen` に失敗する。

#### 実機で確かめたこと（macOS / VW 2026、build 03a175c → 4363d43）

- **本体側からダイアログを開ける。** SDK リファレンスの「まだ確かめていないこと」に唯一
  残っていた項目で、ここが駄目なら設計をやり直すところだった。取り込み設定ダイアログ
  （`VWDialog`）・進捗・完了ダイアログ・VCOM のファイル選択（`IFileChooserDialog`）が、
  すべて本体側から通常どおり開いて動いた。
- **PIO のリセットが境界越しに効く。** 記号・耐力壁ともリセットが走り、取り込み経路
  だけでなく**伏図の作成中に VW 側が起こしたリセット**も通った。約 100 回のリセットが
  1.6 秒ほどで済んでおり、**「載せっぱなしにする」判断が効いている**（毎回読み直す作りなら
  読み込みだけで 30 秒以上になっていた）。
- **本体だけを差し替えれば、再起動せずにコードが入れ替わる。** `.vwpayload` を置き換えて
  同じ VectorWorks のまま取り込み直したところ、ログの見出しの commit が新しい本体のものへ
  変わり、その版でしか直っていない挙動（ログのパス表示）が実際に現れた。**この機能の目的
  そのものが実機で成立している。**
- 描いたものは差し替えの前後で 1174 件が完全に一致し、所要も 1 分 14 秒 → 1 分 15 秒で
  差が無い。

**SDK の挙動として一般化できる分（本体からダイアログを開けること）は
[SDK リファレンスの `Findings/`](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)
へ書き残す**（CLAUDE.md「ドキュメントの分担」）。ここに残すのは本プラグインでの現れ方だけ。

#### まだ確かめていないこと

- **Windows での載せ替え**（`LoadLibraryEx` / `FreeLibrary`）。設計上は同じはずだが、
  SDK リファレンス側でも未実測。
- **本体からダイアログを開いたまま降ろす**経路。いまは深さ 0（本体のコードがスタックに
  無い）でしか降ろさないので安全なはずだが、VectorWorks に本体の番地を持たせたまま降ろす
  操作（イベント登録など）を将来足すなら、降ろす前に手放す設計が要る。
- **長時間・多数回の読み直しでリークしないか。**


### 配置の手順をリリース側へ移す（M22）

**動機は M21 で払った代償。** 本体（`.vwpayload`）というファイルが 1 つ増えただけで、
利用者は zip を手で落として置き直す必要があった。理由は単純で、**更新を実行するのは
「いま入っているビルドに同梱されていたスクリプト」**——つまり必ず古い版——であり、
その版は増えたファイルの存在を知らないからである。zip には入っているのにコピーされない。

これは「今回たまたま」ではなく**構造的な欠陥**だった。同梱スクリプトに配置手順がある限り、
構成を変えるたびに同じ手作業が発生する。

**やったこと**は、役割を 2 枚に割ったこと。

| | 何をするか | どこにあるか | いつの版が走るか |
| --- | --- | --- | --- |
| **アップデータ**（`scripts/vw-update.*`） | 探す・比べる・落とす・ダイアログ | インストール済みプラグインの中／隣 | **古い** |
| **インストーラ**（`scripts/vw-install.*`） | **配置** | **配布 zip の直下**＋リリースのアセット | **新しい**（落としてきたビルドの版） |

`do-install` は zip を展開したあと、その直下の `vw-install.sh` / `vw-install.ps1` を
`--machine --from <展開先>` で呼び、その出力（`installed-shell=` / `ok` / `error=`）を
**そのままプラグインへ流す**。配置の知識が「新しい側」にあるので、ファイルが増えても
利用者の手は要らない。

#### 判断したこと

- **配置の規則は「zip の直下にあるものを、そのまま置く」の 1 つだけ。** ファイル名を
  列挙しない——列挙した瞬間に、いま直している事故（増えたファイルの取りこぼし）が
  そっくり戻ってくる。除くのはインストーラ自身だけ。テストの中心もここにあり、
  フィクスチャには**誰も列挙していないファイル**をわざと混ぜてある。

- **リリースのアセットとしても公開する。** 手動インストールの入口になり、`curl` で 1 本
  落として実行するだけで、取得・展開・隔離解除・アドホック署名・配置まで済む。**手順書に
  書いた手作業は、書いた瞬間から古くなる**が、スクリプトはビルドと一緒に更新される。

- **インストーラは殻の ID（`VW_SHELL_INPUTS`）に入れない。** 殻に入らないので当然でも
  あるが、狙いは「配置の手順を直しただけで再起動を強いない」こと——それはこの仕組みが
  無くそうとしている手間そのもの。

- **アセット名も決め打ちにしない。** アップデータはまず `<名前>.vwlibrary.zip`
  （Windows は `.vlb.zip`）を厳密に探し、無ければ**末尾がその拡張子のアセット**で拾い直す。
  名前を変えた瞬間に、古いアップデータから何も落とせなくなる＝**アップデートの経路そのものが
  切れる**のを避けるため。1 つのリリースが持つ配布 zip はそのチャンネルの 1 つだけなので、
  末尾での照合で取り違えは起きない。

- **知らないオプションでは落とさない。** 新しいアップデータが、古いリリースの zip に入った
  インストーラを呼ぶ向きが起こりうる（そのリリースへ切り替えるとき）。増えた引数で落ちると、
  そこでまた手作業に戻ってしまう。

- **「委ねられた」の判定は結末の行が返ってきたかで行う。** インストーラが古い／壊れていて
  何も言わないときに成功と取り違えると、半端な状態のまま `ok` を返してしまう。何も言わなければ
  アップデータ自身の予備の配置へ落ちる（この仕組みより前のリリースへ当たった場合も同じ経路）。

#### 残る 1 回

**この仕組みより前のビルドから更新する 1 回だけ**は、まだ古い同梱スクリプトが配置を行う。
そのときのファイル構成は変わっていないので正しく入り、その更新で新しいアップデータが入る。
以後は常にリリース側のインストーラが配置する。

#### 続き: プラグインは自分のフォルダを 1 つ持ち、入れる前に前の版を取り除く

置き先を `Plug-Ins` の直下から**プラグイン名のフォルダ**へ移した:

```
<Plug-Ins>/min-nano_structure/min-nano_structure.vwlibrary
<Plug-Ins>/min-nano_structure/min-nano_structure.vwpayload
<Plug-Ins>/min-nano_structure/vw-uninstall.sh
```

**そのプラグインのものが 1 か所に閉じる**ので、取り除くのが「フォルダを 1 つ消す」で済む。
Vectorworks が `Plug-Ins` のサブフォルダも読みに行くことは実機で確認済み。

判断したこと:

- **渡された先が既にそのフォルダなら足さない。** プラグインは「いま自分が読み込まれた
  フォルダ」を渡してくる（`src/Updater.cpp` の `BundlePluginsDir`）ので、無条件に足すと
  更新のたびに `<name>/<name>/…` と際限なく深くなる。この規則はインストーラ・
  アンインストーラ・アップデータの**3 つで同じ**でなければならない——片方だけ変えると、
  入れた場所と読む／消す場所が食い違う。3 つそれぞれに回帰テストを置いた。

- **取り除くのは、その版自身のアンインストーラ。** リリースは `vw-uninstall.*` も同梱し、
  それは**インストール先へ一緒に置かれる**（インストーラ自身は置かれない）。次の
  インストーラは、いま入っているフォルダの中のそれを叩いてから配置に入る。**置く側が
  新しい版の知識を持つのと、ちょうど対**——その版が何を置いたかを正しく知っているのは、
  その版のアンインストーラだけである。

- **順序は「検査 → 取り除く → 置く」。** 取り違えた zip を先に弾かないと、「消しただけで
  入れられない」状態を作ってしまう。

- **一時ディレクトリへ写してから叩く。** アンインストーラは自分が消すフォルダの中に居る。
  POSIX なら実行中でも読み続けられるが、写しておけば考えなくてよい。

- **削除には安全弁を置く。** フォルダ名が一致し、かつ中に殻があるときだけ消す。ここは
  本リポジトリで唯一「利用者のディスク上のものを消す」コードで、`Plug-Ins` そのものを
  名指しされても消さないことを回帰テストで押さえてある。

- **Windows は「退かしてから消す」。** 読み込み中の `.vlb` は削除できないが改名はできる。
  退いた `*.old-*` は拡張子が `.vlb` ではないので読み込まれず、次のインストールが掃く。

**旧配置（`Plug-Ins` 直下）からの移行は自動ではやらない。** 直下のものを消すには
「このプラグインのものだ」と名前で列挙するしかなく、それは**この一連の変更が捨てた作法**
そのものになる。利用者が 1 度だけ手で片付ける（README「自動アップデート」）。

### プラグインの位置付けと、更新の起こし方（M23）

**プラグイン 1 つには複数のコマンドと PIO を同梱できる。** そこで「1 機能 = 1 プラグイン」を
やめ、構造設計に使う機能をこの 1 つへ収めていくことにした。名前は表示名
**「みんなの構造設計支援」**、ファイル名・フォルダ名 **`min-nano_structure`**（dev は
それぞれ `…Dev` を付ける）。取り込みコマンドの名前は変えない。

判断したこと:

- **ユニバーサル名と拡張機能 UUID は据え置く。** これは**コマンドの同一性そのもの**で、
  ワークスペースはこの名前でコマンドを覚えている。改名の巻き添えで付け替えると、利用者の
  ワークスペースからコマンドが消える（登録し直しになる）。プラグインの名前が変わったから
  といって、コマンドが別物になる理由は無い。同じ理由で PIO のユニバーサル名も据え置き
  ——あちらは**図面に保存された既存オブジェクト**の同一性でもある。

- **C++ の名前空間 `HomeskzIfcImport` も据え置く。** 図面にも配布物にも現れない内部の
  綴りで、書き換えても利用者に何も起きない。200 ファイル超の機械的な差分で、本当の変更を
  読めなくするほうが損である。

- **改名は「きれいな切り替え」にする。** フォルダ名もアセット名も変わるので、古い版の
  アップデータは新しい版を自分の場所へ入れられない。移行を自動でやろうとすると「旧名を
  知っている」コードが要り、それは M22 で捨てた作法そのものになる。1 度だけ手で入れ直す
  （README「アップデート」）。

#### 更新の確認を、起動時から 2 つの入口へ

**起動時の自動確認をやめた。** M21 で殻と本体に割って以降、機能追加以外の更新は
**再起動なしでその場から効く**。だから「起動のたびに問う」必要が無くなった。代わりに:

| 入口 | どう振る舞うか |
| --- | --- |
| メニュー「アップデータを確認 (みんなの構造設計支援)」 | 押した以上、結末を必ず出す（更新した／最新／確認できなかった） |
| 取り込みコマンドの頭 | 更新があるときだけ尋ね、取得に失敗したら黙って取り込みへ進む |

判断したこと:

- **手で押したときは黙らない。** 起動時のチェックだった頃は「黙っている」が正しかった
  ——起動を邪魔しないため。コマンドになった以上、何も起きないのでは「最新だった」のか
  「そもそも動いていない」のかが利用者に区別できない。オフラインもその旨を出す。

- **取り込み時の確認は、本体を確保する前に置く。** そこで新しい本体が入れば `PayloadUse`
  がそれを読み直すので、**その 1 回目の取り込みからもう新しいコードが動く**。確保した
  あとでは本体のコードがスタックに載っているぶん降ろせず、反映が次回に回ってしまう。

- **PIO のリセットからは確認しない。** 取り込み直後には記号・耐力壁が数百個リセットされる
  ので、そのたびに GitHub を叩くわけにはいかない。PIO の更新は、手動の確認か、取り込み時の
  更新に乗って入れ替わるのを待つ。

- **dev の取り込み時確認はブランチ選択を出さない。** 取り込みたいだけの人の前に「どの
  ブランチを使いますか」を挟むのは邪魔でしかない。拾うのは**いま動いているのと同じ
  ブランチの、別のコミット**だけ——それだけが「自分のビルドが新しくなった」に当たる。
  そのために `q-dev` の TSV へ 5 列目（ブランチ名）を足した。リリースの表示名は
  `"Dev: <branch> (<sha>)"` なので照合に使えず、素のブランチ名はリリース本文（CI が書く
  `branch=` の行）から読む。**列が無い古い同梱スクリプトでは照合できないので何もしない**
  ——別のブランチのビルドを勝手に入れるよりずっと安全。

#### 再起動を SDK に頼めるようになった

M21 の時点では、再起動は**切り離したヘルパープロセス**に任せていた。SDK の
`CloseAllFilesAndQuitVectorworks` を呼ぶと、`bRestart` の有無にかかわらず
「サポートファイルの読み込みに失敗しました」で落ちたためである
（docs/DEVELOPMENT.md「以前は SDK に頼めなかった」）。

**原因は呼ぶ時機だった。** 当時の確認は**プラグインのロード中**（スプラッシュ表示中）に
走っており、Vectorworks 本体がまだ自分を終了させられる状態になっていなかった。確認が
メニューコマンドと取り込みコマンドへ移り、**Vectorworks が完全に動いている最中にしか
呼ばれなくなった**ので、素直に `CloseAllFilesAndQuitVectorworks(true, true)` に頼める。
未保存ファイルの保存確認も Vectorworks が通常どおり行う。

ヘルパーの一式（`MacRelaunchCommand` / `WinRelaunchCommand` / `PowerShellQuote` /
`MacAppBundleFromExecutable` と、それらが組み立てる shell / PowerShell を検証していた
テスト）はまとめて削除した。**もし将来また起動時に確認したくなったら、この失敗を
思い出すこと**——SDK の終了は「Vectorworks が動いていること」を前提にしている。

## 残っている宿題

- **配筋（保留）**。レコード `配筋` を立上り・底盤に設定する（`Pset_Reinforcement`、鋼種接頭辞
  除去、短辺/長辺→X/Y）。着手するときは**統合キーにも配筋を足す**
  （`parse/Footing.cpp` の `wallSectionKey` / `slabMergeKey`）——配筋の違う部材を 1 つに統合
  すると片方の配筋が失われる。現状は配筋を持たないため、**配筋だけが違う底盤は 1 枚に
  統合されている**。
- **床付け（M17）の実機確認は「スラブ厚・梁せいが一定」の範囲まで。** 実機で確かめられたのは
  底盤の厚みも地中梁のせいも揃っているモデルで、**それらが場所によって違うモデルは未確認**。
  効いてくるのは切り下げの 2 か所で、どちらも**保守側（多めに切る）**に倒れる:
  取り合う地中梁のほうが深いと切り下げ高さが負になり、その区間の捨てコン——場合によっては
  砕石も——が丸ごと落ちる（相手のコンクリートが占める前提。実データではスキップフロアの
  外周 × 内部で起きている）。底盤の厚みが場所で違うと、帯を切り上げる高さ（底盤の砕石の底）が
  地中梁ごとにずれる。**床付けが欠けて見えるようなら、まずこの 2 つを疑う**
  （`parse/Footing.cpp` の `beddingSpans`）。
- **M9（立上り・底盤・基礎ストーリ）の実機確認は M9 固有の項目だけ残っている。** M10 / M11 の
  確認で立上り・底盤・基礎ストーリも一緒に見えているため、残りは壁厚の保持・統合本数・
  布基礎（升目状ラティス）が統合されないこと、といった細目。
- **床版の開口は塞がっている。** VW スラブへ穴を開ける API の調査が要る。
- **登り梁の実データ検証が薄い。** 検証済みフィクスチャに登り梁を含むモデルが 1 件も無く
  （`tests/fixtures/README.md`）、合成モデル・合成命令でのみ検証されている。
- **進捗バーの重みは 1 サンプルの粗い実測。** 別のモデルで大きくずれる要素があれば
  `core::drawWeight` の表を直す（診断ログの経過ミリ秒と見比べる）。
- **draw/ 側の逐語コピーは一部を M19.5 の第 2 弾で整理済み**（`StoryBoundData`・バウンド ID・
  `SetObjectVariable` ラッパー・`AppendLine`・`PushUnique`・`kFitTol` → いずれも
  `draw/DrawUtil`）。**残っている候補**: 伏図と軸組図のフェーズ骨格・診断文言（`draw/Sheet` と
  `draw/Section` でほぼ同文。Sheet は 2 巡構造なので「1 枚ぶんの仕上げ」だけを切り出すこと）、
  スラブ描画手順（`draw/Floor` と `draw/Footing` の生成〜Reset。`ConvertToUnstyledSlab` より
  **前**に削り取りを渡す順序を崩さないこと）、要素ごとの描画ループ（進捗・レイヤ活性化・
  ハンドル記録が 12 か所で同型。ただしレイヤ欠落を数えるかは要素で違う＝挙動判断が要る）、
  `SetClassByName` と `SetAllAttributesByClass` の**対の当て漏れ**（フォールバック描画 4 か所は
  片方しか呼んでおらず、揃えると見た目が変わりうる＝実機確認必須）。いずれも実描画に触れる
  ため、**着手する PR は必ず実機確認を挟む**。`kCosts`（`core/Progress.cpp`）と `kElements`
  （`parse/Summary.cpp`）の命令数ラムダ 17 行の二重管理も未統合（表の統合は無 SDK で閉じるが、
  `DrawPhase` の並びとの手合わせ規約を壊さないこと）。
- **完了報告をモーダルのままにするか**は実使用の感触待ち。
- **実機フィードバックの往復に残る手仕事は「取り消し」だけ（M24）。** 自動の周は前の周の
  図の上へ重ねて描く。**プログラムから取り消しを掛ける手立ては無い**と確定した（Findings
  「Undo」。issue #23）ので、残る道は「前の周がこのプラグインで作ったレイヤを直接消す」
  （`DeleteObject` をレイヤへ。Findings で実機確認待ち）か「新しい文書を開いて描く」で、
  どちらも SDK リファレンス側の調査が先。同じく**絵そのものを送る**（ビューポートを画像に
  書き出して添える）ことができれば所見の負担がさらに減るが、これも書き出し API の調査が先。
- **モードレスのパレット（M24）は実機未確認。** 開くか・タイマーが届くか・表示／非表示が
  効くか・取り込み中の再入が弾かれるか。確かめた結果は SDK リファレンスの Findings
  「モードレス（非モーダル）なパレット」へ足し、注記を外す。
- **端部オフセットのパラメータ名は実機で確定させる（M20）。** PIO のパラメータ名は SDK
  ヘッダのどこにも無い（`ci-debug` の `sdk-grep` で `AxisAlign|StartCondition|MajorBreadth`
  を引いても 1 件も出ない）ので、候補（`StartOffset` / `OffsetStart` / `StartExtension` /
  `StartCutOffset` とローカライズ名「始端オフセット」）を並べて `ResolveParamNameAmong` で
  引いている。実データでは横架材の 7 割・柱のほぼ全数にオフセットが入るので、**外れていれば
  診断ログに「端部オフセットを設定できなかった材 N 本（候補: …）」が必ず出る**
  （`DescribeParamsContaining` がその PIO の似た名前を並べる）。出た名前を
  `draw/StructuralMember.cpp` の候補表へ入れて候補を畳む。
- **登り梁の端部はまだ「受け材の面まで詰める」まま**（`parse/Noboribari`）。傾斜梁は水平面内の
  矩形モデルが成り立たないので M20 の対象から外した。フレーム解析モデルを組み立てるときに
  ここも接合点へそろえる必要が出る。
- **接合点へ送れていない端がまだ残る**（実データで全端の 1〜2 割）。軒の出・継ぎ手のような
  本当の自由端が大半だが、**柱の断面から 100mm 以上外れた端**（実測の最小はみ出しは 80〜145mm）
  が各モデルに十数件ある。取り付く相手を柱・横架材のどちらとも言えていないので、必要になったら
  「何にも取り付いていない端」を診断へ出して実物と突き合わせる。
