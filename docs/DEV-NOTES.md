## 設計の考え方

### 2 フェーズ分離が全ての土台

処理を **IFC 解析（`src/parse/`）** と **VW 描画（`src/draw/`）** に完全分離し、両者を
**命令セット（`src/core/Document.h`）だけ**でつなぐ。`parse/` と `core/` は SDK を一切
include しないので、SDK 無し（約 800MB のダウンロード無し）で**コンパイルも単体テストも
できる**——これがこのリポジトリの生産性のほぼ全てを支えている。

- 解析ロジックは**実 IFC に対して CI で常時テストできる**（`tests/`）。
- 描画は実機でしか確かめられないが、**そこへ持ち込む値は先に固められる**。だから実機での
  切り分けが「命令セットの値が違うのか／SDK の呼び方が違うのか」の 2 択に絞れる。
- 依存の向きは CI が担保する（`core/` `parse/` を無 SDK でビルド・テストするジョブがある）。

**この分離を崩さないこと。** 「ここだけ SDK の型を使えれば楽」という誘惑は、無 SDK
テストの土台ごと壊す。SDK の幾何型が要る計算は `core/Geometry.h` の自前 `Vec2` / `Vec3` /
`Mat4` で書き、`draw/` の入口で変換する。

### 命令セット（Document）の設計則

- **フェーズ間で運べないものを載せない。** SDK ハンドル・STEP エンティティポインタは
  Document に入れない。描画中に必要なハンドルの受け渡しは「命令インデックス → ハンドル」の
  対応表（`draw/ObjectHandles`）で行う（立上り → 壁結合、横架材 → データタグ、柱 → 記号）。
- **同型が並ぶところは 1 つの構造体へ畳む。** アンカーボルト・床束・火打・仕口は中身が
  同じなので `core::SymbolCommand` 1 つで受け、要素の区別は「Document のどのリストか」が
  担う（描画も `draw/Symbol` ただ 1 本）。
- **突き合わせが要る関係は入れ子で持つ。** データタグは `ViewportCommand::tags`、
  グラフィック凡例は `SheetCommand` の中。平らに並べて番号で突き合わせる形にすると、
  突き合わせ自体がバグの温床になる。
- **振り分けは解析側でやり切る。** 「このタグはどのビューポートに載るか」のような判断は
  `parse/` が決め、`draw/` は「渡されたものを置く」だけにする。伏図と軸組図で**描画実装を
  1 つ**にできるのはこのため。
- スキーマを変えるときは、構造体定義・`validateDocument`・テストを**同時に**更新する。

### 描いた結果に対する 5 つの方針

1. **空のものを先に作らない。** 描画対象の無いレベル・レイヤ・凡例は作らない（空レイヤが
   図面に溜まると、利用者はそれが失敗なのか仕様なのか判断できない）。ストーリのレベルは
   「その要素の命令が実際にあるか」で足す。
2. **図面の既存リソースを書き換えない・増やさない。** スラブ／ウォールスタイルも
   データタグスタイルも**作らず**、構成層・基準面・タグレイアウトをオブジェクトへ直接
   与える（スタイルを作る形は、取り込みのたびに名前付きリソースが増え、しかも undo で
   消えないため、どちらも一度採用してから撤回した）。
3. **決定性を守る。** エンティティの列挙順に依存しない結果を出す。ソート・集約は明示的に
   行い、同値のときの順序も決めておく（`#id` 昇順など）。テストは全要素で決定性を見ている。
4. **1 要素の欠損で全体を止めない。** 想定外のエンティティ・解決できない幾何はスキップして
   次へ進む。例外は `parse/` 内部の局所処理に留め、フェーズ境界は値で返す。SDK
   コールバック（`plugin_module_main` / `DoInterface`）へ例外を漏らさない。
5. **診断は「異常だけ」を出す。** 平常時に鳴る診断は外す（後述「[実機確認の作法]
   (#実機確認の作法)」）。完了ダイアログに出るのは、件数の一覧と**起きてはいけないこと**
   だけ。

### 形状を先に確定し、支持部材を合わせる

床（床版）・屋根（屋根版）は建物の外形そのものを表す一次情報で、位置決めの基準になる。
そこで**床・屋根面を先に確定**してから、横架材・柱という支持部材をそこへ合わせる。

- 垂木・野地板は**屋根版から導出**される（IFC に垂木は出力されない）。面が形を決める。
- **登り梁はホームズ君の入力位置が不正確**（軸勾配が屋根版より急・端部が受け材へ食い込む）
  なので、天端中央線を屋根面へスナップし、端部を受け材（横架材・柱）の面まで詰める。
- 床版は IFC の位置を尊重し、スキップフロアの段差を絶対 Z で表す。

### レイヤ・クラス・レベルの規約は 1 か所に置く

同じ定数・述語を 2 か所に書かない。IFC 属性インデックスは `parse/IfcAttr.h`、レベル種別名は
`parse/Story.h`、基礎のレイヤ名・許容値は `parse/Footing.h`、レイヤ名の組み立ては
`storyLayerName` / `spanLayerName`、記号レイヤ名は `parse/ColumnMark`、構造クラス名は
`parse/StructuralClass.h`。**要素を足すときに触る場所が 1 行で済む**形を保つ
（完了ダイアログの要素一覧が `parse/Summary.cpp` の `kElements` 表 1 つなのが典型）。

## Vectorworks SDK の実測知見

**VectorScript（`vs.*`）の名前をそのまま ISDK に探しても無いことが多い。** 3D 変換状態
（`Move3D` / `Rotate3D`）・屋根作成の一連（`BeginRoof` / `GetZVals`）・レイヤ高さの取得
（`GetLayerElevation`）・ステータスバー（`Message`）はいずれも ISDK に無く、SDK 側の作法へ
読み替える必要があった。**着手前に `scripts/ci-debug.sh --mode sdk-grep` で実在を確かめる**
（手元に SDK が無いリモート環境ではこれが唯一の調査手段。[`DEVELOPMENT.md`](DEVELOPMENT.md)）。

### プラグインオブジェクト（PIO）

構造材ツール（`StructuralMember`）・通り芯（`GridAxis`）・データタグ・グラフィック凡例は
すべて PIO で、共通の落とし穴がある。

- **パスの型を間違えると「生成できるのに何も描かれない」。**
  - **水平材は 2D ポリライン**（`VWPolygon2DObj`）を渡す。2 頂点の 3D ポリラインに絶対 Z を
    持たせたところ、構造材は 451 本生成されるのに**長さ 0 で画面に何も出なかった**
    （OIP は「スパン 0 / 長さ 0」。PIO がパスを挿入点としてしか読んでいない）。
  - **鉛直材（柱・小屋束）は `CreateNurbsCurve` ＋ `Add3DVertex`** で下端 → 上端の 2 点。
    平面へ落とすと 1 点に潰れるので 2D ポリラインでは表せない。`Add3DVertex` が VS の
    `AddVertex3D` に当たる（`Insert3DVertex` は別物で頂点が増えない）。`VWNURBSCurve` は
    評価専用で制御点から構築できないが、`ISDK` 側に `Add3DVertex` がある。
- **シンボル定義に中身を入れたら `ResetObject` を呼ぶ（M19。ここに 3 周かけた）。**
  `GS_CreateSymbolDefinition`（`VWSymbolDefObj` の名前の構築子）で定義を作り、
  `AddObjectToContainer` で図形を入れる——ここまでは**最初から正しく効いていた**。
  抜けていたのは**入れた後に `gSDK->ResetObject(定義のハンドル)` を呼ぶこと**で、
  これが無いと**定義の外接が計算されない**。外接が無い定義は絵として成立せず、
  * 実機のシンボル 2D 編集で「すべて選択」しても何も選べない、
  * 配置したインスタンスの外接が `-2147483648`（＝大きさが無い）、
  * 図には何も出ない、
  という「中身はあるのに空に見える」状態になる。実測（`symprobe` v3）:

    ```
    A（入れた後）       type=16 defType=0 外接=無効     中身[0] type=5 外接=300x150 頂点=3 閉=yes
    A（ResetObject 後） type=16 defType=1 外接=300x150  中身[0] type=5 外接=300x150 頂点=3 閉=yes
    ```

    中身は前後で同じ。**変わるのは定義の外接と種別だけ**。
  ついでに分かったこと:
  * **`GetFirstMemberObject()` は空の定義でも非 nil を返す。** 空の定義は type 0 の
    レコードを 1 つ持つので、「入ったか」の検証にこれを使ってはいけない。
    数えるなら `FirstMemberObj` / `NextObject` で辿って**型番号を見る**
    （4=楕円 / 5=多角形 / 11=グループ / 16=シンボル定義）。
  * **`GS_CreateSymbolDefinition` は「名前が既に使われていれば nil を返す」**
    （`APIBase.Legacy.Defs.h` の本文）。**一度壊れた（空の）定義を作ってしまった図面では
    次から作り直せず、空のまま残り続ける**。作り直したいなら
    `DeleteSymbolDefinition` してから。
  * マニュアルが挙げる `EnterContainer` は **ISDK に無い**（レガシー本文に名前が出るだけ）。
    VectorScript の `BeginSym` / `EndSym` に当たる口も無い。`SetActiveSymbolDef` は
    作図先を切り替えない（VWFC のラッパーはアクティブ**レイヤ**へ作られる）。
    **入れる口は `AddObjectToContainer` ただ 1 つでよい。**
  * `SetPageBased(true)`（`ovSymDefPageBased`）は効く（`GetPageBased()` が true を返す）。
  * 定義の種別は `GetSymbolDefinitionType`（`k2DSym`=0 / `k3DSym`=1 / `kHybridSym`=2）。
    **`ResetObject` の後、自作の定義は 3D（1）になった**——テンプレート由来の既存
    シンボルは 3 つとも 2D（0）だったので、VWFC で作った 2D 多角形が「レイヤ平面の
    図形」として入っているせいだと見ている（スクリーン平面へ寄せるなら
    `SetPlanarRefID` ＋ `kPlanarRefID_ScreenPlane`）。
- **紙の上の大きさを一定にしたい絵は「用紙 mm × レイヤ縮尺」で描く。** 縮尺を掛ける
  手掛かりは `GetLayerScaleN`（1/50 なら 50 が返る）だけで、引数はレイヤのハンドルなので
  `ParentObject` で PIO の親を辿って渡す。縮尺が変わったときに描き直させるには
  オブジェクトプロパティ `kObjXPropHasLayerScaleDeps`（＝2。"Object wants to be reset
  when its layer scale changes"）を立てる。**ビューポートの縮尺は使えない**——
  デザインレイヤの図形は複数のビューポートに別々の縮尺で映るので、図形の側からは
  「どの縮尺で見られるか」が決まらない（`ovViewportScale` はビューポート自身の変数）。
- **`VWPolygon2DObj` は既定で「開いた」折れ線。** 頂点を一周ぶん足しても
  `SetClosed(true)` を呼ばないと、**最後の頂点から最初の頂点へ戻る辺が描かれない**
  （M19 の筋かい記号で、直角三角形の斜辺だけが消えた）。塗りが要らない図形ほど
  気付きにくい。閉じ／開きは呼び出しごとに明示する（`draw/Roof`・`draw/DrawUtil` は
  `SetClosed(true)`、`draw/Member`・`draw/Rafter` の直線は `SetClosed(false)`）。
- **高さはストーリバウンドが支配する。パスとバウンドの両方が要る。** 実機で 3 周かけて
  切り分けた結果:

  | 鉛直パス | バウンドの差 | 結果 |
  | --- | --- | --- |
  | 1 点 | 0 | スパン/長さ/高さ 0。オブジェクトはレイヤ原点に置かれ、offset まで VW に上書きされる |
  | 1 点 | 柱高さ | OIP の値は命令どおりになるが、**長さ 0 で描かれない** |
  | **2 点** | 柱高さ | **正しく描かれる** |

  つまり**バウンドの差が高さを決め**、鉛直パスはその高さで実体を作るために要る。上端 offset を
  下端と同値にする（＝差 0）と高さ 0 になるので、**どの柱でも「差＝柱高さ」**にする。
  逆に水平材のパスに傾斜を持たせてはいけない（バウンドの高さ差と二重に効く）。
- **パラメータ名は実機の PIO 登録から採る。** VectorScript のエクスポートから推測した名前
  （`pitch` / `label` / 先頭大文字の `StructuralUse`）では **setter が黙って無視された**。
  書いたら**読み戻して確かめる**（`draw/DrawUtil` の `ResolveParamName` /
  `SetParamRealChecked`）。異常は完了ダイアログの診断行に出す。
- **生成時に「オブジェクトの設定」ダイアログが出る。** `CreateCustomObject` は、その名前の
  PIO が文書に未定義なら定義を作り、その `prefWhen` の**既定が `kCustomObjectPrefAlways`**。
  そのため**最初の 1 個だけ**ダイアログが出て取り込みが止まる。PIO 側の
  `OnInitXProperties` で `kObjXPropShowPrefDialogWhen` を宣言しても**定義が作られる過程で
  走るので 1 回目に間に合わない**。描き始める前に
  `DefineCustomObject(name, kCustomObjectPrefNever)` を 1 度呼んで先に定義しておく。
- **プラグインスタイルは当てただけでは描画属性が流れない。** `SetPluginObjectStyle` は
  関連付けまでしか行わないので、**全部置いてから `UpdateStyledObjects` を 1 回**呼ぶ
  （構造材・柱で共通）。スタイルを当てない PIO（データタグ・グラフィック凡例）には
  そもそも要らない。
- **スタイル名 → RefNumber を名前で引く呼び出しは無い。** `GetNamedObject` ＋
  `GetObjectInternalIndex` で引く（`draw/DrawUtil`）。
- **プロファイル（断面）グループは空でないことを確かめる。** 空の断面は「オブジェクトは
  あるのに描かれない」を招く。生成後に読み戻して数え、診断行に出す。
- **ポップアップの値は表示文字ではなくキー**（英語または数値文字列）で、表示だけがローカライズ
  される。数値キーは**その項目の並び順（0 始まりの索引）**で、`<自動>` のような先頭項目も
  1 つ数える。

  **構造材ツールの「構造用途」の全項目**（実機で「構造材設定」のドロップダウンを開いて確認。
  値は上から 0, 1, 2, …）。本プラグインが使っているのは 梁 `1`・柱 `4`・小屋束 `5`・垂木 `8`
  の 4 つで、残りは今後の作り込みのために記録しておく。

  | 値 | 項目 | 値 | 項目 | 値 | 項目 |
  | --- | --- | --- | --- | --- | --- |
  | `0` | `<自動>` | `6` | コレクタ | `12` | 筋かい |
  | `1` | **梁** | `7` | 弦材 | `13` | 棟木 |
  | `2` | 桁 | `8` | **垂木** | `14` | 隅木 |
  | `3` | 根太 | `9` | 母屋梁 | `15` | 頭つなぎ |
  | `4` | **柱** | `10` | 角材 | `16` | まぐさ |
  | `5` | **小屋束** | `11` | 胴差し | `17` | その他 |

  そのほかのポップアップ:

  | パラメータ | キー | 意味 |
  | --- | --- | --- |
  | `AxisAlign`（断面基準点） | `1` / `4` / `7` | 天端中央 / 中央 / 中下。3×3 グリッドを 0 始まり・行優先で数えたもの（**天端中央と中央は実機確認済み、中下 `7` はその並びからの推定**——M16 のローカル確認項目） |
  | `MemberType`（部材種別） | `2` | 構造材（種別の違いは構造用途の方に出る） |
  | `StartCondition` / `EndCondition` | `3` | 直切り |
- **構造材ツールは軒の出・差し込みを持たない。** 軸組ツール（`FramingMember`）は挿入点＝支持点
  から軒側へ 差し込み＋軒の出 だけ材を伸ばすが、構造材ツールは**パスがそのまま材の範囲**。
  垂木を構造材ツールへ移したとき（M16）は、パスの始端を支持点ではなく**軒先**にし、
  その軒先の位置・高さ・バウンド offset を命令から求める純計算（`core::rafterEaveEnd`）へ
  切り出した。

#### 自作 PIO を足すときの 4 点

CI が全て緑でも次の 4 つは通ってしまい、実機で初めて出た。**新しい PIO を足すときは最初から
この 4 つを入れる**（1〜3 は `Extensions/ExtColumnMark`、4 は `Extensions/ExtShearWall` で出た）。

1. 上記の**設定ダイアログ抑止**（`DefineCustomObject(..., kCustomObjectPrefNever)`）。
2. **PIO のジオメトリは PIO 自身のローカル座標で持たれる。** 走査して見つけた対象の
   ワールド座標へそのまま描くと、PIO を動かした量だけ絵がずれ、リセットしても同じ相対位置に
   描き直すので直らない。`GetObjectToWorldTransform` ＋ `InversePointTransform` でローカルへ
   落としてから描く（回転も戻るので PIO を回しても絵は対象の上に残る）。
3. **リセットの契機は自分で宣言する。** 既定では何も設定されておらず、印刷でも再オープンでも
   描き直されない。`ResetOnMove` / `ResetOnRotate` と `kObjXPropResetBeforeExport`
   （印刷・書き出しの直前）を立てる。

**【限界】他の図形が変わったときに再計算する仕組みは VW に無い。** `kObjXProp*` を全数
確認したが、リセット系はすべて PIO 自身に関するもの（自分のレコード・自分のパス／
プロファイル・ビューポート倍率・書類単位・書き出し前）だけで、association にも追加の公開
API が無い。したがって柱を動かした瞬間には記号が追随しない。実用上は
`kObjXPropResetBeforeExport` が効く——**図面として外へ出る瞬間には必ず実物と一致する**。

4. **1 つの取りこぼしで絵を全部止めない。** PIO の失敗は「選択はできるのに何も
   表示されない」という形で出る——症状からいちばん原因を辿りにくいので、途中で
   諦める枝を作らないほうがよい。具体的には、
   * 書き手側（`draw/*`）は**パラメータを 1 つずつ独立に書き、`ResetObject` は必ず
     呼ぶ**。VWFC の setter は名前が通らないと例外を投げるので、まとめて 1 つの `try`
     に入れると最初の 1 つで残り全部とリセットまで飛び、`Recalculate` が一度も
     走らない。
   * 読み手側（PIO 本体）は、**読めなかった値の分だけを諦める**。耐力壁の伏図記号は
     平面（両端の柱と内法）だけで決まるので、高さが読めなくても描く。両端が
     読めないときも、控えの内法から軸を組み直して描けるところまで描く。

**［診断］PIO の中で何が起きたかは、PIO 自身に書かせるのが唯一の手掛かり。**
実機でしか再現しないうえ、症状（何も出ない）からは「解析が値を出していない」「PIO に
届いていない」「PIO が途中で諦めた」のどれかが分からない。`core/Trace` は
インポート中ずっと開いているので、PIO の `Recalculate` からも書ける——
`Extensions/ExtShearWall` は**実際に登録されているパラメータの一覧**
（`VWParametricObj::GetParamsCount()` / `GetParamName(i)`）と、読めた両端・内法・高さを
1 枚につき数行残す。これがあると切り分けが 1 往復で済む。

**［注意］オブジェクト情報パレットは足りなければスクロールする。** 出ている
パラメータが登録した数より少なく見えても、それは登録漏れの証拠にならない
（M19 で一度そう読み違えた）。数えるなら上の診断ログで数える。

なお **PIO を同梱する代償は小さい**ことを実機で確認した。プラグインを外して過去の図面を
開いても、**PIO が描いたジオメトリは保存されていて表示できる**（更新ができないだけ）。

### シンボル

ISDK にシンボルを配置する呼び出しは無く（在るのは `CreateSymbolDefinition` だけ）、
`VWSymbolObj(name, VWPoint2D, angleDeg)` がレガシーの `PlaceSymbol` を包んでいる。
**どちらも外すと静かに壊れる**作法が 2 つある。

1. **生成しただけでは図面に現れない。** VWFC の他のラッパーと違い、できたインスタンスは
   アクティブレイヤに入らない。生成後に `gSDK->AddObjectToContainer(handle, layer)` で
   配置先レイヤへ入れ直す。
2. **非 nil のハンドルを成功判定に使わない。** `PlaceSymbol` は「定義が nil なら何もしない」
   仕様で、**何も置けていなくても非 nil のハンドルを返し得る**。
   `VWSymbolObj::IsSymbolObject(handle, name)` まで確かめてから 1 件と数える。

この 2 つが無かったために、定義・レイヤ・名前・座標がすべて正しいのに 4 種 472 件が図面に
現れず、しかも**完了ダイアログは全数成功で嘘をついていた**。

- **事前ガードを置かない。** 当初 `VWSymbolDefObj::IsSymbolDefObject` で先に弾いていたが、
  その判定が期待どおりでないと**1 つも置けないうえ原因を誤って指す**。配置そのものを唯一の
  門にし、失敗したときだけ理由を引き分ける。
- **シンボルはストーリバウンドを持てない。** レイヤ平面から外れた高さへ置くには
  `MoveObject3D(handle, 0, 0, zOffset)` で相対移動するしかない（仕口を横架材の天端へ
  合わせるのに使う。登り梁は一端が軒桁・他端が棟木で数 m の高低差がある）。
  **配置行列（`SetEntityMatrix`）には書かない**——行列は「与えるときは Z が絶対・読み戻す
  ときは Z がレイヤ相対」という混在があり、相対値を書くと取り違える。

### 壁

- **`CreateWall` は壁厚を引数に取る**（VS の `DoubLines` → `Wall` の 2 手順は要らない）。
- **高さは壁専用の `SetWallOverallHeights`**（`SStoryObjectData` 2 つ）で与える。汎用の
  `SetObjectStoryBound` では壁の高さ基準が確定せず、**デザインレイヤの「壁の高さ」設定に
  従ってしまう**（構造材・スラブでは効くが、壁だけは専用関数が要る）。
- **`JoinWalls` の X（交差結合）は a の壁を交点で 2 本に分割する。** VW ヘルプにも
  「1 本目に選んだ壁が 2 本に分割され、2 本目へ結合される」とある。**バグではない**ので、
  取り込み後に立上りが増えるのは正常。ここから 2 つの規則が要る:
  - **バックボーンは b にする**（分割されるのは a）。通し壁を分割させない。
  - **X 結合はすべて最後に実行する**。分割で**ハンドルが古くなる**ので、X より後にその壁を
    使う結合が残っていると分割後の片方だけを相手にしてしまう。
- **結合の後に `ResetObject` する。** `JoinWalls` が 54 件中 53 件を受け付けているのに、
  平面では T 字の面線が消えなかった。切断高さ（カットプレーン）もコア構成要素も外れで、
  効いたのは `ResetObject`——**結合は成立していて 2D 表現だけが古いまま**だった。
- **端部のキャップは端ごとに明示する。** VW の壁は端を閉じる線を壁ごとに持ち、明示しなければ
  ドキュメントの壁ツール設定に従う。結合任せにすると「T 字でぶつかる側の端線が残る」
  「自由端に閉じ線が無い」が両方起きた。解析側が端ごとに決めて `SetWallCaps` で設定し、
  **`JoinWalls` の後に入れ直す**（結合が書き換えるため）。
- **VW は結合を記録しても壁芯の端点を変えない**（表示のときに取り合いを解決する）。実機では
  55 件中 48 件が「動かなかった」のに正しく描かれていた。**「端点が動いたか」で結合の成否は
  測れない。**
- ピック点は**交点そのものではなく「残す側」へ寄せた点**にする（交点は相手の壁芯上にあり
  残す側が曖昧で、VW が L でコーナーを詰めない）。
- 結合失敗のダイアログは `showAlerts=false` で抑止し、**拒否された件数と交点の座標**だけを
  診断に残す（これで実データ唯一の拒否箇所を特定できた）。

### スラブ・押し出し

- **スタイルを作らず、unstyled のスラブ／壁へ構成層と基準面を直接与える**
  （`ConvertToUnstyledSlab` / `ConvertToUnstyledWall` → `draw/DrawUtil` の共通手順）。
  床板・底盤・立上りが同じ手順を共有する。
- **厚み 0 の構成層は VW が受け付けない。** 余った層は 0 に潰さず**削除**する。
- **構成要素は素材ごとのクラスに分け、層の描画属性はクラス属性に従わせる**
  （`SetComponentClass` ＋ `SetComponentUseFillClassAttr` / `…UsePenClassAttr`）。
  オブジェクト本体のクラス（その部材が何か）とは別の軸で、**層が何でできているか**を表す。
- **`VWExtrudeObj` は押し出しを「2D 基面 ＋ 基準高さ ＋ 厚み」に持ち替える。** そのため 3D
  ポリゴンから作ると基面の平面を導出したうえで**配置先レイヤの高さを法線方向へ足す**。
  普通の押し出しは鉛直なのでこれは正しい動作だが、**水平押し出し（地中梁）ではそのまま
  軸方向の横ずれになる**（実測: 命令どおりの長さ 11905 のまま、位置だけ +50mm＝レイヤ高さ）。
  対処は**置いた後に `GetObjectBounds` で実位置を測り、`MoveObject3D` で寄せ直す**。
  レイヤ高さを当てにいかず実測で補正するので、VW 側の挙動が変わってもこのままで正しい。
- 押し出しは**基面の法線方向へ伸びる**ので、頂点の並びを法線が伸ばしたい向きを指すよう
  揃える（Newell 法）。
- **スラブへ「足す」噛み合わせは現時点の SDK では実現できない**
  （[打ち切った調査](#打ち切った調査もう一度やらないこと)）。削り取りモディファイアと
  可視ソリッドを**2 回作る**のが最善。

### 屋根面

- **屋根面オブジェクトは `VWRoofFaceObj` をハンドル版コンストラクタで作り直す。**
  `VWRoofFaceObj(type, poly, z, upSlopeDir, rise, run)` は**使えない**（SDK のソース上 `z` を
  読まず、屋根軸を原点を通る線として置く）。外形ポリゴンから作ってから、屋根軸・棟側の点・
  勾配・軸の Z を**オブジェクト変数**（`ovSlabRoofPt1/Pt2/UpslopePt/Rise/Run`・`ovSlabHeight`）
  で与える。`ovSlabRoofUpslopePt` は**方向ではなく棟側の点**。
- シンボルと同じく**生成しただけでは図面に入らない**（`AddObjectToContainer` が要る）。
- VS の 3D 変換状態と `BeginRoof` 系が無いので、**配置行列**
  （`VWTransformMatrix` ＋ `CreateCustomObjectByMatrix`）で置く。副産物として、VectorScript
  版が抱えていた落とし穴（テンプレートのポリゴンを屋根と誤認する／確定後の後付け操作で
  VW がクラッシュする）が構造的に起きない。

### レイヤ・ストーリ・重ね順

- **デザインレイヤは図面のオブジェクト列に並んでいる。**
  `VWDocument::GetDrawingHeaderFristMember` ＋ `NextObject` で辿れ、
  **`InsertObjectAfter` / `InsertObjectBefore`** が VS の `HMoveForward` に当たる。
  これがレイヤ重ね順を変える唯一の手段（`draw/Story` の `reorderStoryLayers`）。
- **ビューポート単位の重ね順上書き（`SetViewportLayerStackingOverride`）は SDK から書けない。**
  読み出しはできるので、これが唯一の手段だと分かっている（詳しい実測は
  [打ち切った調査](#打ち切った調査もう一度やらないこと)）。
- **並べ替えはビューポート生成より前に行う**（ビューポートは生成時の重ね順で描かれる）。
- **【実測】VW はデザインレイヤを「レイヤ高さの降順」で並べる。作った順でも、レベル種別の
  登録順でもない。** 実機のダンプ（レイヤ名 ＋ ストーリ / レベル種別 / レベル高さ）がこれ:

  ```
  3to3.5-柱[屋根/3to3.5-柱/5961] | R-垂木[屋根/垂木/5961] | … | R-野地板[屋根/野地板/5961]
  2-FL[2階/FL/3361] | 2to2.5-柱[2階/2to2.5-柱/3325] | … | 2-野地板[2階/野地板/3325]
  1-FL[1階/FL/561]  | 1to2-柱[1階/1to2-柱/525] | … | 1-横架材天端[1階/横架材天端/525]
  F-アンカーボルト[基礎/基礎天端/400] | F-床束[…/50] | F-底盤[…/50] | F-立上り[基礎/GL/0]
  柱伏図記号・共通（ストーリ非従属。高さ 0 で最背面）
  ```

  高さが 5961 → 3361 → 3325 → 561 → 525 → 400 → 50 → 0 と**きれいな降順**になっている。
  希望順に沿って**作って**も 27 枚中 26 枚が並べ替え対象になった（作った順は完全に無視）。
  ストーリ非従属レイヤ（"共通" / 伏図記号）だけは**作った順**で決まり、ストーリ従属レイヤの
  背面へ回る。
- **【実測】取り込み直後の伏図で床が柱・梁を覆うのは、この高さ順が原因。**
  `n-FL`（床仕上げ天端 3361）は構造天端 3325 より **36mm 高い**ので、VW は物理的に正しく
  床を前面に描く。**こちらの並べ替えは図面には入っているのに、取り込み中の描画には届かない**
  ——ユーザーが「更新」を 1 回押すか、ファイルを開き直すと、図面の並び（＝並べ替え後）で
  描き直されて正しくなる。
- **届かせようとして全滅した 4 通り（もう一度やらない）。** どの回も図面の並びは並べ替え後で
  正しく（読み戻しでも OIP でも）、描き直し自体も走っている（`IsDirty` が下りる）のに絵は
  高さ順のまま:
  1. 並べ替えをビューポート生成の直前に置く（M13 の形）。
  2. 並べ替えを**要素を 1 つも描く前**へ前倒しし、`SetDirty(true)` を立てて描き直す。
  3. 描き直しを **undo イベントを閉じた後**へ回し、口も `ISDK::UpdateViewport` へ替える。
  4. 描き直しを**進捗ダイアログも閉じた取り込みの外**（`Extensions/ExtMenu`）まで遅らせる。
     さらに「取り込み中は 1 枚も描かず out-of-date の印だけ立てて VW に描かせる」も試したが、
     **伏図 6 枚は `SetDirty(true)` を受け付けない**（`IsDirty` が立たない）ので印すら立たない。

  SDK に遅延実行の口は無い（`ISDK` にあるのは `RegisterDialogForTimerEvents`＝ダイアログの
  タイマーだけ）。**残る手は「床の塗りが構造材を隠さないようにする」方向**（伏図ビューポート
  だけ床クラスの塗りを `SetViewportClassOverride` で消す／伏図から床レイヤを外す／FL レベルの
  高さを下げる）だが、いずれも図面の見え方か構造の意味を変えるので、**現状は運用で回避**
  （完了ダイアログと README で「1 回更新してください」と案内する）。
- **「動かせた数」を成否と読まない。** 既に希望どおりでも 0 件、並べ替えに失敗しても 0 件。
  並びそのものを読み戻して確かめること。
- **レイヤ高さを取得する呼び出し（`GetLayerElevation` 相当）が無い。** 高さは命令の絶対 Z を
  そのまま渡す。レイヤ相対へ切り替えられるよう、渡す 1 か所（`draw/Rafter` の `SetOffset` /
  `draw/Roof` の `ovSlabHeight` / `draw/Member` の `kPathZ`）に名前を付けてある。

### ビューポート（伏図・断面）

- **クラスは明示的に表示へ戻さないと非表示のまま。** レイヤが命令どおりでもクラスが全部
  消える。`VWClass::ForEachClass`（＝`ISDK::ForEachClass`）で**ゲスト（参照ファイル由来）を
  含む全クラス**を表示にする。**`SetUseDocumentClassVis`（オブジェクト変数 1031）は使えない**
  ——但し書きが "for dlvps"（デザインレイヤビューポート専用）。
- **伏図は 2D/平面への作り直しが要る。** `CreateViewport` が作ったビューポートは、OIP 上は
  〈2D/平面〉なのに**描画キャッシュが 3D の「上」ビューのまま**で、更新ボタンでも直らない。
  Project 2D（オブジェクト変数 **1005**）を ON にするだけでは作り直されないので、
  **ユーザーの手動操作をそのままなぞる**——ビューの向きを〈上〉（`standardViewTop` = **1007**）
  にし、Project 2D をいったん OFF にして**更新を挟み**、再度 ON に戻して最後の更新を行う
  （`draw/DrawUtil` の `ConfigureViewport`。表示レイヤを絞った後・最後の更新の前）。
  入ったかは `GetProject2D` で**読み戻して**確かめる。
- **断面ビューポートは `ISDK::CreateSectionViewport` で新規作成できる**
  （pt1, pt2, pt3, depth, startHeight, endHeight, layer）。pt3 は「見る側」を示す点。
  VectorScript 版が既製ビューポート 40 枚を手で用意して流用していた運用は丸ごと要らない。
- **断面の範囲は 3 つの数値引数が決める唯一の手段で、「無限」にはできない。**
  実測では **`depth` = 0 → 〈切断面より奥: 無限〉**だが、**`startHeight` / `endHeight` = 0 は
  〈有限・0〜0〉**になって断面から建物が消える。したがって
  **奥行き＝0／高さ＝建物を包む実寸＋余白／長さ＝断面線の長さ**（指示線を通り芯 bbox ＋
  余白まで延ばす）で決める。
- 表示の作法（いずれも**更新より前**に設定する）:
  - 切断面より奥は表示しない … オブジェクト変数 **1064**
  - プレイナー（アクティブレイヤ平面）図形は表示しない … **1035**
  - 2D コンポーネントは表示する … **1059**（**既定は非表示**）
  - **レンダリングは〈隠線消去〉**（`VWViewportObj::SetRenderType(renderFinalHiddenLine)`）。
    **これが先に要る**——シェイドのままでは 1059 を書いても入らない。手作りの断面と OIP の
    項目が違って見えるのもこれが原因で、VW は隠線消去でしか意味を持たない項目を隠す。
- シートレイヤの用意とビューポートの仕上げ（表示レイヤの絞り込み → クラス表示 → 縮尺 →
  図番／図面タイトル → 更新）は**伏図と軸組図で逐語的に同じ**なので `draw/DrawUtil` に 1 つ。

### 用紙（シートレイヤ）と割り付け

M18 で「用紙と建物の大きさから縮尺を自動で決め、重ならないように整列する」を入れた。
分かったことと、決めた規約:

- **用紙の大きさは SDK から読める**（`VWLayerObj::GetSheetWidht()` / `GetSheetHeight()`。
  綴りは SDK ママ）。ただし**返るのはインチ**（ヘッダのコメントが
  "value in inches. Use (result * 25.4) to get mm" と明記）。図面座標は mm なので必ず
  換算する。オブジェクト変数では `ovLayerSheetWidth`（165）/ `ovLayerSheetHeight`（166）が
  同じ値で、用紙（ページ）そのものの大きさは 167 / 168。
- ★**「用紙の大きさ」と「印刷可能領域」は別物で、余白を仮定してはいけない。** 当初は
  用紙の大きさだけを読み、四辺 15mm の余白を定数で決め打ちしていたが、余白は用紙ではなく
  **印刷の設定**が決めるものなので、仮定した瞬間に実際とずれる（狭く見積もれば図が
  1 段階小さくなり、広く見積もれば印刷で切れる）。SDK には両方ある:
  用紙は `ovLayerSheetPaperWidth` / `Height`（167 / 168）、**余白は
  `ISDK::GetPageMargins(hLayer, left, right, bottom, top)`**（4 辺それぞれ）。
  シートレイヤの大きさ（165 / 166）はまた別値。
- ★**`GetPageMargins` だけ単位がヘッダに書かれていない。**【実機で確定】用紙まわりの
  長さは SDK では一貫してインチだが、この 1 つだけ注記が無く、**実際は図面の単位で返る**
  （mm の図面なら mm）。実測: 用紙 420 × 297 に対し `左2.963 右3.006 下2.963 上2.963` が
  返り、引くと 414 × 291 ＝ シートレイヤの大きさ（165 / 166）とぴったり一致した。
  `draw/DrawUtil` の `SheetPaperArea` は「インチとみなした値／mm とみなした値のうち、
  `用紙 − 余白` がシートレイヤの大きさと一致する方」を採るので、この一致で mm を選ぶ。
  **判定を「mm 固定」にはしない**——単位が図面依存である以上、インチの図面では
  インチで返るはずで、そのときは同じ突き合わせでインチが選ばれる。どちらとも一致しな
  ければ用紙に収まる方（両方ならインチ）へ倒し、**採った解釈と生の値は診断行へそのまま
  出す**ので、別の環境でも実機の数字で確かめられる。
- ★**余白の四辺 0 は「読めなかった」ではない**（M18 の後、実機から上がった誤判定）。
  当初は「1 辺でも 0 より大きい値が返ったときだけ余白として解釈する」形にしていたので、
  **縁なし印刷ができる機種で余白 0 の用紙設定を選ぶと**「余白を解釈できなかったので
  用紙いっぱいで割り付けました」という診断が出ていた。割り付けの結果（用紙いっぱい）は
  正しいのに警告だけが出る、という誤判定である。0 はそのまま「余白なし」として受け取る。
  ただし**シートレイヤの大きさ（165/166）が用紙より小さいのに 0 が返った**ときだけは
  辻褄が合わない（印刷可能領域が狭いのだから余白は在るはず）ので、そのときは従来どおり
  「解釈できなかった」側へ倒して生の値を診断に出す。`GetPageMargins` の呼び出し自体が
  失敗して 0 のままなのか、返ってきた 0 なのかも**区別して**持つ（前者を「余白なし」と
  読んではいけない。`draw/DrawUtil` の `SheetPaperArea`）。
- **余白の解釈は `core::resolvePageMargins`（無 SDK）に置いてある。** 読むのは SDK の
  仕事だが、**読めた数字をどう解釈するか**——インチか mm かの突き合わせ・0 の扱い・
  負値の棄却——は算数でしかないので、描画側から切り離して `CoreLayoutTests` で
  テストする（CLAUDE.md「描画側から切り離せる純計算」）。
- **印刷可能領域を読むと図が 1 段階大きくなった**（実機）。決め打ちの余白 15mm/辺に対し、
  実際の余白は 3mm/辺しかなく、A3 横で使える幅が 390 → 414mm に増えた。結果、
  18.07 × 13.52m の建物が **1/75 → 1/50** に上がった（1/50 は 361 × 270mm 必要で、
  凡例 22mm ＋ 間隔 15mm を引いた 377 × 291mm に収まる）。
- ★**用紙が図面座標のどこに在るかを返す呼び出しは無い。** `GetSheetOrigin()` はあるが、
  それが用紙の中心を指すのか隅を指すのかはヘッダからは決まらない（説明が無い）。
  意味の分からない値を使うより規約を 1 つ決める方がよいので、**用紙は原点を中心に
  置かれている**という前提で矩形を組んでいる（`draw/DrawUtil` の `SheetPaperArea`）。
  印刷可能領域はそこから 4 辺の余白を引いた矩形で、**余白は左右・上下で異なりうる**ので
  中心もそのぶんずれる（引いた後の矩形をそのまま使い、中心へ寄せ直さない）。
  **最初の実機確認で真っ先に見るのはここ**——図が用紙の外に出ていたら、この前提が違う。
- **縮尺は「用紙に収まる中で最も大きい図」を階梯から選ぶ**（`core::fitScale`）。
  階梯は 1/200・1/175・1/150・1/125・1/100・1/75・1/50・1/30・1/25・1/20・1/15・1/10・1/5
  のキリの良い値だけで、どれにも収まらなければ**いちばん小さい図**へ倒す
  （はみ出すくらいなら小さく描く）。
- **ビューポートの実寸は描いてみるまで分からない**が、**そこに何が映るかは命令セットが
  全部知っている**。だから縮尺は測る前に決められる（`core::planContentBounds` /
  `core::sectionContentSize`）。位置合わせだけは実物を測る（`GetObjectBounds` →
  `MoveObject`。データタグ・凡例と同じ「置いた後に測って直す」作法）。
- **伏図は全図が同じ縮尺・同じ位置**（用紙をめくっても図が動かないため）。位置は
  「外形の中心を用紙の中心へ」ではなく、**建物の中心が常に同じ点へ来る**ように置く
  ——伏図ごとに映すレイヤが違えば図の中身の広がりも違うので、外形の中心で揃えると
  ページごとに建物がずれる。ずらす量は「その伏図に映る範囲の中心 − 文書全体の中心」を
  縮尺で割ったもの。
- ★**縮尺は凡例の幅を引いてから決める。** 用紙いっぱいで縮尺を決めて凡例は置き場所だけで
  避ける、という形も一度試したが、**建物がギリギリの大きさだと凡例を置くスペースが
  残らない**（凡例も図面の一部で、重なると読めない）。置けなくなるくらいなら図を 1 段階
  小さく描く、が決まりごと。図は「印刷可能領域 −（凡例の幅＋間隔）」の領域で縮尺を決め、
  その領域の中央へ置く。命令の座標に現れないもの（通り芯の丸など）のぶん実際の図は
  見積もりより大きくなりうるので、**はみ出し・重なりは描画側が実測して診断へ残す**。
- ★**縮尺を決めた 3 つの値は結果として残す。** 縮尺は「印刷可能領域・凡例の幅・建物の
  広がり」の 3 つだけで決まるが、ローカル確認の場で分かるのは結果の縮尺だけなので、
  それだけではどれが効いたのかが切り分けられない（実際に「1/50 のはずが 1/75 になる」で
  足止めされ、**建物が 18.07 × 13.52m あって当時の割り付けでは 1/50 が入らない**——
  実装も測り方も正しい——と分かるまで往復した）。`draw/Sheet` は
  「伏図の割り付け（mm）: 用紙 … / 印刷可能 … / 凡例 … / 建物 … → 用紙上 … / 縮尺 1/N」
  の 1 行を完了ダイアログへ出す。
  **調査のための値（余白の生の値・単位の解釈・実測の図の大きさ）はここに出さない**
  ——規約を詰めるために要ったもので、実機で確定した時点で外した（「実機確認の作法」の
  「役目を終えた計装は消す」）。単位を**解釈できなかったとき**だけ、生の値を添えて
  異常側の診断行へ出す。
- **凡例を避ける幅は定数ではなく実測。** 凡例の大きさは
  **その図面に何が並ぶか**で決まる（シンボルが増えれば伸びるし、アンカーボルトを置かない
  文書では凡例そのものが無い）ので、「これだけ空けておけば足りる」という定数は置けない。
  当初は箱幅の定数 150mm をそのまま空けていたが、実機の凡例は 25mm ほどにしか広がらず、
  余らせた 125mm のせいで **1/50 で収まる建物が 1/75 まで落ちて**いた。
  ★**大きさは中身が流し込まれる（`UpdateStyledObjects`）まで確定しない**ので、
  「置く → 流し込む → `GetObjectBounds` で測る」の順で幅を得て `core::planLayout` へ渡す。
- ★**凡例と伏図の縮尺は鶏と卵になる。** 空ける幅は凡例の実測で決まるのに、その凡例に
  並ぶのは**ビューポートに映るシンボル**なので、図が無いと凡例の中身も決まらない。
  そこで `draw/Sheet` は**2 巡**する: 1 巡目は凡例のぶんを空けない仮の縮尺で図と凡例を
  作り、凡例を流し込んで幅を測る。2 巡目で確定した縮尺を当て直し（`ApplyViewportScale`。
  **縮尺が実際に変わったときだけ**——更新は重い）、タグを置いて用紙の上へ動かす。
- ★**ビューポートを動かすのはデータタグを置いた後。** タグは「注釈へ置いた実位置を測って
  目標との差だけ動かす」作りだが、**その実測はビューポートが用紙のどこに在るかに影響
  される**。先に動かすと全タグが同じ量だけ図から外れる（実機で確認）。注釈はビューポートと
  一緒に動くので、**測る → タグを置く → 動かす**の順なら位置は保たれる。
- **軸組図は上下 2 段**になる縮尺を選び、1 段の枚数は用紙の幅から決める。入りきらない
  ぶんはシートレイヤを足し、タイトルを "軸組図(1)" … と連番にする。
  **何枚に分かれるかは用紙が分からないと決まらない**ので、命令セットが持つのは
  「番号の始まり（伏図の続き）とタイトルの基」だけにした（`core::SectionSheetCommand`）。
  用紙の大きさを読むには 1 枚目のシートレイヤが要るので、**先に 1 枚用意してから**
  割り付けを決め、タイトルは本番のループで付け直している。
- **縮尺をデザインレイヤから借りない。** M13〜M15 は「映すデザインレイヤの縮尺」を
  ビューポートへ写していたが、デザインレイヤの縮尺は用紙に対する図の大きさとは関係が
  無く、**図が用紙からはみ出しても気付けなかった**。

### データタグ

- **スタイルは作らない・当てない。** タグの中身（タグレイアウト）は**タグ 1 本ずつへ直接**
  組む——スラブ・壁を構成層で描くのと同じ扱い（上記「描いた結果に対する 5 つの方針」2）。
  一度は「取り込みのたびにデータタグスタイルを作って全タグへ当てる」形にしたが、名前付き
  リソースが増える・undo で消えない・同じ中身のスタイルが `-2`、`-3` と並ぶ、という同じ
  理由で撤回した。**間接段を挟まない方が壊れにくい**——スタイルとして効かせるためだけに
  シンボル定義のサブタイプ（`SetSymbolDefSubType`）とパラメータ対応表
  （`SetAllPluginStyleParameters`）が要り、そのどれかが漏れると実機で「タグは出るのに
  中身が空」になっていた。
- **タグレイアウトはタグ自身のプロファイルグループ**（`GetCustomObjectProfileGroup` /
  `SetCustomObjectProfileGroup`。VW2020 で足された `…InAux` の入り口もあるので両方見る）。
  中身は**式を持たせたテキスト**（`IDataTagTextLinkSupport::SetIsLinked` / `SetFormula`）
  1 つで、**ラベルはテキストの名前ではない**（手で作ったタグのテキストには名前が無い）。
  生成直後のタグが既定で持っているロクスは取り除き、同じ並びに揃える。
- **中身を入れてから渡す。** 空のグループを先に `SetCustomObjectProfileGroup` へ渡して
  後から足すと、VW が渡した時点でグループを複製していた場合に足したテキストが迷子になる
  （実機で「オブジェクトは出るのにタグレイアウトが空」として現れた）。渡した後は実際に
  持っているものを取り直し、複製されていればこちらのグループを消す。
- **組んだら `IDataTagSupport::UpdateUserDefinedTextsUIDs` をタグへ呼ぶ**（SDK のコメント
  どおり「データタグ**または**データタグスタイル」に使える）。これが無いとタグが式を拾わず、
  寸法が空のまま出る。
- **関連付けはレイアウトを組むより先。** タグの本文は関連付け先のレコードから来るので、
  相手を決めてから中身を組み、最後に `UpdateDataTag` で流し込む。
- **タグは指定した挿入点に留まらない。** しかも**タグの実寸はレイアウトの中身が決めるので、
  逃がす量も描くまで分からない**。したがって**置いた後に `GetObjectBounds` で実位置と実寸を
  測って動かす**のが最終位置を決める。VW がどこへ落とすかに依存しない（伏図は指示点から
  タグ幅の半分だけ −X へ寄り、軸組図はビューポートごとにばらばらの場所へ落ちる）。
- **注釈へ後から足した図形のクラスはビューポートで非表示のまま。** ビューポートの設定は
  タグを置く前に走るので、置いた後に全クラスを表示へ戻して再更新する。
- **クラスは "寸法"・描画属性は全てクラス属性**（`SetClassByName` ＋
  `SetAllAttributesByClass`）。**タグ本体だけでは足りず、タグレイアウトの中のテキストにも
  要る**——レイアウトの中身は本体のクラスを継がないので、本体だけに与えると文字が既定クラス
  のまま残る。文字スタイル（`寸法(6pt)`）を当てた**後**にクラスを与える（書体・大きさは文字
  スタイル、色・線の太さはクラスが受け持つ）。

### グラフィック凡例

- **スタイルは作らないし当てない**（スラブ・壁・データタグと同じ扱い）。かつては
  "基礎伏図凡例" / "床伏図凡例" を当てて中身を決めていたが、**スタイルの無い文書では凡例が
  空の箱**になり、名前が 1 文字違うだけで同じことが起きた——取り込みの結果が図面の外の資源に
  左右されるのをやめた。当てないので `SetPluginObjectStyle` も `UpdateStyledObjects` も
  呼ばない（中身は置いた時点の `ResetObject` で決まる）。
- **ソース定義（何を並べるか）は PIO のパラメータでは設定できない。** ソース定義は
  ボタンのフィールド（type=14）で、選んだソースを保持する欄がパラメトリックレコードに無い。
  ISDK にもソースへ触る呼び出しは無い（下の「ビューポートでフィルタ」の項）。
  **そして既定のソースは空**なので、**スタイル無しで置いた凡例は中身が 0 セット＝何も出ない**
  （実機で確認。「既定のソースが集めたものがフィルタで絞られる」と読んでいたのは誤り）。
  スタイルを当てていた頃はソース定義もスタイルから来ていたので、**スタイルを外すなら
  ソース定義を per-instance で書き込む道を用意しないと凡例が空になる**——これが
  スタイル無し化の唯一にして最大の障害で、保存先の見込みは下の `'GrLe'`。
  当座の逃げ道は「図面側で『凡例ソースの定義...』を手で直す」（図面の中で完結し、名前付き
  リソースは増えない）。
- **点で生成すると幅 0 に潰れる**（矩形モードの PIO）。`BoxWidth` を与える。
- **イメージの縮率は当てない**（PIO 既定の 1:50 のまま）。変えられるのは凡例イメージ
  （＝ビューポート）の縮尺＝**中身だけ**で、**セルの枠は既定のまま残る**。中身だけ伏図の
  縮尺・枠は 1:50 という半端な状態は「全部 1:50 で揃っている」より見た目が悪いので、
  当てないほうを採った（下の「打ち切った調査」の「凡例のイメージの縮率を伏図に合わせる」）。
- 見た目（枠線・セル）は**クラスでは制御できない**ので属性として直接与える。
- 凡例はビューポート注釈ではなく**シートレイヤ（用紙）**に置く。
- **「ビューポートでフィルタ」を設定する API は SDK に無い**（VW 2026 SDK のヘッダを
  `Legend` で全文検索して確認）。凡例について公開されているのは
  `ovGraphicLegend*`（1645〜1650。**PIO のリセット中しか有効でない**画像再生成用の
  オブジェクト変数）と、条件ダイアログの文脈 `eGraphicLegendCriteria` だけで、
  ソース定義やフィルタに触る呼び出しは `ISDK` にも VWFC にも無い（`Filter…Viewport` /
  `LegendSource` / `LegendCriteria` / `Get|SetGraphicLegend…` のどれも 0 件）。
  VWFC の `VWObject.cpp` が使う `IGraphicLegendCoreSupport` /
  `IGraphicLegendCoreOperationsSupport` は**ヘッダが SDK に同梱されていない**内部
  インターフェースなので、こちらからは呼べない。
- **フィルタはパラメトリックレコードにも載っていない**（実機のダンプで確認）。UI で
  「ビューポートでフィルタ」を掛けた前後で、36 フィールド中**変わるのは `BoxWidth` だけ**で、
  それも「並ぶセルが減って凡例が細くなった」結果にすぎない（153.99 → 48.80）。
  ついでに分かった中身: 中身を決める 5 つ（`DefineSource` / `DefineImage` /
  `EditCellLayout` / `EditTitleLayout` / `ImageClasses`）は**値を持たない type=14＝ボタン**
  ——**この 5 つのボタンの先にある設定だけがレコードの外**にある。
- **関連（association）でもない。** フィルタを掛けた凡例で `associations=0`。ビューポート側に
  出る `associations=3` は**断面ビューポート（軸組図）だけ**に付いていて（伏図の
  ビューポートは 0）、凡例とは無関係。
- **凡例の中の図形が UUID で持っているのでもない。** 凡例の中身はセルごとに
  グループ（`type=11`）＋ `GraphicLegendFrame`（＋画像は `GraphicLegendImage` か
  **画像描画用のビューポート `type=122`**）で、**UUID を値に持つレコード欄は 1 つも無い**。
  ——ここまでで per-instance の設定を置く「普通の場所」は出尽くした。
- **「ビューポートでフィルタ」の保存先は、凡例にぶら下がるデータオブジェクトのタグ付きデータ**
  だった。実機のダンプで次の順に潰して突き止めた（もう一度やらないこと）:
  * パラメトリックレコード … ✗（フィルタの前後で変わるのは `BoxWidth` だけ＝細くなった結果）
  * 関連（association）… ✗（フィルタ済みでも 0。ビューポート側の 3 件は断面ビューポート固有）
  * 凡例の中の図形 … ✗（セルは group ＋ `GraphicLegendFrame` ＋ 画像で、UUID を持つ欄は無い）
  * オブジェクト変数 … **703 だけが違った**（`ovFirstAuxObject`。"read/write : used to
    manipulate the Aux list - Public for VS"）＝**補助オブジェクトの連鎖**
- **読み方（実機のバイト列）。** `MCObjectHandle` は `GSHandle`＝`char**` なので、参照外しで
  そのまま中身が読める（大きさは `GSGetHandleSize`）。フィルタを掛けた凡例の先頭の補助
  オブジェクトはこうなっていた:

  | オフセット | 中身 |
  | --- | --- |
  | +80 | `54 44 4d 44` ＝ データオブジェクトのタグ `'DMDT'`（リトルエンディアン） |
  | +86 | `67 4c 72 47` ＝ **本当のタグ付きデータの容れ物 ID `'GrLg'`**（Graphic Legend） |
  | +96 | `05 00` ＝ タグ 5 |
  | +108 | `0f 00` ＝ 型 15（`kTaggedDataObjectRefArrayTypeID`） |
  | +110 | `01 00` ＝ 要素数 1 |
  | +114 | `c0 01 00 00` ＝ 448 ＝ **フィルタ先ビューポートの `InternalIndex`** |

  **`'DMDT'` は「入れ物の入れ物」**で、`ISDK::TaggedData*` に渡すべき容れ物 ID は +86 の方。
  ここを取り違えると総なめしても 1 件も返らない（最初はそれで空振りした）。同じ構造の
  補助オブジェクトが 12 個ぶら下がっていて、+86 は `'ptd_'` `'rwtt'`（SDK ヘッダの
  `kTaggedDataContainerNNA_Internal*` そのもの）や `'GrLe'` `'modl'` など。`'FSTL'` は
  文字スタイル（12pt ＝ 4.2333mm の double）で無関係。
- **書き方。** `TaggedDataCreate(legend, 'GrLg', 15, 5, 1)` ＋
  `TaggedDataSet(legend, 'GrLg', 15, 5, 0, &GetObjectInternalIndex(viewport))` を
  **`ResetObject` より前**に呼ぶ（実装は `draw/Legend` の `ApplyViewportFilter`）。
  `'GrLg'` は多文字リテラルを避けて `0x47724C67` と書く。
  **`ModifySlab` のときの `type=121` と違い、データオブジェクトは SDK で扱える**ので、
  UI と同じ状態を作れる。

- **フィルタ先は 1 つとは限らない**（実機のダンプで確認。UI の「ビューポートでフィルタ」は
  チェックボックスの一覧で、複数のビューポートを選べる）。**同じ容れ物・同じ型・同じタグの
  配列の要素数が増えるだけ**で、別のタグへ移ったりはしない。3 つ選んだ凡例の `'GrLg'` は
  こうなっていた（データオブジェクトの中身は 132 バイト）:

  | 中身 | 値 |
  | --- | --- |
  | 型 | `0f 00` ＝ 15（`kTaggedDataObjectRefArrayTypeID`） |
  | 要素数 | `03 00 00 00` ＝ 3 |
  | 要素 0..2 | `29 03 00 00` `db 03 00 00` `8e 03 00 00` ＝ 809 / 987 / 910 |

  809 / 987 / 910 は UI で選ばれていた 3 つのビューポートの `InternalIndex`。1 つだけ選んだ
  凡例では要素数 1（412 / 447 / 628 …）。したがって書くときは
  `TaggedDataCreate(legend, 'GrLg', 15, 5, N)` の後に `TaggedDataSet(..., i, &index)` を
  i = 0..N-1 で回せばよい（**要素数を決めるのは `TaggedDataCreate` の最後の引数**）。
  取り込みでは伏図ビューポート 1 つに絞るので現状 N=1 で足りるが、**仕様としては N 個**。
- **タグ付きデータを「型で総なめ」して探すのは無駄**（1 度やって騙された）。
  `TaggedDataGetNumElements` は**渡した型 ID を検証しない**らしく、実際に入っている型と違って
  いても同じ要素数を返し、`TaggedDataGet` はその型の大きさで切り出したゴミを返す
  （同じタグが 13 種類すべての型で「見つかる」。文字列に見える値も出るが偽物）。
  **信用できるのはハンドルの生バイトだけ**なので、探索は 16 進ダンプでやる。
  **型とタグが分かっていても `TaggedDataGet` の読み値は当てにならない**（`'GrLg'`・型 15・
  タグ 5 で読ませたら、件数は生バイトと一致したのに値はポインタらしき数――
  `-523223174` など――が返った）。**件数は正しく、値は壊れる**。書き込み
  （`TaggedDataCreate` ＋ `TaggedDataSet`）は実機で効いているので、読みだけの問題。
- **パラメトリックレコードには per-instance の設定がちゃんと載っている**（前の版のメモで
  「集計・ソートの軸はスタイル側から来る」と書いたのは誤り。実機の全欄ダンプで、**スタイルの
  違う凡例ごとに違う値**が入っていた）。書き換えられる見込みのある欄:
  `SummarizeBy`（`StyleSymName` / `ClassName`）・`SortBy`（`StyleSymName` /
  `DesignLayerName`）・`SortOrder`・`HideEmptyCells`・`FixedCellWidth` / `FixedCellHeight`・
  `LayoutBy`・`TitleWidth`・`ScaleFactor`（記号の倍率）・`BoxWidth`。
  値を持たない type=14＝ボタンは `DefineSource` / `DefineImage` / `EditCellLayout` /
  `EditTitleLayout` / `ImageClasses` の 5 つで、**ここが押した先＝ソース定義とイメージの定義**。
  レコードの版は `__version` ＝ 3100。
- **レコードの `ImageScale` は OIP の「イメージの縮率」の表示元**だが、**書いても VW が既定へ
  戻す**ので触らない。**枠はこの欄では決まらない**（中身から決まる。下の ★）ので、触れなくても
  困らない——残るのは表示と実描画の食い違いだけ（「打ち切った調査」の
  「凡例の OIP『イメージの縮率』表示を合わせる」）。
- **凡例イメージは独立した節点**——SDK のヘッダを `GraphicLegend|LegendImage|ImageScale` で
  引くと、凡例は 4 つの内部 ID に分かれている（`Kernel/API/MiniCadHookIntf.h`）:

  | 定数 | 値 |
  | --- | --- |
  | `kInternalID_GraphicLegend` | 658 |
  | `kInternalID_GraphicLegendImage` | 659 |
  | `kInternalID_GraphicLegendFrame` | 660 |
  | `kInternalID_GraphicLegendTitleFrame` | 661 |

  ただし**これは `GetObjectTypeN` が返す値ではない**（あちらは `Kernel/API/Objs.TDType.h` の
  節点型で、`kLocusNode` ＝ 17 と同じ系統）。節点型の側を引くと
  **`kWorksheetImageNode` ＝ 56**があり、**凡例のイメージはワークシートのイメージと同じ
  節点型**らしい。そしてこの型のハンドルを取る縮率の API が `ISDK` にある:

  ```
  double GetWorksheetImageScaleFactor(MCObjectHandle hWorksheetImage);
  bool   SetWorksheetImageScaleFactor(MCObjectHandle hWorksheetImage, double scale,
                                      bool redrawImage);
  ```

  **凡例専用の縮率 API が SDK に無いのはこのため**と読める。そこで `draw/Legend` の
  `applyLegendImageScale` は、凡例の中を `FirstMemberObj` / `NextObject` で辿って
  `GetObjectTypeN(h) == 56` を探し、見つけたものへ `SetWorksheetImageScaleFactor` で与える。
  * **凡例イメージは作り直しの後にしか無い**（中身を流し込んだときに作られる）ので、
    呼ぶのは `placeLegends` の後。
  * **単位の取り決めがヘッダに書かれていない**（1:50 を「50」で持つのか「0.02」で持つのか）。
    既定の 1:50 を読んでから決める——1 以上なら分母、1 未満なら倍率と見なして同じ流儀で書く。
  * 1 つも見つからなかったときは完了ダイアログの診断行で知らせる（絵からは分からないため）。
  * ★**型 56 は実機の凡例に 1 つも入っていなかった**（1 度目の空振り。伏図 1/75）。
    そこで「見えた節点型を診断へ出す」計装を足して数えたところ、**答えが出た**:

    ```
    凡例の中で見えた節点型: 0×102, 3×66, 10×6, 11×36, 86×42, 122×12
    ```

    | 型 | 名前 | 中身 |
    | --- | --- | --- |
    | 0 | `kTermNode` | リストの終端 |
    | 3 | `kBoxNode` | セルの枠 |
    | 10 | `kTextNode` | 見出し・ラベル |
    | 11 | `kGroupNode` | セルのまとまり |
    | 86 | `kParametricNode` | 並べている PIO |
    | 122 | **`kViewportNode`** | **凡例イメージ**（凡例 1 つに 1 つ） |

    **つまり凡例イメージはビューポートで、「イメージの縮率」とはそのビューポートの縮尺**。
    `ovGraphicLegendViewType` / `BgRenderMode` / `FgRenderMode`（`ObjectVariables.h`）が
    ビューポートの属性そのものなのとも符合する。与え方は伏図のビューポートと同じ
    `ApplyViewportScale`（`VWViewportObj::SetScale` ＋ `Update`）で、専用 API は要らなかった。
  * **ビューポートの中へは潜らない。** 中身はそれが映している図そのものなので、潜ると設計
    レイヤ全体を歩く（上の数え上げが `86×42` などと膨らんだのはそのため）。
  * ★**動かせるのは中身だけで、枠は動かない。**

    | 何が | どこで決まる | プラグインから |
    | --- | --- | --- |
    | イメージの**中身**の縮尺 | 凡例イメージ（＝ビューポート）の縮尺 | **書ける** |
    | セルの**枠**の大きさ | 凡例の内部状態（レコードの外） | **届かない** |
    | OIP の「イメージの縮率」表示 | 同上（`ImageScale` は UI が書く控え） | **届かない** |

    **枠は作り直しでは中身に合わせて組み直らない**——「中身を変えてから作り直せば枠も揃う」と
    一度は読んだが、実機で否定された（中身 1/75・枠 1:50 のまま）。そのため縮率は当てない
    方針にした（「打ち切った調査」の「凡例のイメージの縮率を伏図に合わせる」）。
  * **一時計装（節点型の数え上げ・全欄ダンプ・段階ごとの推移）は役目を終えたので外した。**
    同じことを調べ直すなら、この節の記録から作り直せる。
  * ★**実機の出力にはビルドを添える。** 実機確認を往復する開発では「その出力がどのビルドの
    ものか」が分からないと切り分けが崩れる——実際に**前のビルドの出力を新しいビルドのものと
    読んで 1 往復無駄にした**（診断が一字一句同じだったので気付けたが、気付けない形もありうる）。
    M19 以降は診断ログの先頭に `CurrentBuildInfo()` がブランチとコミットを書くので、報告に
    貼られたログを見ればどのビルドか分かる。
- **タグ付きデータの型は 6 種類しかない**（`Kernel/API/MiniCadCallBacks.h` の
  `kTaggedData*TypeID` と `VWFC/Tools/TaggedData.h` の `ETaggedDataType`）:
  1 = byte 配列 / 8 = uint32 配列 / 6 = double 配列 / 7 = 変換行列 / 13 = ColorRef 配列 /
  15 = オブジェクト参照配列（ほかに 2・17・18・20・21・22・23 の ID が定義だけある）。
  **16 ビット幅の値も文字列も byte 配列（型 1）に載る**——VWFC の `CTaggedDataContainer` が
  `CreateTagUint16` / `CreateTagString` を byte 配列で実現している。したがって
  「奇数バイト数・偶数バイト数の中身」は素直に型 1 と読んでよい。
- **ソース定義とイメージの定義の保存先は `'GrLe'` らしい**（`'GrLg'` と 1 文字違い。
  Graphic Legend の別の容れ物）。**手で「凡例ソースの定義...」を設定した凡例にだけ**
  ぶら下がっており（データオブジェクト 142 バイト、タグ 0、中身 22 バイト）、素のままの凡例には
  無い。3 枚とも中身が完全に同じで、その 3 枚は検索条件も同じ
  （`(INVIEWPORT & (T=SYMBOL))`）／集計基準だけが違う——**集計基準はレコード側**なので
  辻褄が合う。16 進は次のとおり（16 ビットずつ読んだ値を併記）:

  ```
  9a 02  96 02  1e 03  96 02  09 03  0f 00  47 06  65 06  4f 06  a5 02  90 06
   666    662    798    662    777     15   1607   1637   1615    677   1680
  ```

  検索条件の文字列（`INVIEWPORT` 等）はどこにも現れない——**条件は文字列ではなくトークン列
  （番号の列）**である。そもそも `(INVIEWPORT & (T=SYMBOL))` は ASCII で 25 文字あって
  22 バイトに入らない。
- **そのうち 6 番目が「条件が指すオブジェクトの型」だと割れた。** 検索条件だけが違う 4 枚を
  突き合わせると、**変わるのは 6 番目の 16 ビット値だけ**だった:

  | 6 番目 | 検索条件 |
  | --- | --- |
  | 15 | `(INVIEWPORT & (T=SYMBOL))`（シンボル） |
  | 86 | `(INVIEWPORT & (T=PLUGINOBJECT))`（プラグインオブジェクト） |

  15 と 86 は**オブジェクトの型番号**そのもの（ダンプで凡例自身が `type=86` なのが裏取り）。
  したがって残りの 10 個は `( INVIEWPORT & ( T = … ) )` の器で、**6 番目を差し替えれば条件を
  変えられる**（`draw/Legend` の `kCriteriaObjectType`）。器の 10 個の意味は解けていない。
- **条件のトークン列の文法**（複数条件・グループ・文字列つきの凡例を 2 度ダンプして詰めた）。
  16 ビットずつ読む。**枠**は `666 662 798 …（条件）… 677 1680` で、`798` が `INVIEWPORT`。

  **セレクタ**（何で絞るか）と値の入れ方:

  | 値 | 意味 | 値 |
  | --- | --- | --- |
  | 798 | `INVIEWPORT` | 無し |
  | 777 | `T`（タイプ） | **生の 16 ビット値**（11=グループ / 15=シンボル / 86=プラグインオブジェクト） |
  | 773 | `L`（レイヤ） | 文字列（マーカー 1627） |
  | 774 | `C`（クラス） | 文字列（マーカー 675） |
  | 808 | `PON`（プラグインオブジェクト名） | 文字列（マーカー 1627） |
  | 822 | 基準面 | 文字列（マーカー 1627） |

  **文字列は `<マーカー> 0 0 <UTF-16LE> 0`。** マーカーはセレクタごとに決まっているらしく
  （`773`/`808`/`822` は 1627、`774` は 675）、**比較の向きではない**——同じ `774 675` が
  「クラスが 右項目のもの」でも「右項目ではないもの」でも出た。

  **比較の向きは条件の後ろに来る**（後置）: **1607 ＝「右項目のもの」（＝）／1606 ＝
  「右項目ではないもの」（≠）**。実例（ダイアログの 8 行とそのまま対応した）:

  ```
  666 662 798                                   ← 枠 ＋ INVIEWPORT
    777 11                             1607     ← タイプが ＝ グループ
    1637 773 1627 0 0 "共通" 0          1607     ← レイヤが ＝ 共通
    1637 1608 822 1627 0 0 "スクリーンプレーン" 0  1606  ← 基準面が ≠ スクリーンプレーン
    1637 1608 777 86                   1607     ← タイプが ＝ プラグインオブジェクト
    1637 774 675 0 0 "一般" 0            1607     ← クラスが ＝ 一般
    1637 1615 773 1627 0 0 "共通" 0      1607     ← レイヤが ＝ 共通
  1637 1615 1637 1608 1637 1615 677 1680        ← 閉じ
  ```

  **1637 / 1608 / 1615 は構造**（条件の区切りとグループの開閉）で、対応はまだ詰めていない。
  「いずれかの検索条件（OR）」と「すべての検索条件（AND）」の入れ子はこの 3 つで表されて
  いるはずなので、**グループの種類だけを変えた 2 枚**を差分に取れば決まる。

  **つまり条件は組み立てられる。** 単純な 1 条件（`(INVIEWPORT & (T=…))`）は写した 22 バイトの
  6 番目を差し替えるだけで足り、文字列を使う条件（`L=` / `C=` / `PON=`）も上の形で書ける。
  複数条件・グループが要るようになったら、構造の 3 つを割ってから。
- **いま書き込んでいるのは 15＝シンボル**（`(INVIEWPORT & (T=SYMBOL))`）。凡例を載せるのは
  基礎伏図だけで、並べたいのはアンカーボルト＝ハイブリッドシンボルだから。構造材ツールの
  部材（横架材・柱・垂木）を並べたくなったら **86** にする。
- **そこで「写したバイト列をそのまま書き込む」実験をしている**（`draw/Legend` の
  `ApplySourceDefinition`）。`TaggedDataCreate(legend, 'GrLe', 1, 0, 22)` ＋
  `TaggedDataSet(..., i, &byte)` を 22 回、フィルタと同じく **`ResetObject` より前**に。
  器の 10 個の意味が解けていないので**文書や VW の版をまたいで通用する保証は無い**——実機で
  「並ぶかどうか」を見て決める。**駄目ならスタイルを当てる方式へ戻す**（ソース定義を
  per-instance で持てないなら、スタイル無しの凡例は原理的に空にしかならない）。

### Undo（取り消し）

- **VW は取り込みの開始時に undo イベントを開かない。** 診断ログの実測は
  `undo: start building=no` / `afterParse=no` / `afterDraw=yes`——それでも描画の終わりには
  「組み立て中」になるのは、**断面ビューポートの生成のように SDK 内部が自前でイベントを
  開く呼び出しがある**ため。この半端な記録を取り消すと**図面が壊れる**（実機: ビューポート
  だけ消え、レイヤは戻らず、構造材や立上りが断面を失って単線・2D 面になった）。
  `GS_EndUndoEvent` の説明にある「外部の終了時に自動で**閉じる**」は「自動で開く」ではない。
- **`SetUndoMethod(kUndoSwapObjects)` ＋ `NameUndoEvent(...)` が開始も兼ねる**（ISDK に開始
  専用の呼び出しは無い）。RAII（`draw::ImportUndoScope`）で包み、破棄で `EndUndoEvent()`。
- **登録するのは「この取り込みが新しく作ったレイヤ」だけ。** レイヤを消せば上の図形も消える
  ので図形を 1 つずつ登録する必要が無く、**二重登録で「もう無いものを消しにいく」事故**も
  避けられる。
- **登録が 1 件も無いときはイベントごと捨てる**（`EndAndRemoveUndoEvent`）。空のイベントを
  残すと、SDK 内部が開いた記録が取り消しの対象になって図面が壊れる。
- **SDK へ渡して消費させた下ごしらえは取り消しで復活する。** 通り芯は
  `CreateCustomObjectPath` にポリラインと空グループを渡すが、SDK はそれらを**undo 記録つきで
  削除**して PIO へ取り込む。こちらがイベントを開いていると、その削除が記録に入り、
  **取り消したときにポリラインだけが図面へ復活する**（そのせいでレイヤも消えずに残る）。
  対処は SDK の作法どおり「自分が追加したものは申告する」——`AddAfterSwapObject` は
  "that object is deleted when Undo is selected" なので、申告しておけば復活したそれが改めて
  消える。**レイヤの上に普通に置いた図形へは使わない**（レイヤごと消えるものを二重登録しない）。
- **戻らないもの**: クラス・ストーリ・レベルテンプレートはリソースなので残る（図面の見た目は
  取り込み前に戻る）。**取り込み前から在ったレイヤへ描いた分**も、そのレイヤごと消すわけに
  いかないので戻らない——完了ダイアログがその旨を伝える。

### 進捗・診断・例外

- **進捗はダイアログ（`VWFC::Tools::CProgressDlg`）で出す。** ISDK に `vs.Message`
  （ステータスバー）相当は無い。**1 件ごとに `DoYield`** すると進み具合が見えるだけでなく、
  VW の再描画とイベント処理が戻り、キャンセルも効く（オーバーヘッドは実機で体感問題なし＝
  間引きは不要）。
- **進捗バーの重みは実測で按分する。** 1 件あたりの重さは要素で**3 桁**違った——仕口
  0.1ms/件・アンカーボルト 0.1ms/件に対し、底盤 670ms/件・軸組図 520ms/枚・伏図 480ms/枚・
  横架材 130ms/本。件数比で配分すると、シンボル 472 件（全命令の 4 割超）が 0.05 秒でバーを
  4 割進め、17 秒かかる軸組図 33 枚が 3% しか進まない**嘘の進捗**になる（`core::drawWeight`）。
- **診断ログは 1 行書くたびにフラッシュする。** 無言クラッシュでも「ログ最終行の直後」が
  原因箇所になる。行頭に経過ミリ秒を付けると、どのフェーズで時間を使ったかも読める。
  **書き出し口は `core::ProgressReporter::beginPhase` ただ 1 か所**（各要素へ `trace::log` を
  撒かない）。出力先は一時ディレクトリで、**図面や IFC の隣には置かない**。
- **SDK コールバックへ例外を漏らさない。** `DoInterface` はインポート本体を `try` で包み、
  `std::exception` と `catch(...)` の両方をエラーダイアログ 1 通にする。
  **`plugin_module_main` の起動時処理も包む**——起動経路の未捕捉例外は VectorWorks の起動
  そのものを落とす。
- **平常時に鳴る診断は外す。** 「レイヤ上の壁の本数」「結合前後の端点の一致」は切り分けには
  役立ったが、**結合は壁芯の端点を動かしうるし、X 結合は仕様で壁を 1 本増やす**ので、
  異常として出すと鳴り続ける。役目が終わった診断は消し、必要になったら作り直す
  （当時の実装は PR の履歴にある）。
- **完了ダイアログは読まれない前提で組む（M19）。** 要素 17 行の一覧を毎回出していたが、
  うまくいっているときに読むものではないし、うまくいかないときは**その一覧では足りない**
  （原因は診断行にしか出ない）。ダイアログは「どのファイルを・成功したか・問題はあったか」
  の 3 つに絞り、内訳・注意・記録はログへ移した。ダイアログに残すのは**その場で操作が
  要ること**だけ——伏図・軸組図の「1 回更新」と、「取り消し」が普通には効かないときの断り。
  **描けた件数も所要時間も出さない**: うまくいっているときには読む必要が無く、うまく
  いっていないときはその数だけでは足りない（どちらもログにある）。
  **当たり前のことは書かない**: 「取り消し」コマンドが有効なら取り消せるのは当然なので、
  1 回で戻せるときは何も出さない（戻せない・一部しか戻らないのは当然でないので出す）。
  ログには常に残す——後から「戻せたはずでは」を確かめる手掛かりになる。
- **「問題あり」の判定には、平常でも出る説明を混ぜない（M19）。** 用紙の割り付けの内訳は
  毎回出るので、これを診断（`DrawCounts::diagnostics`）に入れたままだと完了ダイアログが
  常に「問題あり」になる。**異常＝ `diagnostics` / 平常の記録＝ `notes`** と行き先を分け、
  前者だけを結末の判断に使う（`parse::importOutcome`）。
- **ログは取り込みのたびに必ず開く（M19）。** 以前は dev ビルドと `HOMESKZ_IFC_TRACE`
  指定時だけだったが、「困ったらログを貼る」を運用の柱にした以上、要るときに限って
  無いのでは意味がない。ログは**ファイルと同時にメモリにも溜める**（`core::trace::text`）
  ——一時ディレクトリへ書けない環境でもダイアログのログ欄には出せるし、表示のために
  読み直さずに済む。
- **ログの置き場所はログ自身に書く（M19）。** 完了ダイアログに出していたが、場所を
  知りたいのは「ログを見よう」と思ったときだけで、そのときログはもう目の前にある
  （ダイアログのログ欄）。見出しの「ログ:」の行に書けば、開いた人がそのまま読める。
  書けなかったときは黙らず「ファイルは無い」と出す——黙ると、出ていないファイルを
  探しに行かせる。
- **報告に貼られたログから最初に知りたいのは「どのリビジョンを・いつ・どのファイルに
  対して動かしたか」（M19）。** dev ビルドは PR ごとに中身が違うので、これが無いと
  「直したはずの不具合」の報告を古いビルドと取り違える。見出しにビルド（名前・チャンネル・
  コミット・ブランチ）・実行環境・日時・対象のフルパスと大きさを置く。ビルドの素性を
  詰めるのは SDK 側（`Extensions/ExtMenu`）——`BuildConfig.h` を見られるのはあちらだけで、
  `parse/Summary` は受け取った文字列を並べるだけ。
- **VW 本体のバージョンは C++ SDK から取れない。** `vs.GetVersionEx` は VectorScript に
  しか無く、SDK ヘッダ（`ISDK` ほか）に相当する取得 API は見当たらなかった（`sdk-grep`
  で全ヘッダを走査済み）。ログの見出しに VW のバージョンが無いのはこのため。

### 結果ダイアログ（折り畳めるログ欄）

- **`gSDK->AlertInform` では本文を出すことしかできない。** 「ふだんは 3 行・困ったときは
  ログ全文」を 1 枚で満たすには、自前のレイアウトダイアログ（`VWFC::VWUI::VWDialog`）が要る
  （`draw/ResultDialog`。作法は Updater のビルド選択ダイアログと同じ）。
- **ログ欄は `VWEditTextCtrl`。** `CreateControl(dlg, text, widthInStdChar, heightInLines)` で
  複数行の編集欄になり、**スクロールでき・選択してコピーできる**。静的テキストでは
  コピーできず、報告に貼れない（編集できてしまうが、閉じるときに捨てるだけなので害は無い）。
- **本文は 1 行 1 コントロールで積む。** `VWStaticTextCtrl` は 1 行を出すためのもので、
  埋め込んだ改行がそのまま行になる保証が無い。本文を改行で切って静的テキストを並べ、
  空行は `AddBelowControl` の行間で表す。
- **レイアウトダイアログの大きさは、作るときに 1 度だけ決まる。** 折り畳みを
  `ShowControl(id, false)` でやろうとして 2 度失敗した（いずれも実機で確認）:
  ログ欄を出すとダイアログは大きくなるが**隠しても縮まない**し、`OnInitializeContent`
  で最初から隠しておいても**その分の高さは空いたまま**だった。`Get/SetDialogSize`
  （`GS_Get/SetLayoutDialogSize`。単位はピクセル、`ViewCoord` は `Sint16`）で押し込むのも
  安定しない。**大きさを変えたいなら、その状態のダイアログを作り直すしかない**——
  ログ欄を持たない枚は、VW が計算する大きさが最初から正しい。
- **開閉できるように見せない。** 上のとおり畳むには作り直しが要り、押すたびに開き直る
  ダイアログは落ち着かない。**ログは一方通行で開く**ことにして、開いたら閉じるまで
  そのまま（M19）。
- **ボタン行（OK のある行）へコントロールを足す API は無い。** その行は
  `GS_CreateLayout` が `CreateDialog(title, ok, cancel, hasHelp)` の引数から作る。
  OK の隣にボタンを出したいなら、**キャンセルのボタンに別の名前を付ける**のが唯一の手
  （押されたことは `OnCancelButtonEvent` で分かる。Esc も同じ扱いになる点だけ注意）。
- **作り直すときは位置を引き継ぐ**（`Get/SetDialogPosition`）——引き継がないと画面中央へ
  飛び、開き直したのが丸見えになる。ハンドラの中からモーダルを閉じるのは
  `VWDialog::SetDialogClose(bCloseWithOK)`（protected。押されたボタンを差し替える）。
- **ボタンのクリックは `EVENT_DISPATCH_MAP` で受ける。** `ADD_DISPATCH_EVENT(id, f)` の
  `f` は `void f(TControlID, VWDialogEventArgs&)`（`VWFC/VWUI/DialogEventArgs.h` の
  `CDialogEventHandlers`）。`CreateDialog(title, "OK", "", false)` のように**キャンセルを
  空文字**にすると OK だけのダイアログになる。
- **出せなかったときの逃げ道を必ず持つ。** レイアウトを組めなければ `AlertInform` へ落とす
  ——結果を伝えられないまま黙って終わるのが最悪。

## IFC / STEP 側の癖

ホームズ君構造EX が出す IFC（IFC2X3）に固有の性質。**汎用 IFC 対応は非目標**で、この
既知サブセット前提に最小 STEP リーダ（`parse/Step`）を組んでいる。

- **日本語の `Name` は ISO 10303-21 の拡張文字エスケープで出る**（`\X2\…\X0\` / `\X\HH` /
  `\S\c` / `\P?\`）。**デコードしないと名前による要素判別が一切通らない**（`床版` /
  `木梁:床大梁` など、ホームズ君の命名規約に全面的に依存している）。
- **IFC2X3 のファイルに IFC4 専用エンティティが混入する**（`IFCFOOTINGTYPE`）。スキーマ検証を
  する読み取り系はここで止まるが、**自前リーダは非正規エンティティもそのまま読める**ので
  除去は不要（本プラグインはそれらの型を参照しないので、グラフ上に残っていても無害）。
  `parse/Loader` はファイル読み込みだけを担い、サニタイズを持たない。
- **要素配置は `RelativePlacement` のみを使い、親を合成しない。** 親を合成すると階高が
  二重計上される。
- **開口付き断面（`IfcArbitraryProfileDefWithVoids`）がある。** 階段の吹抜けを持つ床版がこの型
  で出力され、未対応だと**床が丸ごと落ちる**（実データ 2 件で 2 階・3 階の床が入っていなかった）。
  現状は外形（`OuterCurve`）だけを読み、開口（`InnerCurves`）は無視する＝**床は開口を塞いだ
  形で入る**。
- **差演算（`IfcBooleanResult` / `IfcBooleanClippingResult`）の第 1 オペランドを再帰で辿る。**
  第 2 オペランド（削り取る側）は人通口の抽出に使う。
- **ロフト（小屋裏収納）の床版は出力されない。** 一方で小屋伏図には床梁が出るので、屋根階に
  床版が無いときに限り**床梁が囲む領域**を床の外形とみなす（`core/Region`）。近似であること
  ——床梁で囲まれた吹抜けは塞がり、骨組みが閉じていない部分は床にならない。
- **小屋束の断面は当てにならない。** 直上に乗る母屋・棟木・登り梁の幅に合わせた正方形へ
  置き換える。
- **登り梁の入力位置が不正確**（軸勾配が屋根版より急・端部が受け材へ食い込む）。天端中央線を
  屋根面へスナップし、端部を受け材の面まで詰める。また端部が直切り（鉛直面）なので、
  天端は XY ずらし無しで **せい/(2·cosθ)** 持ち上げる（矩形前提の軸直交持ち上げだと天端が
  垂木下面に届かない）。
- **基礎梁は底盤の底面までの全高でモデリングされている。** 立上りの下端をさらに下げる必要は
  無い（下げると底盤の下へ突き出すだけで意図と逆になる）。深さの差（スキップフロアなど）は
  IFC の実形状のまま残す。
- **地中梁の断面は立上りの外面に片側の垂直面が付き、内側へ広がる逆台形**（ハンチ。例:
  `(0,0) (-200,0) (-380,150) (0,150)` で配置原点が立上りの外面）。壁芯に対して中心を
  合わせたいなら、それは IFC の実形状から意図的に変える話になる。
- **人通口は実寸法でモデル化されている**（長さ補正しない）。立上りソリッドから天端の下方へ
  削り取った別ソリッドとして出るので、「天端まで届き底面には届かない」削りだけを拾う
  （端部が他材で削られた全高の差演算を人通口と誤認しないため）。
- **床束は IFC に出力されない。** 大引の下へ 910mm 間隔で決め打ち配置する（継手で分断された
  大引は 1 連へ統合し、端部は受けている支持材の芯にする）。

## 打ち切った調査（もう一度やらないこと）

**同じ道を再探索しないための記録。** どれも実機まで行って確かめた結論なので、状況
（VW のバージョン・SDK の版）が変わらない限り再挑戦の価値は無い。

### 凡例のイメージの縮率を伏図に合わせる

**結論: プラグインからは合わせられない。縮率は当てず、PIO 既定の 1:50 のままにする。**
変えられるのは凡例イメージ（＝ビューポート）の縮尺＝**中身だけ**で、**セルの枠は既定のまま
残る**。中身だけ 1/75 で枠が 1:50 という半端な状態は「全部 1:50 で揃っている」より見た目が
悪いので、当てないほうを採った。**手で OIP の「イメージの縮率」を変えれば枠も中身も正しく
変わる**ので、合わせたい利用者にはそちらを案内する（README「既知の制限」）。

★**この凡例は将来 独自 PIO へ置き換える方針**（VW 標準のグラフィック凡例は、中身も縮率も
外から十分に制御できないことがこの調査で分かったため）。**標準凡例をこれ以上いじらない。**

**決め手になった実測**（同じ文書に、手で設定した凡例とこちらが置いた凡例を並べて全欄を比較）:

| | レコードの `ImageScale` | 絵 |
| --- | --- | --- |
| 手で OIP のポップアップを 1:5 にした凡例 | **5 に変わる** | **1:5 に変わる** |
| こちらが `SetParamReal` / `SetParamAsString` で 75 を書いた凡例 | **75 になる** | **変わらない** |

つまり `ImageScale` は縮率そのもの（ポップアップも「カスタム 1:」も同じ欄に落ちる）で、
**UI 側の書き込みだけがイメージの作り直しまで走らせている**。こちらの書き込みはレコードに
届いても、その副作用が起きない。`ImageScale` は UI が書く控えで、本体は別にある。

潰した道:

- **レコードを実数で書く**（`SetParamReal`）… レコードは変わる。絵は変わらない。
- **レコードを文字列で書く**（`SetParamAsString`。OIP の欄は文字列で入るので、同じ変換・
  通知の経路を通ることを期待した）… **結果は実数と同じ**。
- **書く位置を総当たり**（作り直しの前／後／最後、undo イベントの内／外）… どれも同じ。
  段階ごとに測った推移が `記録 記録=75 中身=[50,50,50]` で、書き込みが中身へ伝わらないことを
  はっきり示している。
- **ポップアップ用の別の欄を探す** … レコードの全欄を実機で並べたが、種別 8（ポップアップ）は
  `TitleWidth` / `LayoutBy` / `SummarizeBy` / `SortBy` / `SortOrder` の 5 つだけ。縮率の
  ポップアップに当たる欄は無い。
- **文書内の全凡例を比べる** … 手で設定した凡例とこちらの凡例の差は `BoxWidth`（凡例ごとの
  幅なので当然）と、手で変えた凡例の `ImageScale` だけ。**こちらが書いている内容は、手で
  設定した凡例のレコードと一致している。**
- **パラメータ変更を PIO へ伝える** … `kParameterChangedReset`
  （`ObjectStateData_ParamChanged`）は **PIO 側が受け取る**メッセージ
  （`IObjUpdateSupport::OnState`）で、こちらから送る API は `ISDK` に無い。
- タグ付きデータにもオブジェクト変数にも縮率は無い（「グラフィック凡例」節）。

**ここへ辿り着くまでに何度も読み違えた。** 教訓:

- **「書けたのに絵が変わらない」＝「その欄は効かない」ではない。** PIO の欄は作り直しの
  ときに読まれるので、まず `ResetObject` を挟んだかを疑う。
- **1 つの見た目が 1 つの設定から来ているとは限らない。** 縮率は「中身」と「枠」に分かれて
  いて、**中身だけが動かせて枠は動かない**。片方を直して
  **半分だけ直った**ときは、残りが別の場所にある。
- **順序を疑う。** 枠が合わなかった原因は「中身を変えるのが作り直しより後だった」という
  ただそれだけだった。置き場所を探し回る前に、**書く順番を並べ替えてみる**。
- **オブジェクトの中身を型で数えるのがいちばん早い。** 凡例イメージがビューポートだと
  分かったのは、凡例の中の節点型を数える 1 行を診断へ出したときだった。**中を見ずにヘッダ
  だけで推測していた間はずっと外していた。**
- **同じ文書に「正解」を並べて差分を取る。** 手で設定した凡例と比べたことで、「欄が足りない」
  のではなく「書き込み経路が違う」と分かった。**推測を重ねるより、正解を 1 つ用意して
  比べるほうが速い。**
- **実機の出力にはビルドを添える。** 前のビルドの出力を新しいビルドのものと読んで 1 往復
  無駄にした（M19 以降、診断ログの先頭に `CurrentBuildInfo()` が出る）。

### スラブへ「足す」噛み合わせ（`ModifySlab`）

地中梁を底盤へ噛み合わせたい。SDK には**専用の API がある**——
`ISDK::ModifySlab(slab, modifier, isClipObject, componentFlags)`（説明は "Adds to or clips
from a slab."）。API の形の上では `isClipObject = false` が「足す」に当たる。

- しかし**実機（VW 2026）では「選択が間違っています」のダイアログを出して false を返す**。
  底盤は直方体のまま・地中梁は独立したプリズムのまま残り、ダイアログは呼んだ回数ぶん出る。
- 「全解除 → 底盤とプリズムだけを選択 → 呼ぶ」も試したが結果は同じ。引数のハンドルの問題でも
  選択状態の問題でもなく、**VW 側の不具合の可能性が高い**。
- スラブのモディファイアを扱う API は `ModifySlab` だけで、他の手段は無い。
- **UI 産物を解析した結果**（dev ビルドへ一時的に足した診断コマンドで、同じスラブに我々の
  削り取り 12 本と UI の噛み合わせ 1 本が同居する状態を覗いた）:

  | | 我々の削り取り | UI の噛み合わせ |
  | --- | --- | --- |
  | 押し出しの補助オブジェクト | `type=114` ＋ `DMDT`×3 | `type=114` ＋ **`type=121`** ＋ **`OPhI`** ＋ `DMDT`×4 |

  構造そのものは同じ（スラブのプロファイル群に押し出しが入るだけ）で、**違いは押し出しに
  付く補助オブジェクト**。しかも**スラブ本体にも同じ組が付く**（両側にリンクが張られる）。
- **この 2 つは SDK からは作れない。** `NewDataObject` が作れるのはデータオブジェクト
  （`type=76`）だけで、`type=121` のノードを作る API は無い。`OPhI` / `DMDT` などのタグは
  **SDK ヘッダのどこにも定義が無い**（VW 内部専用）ため中身のバイト列も分からない。
- **結論**: 削り取りモディファイア＋可視ソリッドの**2 回作り**が現時点の最善。UI でできるのに
  API でできないのは VW 側の不具合か未公開機能なので、筋としては Nemetschek へ報告して
  `ModifySlab` の修正を待つ。

### 断面ビューポートの範囲を「無限」にする

UI で手作りすると〈無限〉が既定なので、公開ヘッダに載っていないオブジェクト変数
（欠番 1060〜1090）に範囲が載っているのではと疑い、dev ビルドに読み取り専用の一時診断を
入れて実機で確かめた（手で 1 枚だけ〈無限〉に変えてから再インポートし、値の違う変数を探す）。
**結果は断面ビューポート 66 枚・値の組み合わせ 1 通り＝差のある変数は 1 つも無し。**
範囲はオブジェクト変数の外に保持されており、SDK からは触れない。建物の大きさから決めた
有限範囲で確定（実用上は無限と同じ見え方になる）。

### ビューポート単位のレイヤ重ね順上書き

伏図の重ね順を「図面のレイヤの並びを動かさずに」与えたくて 2 度（M13 と、その後の再挑戦で）
試したが、**`SetViewportLayerStackingOverride` は書けない**。呼び出しは毎回 true を返すのに
`GetNumViewportLayerStackingOverrides` は 0 のままで、OIP も「順序を上書き: いいえ」。
デザインレイヤの並べ替え（`InsertObjectAfter`）が唯一の手段。

**読み出しはできる**——GUI で「順序を上書き」を付けたビューポートを
`GetNumViewportLayerStackingOverrides` / `GetViewportLayerStackingOverrideLayer` /
`GetViewportLayerStackingOverride` で読むと 27 件が返り、レイヤ名も引けた:

```
共通=1  2-柱伏図記号=2 … 1-FL=17 … R-野地板=25  2-FL=26  2-野地板=27
```

つまり**記録の形式は分かっている**（位置は 1 始まり・**1 が最前面**・図面の全デザインレイヤに
振る）。それでも書けない。実機で潰した呼び方は次の 3 通りで、いずれも記録 0 件:

| 位置の基点・向き | 対象 | 呼ぶ時点 | 結果 |
| --- | --- | --- | --- |
| 0 始まり・0 が最背面 | その図に映るレイヤだけ（5 件） | 生成直後 | 記録 0 件 |
| 1 始まり・1 が最前面 | 全デザインレイヤ（27 件） | 生成直後 | 記録 0 件 |
| 1 始まり・1 が最前面 | 全デザインレイヤ（27 件） | **仕上げ・更新の後** | 記録 0 件 |

同時に潰した可能性:

- `CreateViewportLayerOverride` は**色・不透明度**の上書きの族（`SViewportLayerOverride` は
  `fFillFore` / `fPenFore` / `fPercentOpacity`）で、重ね順とは別物。重ね順の族にだけ
  `Create…` が無く、`Set…` が記録の作成を兼ねる建て付けなので、事前に作るものは無い。
- **レイヤの索引は正しい。** ビューポート側の API はレイヤをハンドルではなく `InternalIndex`
  で指す（`VWViewportObj::SetLayerVisibility` も索引。ハンドルを取るのは
  `ISDK::SetViewportLayerVisibility` だけ）。`GetObjectInternalIndex(レイヤ)` がその索引で
  あることは、読み出した索引からレイヤ名が全件引けたこと＋
  `VWViewportObj::GetLayerVisibility(索引, …)` が読めることの両方で確認した。
- **有効/無効を切り替えるオブジェクト変数は無い。** `ObjectVariables.h` を `stack` /
  `override` で全文検索して該当なし（ヒットは `ovDimWitnessOverride` と
  `ovViewportLightingDevice` だけ）。ビューポートの変数は 1030〜1079 に並ぶが重ね順は無い。
  `ovSheetSaveStackLayers` / `ovSheetStackLayersStatus` は保存ビューの「レイヤを重ねる」で別物。
- **VectorScript にも重ね順上書きの関数が無い**（`vs.py` に `Stacking` のヒット無し）ので、
  SDK 以外に手掛かりも無い。

> **教訓**: setter の戻り値を信用しない。この族は書けなくても true を返すので、
> **読み戻しで確かめる**しかない。同じ形の setter（`SetUseDocumentClassVis` も同様だった）に
> 当たったら、まず GUI で作った実物を読んで「読める形式」と「書けるか」を切り分ける。

### `VWNURBSCurve` を制御点から構築する

`VWNURBSCurve` は評価専用で、制御点から構築できない。**ただし `ISDK` 側に `Add3DVertex` が
ある**（VS の `AddVertex3D`）ので、`CreateNurbsCurve` ＋ `Add3DVertex` で頂点は足せる。
「頂点を足す呼び出しが無い」と一度書いたのは取りこぼしだった。

### 地中梁のずれを端部の延長で直す

「地中梁の角が底盤の角と合わない」に対して 3 リビジョン続けて延長規則を足して外した
（① 底盤の外形へレイを飛ばして縁まで伸ばす ② ＋「別の地中梁が続いている端は伸ばさない」
③ 端が直交する立上りの壁芯上にあるときだけ半壁厚伸ばす）。**真因は `VWExtrudeObj` の
平行移動**で、伸ばす必要のないところに延長を足していた。

> **教訓**: 症状が同じまま 3 リビジョン続いたら、対処の方向ではなく**前提**（＝命令と図面の
> どちらがずれているか）を実測で確かめる。今回は「梁 1 本の両端の座標と長さ」を測った時点で
> 確定した（長さが一致して位置だけ違えば描画側、長さも違えば解析側）。

### データタグを関連付け先からの相対で置く

「VW がタグを関連付け先へ吸着させるので、そこからの相対で置けば原点を知らなくてよい」という
方式を 2 度試して外した（基準点の当て推量 → 実測からの較正）。診断が**残差 2824mm・標本
4 件（不採用）**を返し、どの基準点候補も当てはまらない＝**前提そのものが成り立っていない**と
分かった。正しかったのは最初の観測——**高さは合っていて横だけ一定量ずれ、タグ同士の間隔は
材の間隔に比例していた**（＝純粋な平行移動）。

> **教訓**: 実機の観測と食い違う仮説を足して複雑にするより、**観測をそのまま素直に写す**。

### 結合の成否を壁芯の端点で測る／レイヤ上の壁を数える

いずれも切り分けには役立ったが、**平常時から鳴る**ので外した（[進捗・診断・例外]
(#進捗診断例外)）。

## 実機確認の作法

**CI が全て緑でも、実描画（高さ・傾き・スタイル・PIO の挙動）は検証できない。** このリポジトリの
`draw/` に自動テストが無いのはそのためで、代わりに次の作法で確かめる。

- **切り分けは「完了ダイアログの診断行」と「OIP の値」の読み合わせで進む。** 例えば柱の高さは、
  「鉛直パスが 2 点にならなかった件数」と OIP の 高さ／始端・終端オフセット／スパン・長さの
  組み合わせで、原因が解析側（命令の値）か描画側（パス・パラメータ）かを 1 周ごとに絞り込めた。
- **書いたパラメータは読み戻す。** 名前が違えば setter は黙って無視する。
- **数えるより測る。** 「命令の値」と「図面の実測値」を突き合わせれば、ずれが平行移動なのか
  スケールなのか回転なのかが 1 本のサンプルで分かる。
- **API の無い設定は「UI で手作業したもの」と見比べて突き止める。** 読み取り専用の
  ダンプを設定の前と後で 2 回取り、diff を見る（選択オブジェクトのパラメトリック
  レコード・付いているレコード・オブジェクト変数・文書内のビューポート一覧を
  [`scripts/vw-dump-pio-fields.py`](../scripts/vw-dump-pio-fields.py) が書き出す）。
  `ModifySlab` の噛み合わせも断面ビューポートの範囲も、この見比べで決着した
  （[打ち切った調査](#打ち切った調査もう一度やらないこと)）。
- **役目を終えた計装は消す。** 規約を詰めるための実測コード・一時診断コマンドは、確定と同時に
  外す（履歴に残っているので必要なら作り直せる）。
- **描画に触れる変更は、実機で確認できるまでマージしない**（[`CLAUDE.md`](../CLAUDE.md)
  「開発プロセス: PR とマージ」）。未確認の描画が積み上がると、不具合が出たときにどの変更が
  原因か切り分けられなくなる。

### 基礎の床付け（捨てコン・砕石）は 3 通りに分かれる（M17）

M9 の当初は底盤スラブの構成層を「コンクリート / 捨てコン / 砕石」の 3 層にしていたが、
実際の施工は**底盤の下と地中梁の下で違う**。M17 で次のように描き分けた。

| どこ | 何を敷くか | どう表すか |
| --- | --- | --- |
| 底盤の下 | **砕石のみ**（厚みは捨てコン + 砕石ぶん＝130mm） | 底盤スラブの構成層（コンクリート + 砕石の 2 層） |
| 地中梁の下 | 捨てコン 30 + 砕石 100 | 地中梁と同じ押し出しのソリッド（`core::BeddingCommand`） |
| 地中梁の傾斜部 | **砕石のみ**で、法線方向に 130mm | 同上（傾斜に沿った帯になる） |
| 外周部 | 上記が地中梁の外側へ 50mm 張り出す | 同上（側面を回り込まず張り出しで終わる） |

**なぜ構成層で表せないか。** VW スラブの構成層は「一様な厚みの水平な層」しか表せない。
床付けは地中梁の下で深さが変わり、傾斜部では**法線方向**に厚みを持つので、層では表現できない
——地中梁のコンクリート自身を台形プリズムで描いているのと同じ理由で、押し出しソリッドにするしかない。

**断面の作り方**は「地中梁の**下面**（側面 → 下端 → 側面 と続く折れ線。天端の辺は含まない）を
外向き法線へ 130mm オフセットし、隣り合うオフセット線の交点（マイター）を頂点にする」。
これで傾斜部の法線方向の厚みが自動的に保たれる（真下へ 130mm 下げる素朴なやり方だと、
45 度の傾斜部で法線方向の厚みが 92mm に痩せる）。捨てコンはそのうち**下端の平らな面の
直下 30mm だけ**で、残りが砕石になる。

**外周部の判定は「底盤の外形の外か」**で行う。地中梁の側面のすぐ外側（1mm）を押し出し方向の
3 か所で突き、**すべてが底盤の外形の外**なら外周部とみなす。側面が鉛直かどうかは見ない
——外周の地中梁は外面が鉛直で底盤の外形とちょうど一致するが、**わずかに傾いていても
「外に回り込ませない」ほうが安全**（回り込ませると建物の外に砕石の壁が立つ）。この判定に
底盤の外形が要るので、床付けは**地中梁を底盤へ振り分けた後**でなければ求められない。

**砕石の帯は「立ち上げすぎない」のが要点で、上端を 2 段階で切る。** 素直に組むと帯は地中梁の
天端（＝底盤の底面）まで立ち上がるが、それだと**直交する地中梁と取り合うところで相手の
コンクリートへ食い込む**（実機で判明。実データを測ると最大 200mm、床付けの体積の 2〜9%）。

1. **底盤の砕石の底まで切る。** 底盤は地中梁の台形プリズムでしか削り取られないので、傾斜部の
   すぐ外側には底盤の砕石（130mm の水平な層）が残っている。**帯のうちその層と重なる部分は
   切っても和が変わらない**——同じ砕石が同じ場所を埋めているため。これだけで外周の取り合い
   （建物の四隅・T 字）は全て解消する。
2. **取り合う地中梁の下端まで切る。** それでも内部どうしの直交（互いに同じ深さ）が残るので、
   相手の平面外形が掛かる区間だけ更に切り下げる。区間ごとに切る高さが違うので、床付けの命令は
   押し出し方向の区間（`BeddingCommand` の `start` / `depth`）を持ち、**切る高さの同じ区間は
   1 本へ繋いで**無用な継目を作らない（取り合いの無い地中梁では区間は 1 つ＝全長）。

区間が掛かるかどうかは、相手のコンクリートの平面外形の 4 隅をこちらの (押し出し方向, 幅) 座標へ
写した外接矩形で見る。**直交・平行な取り合いでは厳密**で（実データはこの 2 通りしか無い）、
斜めでは安全側（広めに切る）に倒れる。

床付けのソリッドには**呑み込み（bite）を掛けない**——呑み込みは同じ素材どうしの coplanar
対策で、床付けの天端が接する相手（地中梁のコンクリート・捨てコン）は別素材なので、
そこに線が出るのはむしろ正しい。

**回帰は「食い込まないこと」で押さえてある**（`tests/ParseFootingTests.cpp` の
`ground_beam_bedding_never_bites_into_a_crossing_beam`）: 実フィクスチャ全件で床付けを格子状に
標本化し、どの点も他の地中梁のコンクリートに入らないことを確かめる。

### 耐力壁は「柱に紐付く線分 PIO」で描く（M19）

耐力壁（筋かい・面材）は、伏図では**記号**・軸組図では**形状**という、図によって別物を
見せる要素で、しかも**両端の柱に紐付いて伸縮**してほしい。素のジオメトリでは
「柱を動かすと間違った耐力壁が残る」という、記号（M12）とまったく同じ問題が起きるので、
**自作 PIO**（`Extensions/ExtShearWall`）で描く。線分 PIO（`kParametricSubType_Linear`）に
してあるので、両端のハンドルがそのまま「どの柱とどの柱の間か」を表す。

**追随の限界は M12 と同じ。** 柱を動かした瞬間には動かず、リセット・再オープン・
書き出し前（`kObjXPropResetBeforeExport`）に描き直される（上記「自作 PIO を足すときの 3 点」）。

解析（`parse/ShearWall`）で分かったこと:

- **壁の軸は押し出し方向から取る。** 筋かいも面材も「壁面内の断面を壁面に直交する向きへ
  押し出した」ソリッドなので、押し出し方向がそのまま平面の法線になり、それに直交する向きが
  壁の軸になる。平面 footprint の外接矩形や「最も離れた 2 点」から向きを推し量ると、
  厚み 45mm の帯では**対角線を軸と取り違える**（実際に一度そう書いて、見付け幅が 2 倍近くに
  化けた）。
- **見付け幅は回転キャリパの最小幅で測る。** 壁面座標 (軸方向, 高さ) へ落とした断面外形は
  IFC のプロファイルを回転しただけの形になるので、その最小幅がそのまま見付け幅（45×90 の
  90）になる。
- **たすき掛けは「同じ Name の 2 要素」。** ホームズ君は `筋かいダブル:1FL_18` を、互いに
  逆向きに傾く `IfcMember` 2 本として**同じ Name で**出す。Name でまとめて 1 枚にする。
- **大壁の表裏は「同じ軸・同じ区間」の面材 2 枚。** ただし軸と区間だけでまとめると、
  同じ通りに並ぶ**別の部屋の壁**まで 1 枚になる（間口が同じなら軸も区間も一致する）。
  法線方向の近さ（柱幅＋板厚ぶん）も条件に入れて初めて正しく分かれた。
- **表と裏に実世界の意味は無い。** IFC には内外の区別が無いので、「軸（始点→終点）を見て
  左手側が表」という幾何の約束で決める。始点は (x, y) の辞書順で小さい方に固定してあり、
  列挙順で軸が反転して表裏が入れ替わることはない。用途は**ハッチングの向きで 2 枚を
  見分ける**ことだけなので、決定的でありさえすればよい。
- **柱の無い端も軸の線に載せる。** 面材は壁芯から板厚ぶん外れた位置にあるので、片端だけ
  柱に吸着させると軸が斜めになる。柱芯を通る線を先に決めて、柱の見つからない端はその線へ
  射影する。

描画（`Extensions/ExtShearWall`）の要点:

- **軸組内法は毎回実物の柱から引く。** 対象レイヤ（`";"` 区切りの span 柱レイヤ。管柱と
  通し柱が別レイヤに分かれるので 1 つでは片端を取り逃がす）を走査し、構造用途 4 の
  構造材の外接矩形を PIO ローカルへ落として、両端の柱の**内側面**を内法とする。
  柱が見つからない図面では解析時に測った控え（`ClearSpan`）を両端の中央へ置く——柱が
  無いだけで耐力壁が消えるのは、図面として黙って欠ける最悪の形。
- **筋かいの帯は内法の矩形で切る。** 対角線に沿った幅 90 の帯は角が内法の外へ出るので、
  4 隅がそれぞれ別の辺で落ちて八角形になる。この計算は SDK に依らないので
  `core::shearWallBracePolygon`（＋`core::clipPolygonToRect`）に置いて無 SDK でテストしてある。
- **表裏の描き分けはクラスに委ねる。** ハッチングの向きはクラス属性なので、面材の面ごとに
  クラス（`…-01壁-01表` / `…-01壁-02裏`）を与えるだけでよい。プラグインは図面リソース
  （ハッチング定義）を作らない。

実機（ローカルの VW）でしか出なかったこと:

- **`SetLinearObjectPos` が効かない。** `CreateCustomObject` で置いた直後に
  `VWParametricObj::SetLinearObjectPos` で両端を与えても例外は出ないのに、
  `Recalculate` の中で `GetLinearObjectPos` を読むと **(0,0), (0,0) が返る**（＝線分として
  置けていない）。同じ症状は 53 枚すべてで再現した。中身は `GS_SetEndPoints` /
  `GS_GetEndPoints` そのもの（`SDKLib/Source/VWSDK/VWFC/VWObjects/VWParametricObj.cpp`）で
  戻り値が無いので、失敗しても呼び出し側からは分からない。原因は追えていないが、
  **「両端が取れない」前提で描けるようにしてある**ので実害は出ていない:
  `CreateCustomObject` に**始端→終端の角度**を与えてあるのでローカル +X は壁の向きに
  揃っており、控えの内法（`ClearSpan`）から軸を組み直して柱を探せば、内法は実物の柱から
  引き直せる。**PIO の絵は正しく、柱の移動にも（±300mm の探索窓の中なら）追随する**が、
  両端のハンドルで伸ばす操作はできない。診断ログの
  `shearwall: 線分の両端を読めない` / `軸を控えの内法から組み直す` がこの経路の目印。
- **伏図の記号は壁芯に置くと必ず横架材の下へ潜る。** 壁芯には土台・胴差が幅 105 前後で
  載っているので、面材の実物の離れ（半柱幅＋板厚の半分＝58.5 程度）では足りない。
  記号は `MarkOffset`（既定 200mm）だけ壁芯から離し、**面材ならその面材のある側**へ寄せる。
  実物の離れ（`PanelOffset`）は軸組図の面の位置にだけ使う。
- **耐力壁レイヤは最前面群へ回す。** 記号は「材の絵の上に重ねて読む注記」なので、
  背面に回ると意味が無い。`core::desiredStoryLayerOrder` が床（FL）・野地板を背面へ集める
  のと対称に、耐力壁レベルを `"共通"`／`topLayers` の直後へ集める。
- **伏図はその階自身の耐力壁を映す。** 当初は伏図記号レイヤ（M12）に倣って「切断の直下の
  階」を映していたが、図面の読み方は「n 階の耐力壁は n 階の伏図」だった（1 階の耐力壁は
  土台伏図＝1 階床伏図）。**重ね順の面でもこちらが正しい**——下の階のレイヤを載せると、
  上の階の横架材レイヤより必ず後ろに積まれる（順は最上階→最下階）ので、記号が隠れる。
- **伏図記号の大きさを内法で割らない。** 当初は内法の 1/3 を上限にしていたが、455mm 幅の
  壁（内法 350）だけ記号が 1/3 に縮んで図が不揃いに見えた。大きさは `MarkSize` 一定にし、
  内法より長くなる三角だけ内法まで詰める。
- **`VWPolygon2DObj` を閉じ忘れると斜辺が 1 本消える。** 直角三角形にしたら斜辺だけが
  出なかった（`SetClosed(true)` を呼んでいなかった）。詳細は上記「プラグインオブジェクト
  （PIO）」の同名の項。
- **軸組図は壁芯で切っているので、面材を実物の位置へ置くと消える。** 断面ビューポートは
  通り芯（＝壁芯）で切ってあり、**切断面より奥は表示しない**設定（draw/Section の 1064）。
  実物どおり壁芯から 58.5mm 外した面は、表側が手前で切り落とされ裏側は奥に隠れて、
  **両方とも図に出ない**。筋かいの帯が出ていたのは offset 0＝切断面の上に載っていたから。
  面材の面も**壁芯の鉛直面へ置く**（両面のときは 2 枚が重なるので、表裏はハッチングが
  重なって見えるかどうかに委ねる）。実物の離れ（`panelOffset`）と材厚（`thickness`）は
  命令セットに残すが、作図には使わない**測った値の記録**になる。
- **PIO のパラメータの既定値は「図面」に記録される。** コード側で既定値を変えても、
  **その PIO を一度使った図面では古い既定のまま**になる（M19: `MarkOffset` の既定を
  4 → 200 にしたのに、実機のログはずっと `記号の離れ 4.0mm` だった。記号が横架材の下へ
  潜って見えなかった原因）。**見た目に効く値は書き手（draw/）から毎回明示的に書く**こと。
- **用紙基準シンボル（`ovSymDefPageBased`）は「レイヤの縮尺」が基準。** 紙の上の大きさを
  保つ仕組みだが、その「紙」は**そのシンボルが載っているレイヤの縮尺**で決まる。
  このプラグインが作るデザインレイヤは縮尺 1:1（PIO が読んだレイヤ縮尺も 1.0）なので、
  用紙 6mm の記号は**図面でも 6mm**になり、1/50 の伏図では紙の上で 0.12mm——読めない。
  （なお M19 で「シンボルが空に見えるのはこれが原因＝小さすぎるだけ」と一度読んだが、
  **これは誤り**だった。実機のシンボル 2D 編集で「すべて選択」しても何も選べず、
  定義は本当に絵として成立していない。上記「シンボル定義を SDK から組み立てられて
  いない」を参照。）
  伏図の縮尺はビューポートが持ち、デザインレイヤの図形からは分からないので、
  **記号は図面 mm で持つ**（1/50 で読める寸法＝用紙寸法の 50 倍）。真の縮尺非追従が要る
  なら、耐力壁レイヤの縮尺を伏図の縮尺に合わせたうえで用紙基準に戻すしかない。
- **伏図記号は PIO が図面 mm で描く。** 記号は実物の大きさを表さない**表記**なので、
  内法でも縮尺でも割らず、1/50 の伏図で三角 6×3mm・丸 直径 3mm に読める寸法
  （図面 300×150mm / 直径 150mm）に固定する。シンボルにする案・用紙基準（縮尺非追従）に
  する案はどちらも実機で行き止まりだった（上記「プラグインオブジェクト（PIO）」の 2 項）。
  **真の縮尺非追従が要るなら**、伏図の縮尺（`core::planLayout` が決める）を耐力壁 PIO へ
  書き戻し、記号の寸法をその縮尺に掛ける（用紙 mm × 伏図の縮尺）ことになる——伏図を
  作った後にもう一度 PIO を更新する経路が要る。
- **筋かいの三角は直角三角形にする。** 二等辺三角形では「どちら向きに傾いた筋かいか」が
  読めない。壁と平行な脚を底に、直角を材が高くなる側の端へ立てると、斜辺の傾きが
  そのまま筋かいの向きになる。たすき掛けは**同じ場所へ反転して重ねる**（斜辺が交差する）。


## 残っている宿題

- **配筋（保留）**。レコード `配筋` を立上り・底盤に設定する（`Pset_Reinforcement`、鋼種接頭辞
  除去、短辺/長辺→X/Y）。着手するときは**統合キーにも配筋を足す**
  （`parse/Footing.cpp` の `wallSectionKey` / `slabMergeKey`）——配筋の違う部材を 1 つに統合
  すると片方の配筋が失われる。現状は配筋を持たないため、**配筋だけが違う底盤は 1 枚に
  統合されている**。
- **床付け（M17）の実機確認は「スラブ厚・梁せいが一定」の範囲まで。** 実機で確かめられたのは
  底盤の厚みも地中梁のせいも揃っているモデルで、**それらが場所によって違うモデルは未確認**。
  効いてくるのは切り下げの 2 か所で、どちらも**保守側（多めに切る）**に倒れる:
  取り合う地中梁のほうが深いと切り下げ高さが負になり、その区間の捨てコン——場合によっては
  砕石も——が丸ごと落ちる（相手のコンクリートが占める前提。実データではスキップフロアの
  外周 × 内部で起きている）。底盤の厚みが場所で違うと、帯を切り上げる高さ（底盤の砕石の底）が
  地中梁ごとにずれる。**床付けが欠けて見えるようなら、まずこの 2 つを疑う**
  （`parse/Footing.cpp` の `beddingSpans`）。
- **M9（立上り・底盤・基礎ストーリ）の実機確認は M9 固有の項目だけ残っている。** M10 / M11 の
  確認で立上り・底盤・基礎ストーリも一緒に見えているため、残りは壁厚の保持・統合本数・
  布基礎（升目状ラティス）が統合されないこと、といった細目。
- **床版の開口は塞がっている。** VW スラブへ穴を開ける API の調査が要る。
- **登り梁の実データ検証が薄い。** 検証済みフィクスチャに登り梁を含むモデルが 1 件も無く
  （`tests/fixtures/README.md`）、合成モデル・合成命令でのみ検証されている。
- **進捗バーの重みは 1 サンプルの粗い実測。** 別のモデルで大きくずれる要素があれば
  `core::drawWeight` の表を直す（診断ログの経過ミリ秒と見比べる）。
- **完了報告をモーダルのままにするか**は実使用の感触待ち。
