# 配置の手順をリリース側へ移す（M22）

**動機は M21 で払った代償。** 本体（`.vwpayload`）というファイルが 1 つ増えただけで、
利用者は zip を手で落として置き直す必要があった。理由は単純で、**更新を実行するのは
「いま入っているビルドに同梱されていたスクリプト」**——つまり必ず古い版——であり、
その版は増えたファイルの存在を知らないからである。zip には入っているのにコピーされない。

これは「今回たまたま」ではなく**構造的な欠陥**だった。同梱スクリプトに配置手順がある限り、
構成を変えるたびに同じ手作業が発生する。

**やったこと**は、役割を 2 枚に割ったこと。

| | 何をするか | どこにあるか | いつの版が走るか |
| --- | --- | --- | --- |
| **アップデータ**（`scripts/vw-update.*`） | 探す・比べる・落とす・ダイアログ | インストール済みプラグインの中／隣 | **古い** |
| **インストーラ**（`scripts/vw-install.*`） | **配置** | **配布 zip の直下**＋リリースのアセット | **新しい**（落としてきたビルドの版） |

`do-install` は zip を展開したあと、その直下の `vw-install.sh` / `vw-install.ps1` を
`--machine --from <展開先>` で呼び、その出力（`installed-shell=` / `ok` / `error=`）を
**そのままプラグインへ流す**。配置の知識が「新しい側」にあるので、ファイルが増えても
利用者の手は要らない。

## 判断したこと

- **配置の規則は「zip の直下にあるものを、そのまま置く」の 1 つだけ。** ファイル名を
  列挙しない——列挙した瞬間に、いま直している事故（増えたファイルの取りこぼし）が
  そっくり戻ってくる。除くのはインストーラ自身だけ。テストの中心もここにあり、
  フィクスチャには**誰も列挙していないファイル**をわざと混ぜてある。

- **リリースのアセットとしても公開する。** 手動インストールの入口になり、`curl` で 1 本
  落として実行するだけで、取得・展開・隔離解除・アドホック署名・配置まで済む。**手順書に
  書いた手作業は、書いた瞬間から古くなる**が、スクリプトはビルドと一緒に更新される。

- **インストーラは殻の ID（`VW_SHELL_INPUTS`）に入れない。** 殻に入らないので当然でも
  あるが、狙いは「配置の手順を直しただけで再起動を強いない」こと——それはこの仕組みが
  無くそうとしている手間そのもの。

- **アセット名も決め打ちにしない。** アップデータはまず `<名前>.vwlibrary.zip`
  （Windows は `.vlb.zip`）を厳密に探し、無ければ**末尾がその拡張子のアセット**で拾い直す。
  名前を変えた瞬間に、古いアップデータから何も落とせなくなる＝**アップデートの経路そのものが
  切れる**のを避けるため。1 つのリリースが持つ配布 zip はそのチャンネルの 1 つだけなので、
  末尾での照合で取り違えは起きない。

- **知らないオプションでは落とさない。** 新しいアップデータが、古いリリースの zip に入った
  インストーラを呼ぶ向きが起こりうる（そのリリースへ切り替えるとき）。増えた引数で落ちると、
  そこでまた手作業に戻ってしまう。

- **「委ねられた」の判定は結末の行が返ってきたかで行う。** インストーラが古い／壊れていて
  何も言わないときに成功と取り違えると、半端な状態のまま `ok` を返してしまう。何も言わなければ
  アップデータ自身の予備の配置へ落ちる（この仕組みより前のリリースへ当たった場合も同じ経路）。

## 残る 1 回

**この仕組みより前のビルドから更新する 1 回だけ**は、まだ古い同梱スクリプトが配置を行う。
そのときのファイル構成は変わっていないので正しく入り、その更新で新しいアップデータが入る。
以後は常にリリース側のインストーラが配置する。

## 続き: プラグインは自分のフォルダを 1 つ持ち、入れる前に前の版を取り除く

置き先を `Plug-Ins` の直下から**プラグイン名のフォルダ**へ移した:

```
<Plug-Ins>/min-nano_structure/min-nano_structure.vwlibrary
<Plug-Ins>/min-nano_structure/min-nano_structure.vwpayload
<Plug-Ins>/min-nano_structure/vw-uninstall.sh
```

**そのプラグインのものが 1 か所に閉じる**ので、取り除くのが「フォルダを 1 つ消す」で済む。
Vectorworks が `Plug-Ins` のサブフォルダも読みに行くことは実機で確認済み。

判断したこと:

- **渡された先が既にそのフォルダなら足さない。** プラグインは「いま自分が読み込まれた
  フォルダ」を渡してくる（`src/Updater.cpp` の `BundlePluginsDir`）ので、無条件に足すと
  更新のたびに `<name>/<name>/…` と際限なく深くなる。この規則はインストーラ・
  アンインストーラ・アップデータの**3 つで同じ**でなければならない——片方だけ変えると、
  入れた場所と読む／消す場所が食い違う。3 つそれぞれに回帰テストを置いた。

- **取り除くのは、その版自身のアンインストーラ。** リリースは `vw-uninstall.*` も同梱し、
  それは**インストール先へ一緒に置かれる**（インストーラ自身は置かれない）。次の
  インストーラは、いま入っているフォルダの中のそれを叩いてから配置に入る。**置く側が
  新しい版の知識を持つのと、ちょうど対**——その版が何を置いたかを正しく知っているのは、
  その版のアンインストーラだけである。

- **順序は「検査 → 取り除く → 置く」。** 取り違えた zip を先に弾かないと、「消しただけで
  入れられない」状態を作ってしまう。

- **一時ディレクトリへ写してから叩く。** アンインストーラは自分が消すフォルダの中に居る。
  POSIX なら実行中でも読み続けられるが、写しておけば考えなくてよい。

- **削除には安全弁を置く。** フォルダ名が一致し、かつ中に殻があるときだけ消す。ここは
  本リポジトリで唯一「利用者のディスク上のものを消す」コードで、`Plug-Ins` そのものを
  名指しされても消さないことを回帰テストで押さえてある。（M38 で実機テストの一時ファイルの
  片付け、M39 で実機テストの図面を保存せずに閉じるところが加わり、いまは 3 か所。
  CLAUDE.md「開発の基本方針」8。）

- **Windows は「退かしてから消す」。** 読み込み中の `.vlb` は削除できないが改名はできる。
  退いた `*.old-*` は拡張子が `.vlb` ではないので読み込まれず、次のインストールが掃く。

**旧配置（`Plug-Ins` 直下）からの移行は自動ではやらない。** 直下のものを消すには
「このプラグインのものだ」と名前で列挙するしかなく、それは**この一連の変更が捨てた作法**
そのものになる。利用者が 1 度だけ手で片付ける（[「アップデート」](../../user-guide/update.md)）。
