# 実機確認の往復をプラグインに回させる（M23）

（実機確認の往復をプラグインに回させる（M23）は 5 ページに分けてある: **割り方と公開の扱い** → [人に尋ねること・伝えること](asking.md) → [周の回し方](loop-flow.md) → [同梱スクリプトの落とし穴](bundled-scripts.md) → [図面が戻っているかを測る](baseline.md)）

**動機は M21 が開けた道。** アップデートに Vectorworks の再起動が要らなくなったことで、
「新しいビルドを、動かしたまま、その場で再読み込みする」が可能になった。すると実機確認の往復
——このリポジトリで**実装そのものより時間を消費していた**もの——を、プラグイン自身に
回させられる。

従来の 1 往復は、人が全部やっていた:

> 新しいビルドを入れる → **再起動** → 図面を戻す → IFC を選ぶ → 設定を選ぶ → 取り込む
> → ログをコピーして PR へ貼る

いまはこうなる:

> **描画結果を見て一言書く → 送る**（あとは待つだけ。次の周は無操作で走る）

（この往復は [M38](../m38-local-mcp-verification.md) で削除した——PR への投稿
（`scripts/vw-feedback.*`）も、尋ねずに入れる更新（`UpdateCheckKind::Auto`）も無い。いまは
ローカルの Claude Code が MCP ブリッジ越しに更新と実機テストを起こす。）

## 何をどう割ったか

| | 中身 | どこ |
| --- | --- | --- |
| 覚えておく値 | 1 周目の選択（IFC・設定・宛先 PR）・周回数・前の周の内訳 | `core/FeedbackSession`（無 SDK） |
| コメント本文 | 内訳・**前の周との差分**・注意・ログ・匿名化 | `parse/Feedback`（無 SDK） |
| 往復の運転 | **取り込みの前に**送るか決め、終わったら黙って投稿（**待たない**。[周の回し方](loop-flow.md)） | `draw/Feedback`（SDK 依存） |
| 入れ替え | 次の取り込みの頭で、尋ねずにインストールして本体を再読み込みする | `src/UpdaterFlow.cpp`（`UpdateCheckKind::Auto`） |
| ネットワーク | トークンの保管・PR の特定・コメントの投稿 | `scripts/vw-feedback.*`（同梱） |

**ネットワークを C++ で書かない**のは自動アップデートと同じ分担（`src/Updater.h`）。
おかげでコメント本文の組み立て——いちばん頻繁に直るところ——が**丸ごと無 SDK で
テストできる**。

## 入れ替えは必ず殻の側で起きる

新しい本体をその実行のまま反映させるには載っている本体をアンロードする必要があり、それができるのは
**本体のコードがスタックに 1 つも無いとき**だけである（`src/PayloadSession.h`）。したがって
入れ替えは必ず「本体から戻ったあと」＝取り込みコマンドの頭になる。本体がするのは投稿まで
で、殻へ返すのは「**次は尋ねずに入れてよい**」という 1 ビットだけ。殻に追加したのはそれを
1 回ぶん覚える `static bool` で、往復の中身はすべて本体側にある（＝往復のふるまいを
直しても再起動は要らない）。ABI は 2 へ上げ、**同梱スクリプトの実行**を貸すようにした
（本体が読まれるのは一時ディレクトリの複製なので、自分の在り処から同梱物へたどり着けない）。

## インストールの経路は 1 本に保つ（#108 を取り込んで整理）

最初の実装では、本体が待ったうえで `do-install` まで自分で呼んでいた。**そこは間違いで、
インストールの経路が 2 本になっていた**（殻の更新の流れと、往復のためのもの）。「再起動が
要るか」の判定も、失敗したときの文言も、2 か所で同じことを書くことになる。

`#108`（[「更新の確認を、起動時から 2 つの入口へ」](../m23-update-trigger.md#更新の確認を起動時から-2-つの入口へ)）で
更新の確認が**起動時から取り込みコマンドの頭へ移った**ので、往復はそれに乗れば
よくなった——本体は「出た」と見届けて戻るだけで、入れるのは**もともとそこにある**更新の
確認である。そのために `UpdateCheckKind` に `Auto`（尋ねない・報せない・再起動しない）を
追加し、流れは「この実行のまま自動で続けてよいか」を `bool` で返すようにした。**本体から
`do-install` が消え**、往復のために増えた経路は 0 本になった。

`Auto` が**再起動を仕掛けない**のは、利用者が図面を開いたまま輪を回しているからである。
殻まで変わったら、伝えて輪を止め、再起動するかどうかはその人に委ねる。

## 公開されることの扱い

PR コメントは公開なので、**既定で伏せる**: IFC のファイル名は仮名（`model-8f3a12.ifc`。
**同じ入力なら毎回同じ**なので周回どうしの同一性は保たれる）へ、パスのユーザー名は伏せ字へ。
残すのは要素ごとの命令数と描画できた数・描画側の注意・所要時間で、これは**案件ではなく
プラグインの話**である。「フィクスチャに実案件データを使わない」という運用と合わせて、
公開でも困らない形にしてある。私有リポジトリへ向けることもできるが、その PR のイベントで
Claude が起きないので往復の自動性は落ちる。

（報告の伏せ字は [M38](../m38-local-mcp-verification.md) で PR への投稿と一緒に削除した。報告は
利用者の PC の中だけで読まれる。）

## 実機フィードバックの伏せ字（公開済みの投稿を洗い直して分かったこと）

公開済みの往復のコメントを全部（47 本の PR）洗い直したところ、次が見つかった。

* **図面枠のスタイル名がそのまま出ていた**（PR #129・#133 の round 1。スタイル名を伏せる
  前の版の投稿）。スタイル名は事務所名を含むのが普通で、実際にそうだった。該当のコメントと
  PR 本文は取り下げ・伏せ字にし、テストの値に複製されていた同じ名前も架空の名前へ替えた。
  **テストやドキュメントに実在の名前を複製しない**——実機の記録から値を取得するときは、必ず
  架空の名前へ置き換える。
* **仮名は鍵なしのハッシュだった**ので、名前の心当たりから照合して特定できた。
  利用者の機械にだけある鍵（`core::FeedbackSession::anonKey`）を混ぜるようにした。
* **いま開いている図面のパスが伏せ字の外だった**（準備の行「いま開いている図面（…）」）。
  これまでは保存前の「名称未設定 N」だったので無害だったが、保存済みの図面で回すと
  物件名のフォルダとファイル名がそのまま出る。押したときに開いていた図面のパスを
  `parse::FeedbackRound::privatePaths` で渡して仮名（`drawing-…`）にする。
* **macOS の利用者ごとの一時ディレクトリ**（`/var/folders/<xx>/<yyyy>/`）が全投稿に
  出ていた。名前ではないが投稿どうしを同じ機械へ結び付けるので、2 区画とも伏せる。
  外部ボリューム名（`/Volumes/<名前>/`）も同じ理由で伏せる。

**GitHub のコメントは編集しても履歴に元の文が残る**（公開リポジトリでは誰でも「edited」
から読める）。投稿後に手で伏せ字へ書き換えても漏れは塞がらないので、漏れたコメントは
削除するか、履歴の版を消す。
