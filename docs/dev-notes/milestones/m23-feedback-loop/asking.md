# 人に尋ねること・伝えること（M23）

（実機確認の往復をプラグインに回させる（M23）は 5 ページに分けてある: [割り方と公開の扱い](README.md) → **人に尋ねること・伝えること** → [周の回し方](loop-flow.md) → [同梱スクリプトの落とし穴](bundled-scripts.md) → [図面が戻っているかを測る](baseline.md)）

## 所見は別プロセスのダイアログで訊く（round 1〜4。**のちに丸ごと外した**）

**round 1 の所見がこうだった:**

> ダイアログを非モーダルで表示してもらわないと実行結果を確認できません。

そのとおりで、取り込み直後にモーダルのダイアログで所見を求めると、**その所見の材料である
図面が見られない**。「絵を見てから書く」が成り立たないと、この往復の価値はほとんど消える。

**SDK にモードレスの口はある。** `IExtensionWebPalette`（5 つ目の拡張種別。
[SDK リファレンス「モードレス（非モーダル）なパレット」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layout%20Dialogs.md)）。
ただし中身は HTML/JS で、登録は殻に置くしかなく（VW に vtable を握られる）、閉じる API も
見つかっていない。そして**全部が実機未確認**である。所見欄 1 つのために UI スタックを
もう 1 つ背負う判断は、まだできない。

**代わりに、既にある仕組みで足りた。** プラグインは同梱スクリプトを起動できる
（自動アップデートの経路）。**スクリプトが OS 標準のダイアログを出せば、それは別プロセス
なので Vectorworks を止めない。**

肝は**待たないこと**。プラグインはスクリプトの出力を読み終わるまでメインスレッドを止める
（`popen`）ので、ここで待つと結局図面が固まる。そこで `ask-note` は**自分自身を detached
で起こし直して即座に `ok` を返す**——プラグインはすぐ戻り、Vectorworks は完全に操作できる
状態になる。

**戻ってしまう以上、こちらへは返せない。** だから尋ねてから投稿するところまでスクリプトの
仕事にし、**所見は独立した 1 通**として PR に載せる（目印 `homeskz-ifc-feedback-note`）。
取り込み結果の本文へ差し込む形にしなかったのは、そうするとコメントの組み立てが C++ 側
（`parse/Feedback`）とスクリプト側の 2 か所に割れるため——差し込み位置の目印を置いて
awk で嵌める案も試したが、「所見の節をどう書くか」が二重定義になるので採らなかった。

分けたことで良くなった点もある: **投稿の成否がプラグインの手に残る**ので、記憶
（round / 内訳）の更新は従来どおり確実で、所見を書かなかった周も正しく数えられる。

この分離だけでは足りなかった——**待機のほうが残っていた**（[「ビルドを待つのをやめた」](loop-flow.md#ビルドを待つのをやめたround-3-の実機で判明)）。

## 所見はプラグインの仕事ではなかった（実機の指摘）

所見を訊く仕組みは、round 3 の「モーダルで図面が見られない」から始まって、別プロセスの
OS ダイアログ・`posted=no` の周・ボタンの文言と、3 周かけて作り込んだ。**そして外した。**

外した理由は 1 行である——**所見を書くには、その人が実機を見ている必要がある。見ている
なら、チャットへ書くほうが速い**（スクリーンショットも貼れる）。プラグインが間に入る
価値が無い。

作っている間はこれが見えなかった。「往復をプラグインが回す」という枠に、**回さなくてよい
ものまで入れていた**のが原因である。**この往復でプラグインにしかできないのは「数字と
診断ログを機械的に集めて投げること」だけ**で、それ以外は人の側でやったほうが速いか、
そもそも人にしかできない。

消えたもの: `ask-note` / `ask-note-worker`（両スクリプト）、別プロセスを起こす仕掛け
（`spawn_self` / `Invoke-SelfDetached`）、OS ダイアログのラッパー 3 つ、`posted` の
受け渡し、それらのテスト。**足したものより消えたものが多い変更**になった。

## 取り込みのあとに人の操作を残さない（実機の指摘）

同じ指摘の後半がこれである:

> 結果を送るかどうかはコマンド実行の最初に選択します。そうしないと、インポートを待って
> 操作しなければなりません。

**取り込みは 1 分以上かかる。** その終わりに確認が待っていると、その人は席を離れられない
——「実行して放っておく」が成立しない。ダイアログを 1 枚に減らしても、**終わりに置いて
ある限り同じこと**だった。

そこで**尋ねることを全部、取り込みが始まる前へ移した**: 送るかどうか・宛先の PR・伏せ字・
トークンの登録。取り込みが終わったあとにするのは投稿だけで、**結果ダイアログも出さない**
（投稿できたなら内訳もログも PR にあるので、見せる相手がいない）。

投稿に失敗したときだけ、いつもの結果ダイアログに理由を添えて出す。ここでアラートを重ねる
と、無操作で終わるはずの取り込みにボタンが 1 つ増えてしまう。

**「取り込みの前か、後か」は、この往復では機能そのものである。** ダイアログの枚数や文言
より先に、それを問うこと。

## ボタンが何を指しているのか分からなかった（実機の指摘）

「送る／送らない」というボタンが**2 つの別々のダイアログ**（結果のダイアログと所見の
ダイアログ）に同じ文言で並んでいて、しかもどちらも**往復が続くのか終わるのかを何も
言っていなかった**。結果として「送らない＝往復が終わる」と読まれた。

**動詞だけのボタンは、対象が 1 つしか無い画面でしか成立しない。** ここは対象が 2 つある
（結果と所見）ので、ボタンに対象を持たせた:

| ダイアログ | いま |
| --- | --- |
| 送るかどうか（取り込みの前） | 「取り込み結果を送る」／「送らない」 |
| 続きの確認 | 「続ける」／「往復を終える」 |

（所見のダイアログはこのあと丸ごと外した。上記「所見はプラグインの仕事ではなかった」。）

**結末そのものをボタンに書く**のも同じ理由である——「やめる」では「この取り込みをやめる」
とも読めるが、「往復を終える」なら読み違えようがない。加えて結果のダイアログには、押した
あと何が起きるか（所見のダイアログが出る・往復は終わらない）を 2 行で書いた。**押す前に
結末が分かること**が、ここでの唯一の要件である。

（Windows の所見ダイアログは `InputBox` でボタン名を変えられないので、そちらは本文で
「OK で所見を送り、キャンセルなら書かずに閉じます」と名乗る。）
