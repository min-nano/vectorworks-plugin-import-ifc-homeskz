# 「いま動いているビルド」はディスクに聞く（M26）

**症状は「開発版の更新で、現在のビルドとは別のブランチを選んでインストールしても、その
ブランチのビルドに切り替わらない」。** 入れ替え自体は成功していて、絵を描くコード
（本体）も新しいブランチのものに替わっている——替わっていないのは**プラグインが自分を
どのブランチだと思っているか**だった。

原因は殻と本体に割った（M21）ことの副作用である。開発版の流れは「いま動いているビルド」を
**殻にコンパイルされた** `VW_BUILD_BRANCH` / `VW_BUILD_VERSION` で名乗っていた。M21 以前は
それが正しかった——更新は殻ごと入れ替わるしかなく、再起動すれば値も新しくなる。ところが
M21 以降、**本体（`.vwpayload`）だけの更新は再起動せずにその場で効く**（殻の ID が同じなら
「再起動は要りません」と言って載せ替える）。2 つのブランチが殻に入るファイルを 1 行も
変えていなければ殻の ID は一致するので、**別のブランチへ乗り換える経路がまさにそこを通る**。
通った結果、走っているのは新しいブランチの本体なのに、殻の 2 つの定数は前のブランチを
名乗り続けた:

| 起きたこと | なぜ |
| --- | --- |
| 選択ダイアログが「現在: 前のブランチ」と出し、**いま入れたビルドをまた候補に並べる** | 候補から除くのを殻の sha で決めていた（`DevSwitchCandidates`） |
| 取り込みのついでの確認・往復の周期確認が**前のブランチ**の新しいビルドを入れる | 同じブランチかの照合を殻のブランチで決めていた（`FindDevBuildForBranch`） |

前者は「選び直しても切り替わらない」と見え、後者は**実際に乗り換えを巻き戻す**。

**直し方は「いまはディスクに入っているビルドである」に統一すること。** 次に読み込まれるのは
ディスクのものなのだから、そちらが「いま」である——安定版が最初から `q-stable` の
`installed=` を基準にしているのと同じ考え方で、往復の周期確認も M24 で sha だけは
すでにそうなっていた（`installed=` を見ないと同じビルドを毎周入れ直す）。M26 でそれを
**ブランチにも広げ、3 つの入口（Manual / Silent / 往復の周期確認）で共有**した
（`src/UpdaterParse.h` の `ResolveCurrentDevBuild`）。

- `q-dev` が `installed-branch=` を出す（mac: `Info.plist` の `VWBuildBranch`、win: 新しく
  足した `<name>.branch` の控え。`.commit` / `.shell-id` と同じやり方）。
- 読めないときは**並んでいるビルドの中で sha が一致する行のブランチ**へ落ちる。走るのは
  常にインストール済みの（＝古い）同梱スクリプトなので、「新しい殻＋古いスクリプト」は
  必ず起こる——`ParseDevBuilds` が 4 列の出力も読めるようにしてあるのと同じ備えである。
- それでも分からなければ殻の値へ落ちる。**殻の 2 つの定数は「いまの控え」ではなく
  「最後の落としどころ」**になった。

**教訓は「コンパイル時に焼いた素性は、モジュールが入れ替わらない限りしか正しくない」。**
ホットリロードを足した時点で、殻に焼いた値の意味が静かに変わっていた——同じ罠は、殻に
焼いた値を「いまの状態」として使うところすべてに残る。ディスクやプロセスの実物に聞ける
ものは、焼いた値で代用しない。
