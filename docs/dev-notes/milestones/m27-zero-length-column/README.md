# 柱が長さ 0 で描かれる（M27）

（柱が長さ 0 で描かれる（M27）は 5 ページに分けてある: **症状と最初の 10 周** → [自己修復をやめた](self-repair.md) → [原因を突き止めた](root-cause.md) → [直ったあとに外したもの](after-fix.md) → [パスは 2D で渡す](path-2d.md)）

> **原因は「渡したパスが PIO 化で退化する」ことだった**（実機 round 1〜10 で 10 周かけて
> 突き止めた）。高さ基準を疑った 4 周はすべて見立て違いで、下記「打ち切った直し方」に理由つきで
> 残してある。直し方は**退化していたらパスを再生成して差し替える**こと。
>
> （この直し方はのちに撤去した。退化する原因は生成直後のパスに残る 1 ULP（mm↔インチの往復と
> 推測）で、根本の直し方は両端に同じ Z を渡す（[原因を突き止めた](root-cause.md)）→ パスに
> Z を渡さない（[パスは 2D で渡す](path-2d.md)）になった。）

**症状**: スキップフロアのモデルを取り込むと、**1 階の柱の一部（46 本）が図に出ない**。柱
オブジェクトは在り、OIP の高さ・始端／終端の高さ基準・オフセットはすべて命令どおりなのに、
**長さが 0**（＝実体が無い）。ドラッグするか OIP の数値を 1 つ更新すると、その場で正しい
高さに再描画される。

**確定した事実だけ書く。** 実体が無いのは**1 階の管柱のうち、上端が 2 階の横架材天端
（＝上階のレベル）にちょうど届く 46 本**で、終端が**始端と同じ Z**（572 ＝ その柱が載って
いる span レイヤの高さでもある）に解決されている。実機の実測（round 3）:

````
命令 2959（パスの頂点 piece0=2）に対し実測 4.5e-13 … StartElevation=572 / EndElevation=572
````

パスは 2 点あり、退化しているのは**バウンドの解決の側**である。実機で切り分けた分かれ目は
次の 3 つで、**上階参照そのものは機能している**（offset が 0 でなければ上階のレベルに正しく
解ける）。

| 上端のバウンド | 実機 | なぜ |
| --- | --- | --- |
| `{上階, 横架材天端, 0}` | **壊れる**（46 本） | 横架材天端は**自階にもある**種別 |
| `{上階, 軒高, 0}` | 無事（32 本） | 軒高は最上階にしか無い＝**自階に無い**種別 |
| `{上階, 横架材天端, 2374}` | 無事（通し柱） | `EndElevation=5905`（＝ 3531 + 2374）と解ける |

**「階だけ違う同じ記録」だからではない**（round 4 で否定した）。上下端が同じ記録に見える
のを嫌って**下端を FL 基準へ振り替え**、レベル種別が違う記録にしてもう 1 周回したが、
**46 本は 1 本も直らなかった**。影響するのは上端の指し方だけで、下端は関係が無い。

**高さ基準の書き方を変えても直らなかった（round 5 で否定）。** 「上階の、自階にもある種別を
offset 0 で指しているのが悪い」と見て、offset が 0 にならない言い方（`{上階, FL, −40}`）へ
書き換えたが、**46 本は 1 本も直らなかった**。しかも**測った値は 572 のまま**で、これは
偶然ではない——2 階の FL は 3571、そこから −40 は 3531 のはずだが、**1 階の FL（612）から
−40 を引くと 572 になる**。つまり**どう書き換えても同じ間違った答えが返る**ので、
「レベル種別」や「offset」の選び方の話ではない。

**この事実と噛み合わないこと**——**手で同じ値を入れ直すと正しく描画される**（利用者の
実測。ドラッグしても直る）。値が同じなのに結果が違うなら、犯人は record ではなく
**生成したその場の解決**だとも読める。ただし**「同じ指定のまま解かせ直す」（`ResetObject`）
では 46 本中 0 本しか直らない**ので、単なる再計算の取りこぼしでもない。
**分かれ道は「図面が実際に何を持っているか」**で、そこは命令を参照しても分からない:

* `ISDK::SetObjectStoryBound` は **bool を返す**のに、M27 まで**戻り値を捨てていた**
  （＝書けなかったことに気付けない）。**いまは戻り値を確認して、書けなかった本数を診断へ載せる**
  （`draw/DrawUtil` の `ApplyStoryBound`）。
* **VW が持っている高さ基準**は `HasObjectStoryBound` ＋ `GetObjectStoryBound` で読み戻せる。
  実体が無い柱では、命令の値と図面の値を**並べて**診断へ載せる（`DescribeStoryBound`）。
  * 図面の値が命令どおりなら → record は入っている＝**解決の側**の話（上の見立て）。
  * 図面の値が違えば → **書けていない**＝描画側の話で、そこを直せばよい。

**当階へバインドし直す方向へは倒さない。** 上階の横架材天端が FL と同じ高さの階（＝その階に
負の配置 Z を持つ要素が 1 つも無く、横架材天端オフセットが 0。`グレー本モデルプラン2` が
全階そう）は、FL へ移しても offset が 0 のままで**上階を指す言い方が残らない**が、そこで当階
基準の固定値にすると**階高の変更に追随しなくなる**（利用者の指摘）。見立てが確かめられるまで、
その階は上階を指したままにする。

**なぜ M20 から出たか**: 柱の上端を「材が止まる高さ（梁の下端）」から**受ける梁の天端＝その
芯線**へ移した結果、上端 offset がちょうど 0 になった（それ以前は −105 などの非 0）。**この
事故は全モデルで起きうる形になっていた**——`サンプル1` で 58 本、`伏図次郎` で 54 本、
`グレー本モデルプラン1` で 47 本、`グレー本モデルプラン2` で 70 本が同じ形である
（**実機で確かめたのはスキップフロアだけ**なので、他のモデルで本当に欠けていたかは未確認）。
スキップフロアは「上端がレベルに乗る柱」と「乗らない柱」が**同じレイヤに混在する**初めての
データで、だから「一部だけ出ない」という形で気付けた。

**高さ基準は犯人ではない（round 6 で確定）。** 図面の側を読み戻して 2 つ分かった:

* **VW は命令どおりに記録している。** 実体が無い柱の `GetObjectStoryBound` は
  `始端[種別=2 階=+0 レベル="横架材天端" offset=0]` / `終端[種別=2 階=+1 レベル="FL"
  offset=-40]`——書いたそのままである（`SetObjectStoryBound` の戻り値も true）。
* **レイヤの高さ基準（`eStoryObjectBound_LayerElevation`）で言い直しても 0 のまま。**
  `始端[種別=0 offset=0]` / `終端[種別=0 offset=2959]` という**曖昧さの無い 1 対**を
  書き込んで解かせ直しても `Z 572→572`。

**つまり両端の Z は高さ基準から来ていない。** 残る入力は**パス**なので、
`GetCustomObjectPath` ＋ `NurbsGetPt3D` で**図面上のパスの頂点そのもの**を読み戻した
（round 7）。**パスが退化していた**:

| | 図面のパス（PIO が持っているもの） |
| --- | --- |
| 実体が無い柱（命令のパス長 2959） | `(0,0,0) (0,0,4.54747e-13)` ← **2 点あるのに同じ位置** |
| 同じレイヤで無事な柱（1857） | `(0,0,0) (0,0,1857)` |
| 通し柱（5333） | `(0,0,0) (0,0,5333)` |

**退化させているのは PIO 化のときである**（round 9）。`CreateNurbsCurve` ＋ `Add3DVertex` で
作った直後の曲線を読み戻すと **`(572→3531)` と正しい**のに、その曲線から
`CreateCustomObjectPath` で作った PIO のパスが上表のとおり退化している。**渡すものは正しい。**

**`4.54747e-13` は 2048〜4096 の double の 1 ULP** で、`2959 ÷ 25.4 × 25.4 − 2959` のような
**単位の往復で出る残り**と同じ大きさである（＝2 点の差を取ったら 0 になった痕跡）。

**直し方（round 10 で実機で直った）: 退化していたらパスを再生成して差し替える**
（`SetCustomObjectPath` ＋ `ResetObject`。`draw/StructuralMember` の `retryWithFreshPath`）。
46 本すべてが実体を持ち、実測もパス長どおり（2959）になった。**`NurbsSetPt3D` で座標を
入れ直すだけでは足りない**（入れ直しは反映されていて `(→3531)` と読めるのに、PIO のパスは
退化したまま）。

> **この直し方は、のちに仕組みごと撤去した**（「[自己修復を仕組みごと畳んだ](self-repair.md#自己修復を仕組みごと畳んだ)」）。
> 当座は機能したが、**差し替えると `ResetObject` がバウンドの `fOffset` を書き換える**ので、
> 利用者が階高を編集した瞬間に長さとして表に出る。**根本の直し方は「パスに Z を渡さない」**
> のほうで、そちらが入った時点でこの対症療法は要らなくなっていた。

**46 本が実体を持つと、伏図・軸組図の収まりが悪くなる**（round 10 で軸組図が 10 枚 → 13 枚、
伏図が新たに凡例と 3 枚重なった）。**図のほうが正しくなったので、誤っているのは縮尺の
見積もり**（`core::Layout`）である。パスが退化した柱のぶん図が小さく出ていたのが隠していただけで、
**M27 とは別の宿題**として残す。（用紙への収まりは
[M29](../m29-fit-overflow-jitter.md) で追った。）

**差し替えるパスは「挿入点からの相対」で渡す。** 生成の `CreateCustomObjectPath` は
**世界座標**のパスを取るのに、あとから差し替える `SetCustomObjectPath` は**相対**で取る
——世界座標のまま渡したら、長さは正しいのに材が挿入点の Z ぶん高い位置に出た
（実機 round 10 で `Z 1144→4103`。正しくは `572→3531`）。**この 2 つの非対称は SDK の
挙動なので、[SDK リファレンス](https://github.com/min-nano/vectorworks-developer-sdk-reference)の
`Findings/` へ書き残す**（「渡した 2 点の NURBS 曲線が PIO 化で潰れることがある」も同じ）。

**再生成した曲線は後始末する。** `CreateNurbsCurve` は曲線を**図面へ**作るので、差し替えに
使った曲線を PIO が引き取らなかったなら、消さない限り図面に残る——パスが退化する柱は実機で 46 本
あるので、放っておけば取り込みのたびにその数だけ原点に立った線が積み上がる。**引き取ったか
どうかは推測しない**——`GetCustomObjectPath` が返すのが渡した曲線そのものなら引き取られて
おり、消せば材のパスを消すことになる。違う実体なら VW が複製したということで、渡した曲線は
こちらの後始末である。差し替えに失敗したときは PIO が受け取っていないので必ず消す。
どちらだったかは診断の 1 行に残してある（実機でしか分からない挙動なので、次の周で結果を
記録する）。

**退化の検出と自己修復は横架材にも垂木にも組み込んだ。** パスを作る口（`draw/StructuralMember` の
`CreatePath`）と PIO 化の口（`CreateCustomObjectPath`）は柱と横架材で同じものなので、**同じ
事故は横架材でも起きうる**（実機で出たのは柱だけだが、出ていないことの保証にはならない）。
柱側にだけ検査があると、横架材や垂木のパスが退化しても件数が揃ったまま黙って通る。**垂木も
両端の Z が等しい**（勾配はストーリバウンドの offset 差が表す）ので、横架材と同じ測り方で
測る。（自己修復はのちに撤去し、退化の検出だけが開発ビルドに残る——
[自己修復を仕組みごと畳んだ](self-repair.md#自己修復を仕組みごと畳んだ)。）

**ただし測る値は部材の向きで違う**（`draw/StructuralMember.h` の `StructuralExtentKind`）。
鉛直材は**両端の解決済み絶対 Z の差**で測れるが、**水平材は両端の Z が等しいのが正常**なので
その差では全数が 0 になる——水平材は**PIO が実際に持っているパスの両端の距離**で測る
（「[水平材の実体は「スパン」では測れない](self-repair.md#水平材の実体はスパンでは測れないpio-のパスで測る)」。
当初は OIP の「スパン」で測るつもりだったが、**そのパラメータは実機に無かった**）。
**取り違えると診断が誤るだけでなく、正常な材のパスまで再生成する**ので、どちらで測るかは
命令ごとに明示する（`spec.extentKind`）。

**打ち切った直し方は増えた**（下記 1〜4）。**`{1, FL, …}` への書き換えは残してある**
（`parse/Column` の `buildColumnCommands`）——絶対 Z を動かさない書き換えなので害が無く、
「上端が上階のレベルにちょうど届く柱」を命令の側からも見分けやすい。

* **上端は上階のレベルに紐付いたまま**なので、**階高の変更に柱が追随する**という、この
  バインドの本来の値打ちを失わない。
* **絶対 Z は 1mm も動かない**（レベルを FL へ移し、offset をその差で取り直すだけ）。全
  フィクスチャで、パス長・下端／上端の絶対 Z が変わらないことを確認してある。
* **上階が最上階のときは何もしない**——種別が軒高＝自階に無いので、offset 0 でも正しく解ける
  （実機で 32 本が無事）。
* **上階の横架材天端が FL と同じ高さの階もそのまま**（上記「当階へバインドし直す方向へは
  倒さない」）。フィクスチャでは `グレー本モデルプラン2` の 70 本が該当する。
* 不変条件は `tests/ParseColumnTests.cpp` の
  `all_fixtures_bounds_span_the_column_height` に追加した——**offset 0 で上階を指してよいのは、
  種別が軒高のときか、上階の横架材天端が FL と同じ高さのときだけ**。

（この書き換えと不変条件は、実機 round 4 のあとで削除した——
[解析側に残っていた回避策も外した](after-fix.md#実機-round-4-のあと-解析側に残っていた回避策も外した上端の基準が-fl-になっていた)。）

**打ち切った直し方（もう一度やらないこと）**

1. **上端を当階のレベルへバインドし直す**（小屋束と同じ形にする）。**機能的な後退**である
   ——柱の上端が上階のレベルに紐付いているから階高を変えると柱が追随するのであって、当階
   基準の固定値に置き換えるとそれを失う。**「上階を指す言い方が残っていない」階に限っても
   採らない**（上記）。
2. **同じ指定のまま解かせ直す**（高さ基準を入れ直して `ResetObject`）。**実機で 46 本中
   0 本しか直らなかった**。人が OIP で直せる（ドラッグでも直る）のとは違う道筋だという
   ことで、**「再計算すれば直る」では説明が付かない**。
3. **下端を FL 基準へ振り替えて「階だけ違う同じ記録」を崩す**（round 4）。**46 本中 0 本**。
4. **上端の言い方を変える**（`{上階, FL, −40}`。round 5）／**レイヤの高さ基準で言い直す**
   （`{レイヤ, 0}`〜`{レイヤ, 2959}`。round 6）。どちらも**46 本中 0 本**で、実測は 572 の
   まま動かない。**高さ基準をどう書いても両端の Z は変わらない**ので、ここを触る直し方は
   もう試さない。

**測り方（ここが突破口だった）**: 構造材 PIO に**部材長のパラメータは無い**。名前で引ける
`CenterPointLength(長さ)` は別物で、実長 5333mm の通し柱で **100** を返す——これを長さだと
思って測っていた 2 周は、何も測れていなかった。使えるのは次の 2 つで、**その差が実体**である。

| パラメータ | 意味 |
| --- | --- |
| `StartElevation` | 解決済みの絶対 Z（始端） |
| `EndElevation` | 解決済みの絶対 Z（終端） |

**ローカライズ名で引いてはいけない**——「始端高さオフセット」は設定ダイアログ側の
`DialogStartElevation`（別物。`レイヤの高さ` 基準で 0 を返す）とぶつかる。この測定は
`draw/Column` の `recheckColumns` に**監視として残してある**（同じ事故がもう一度起きたら
件数で分かる）。

**SDK リファレンスの `Findings/` へ書き残すのは、実機で確かめが取れた次の 2 つだけである**
（[SDK リファレンス](https://github.com/min-nano/vectorworks-developer-sdk-reference)）:

* **渡した 2 点の NURBS 曲線が PIO 化（`CreateCustomObjectPath`）で退化することがある**
  （作った直後の曲線は正しいのに、PIO の中のパスが `(0,0,0) (0,0,4.5e-13)` になる）。
  直し方は `SetCustomObjectPath` で再生成したパスへ差し替えること。
* **`CreateCustomObjectPath` は世界座標のパスを取るのに、`SetCustomObjectPath` は挿入点から
  の相対で取る**（世界座標のまま渡すと材が挿入点の Z ぶん高く出る）。差し替えた曲線は
  **PIO が引き取る**（実機 round 13・14 で読み戻して確認）。

**「上階のレベルを、自階にもある種別＋ offset 0 で指すと自階へ解決される」は書き残さない。**
いったんそう見立てたが、round 5（offset を非 0 の `{上階, FL, −40}` にしても 46 本中 0 本）・
round 6（レイヤの高さ基準で言い直しても実測は動かない）で**反証済み**である——高さ基準は
そもそも両端の Z を決めていなかった。**反証済みの見立てを `Findings/` に固定すると、
「打ち切った調査は再調査しない」という運用のせいで将来の正しい調査まで止めてしまう。**
