# 直ったあとに外したもの（M27）

（柱が長さ 0 で描かれる（M27）は 5 ページに分けてある: [症状と最初の 10 周](README.md) → [自己修復をやめた](self-repair.md) → [原因を突き止めた](root-cause.md) → **直ったあとに外したもの** → [パスは 2D で渡す](path-2d.md)）

## 実機 round 3: **直った。対症療法を外した**

`67359ec`（両端に同じ Z を渡す）で取り込み直したところ、**柱の診断そのものが出なくなった**。

| | round 2（`6027b33`） | round 3（`67359ec`） |
| --- | --- | --- |
| 柱 | 197 / 197 | 197 / 197 |
| パスを作り直して直った柱 | **46 本** | **0 本（行が出ない）** |
| 所要 | 102.7 秒 | 79.1 秒 |

描き上がった柱のパスも `(0, 0, 0) → (0, 0, 5333)` と実体を持っている（`5905 - 572`）。
**「注意」に残るのは伏図の用紙収まりだけ**で、これは M27 とは別件である。

そこで**柱の対症療法（`retryWithFreshPath`）を外した**。両端に同じ値を渡す以上
`f(z) - f(z)` は常に厳密に 0 なので、**入力によらず再構築に乗る**——「効かない入力が
残っているかもしれない」たぐいの直し方ではないので、控えを残す理由が無い。
併せて**原因を突き止めるための計装を全部落とした**（①②③ の読み戻し・`StructuralMemberProbe`・
`ReadPioPathZ` ほかの読み口・`core::boundsDifferOnlyByStory` とそのテスト）。とくに
`boundsDifferOnlyByStory` は**外れた仮説を形にしたもの**なので、残すと次に読む人を同じ
間違いへ案内する。

**ただし「潰れの検出」は残す**（`collapsed` と `collapsedProbe`）。直ったから見張りを外す、
ではない——再発したときに**黙って繕わずに報せる**ためで、繕う側だけを外して見張りを残すのが
正しい形である。

**横架材・垂木の `retryWithFreshPath` は触っていない。** どちらもパスに水平の広がりがあって
退化しないので、この経路とは事情が違い、実機でも一度も走っていない——**直す根拠が無いものを
巻き添えで消さない**。

> **のちに撤去した。** 「事情が違うから触らない」は当時としては正しかったが、その後
> **繕った結果のほうが悪い**と分かった（差し替えがバウンドの `fOffset` を書き換える）ので、
> 水平材の側も畳んだ。経緯は「[自己修復を仕組みごと畳んだ](self-repair.md#自己修復を仕組みごと畳んだ)」。

## 実機 round 4 のあと: **解析側に残っていた回避策も外した**（上端の基準が FL になっていた）

高さが出るようになったところで実機を見た利用者から、**「`FL -40` の柱の終端が FL 基準に
なっている。横架材天端基準にしてほしい」**という指摘が出た。

出どころは `parse/Column` に残っていた**もう 1 つの M27 の回避策**である。

> 上端の offset が 0 になるときだけ、上階の **FL** を基準に取り直す（`{1, FL, floorOffset}`）。

これは「**`{上階, 横架材天端, 0}` という形が柱を潰す**」という見立てによるものだった
——`{上階, 軒高, 0}` は無事、`{上階, 横架材天端, 2374}` も無事、という実機の観察から
「自階にもある種別を offset 0 で指すと VW が自階のレベルへ解決してしまう」と読んだ。
**その見立ては外れだった**（真犯人はパスの 1 ULP。バウンドは白＝[reference#59](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/59)）。

**なぜ「無事に見えた」のかも、いま説明が付く。** この回避策は絶対 Z を変えないので、
`{1, 横架材天端, 0}` → `{1, FL, -40}` と書き換えても解決先は同じ 3531 のままだった。
そして**壊れるかどうかを決めていたのは Z の値そのもの**（3531 は mm↔インチの往復で戻らない）
なので、書き換えても壊れ方は変わらなかった——「効かない回避策」が「効いた場面もある回避策」に
見えていただけである。

**症状は「絵は合っているのに基準が違う」だった。** 絶対 Z が同じなので高さは正しく、数字にも
現れない。OIP に「FL −40」と出るところと、**階の横架材天端オフセットを変えても追随しない**
というふるまいにだけ現れる——**まさに「数字が揃っていても実機で見ないと分からない」型の
不具合**で、往復の前提そのものだった。

外したもの: 上の分岐と `kBoundIdentityTol`、そして**その形を全フィクスチャで強制していた
不変条件**（`tests/ParseColumnTests.cpp`）。不変条件は「上階を指す上端は横架材天端か軒高で
あること」へ入れ替えた——外れた見立てを試験で固定していると、正しい形に戻すほうが落ちる。

## SDK 側の答え: **バウンドは白**（リファレンス issue #59）

切り出した問いには実機で答えが出た（[issue #59](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/59)
→ [Findings「同じオブジェクトに 2 本のバウンドを書く」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)）。
**こちらの書き方に落ち度は無い**と確定したので、疑う先は残り 1 つに絞れた。

**本プラグインにとっての結論だけを書く**（バウンド ID の規則・複数バウンドの独立解決・
新規 PIO の既定状態といった **SDK の挙動そのものは上の `Findings/` にある**。
CLAUDE.md「ドキュメントの分担」）。

* **こちらの書き方は正しい。** 階だけが違う 2 本の `_Story` バウンドは畳まれず独立に解決され、
  `kStartBoundID`(0)＝下端・`kEndBoundID`(1)＝上端という当てはめも規則どおりだった。
* したがって**バウンドを疑うのはここで終わり**。残る容疑者はパスの側だけになった。

**#56 の「原因は `LayerElevation`」という帰属も訂正された**（本プラグインはその経路を
持たないため）。あちらの機構の記述自体は実測として正しいので、「`LayerElevation` で書くと
こうなる」として残っている。
