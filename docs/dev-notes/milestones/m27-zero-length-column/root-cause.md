# 潰れる原因を突き止めた（M27）

（柱が長さ 0 で描かれる（M27）は 5 ページに分けてある: [症状と最初の 10 周](README.md) → [自己修復をやめた](self-repair.md) → **原因を突き止めた** → [直ったあとに外したもの](after-fix.md) → [パスは 2D で渡す](path-2d.md)）

## なぜ潰れるのかは、まだ分かっていない

**上の直し方は対症療法である。** 「潰れていたら作り直して差し替える」で絵は出るが、
**なぜ潰れるのか**は分かっていない。分かっていないまま置くと、同じ形の柱が他の 4 モデルにも
47〜70 本ずつあるので、条件が少し変わるたびに同じ事故を踏み直すことになる。

**壊れる 46 本の形は、命令セットの全数検算で一意に決まる。** 実機へ行かずに決まることは
実機へ持っていかない。`buildDocument` を回し、197 本の柱のバウンドを**レベル定義から自前で
解いて**署名ごとに数えた（無 SDK・実データ）。

```
  46 本 | 1to2-柱   下端{階+0,"横架材天端",off=0}→572   上端{階+1,"横架材天端",off=0}→3531   ← 壊れる
  10 本 | 1to2-柱   下端{階+0,"横架材天端",off=0}→572   上端{階+1,"横架材天端",off=-937}→2594  ← 無事
   3 本 | 1to2-柱   下端{階+0,"横架材天端",off=0}→572   上端{階+1,"横架材天端",off=-1102}→2429 ← 無事
   2 本 | 1to3-柱   下端{階+0,"横架材天端",off=0}→572   上端{階+1,"横架材天端",off=2374}→5905  ← 無事
  29 本 | 2to3-柱   下端{階+0,"横架材天端",off=0}→3531  上端{階+1,"軒高",off=0}→6374           ← 無事
```

**46 本という数がぴたり一致し、この 46 本だけが持つ特徴は 1 つだった**——**上下端のレコードが
`storyOffset` 以外まったく同一**（どちらも `{横架材天端, offset 0}` で階だけ 0 と +1）。
同じレイヤの無事な柱は上端 offset が非 0、上階のレベルにちょうど乗るのに無事な 29 本は
上端のレベル種別が違う（`軒高`）。**「上階のレベルにちょうど乗るから」でも「階を跨ぐから」
でもない。** この述語は `core::boundsDifferOnlyByStory` に置いて無 SDK テストで押さえてある。

**次にやること: 直す前に測る。** これまで読んでいたのは `CreatePath` の `PathProbe`
（＝渡す直前の曲線。正しかった）と `MeasureDrawnMember`（＝全部終わったあと。潰れていた）
だけで、**その間の 3 手を一度も分けていない**。分ければ犯人が一意に決まる
（`draw/StructuralMember` の `StructuralMemberProbe`）。

| 読めるもの | 犯人 |
| --- | --- |
| ① `CreateCustomObjectPath` の直後から潰れている | `CreateCustomObjectPath`。**高さ基準は無関係**だと確定する |
| ① は正しく ② `SetObjectStoryBound` の直後で潰れる | `SetObjectStoryBound` がその場でジオメトリを触っている |
| ①② 正しく ③ `ResetObject` の後で潰れる | `ResetObject` の再構築（＝高さ基準の解決）。`GetObjectBoundElevation` の 2 値が理由を名指しする |

**③ はパスの差し替えより前に読む**——差し替えたあとでは「もともと潰れていたか」が消える。

併せて **`GetObjectStoryBoundsCount` / `GetObjectStoryBoundsAt` で実際に並ぶバウンド ID** を
出す——`ISDK.h` には `kPIOGenericStoryLevelBoundID = -3`（2017 年のストーリレベル対応 PIO 用）
という別の ID があり、**構造材 PIO が `kStartBoundID`(0) / `kEndBoundID`(1) を見ているのかは
未確認**である。`GetStoryObjectDataBoundHeight`（**オブジェクトを作らずにレコードを解ける**）
の値も並べて、「レコードの解き方」と「そのオブジェクトの解決結果」を分けて読めるようにする。

**`GetObjectBoundElevation` の "bound" はバウンディングボックスではない**（利用者の確認依頼で
SDK ヘッダに当たった）。`vs.py` の引数説明が "The identifier of the story bound." で、ISDK.h
でも `Has/Get/Set/DelObjectStoryBound` と同じブロックに並ぶ（2221〜2229 行）。**水平材・
傾斜材でも「そのバウンドが解決された絶対 Z」**を返し、材の外接とは無関係である。

## 実機 round 1 の測定: **潰しているのは `CreateCustomObjectPath`、直しているのは `ResetObject`**

3 地点を分けて測った結果（`5516866`。スキップフロア 197 本）:

```
潰れた地点: ①生成直後 46 / ②基準書込後 46 / ③リセット後 46 本

潰れた 1 本目[1to2-柱 下端{階+0 "横架材天端" off=0} 上端{階+1 "FL" off=-40} あるべき長さ=2959]
  ①生成直後 4.54747e-13(2点) ②基準書込後 4.54747e-13 ③リセット後 4.54747e-13
  解決済みZ 始端=572 終端=3531／検算 始端=572 終端=3531
  バウンドID一覧: 2 個 [id=0 解決Z=572] [id=1 解決Z=3531]

対照 レベル種別違い[2to3-柱 … あるべき長さ=2843]
  ①生成直後 0(2点) ②基準書込後 0 ③リセット後 2843        ← **無事な柱も ①② では 0 長**
  解決済みZ 始端=3531 終端=6374／検算 始端=3531 終端=6374
  バウンドID一覧: 2 個 [id=0 解決Z=3531] [id=1 解決Z=6374]
```

**読み取れたことは 3 つ。**

1. **バウンドは完全に正しい。** 解決済み Z（572 / 3531）は命令の意図どおりで、オブジェクトに
   依らない検算とも一致し、ID は 2 個で 0 と 1。**0 長になる 2 条件（解決 Z の一致／バウンド
   0 件）のどちらにも当たらない**——SDK 側の「バウンドは白」（[SDK 側の答え](after-fix.md#sdk-側の答え-バウンドは白リファレンス-issue-59)）が、こちらの実データでも
   裏付けられた。**高さ基準を触る直し方はもう無い。**
2. **`CreateCustomObjectPath` がパスを潰すのは普遍である。** 対照（＝最後まで無事な柱）も
   **① と ② では 0 長**だった。世界座標で正しい 2 点を渡しても、PIO の中のパスは生成直後に
   潰れている。**「潰れているかどうか」は ① では分かれない。**
3. **分かれ目は ③ の `ResetObject` が作り直してくれるかどうか。** 対照は `0 → 2843` と
   解決済みバウンドから再構築されたのに、46 本は `4.54747e-13 → 4.54747e-13` のまま動かない。

**いま見えている唯一の差は「① のパスが厳密に 0 か、極小の非ゼロ（`4.54747e-13`）か」**である。
`4.54747e-13` は 2048〜4096 の double の 1 ULP で、**再構築が「パスは既に有効」と判断する
だけの大きさ**にも読める。次の周では**①② で潰れていた柱を全数で数え**（無事な柱も含めて）、
**潰れた柱と同じレイヤの無事な柱**を対照に並べて、この差が一意かを確かめる。

> **読み分け表を訂正する。** 当初は「①＝③ なら犯人は `CreateCustomObjectPath`」としていたが、
> **無事な柱も ① では 0 長**なので、① だけでは犯人を決められない。正しくは
> **「③ で再構築されるか否か」**が分かれ目で、①② はその前提条件を見るためのものである。

### 仮説 B: **`ResetObject` は「ちょうど潰れているパス」だけを作り直す**

round 1 で残った唯一の差——**① が厳密に 0 か、1 ULP ぶんだけ 0 でないか**——をそのまま
原因として読むと、観測が両方とも説明できる。

* `ResetObject` の再構築が「パスが**退化している**ときだけ解決済みバウンドから作り直す」
  という条件付きなら、**厳密に 0 長**のパスは退化と見なされて作り直され（対照の
  `0 → 2843`）、**1 ULP でも 0 でない**パスは「呼び出し側が与えた有効なパス」と見なされて
  そのまま残る（46 本の `4.54747e-13 → 4.54747e-13`）。
* だとすれば真犯人は「バウンド」でも「`ResetObject`」でもなく、**`CreateCustomObjectPath`
  が世界座標を局所座標へ落とすときの丸め**である。0 になりきらなかった柱だけが、
  再構築の対象から外れて長さ 0 のまま残る。

**検算はこう置いた**（`draw/Column.cpp`）。① の**両端の生の Z を `%.17g` で持ち帰り**、
「ちょうど 0 長（`z0 == z1`）」と「0 でない微小長」を全数で数える。仮説 B が真なら
次の 2 つがぴたりと一致し、偽ならどちらかが必ずずれる。

* `ちょうど0長 ＋ 0でない微小長 ＝ 測れた本数`
* `0でない微小長 ＝ 最後まで潰れていた本数`

**一致したら、直し方は「パスを作り直して差し替える」対症療法ではなく「渡す Z を
退化させる（＝両端を厳密に等しくする）」か「そもそも丸めが出ない渡し方にする」へ変わる。**

## 実機 round 2 の測定: **原因が確定した**

round 2（`6027b33`）で件数が揃い、仮説 B が裏取りされた。

| 測った値 | 結果 |
| --- | --- |
| 測れた柱 | 197 本 |
| ① 生成直後に潰れていた | **197 本（全数）** |
| ② 基準書込後に潰れていた | **197 本（全数）** |
| ③ リセット後も潰れていた | 46 本 |
| レコードが階以外同一の柱 | **0 本中 0 本**が潰れた |

**まず、当初の仮説（上下端のレコードが階以外同一の柱だけが潰れる）は死んだ。** 実機の
モデルにはその形の柱が **1 本も無い**のに 46 本が潰れている。ローカルのフィクスチャ
（`スキップフロア_サンプル.ifc`）で 46 本がぴたりと一致して見えたのは、**別のモデルでの
偶然**だった——件数が合ったことを根拠にしてはいけない、という例そのものである。

**そして分かれ目は、生成直後のパスがちょうど 0 長かどうかだった。** 同じレイヤ・同じ下端
バウンドの対を並べると、差が 1 つに絞れる。

| | 下端 | 上端 | ① 生成直後 | ③ リセット後 |
| --- | --- | --- | --- | --- |
| 潰れた | `階+0 "横架材天端" off=0` → 572 | `階+1 "FL" off=-40` → **3531** | **`4.54747e-13`** | `4.54747e-13`（**作り直されない**） |
| 対照（同じレイヤ） | `階+0 "横架材天端" off=0` → 572 | `階+1 "横架材天端" off=-1102` → 2429 | **`0`** | `1857`（作り直された） |
| 対照（レベル種別違い） | `階+0 "横架材天端" off=0` → 3531 | `階+1 "軒高" off=0` → 6374 | **`0`** | `2843`（作り直された） |

どの柱もバウンドは正しく解決されている（検算とも一致・ID は 0 と 1 の 2 個）。違うのは
**① のパスがちょうど 0 か、1 ULP だけ 0 でないか**だけである。

### 1 ULP はどこから出るのか: **mm ↔ インチの往復**

`4.54747e-13` の出どころも当たりが付いた。**mm の値をインチへ直して戻す**
（`v / 25.4 * 25.4`）と、整数 mm の 12.6%（0〜10000mm で 1257 個）が**元の値に戻らない**。
そして実機に出ていた Z のうち、**戻らないのは 3531 だけ**である。

| Z（mm） | `v / 25.4 * 25.4 - v` |
| --- | --- |
| 572 | 0 |
| **3531** | **-4.547473508864641e-13** |
| 2429 | 0 |
| 6374 | 0 |
| 5905 | 0 |

観測された残差と**ビット単位で一致**する。VW が内部でインチ系の単位を使っているとすれば、
`CreateCustomObjectPath` が世界座標を取り込んでパスを平らに潰すときに、**端点の Z が往復で
戻らない柱だけ**残差が残る、と読める。潰れていた 46 本が「上端が 3531mm の柱」に固まって
いたこととも合う（当初疑っていた「レコードの形」ではなく、**レベルの Z の値**が当たりだった）。

> **この単位往復は推測である**（VW の内部単位を直接見たわけではない）。SDK 側の裏取りは
> [リファレンス issue #61](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/61) へ出した。
> **ただし直し方はこの推測に依らない**（下記）。

### 直し方: **両端に同じ Z を渡す**（`f(z) - f(z)` は厳密に 0）

残差がどの単位系のどんな丸めから出ていようと、**2 点に同じ値を渡せば差は厳密に 0 になる**。
だから柱のパスも**横架材と同じ形**——両端とも下端の Z——で渡す（`draw/Column.cpp`）。
高さはストーリバウンドが支配し、その解決は実機で命令どおりだと確認済み
（[reference#59](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/59)）。

**これは「パスに高さを持たせると二重に適用されうる」という横架材の注意（`draw/StructuralMember.h`
冒頭）と揃う形でもある。** 柱だけが例外だと思っていたのが、そもそも思い違いだった
——`CreateCustomObjectPath` は柱のパスの高さも受け取っていなかった。
