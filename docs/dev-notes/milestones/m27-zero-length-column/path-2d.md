# パスは 2D で渡し、3D はオブジェクトに作らせる（#119 の次）

（柱が長さ 0 で描かれる（M27）は 5 ページに分けてある: [症状と最初の 10 周](README.md) → [自己修復をやめた](self-repair.md) → [原因を突き止めた](root-cause.md) → [直ったあとに外したもの](after-fix.md) → **パスは 2D で渡す**）

**#119 で分かったことを、そのまま設計へ引き取った。** 「両端の絶対 Z の差が 0 のパスを渡すと、
構造材オブジェクトが高さ基準とオフセットから 3D のパスを再生成する」——これは**2D のパスを
渡されたときに機能することを想定した作り**と読むのが自然である（利用者の指摘）。構造材ツール
は平面に線を引いて使う道具なので、3D 化を自分で行うのは当たり前のふるまいで、こちらが Z を
渡していたことのほうが筋違いだった。

そこで**パスから Z を除外した**（`draw/StructuralMember` の `CreatePath` は `core::Vec2` しか
取らない）。横架材・柱・垂木のいずれも、渡すのは平面座標だけである。

**これで「高さを 2 か所で指定する」形が消えた。** 従来は同じ高さを

* PIO のレコード（上下端のストーリバウンド＝ `SetObjectStoryBound`）と、
* パスの頂点の絶対 Z

の**両方**へ書いていた。どちらも VW が読むわけではない——読まれるのはバウンドだけで、パスの
Z は捨てられる——のに、**捨てられ方の丸め**が残った柱 46 本が長さ 0 になった（[round 2](root-cause.md#実機-round-2-の測定-原因が確定した)）。
指定が 1 か所になれば、その残差が出る余地は原理的に無い。M27 の「両端に同じ Z を渡す」は、
同じ結論の**一歩手前**だったということでもある（差を 0 にするのではなく、Z を渡さない）。

**形としては M7 へ戻った。** M7 の横架材は**2D ポリライン**のパスで描画されていて、高さは
バウンド（横架材天端・オフセット 0）だけで正しく決まっていた（ローカル確認済み）。M8 で
`Add3DVertex` が見つかってパスを 3 次元の曲線に統一したときに絶対 Z も持たせたが、その Z は
最初から要らなかった。**「Z に 0 を渡してはならない」という当時の注意も撤回する**——3D 座標が
絶対 Z として渡るのは事実でも、**構造材 PIO はパスの Z を受け取っていない**（round 1 で
197 本全数が生成直後に 0 長だった）。

**代わりに監視を追加した**（`draw/StructuralMember` の `checkElevation`）。高さを決めるのが
バウンドだけになった以上、**その解決が意図とずれても件数には一切出ない**——本数もスパンも
揃ったまま、材が揃って違う高さに並ぶ。これは「数字が合っていても描画結果が破綻している」型そのもの
なので、描画された両端の絶対 Z（`StartElevation` / `EndElevation`）を読み戻して命令と
照合し、**ずれた本数と 1 本目の実測を診断へ載せる**。横架材・柱・垂木の 3 要素に組み込んで
ある（水平材でも読むので、`DrawnMemberSize` は kind に依らず両端の Z を返すようにした）。

**実機で確かめること**は 2 つ: 材が正しい高さに立っているか（数字では上の監視が、描画結果では
利用者が確認する）と、**傾斜材（登り梁・垂木）の勾配が二重にならないか**——勾配はもともと
バウンドの offset 差だけで表していたので変わらないはずだが、パス側の入力が変わった以上
確かめる価値がある。
