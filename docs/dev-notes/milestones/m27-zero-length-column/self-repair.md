# パスを差し替える自己修復をやめた（M27）

（柱が長さ 0 で描かれる（M27）は 5 ページに分けてある: [症状と最初の 10 周](README.md) → **自己修復をやめた** → [原因を突き止めた](root-cause.md) → [直ったあとに外したもの](after-fix.md) → [パスは 2D で渡す](path-2d.md)）

## 水平材の実体は「スパン」では測れない——PIO のパスで測る

**[最初の調査](README.md)の「水平材は OIP の『スパン』で測る」は外れだった。** 実機フィードバック round 1
（PR #124、build 710b26a、macOS）の診断に、横架材と垂木で毎周この 1 行が出ていた。

````
横架材の診断: 「長さ」パラメータを引けませんでした（候補: CenterPointLength(長さ)）。
垂木の診断: 「長さ」パラメータを引けませんでした（候補: CenterPointLength(長さ)）。
````

**絵は欠けていない**（横架材 266/266・垂木 54/54 が描けている）。言っているのは
**検査そのものが一度も動いていない**ということである。

* universal 名 `Span` もローカライズ名「スパン」も**引けなかった**——構造材 PIO に
  そのパラメータは無い。「長さ」を含むパラメータの一覧にも `CenterPointLength` しか
  出ておらず、それは部材長ではない（実長 5333 の柱で 100。[「測り方」](README.md)）。
* 引けないので `DrawnMemberSize::found` が false のまま早期 return し、
  **`collapsed` は永久に false**。潰れた材の件数が出ないだけでなく、
  **パスを作り直す自己修復（`retryWithFreshPath`）の引き金も引かれない**——こちらは検算では
  なく**描画の一部**（`draw/Verify.h` の「囲まない」側）なので、**本番ビルドでも効いていな
  かった**。

**代わりに測るのは PIO が実際に持っているパスの両端の距離**（`draw/DrawUtil` の
`PioPathChord`。`GetCustomObjectPath` ＋ `NurbsGetNumPts` ＋ `NurbsGetPt3D`）。これが
「描かれた実体」そのものであることは SDK 側で確かめが取れている——`ResetObject` は
**解決済みストーリバウンドからパスを作り直し**（始点が ID 0 の解決 Z・終点が ID 1 の
解決 Z）、**水平成分は渡したパスのまま残す**（[Findings「Parametric
Objects」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)
の「高さ・実体を最終的に決めるのは…」／「水平成分が 1e-7 以上ある部材は…」）。同 Findings が
検算の手立てとして挙げているのもこの読み方である。

**パラメータを探し直す道は採らない。** 名前が違うだけかを確かめる手掛かりは
`DescribeSizeParams` の一覧で、そこに「スパン」を含む名前は 1 件も出ていない。**無い名前を
引き続けるより、在る値（パス）を読むほうが確かで、しかも名前の解決（パラメータ表の走査）が
1 本につき 2 回減る。**

**その後 SDK リファレンス側で「無い」が確定した**——
[issue #95](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/95) →
[PR #96](https://github.com/min-nano/vectorworks-developer-sdk-reference/pull/96)。
パラメータ表 **181 件の全数列挙**・SDK の全数検索・実運用の全数確認が独立に同じ答えを出して
いて、[Findings の「打ち切った調査: 構造材 PIO から『スパン』『部材長』をパラメータで読む」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)
に畳んである（**再調査しない**）。こちらが残していた疑問にも答えが付いた:

* **`CenterPointLength(長さ)` の正体はセンターマーク（作図記号）の線の長さ**【推定】。
  パラメータ表の索引 153〜160 が `CenterPointMarker*` の並びで、その直後に「長さ」と
  「間隔」が来る。既定値 100 が実長 5333 の柱でそのまま出ていたのは、部材と連動して
  いないからである。**ローカライズ名だけで当てない**——引き当てたら値を実測と突き合わせる。
* **OIP に見えている「スパン」の欄はパラメータに紐づかない計算値**【推定】で、読み書き
  できる値としては存在しない。**欄の正体を確かめに行く必要も無い**——読む道が無いことは
  確定していて、正体が何であっても実装は変わらない。

**自己修復はどこにも残さない（武装している呼び出し側が 0 になった）。** 当初は「水平材では
残す」としていたが、**差し替えたあとに何が残るかを勘定に入れていなかった**ので改めた。

* **帯に入る経路がもう無い。** M27 の 46 本は「作り直しが残した 1〜2 ULP の長さが
  `(0, 1e-7)` の死角に入り、以後作り直してもらえない」というもの。柱はパスに Z を渡すのを
  やめて長さが**厳密に 0** になり必ず作り直される。水平材は実寸の水平成分を持ち、作り直しは
  **水平成分をビット一致で残す**ので、やはり帯に入らない（同 Findings「水平成分が 1e-7 以上
  ある部材は…」。72 ケースで確認済み）。
* **差し替えると、あとで壊れる。** `ResetObject` が差し替えたパスに合わせて**バウンドの
  `fOffset` を書き換える**ので、上端が「上階のレベルちょうど」から「上階のレベル −2959」の
  ような値に化ける。階への追従自体は続くが**何に揃えていたか**が壊れ、**利用者が階高を編集
  した瞬間に長さとして表に出る**（同 Findings「差し替えで `fOffset` を書き換えられた部材は、
  階を動かすと長さが変わる」。実測: 階を +100 動かすと本来 3059 になるべき部材が 100）。
  同 Findings も「**差し替えを対症療法に使わない**」と明記している。
* **残る唯一の 0 長の経路**（高さ基準を 1 本も書けないまま `ResetObject` を呼ぶ）は向きを
  問わず起こりうるが、**本番ビルドでも件数が出る**（`StructuralFailures::bound` ＝「高さ基準
  を図面へ書けなかった材 N 本」。`VW_DRAW_VERIFY` の外）ので、黙って見逃すことにはならない。
* **潰れの検出は開発ビルドでは引き金に依らず走る**ので、武装を外しても診断は 1 つも
  失われない（`draw/StructuralMember` の `measureDrawn`）。

**仕組みそのものは役目を終えたので、続けて撤去した**（下記）。

## 自己修復を仕組みごと畳んだ

武装している呼び出し側が 0 になった時点で、`retryWithFreshPath` ／ `SetCustomObjectPath` に
よる差し替え ／ `repairedByPath` ／ `StructuralFailures::repaired` ／ **本番側の測定**が
まとめて死んだ。残すと**効いているように見える死んだコード**になるので畳んだ。

* **`DrawStructuralMember` の読み戻しはまるごと開発ビルドだけになった。** 以前は「検算」と
  「自己修復の引き金」という 2 つの理由で測っていて、後者のために本番でも半分測っていた。
  繕うのをやめたので**測る理由は検算だけ**になり、本番では材 1 本あたりのパラメータ走査と
  パス読みがまるごと無くなる（数百本ぶん）。
* **`MeasureDrawnMember` / `DrawnMemberSize` / `PioPathChord` も `#if VW_DRAW_VERIFY` の中へ
  入った。** 呼び出し側が全部そちらにしかいなくなったため。ついでに「本番の水平材では
  絶対 Z を読まない」という分岐も消えた——本番で呼ばれないなら、分ける理由が無い。
* **報せる側は 1 つも減っていない。** 潰れの件数（`collapsed`）と 1 本目の実測
  （`collapsedProbe`）は開発ビルドで従来どおり出るし、**高さ基準を書けなかった本数
  （`bound`）は本番でも出る**——「残る唯一の 0 長の経路」はそこで捕まる。

**教訓は `src/draw/Verify.h` にも書いた**: **「絵を変える」は「絵を良くする」ではない。**
自己修復は「外すと潰れた材がそのまま残る＝絵が変わる」という理由で「囲まない」側に置かれて
いたが、繕った結果のほうが悪かった。囲まない側へ置くときは、その変え方が正しいかまで見る。

**本番ビルドの水平材では両端の絶対 Z を読まない。** そこでは高さの検算が畳まれていて
使い道が無いのに、名前の解決はパラメータ表を 1 本につき 2 回舐める（材は数百本ある）。
読むのは**開発ビルド**と**鉛直材**だけにした。
