# 往復をモードレスのパレットで回す（M24）

**動機は M23 の結び目そのもの。** M23 は「投稿したら戻り、次の周は人がメニューを 1 回押して
始める」で落ち着いた。プラグインが自分で待つとモーダルのダイアログが図面を塞ぎ、絵を見る
ために回している往復で絵が見られなくなるからである（M23「ビルドを待つのをやめた」）。
そのとき残した選択肢が「モードレスなパレットへ載せ替える」で、**完全な無操作と図面の操作を
両立する道はこれしか無い**と書いてあった。M24 はそれを行い、あわせて**往復の終わり方を
Claude の合図にした**——「一度 PR ビルドを回したら、エージェントが要らないと言うまで
アップデートとフィードバックが続く」状態が目標である。

## 何をどう割ったか

| | 中身 | どこ |
| --- | --- | --- |
| 駆動 | 合図を見る → 新しいビルドを見る → 入れて本体を降ろす → 取り込み（本体）→ 投稿、と止まる条件 | `src/FeedbackLoop`（**殻**・無 SDK・テストあり） |
| 殻の実物 | 本体への問い合わせ・同梱スクリプト・尋ねないアップデート（`PollDevBuildWith`）・パレットの表示 | `src/FeedbackLoopHost`（殻・SDK 依存） |
| パレット | 登録と JS の取り次ぎ。**判断は持たない**（JS のタイマーで `homeskz.tick()` を呼び、返った文言を並べる） | `src/Extensions/ExtFeedbackPalette` ＋ `resources/<vwr>/html/index.html`（殻） |
| 本体が殻へ見せるもの | 往復の記憶（`vw_payload_loop_status`）と「止めた」の受け口（`vw_payload_loop_end`） | `src/PayloadAbi.h` v3 / `draw/Feedback` |
| 合図 | PR が open か・自分の投稿より後に `control=stop` が付いたか | `scripts/vw-feedback.*` の `loop-control` |

**駆動が殻にあるのは、入れ替えが殻でしか起きないから**（本体は自分を降ろせない。M21）。
これは「殻に実処理を書かない」の例外ではなく、殻に残る唯一の実処理である自動アップデートの
一部——「新しいビルドが出たら入れて取り込みを頼む」という、往復のための顔である。取り込み
そのものは相変わらず本体が行う。UpdaterFlow と同じく副作用を host の後ろへ出したので、
状態機械は無 SDK でテストできる（`tests/FeedbackLoopTests.cpp`）。

## なぜ Web パレットか（そして何が未確認か）

SDK でモードレスに出せる口は `IExtensionWebPalette` だけである（SDK リファレンス
[Findings「モードレス（非モーダル）なパレット」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layout%20Dialogs.md)。
`RunDialogLayout` はモーダル、`RegisterDialogForTimerEvents` はダイアログのタイマーで、
SDK に遅延実行の口は無い）。中身は HTML/JS で、**JS の `setInterval` がこのプラグインで
唯一の周期的な駆動源**になる。JS → C++ は `AddFunctionPromiseSync` で登録した関数が
`OnFunction` に届き、`Resolve` で Promise を返す（`Sync` はメインスレッド＝SDK と本体を
触ってよい）。

**この拡張種別は実機未確認である**（Findings はヘッダ根拠と構文チェックまで）。本リポジトリで
SDK の調査はしない決まりだが、Findings に載っている宣言を `ci-debug` の `sdk-ls` で写し取り、
その範囲で書いた。確かめること: (1) 開いて図面を操作しながら見えるか (2) タイマーからの
呼び出しが届き続けるか (3) `SetWebPaletteVisibility` で表示・非表示が切り替わるか (4)
取り込み中（進捗ダイアログの `DoYield`）に届く呼び出しが無視されるか（駆動は再入を弾く）
(5) `.vwr` の `html/index.html` が `GetStandardURL` の既定で読まれるか。**効かなくても手動の
周は壊れない**——メニューからの取り込みは M23 のまま動くので、この PR の往復自体でそれを
確かめられる。分かったことは Findings へ足す。

## 止まる条件と、記憶を消さないこと

止まる入口は 3 つ——人がパレットで止める・Claude が PR に
`<!-- homeskz-ifc-feedback v1 control=stop -->` を投稿する・PR が閉じる（マージを含む）。
加えて入れられなかった・殻まで変わった・取り込めなかった・投稿できなかったときも止まる。
**確認そのものができなかった（オフライン等）ときは止めない**（次の周期にもう一度見る）。

**どれも記憶は消さない**（`FeedbackSession::loop` を下ろすだけ）。M23 で「送らない」が記憶を
消すのをやめたのと同じ理屈で、止めたことが「ファイルと設定を選び直し」に化けるのは割に
合わない。人がメニューから取り込みを実行すれば続きの周として走り、そこでまた回り出す。
だから止めるボタンは往復を止めるだけで、取り込みのダイアログには足していない。

**合図は「自分の投稿より後」だけを読む。** `post` が返す `created_at` を記憶し
（`lastPostedAt`）、`loop-control` の `since` に渡す。切らないと一度読んだ古い合図を毎回
読み直す。プラグイン自身が投稿する「終えました」（`control=ended`）を合図と読み違えない
よう、`control=stop` の直後が空白か `-->` のものだけを合図とする。

**Claude の合図には返事をしない。** 人が止めたときと入れ替えに失敗したときだけ PR へ
「終えました」を載せる（読む側が push しても周が来ないことを知るため）。

## 合図は行であって、文中の引用ではない（実機 round 1 で判明）

**round 1 を投稿した直後、パレットが「往復を終えました（Claude が「もう要らない」と合図
しました）」になった。** 誰も合図していない。犯人は**プラグイン自身の投稿**だった——
コメントの末尾には「往復がもう要らなくなったら `<!-- … control=stop -->` を含むコメントを
投稿してください」という案内が入っており、合図を探す側は**本文のどこかにその目印があるか**
しか見ていなかった。しかも合図を探す範囲の起点（`since`）は自分が投稿した時刻なので、
**1 通目に読むのは自分のその投稿**である。つまりこの仕組みは、**始めた瞬間に自分の言葉で
自分を止めていた**。

**「書いてある」と「合図である」は別物である。** 目印を本文のどこかで拾う作りは、その
目印を説明・引用・転載した文章をすべて合図にしてしまう——案内文・PR 本文・レビューでの
言及・過去のコメントの引用、どれも同じ形をしている。**合図は「その行だけの行」**と定義し
直した（`scripts/vw-feedback.*` の `control_of_comment` / `Get-CommentControl`）:

1. **行がまるごと目印**であること（前後は空白だけ）。文中に引用したものは合図でない。
2. **``` で囲まれた中は読まない**（例として貼ったものを合図にしない）。
3. **プラグイン自身の投稿は合図にしない**（`round=` / `control=ended` の目印を持つ本文）。

3 は 1 と 2 があれば要らないが、**「自分の言葉で自分が止まる」を二度と起こさない**ための
歯止めとして重ねてある。書く側も直した——本文へ生の目印を置かず、`control=stop` と綴りだけ
書いて書き方は CLAUDE.md へ送る（`parse/Feedback.cpp`。読む側・書く側の二重の歯止め）。

**教訓は目印の設計そのものにある。** 機械可読な目印を人の読む文書へ埋めるなら、**その目印を
語れる場所**を必ず残すこと。「本文に含まれるか」で判定する目印は、自分について書けなくなる。

## 実機で確かめられたこと（round 1）

上の誤検知と引き換えに、**実機未確認だった拡張種別がひととおり動くことは確かめられた**
（macOS / VW 2026）。パレットのスクリーンショットで確認:

| 確かめたこと | 結果 |
| --- | --- |
| `IExtensionWebPalette` がモードレスに開くか | **開いた。** 図面（軸組図のシート）を表示したまま、パレットが手前に浮いている |
| `SetWebPaletteVisibility` で表示できるか | **できた。** 投稿できた周の終わり（`ArmFeedbackLoop`）で自動的に開いた |
| JS のタイマーから C++ へ届くか | **届いた。** `homeskz.tick` が返した見え方（phase / message / branch / round / build）がそのまま描かれている |
| 見え方の JSON を JS が読めるか | **読めた。** 「ブランチ: … ／ round 1 (a618af6)」がパレットに出ている |
| ボタンの活殺 | **効いた。** 止まった状態なので「今すぐ確認」「往復を止める」が無効、「閉じる」だけ有効 |

**残っているのは「自動で次の周が走るか」だけ**（新しいビルドを見つけて入れ替え、取り込み、
投稿する一周）。これは合図の誤検知で止まっていたため、まだ 1 度も走っていない。
分かったことは SDK リファレンスの Findings「モードレス（非モーダル）なパレット」へ足し、
【実機未確認】の注記を外すこと。

## 分かったこと・決めたこと

- **殻の sha を「いま動いている版」に使ってはいけない。** 本体だけを入れ替えたあと、殻に
  コンパイルされた sha は古いままである（殻は起動時にしか読み直されない）。それを基準に
  すると `q-dev` は毎回「新しいビルドがある」と言い、同じビルドを周ごとに入れ直す。
  `PollDevBuildWith` は `q-dev` の `installed=`（ディスク上の版）を基準にした。既存の
  `Auto` の経路（メニュー）は据え置いてある——そちらは人が押したときにしか走らないので、
  入れ直しは無駄だが害は無い。
- **GitHub を見る間隔は 1 分。** CI の dev ビルドは push から十数分かかるので十分に早く、
  同梱スクリプトの起動（1〜2 秒）でメインスレッドが止まる回数も許容できる。JS のタイマーは
  5 秒で、間隔に満たない tick は現在の見え方を返すだけ。
- **パレットの HTML は殻の ID に入れない。** `.vwr` の文字列と同じで、殻へコンパイル
  されるものではない。起動時に読み込まれた `.vwr` が入れ替えに追随するかは未確認だが、
  追随しなくても古い見た目のまま動くだけで、入れると HTML を直すたびに再起動を強いる。
- **前の周の図は自動では戻らない。** プログラムから取り消しを掛ける手立ては無い
  （Findings「Undo」。issue #23 で確定）。自動の周は前の周の上に重ねて描き、PR コメントの
  「図面の状態:」がそれを言う。読む側はそれを前提に数字を読む。

## 往復の相手は PR であって、ブランチではない（#137 → #138 で判明）

マージされた PR のブランチを main から作り直し、**同じブランチ名のまま新しい PR** を立てる
運用で、新しい PR のビルドが往復に乗らなくなった。更新の経路（`q-dev` とブランチでの照合）は
正しく新しいビルドを見つけていたが、往復の記憶（`core::FeedbackSession`）が**ブランチでしか
見分けていなかった**ため、閉じた前の PR 番号を持ったまま「同じ往復の続き」と読まれた。
パレットは PR の状態を先に確かめて「マージされました」で止まるので**ビルドを取りに行く段まで
進まず**、メニューから押すと続きの周として**閉じた前の PR へ投稿**していた。

直し方: 手で押した周の入口で記憶の PR の状態を `loop-control` で確かめ、merged / closed なら
**新しい往復の 1 周目**に戻す（`core::restartedFeedbackSession`。持ち越すのは投稿先の
リポジトリと伏せ字の好みだけ）。1 周目のダイアログはブランチから open な PR を引き直すので、
宛先は新しい PR になる。**確かめられなかった（オフライン）ときは記憶を消さない**——止まる
入口と同じく、不確かなときは記憶を消す側へ倒さない。パレット（殻）は触っていない——閉じた
PR で止まるのは従来どおりで、人がメニューを 1 回押せば新しい PR で回り出す。
