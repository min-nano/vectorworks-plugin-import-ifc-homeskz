# 「用紙に収まらなかった」が周ごとにぶれる（M29）

**症状は「用紙・マスへの収まりの判定だけが周ごとに動く」。** PR #124 の実機フィードバック
（macOS・A3 横・同じ IFC）で、**用紙の割り付けはまったく同じ**
（`用紙 420×297 / 印刷可能 420×297 / 凡例 22 / 建物 16250×9880 → 用紙上 325×198 / 縮尺 1/50`）
なのに、はみ出しの件数が round 1 の 1 枚から round 2 の 2 枚へ増え、round 1 に無かった
「凡例と重なった伏図 1 枚」「割り当てたマスに収まらなかった軸組図 6 枚」が出た。
**2 つのビルドの差分は `draw/StructuralMember` だけ**で、割り付けにも描画にも触れていない。
要素の内訳は両周とも 18 種すべて命令数＝描けた数で完全に一致している。

**割り付けが決定的なのに判定だけが動くなら、疑うのは測る側である。** 収まったかは
`GetObjectBounds` が返すビューポートの外形で決まり、**この呼び出しが返すのは
「いま図面に何が在るか」ではなく「最後に描画したときの外形」**である。伏図の 2 巡目には、
その前提が 2 か所で崩れていた。

- **中身を変えた後に再描画せずに測っていた。** 2 巡目の頭で
  `applyShearWallLayerScale`（いまは `draw/Sheet` の `applyPlanLayerScale`）が
  耐力壁レイヤの縮尺を伏図の縮尺へ揃える（伏図記号は用紙基準シンボルなので、
  **レイヤ縮尺が変わると図の中の大きさが変わる**）。ところがビューポートを再描画するのは
  「仮の縮尺と確定した縮尺が違ったとき」だけで、今回のように両者が同じ 1/50 に
  落ち着くと**1 巡目に描画した外形のまま測る**。再描画が VW の都合で起きたか
  起きていないかで測る値が変わるので、**図面の直前の状態（前の周を取り消した
  直後か・開いたばかりか）で答えが動く**。
- **タグを置く前の外形で判定していた。** 用紙に載るのは「ビューポート＋その注釈」なのに、
  収まったかはデータタグを置く前に測った外形で判定していた。位置合わせ（`delta`）だけは
  タグより先に測らなければならない（タグの位置合わせがビューポートの位置に依るため。
  `draw/DrawUtil` の `MoveViewportBy`）ので、**測るのは 2 回に分ける**しかない
  ——位置は前、収まりは後。
- **凡例との重なりだけ遊びを引いていた。** はみ出しの判定は `枠 + kFitTol` と比べるのに、
  凡例との重なりだけ `凡例の左端 - kFitTol` と比べており、**ぴったり接した図を「重なった」と
  数えていた**。遊びは「ぴったりの図をはみ出したと数えない」ためのものなので、向きは
  加える側でなければならない（`draw/DrawUtil.h` の `kFitTol`）。

**そして、件数しか出ていなかったのが切り分けを止めていた。** 「用紙に収まらなかった伏図
2 枚」は原因を何も示していない——見積もりが用紙 2〜3mm ぶん足りないのか、前の周の描画結果が
残っていて図が倍になっているのかで直す先がまるで違う。**はみ出した 1 枚目の実測**
（図番・測った外形・割り当てた枠・はみ出し量）を添えれば、その差が一目で見分けられる
（柱・横架材のパスが退化した 1 本目の実測を添えるのと同じ流儀。`DescribeFitOverflow`）。

## 見積もりの単位が合っていない（構造上の限界。数字が出てから直す）

`core::kPlanContentMargin`（300mm）は「命令の座標には現れないもの」への遊びだが、
**モデル mm の定数**である。一方、図に映るもののうち**縮尺に追随しないもの**——通り芯の丸・
柱記号・耐力壁の伏図記号（どれも用紙基準シンボル）・データタグ・図面タイトル——が
モデル座標で占める幅は「用紙 mm × そのレイヤの縮尺」で、**縮尺が上がるほど広がる**。
1/50 では 300mm ＝ 用紙 6mm しか考慮していないのに、用紙 20mm の伏図記号はモデルで 1000mm を
占める。**用紙 mm の余白として持ち直すのが筋**だが、そのためには「記号とタグが用紙で
何 mm を占めるか」の実測が要る（どれも描画してみるまで大きさが決まらない）。

**数字が揃うまで縮尺の決め方は変えない。** 変えると図そのものが変わり、前の周と
照合できなくなる——上の実測がまさにその数字を記録するので、次の周を待つ。

## はみ出しの正体は屋根面の勾配基準線だった（見積もりの単位ではなかった）

**上の「用紙 mm へ持ち直す」は、今回のはみ出しの原因ではなかった。** 計装を入れた最初の周が
出した数字がそれを否定している——`6: 測った 325.2×311.2 / 枠 383.0×297.0`。

* **横は見積もり 325.0 に対して 325.2**（+0.2mm）。記号・タグ・通り芯の丸のような
  「縮尺に追随しない飾り」が影響しているなら**両軸に**出るはずで、片軸だけぴったり合うことは無い。
* **縦だけ 197.6 → 311.2**（モデルで +5,680mm）。しかも `planContentBounds` はレイヤで
  絞るほど狭くなるので、**文書全体の 9,880mm はどのシートの上限でもある**。命令の座標では
  説明が付かない、という結論がここで確定する。

**実機の画面で確認すると、屋根面（野地板）の勾配基準線が建物の南へ 1 スパンぶん飛び出していた。**
`parse/Roof` の軒（屋根軸）の作り方が原因である。

```
旧: 最も軒側（+d 側）の頂点を 1 つ選び、そこから軒方向へ eSpan だけ伸ばす
```

選ばれた頂点が**軒方向の終わり側**（e = eMax）に在ると、終点が `eMax + eSpan` ＝ footprint
1 つぶん外へ出る。屋根面オブジェクト（`VWRoofFaceObj`）は**この軸を勾配の基準線として図に
描画する**ので、飛び出した軸がそのままビューポートの外形を広げ、伏図が用紙に収まらなくなっていた。
**頂点の並び順しだいで出たり出なかったりする**ので、同じモデルでも面によって症状が違う。

直し方は、軸を**勾配座標系で見た footprint の外接矩形の軒側の辺そのもの**にすること。
`{along, down}` は正規直交なので射影値の組 `(e, d)` から平面座標へ戻せる。

```
新: axisStart = (e=eMin, d=dMax) / axisEnd = (e=eMax, d=dMax) / upslope = (e=中央, d=dMin)
```

**屋根面の平面は変わらない。** 軸は変更前と同じ `d = dMax` の直線上にあり、動かすのは直線上の
端点だけなので、勾配も軒の高さも同じものが出る（軒の Z は軸のどこで測っても同じ）。

**直せるのは「余計に 1 つぶん伸びる」ところまでで、「xy の外接矩形に収まる」ではない。**
footprint が矩形でなければ、`(e, d)` の外接矩形の角を xy へ戻した点は外接矩形の外に出うる
——**三角形の屋根面では軒が 1 頂点に退化する**ので、その点を通る軒の直線上に長さを持つ線分を
取る限り原理的に避けられない。最初はこれを「外接矩形に収まる」と書いてしまい、自動レビューに
反例（45°振った直角三角形）を出されて気付いた。**実データにも非矩形の屋根面が 7 面・三角形が
4 面ある**（フィクスチャ「伏図次郎【2階】」を数えた）ので、仮定の話ではない。

したがって不変条件は**勾配座標系の射影範囲で言う**——軸は軒側の端（d 最大）に乗り、軒方向 e で
`[eMin, eMax]` ちょうどを張る。テストも xy の外接矩形ではなく、**軸の向きから (e, d) を復元して**
この範囲を確かめる（`tests/ParseRoofTests` の `checkAxisSpansFootprint`）。こちらの方が判定も鋭く、
旧コードに対して実フィクスチャで 18 か所失敗する（外接矩形版は 9 か所だった）。

**教訓は「片軸だけ合っている」を読み落とさないこと。** 横が 0.2mm しか違わない時点で、
「飾りの見込みが足りない」系の仮説はすべて否定されていた。件数だけを参照していた間は 2 つの
仮説（用紙 mm の余白・空のデータタグ）を立てて両方とも誤っており、**1 枚目の実測を出すようにした
最初の周で正しい向きに絞れた**。

## 余白が四辺 0 のとき、「縁なし」と「読めなかった」は数字では分かれない

診断の `印刷可能 420×297` は用紙と同じ、つまり余白が四辺 0 である。`resolvePageMargins` は
**四辺 0 を「余白なし」として受け取る**（縁なし印刷ができる機種では実際に選べる設定なので、
ここを「読めなかった」に倒すと正しい設定に警告が出る。M18 の後の実機の指摘）。ところが
**`ISDK::GetPageMargins` は戻り値を持たない**ので、SDK が何も書かずに戻っても出てくる数字は
同じ 0 になる。

見分けるには**有り得ない値（負）を種に置いてから呼ぶ**しかない——戻ってきて種のままなら
SDK は 4 辺のどれにも触れていない。あわせて、四辺 0 のときだけ「SDK が値を書いたか」と
「シートレイヤの大きさ」を診断ログへ添える（**平常でも出る記録なので `note` ではなく
`outInfo`**）。実機が本当に縁なしなら「SDK は値を書いた / シートレイヤ 420×297」と出る。
