# MCP ブリッジを常駐させる（M30）

**頼まれたのは 2 つ——「MCP から Vectorworks を起動したい」「Vectorworks が動いている間は
いつでも受け付けてほしい」。** M24 の橋はメニューを押している間だけ架かり、その間は
進捗ダイアログが図面を塞いでいた。Claude に図面を読ませるたびに人がメニューを押し、
読ませている間は図面を触れない——道具として使うには手間が大きすぎた。

## 常駐の口は「パレットの時計」しか無い

SDK にアイドルコールバックは無い（M24「形を決めた 3 つの制約」の 1）。周期的にメイン
スレッドで動く手立ては、**モードレスな Web パレットの JS タイマー**だけで、これは往復の
パレット（M24「往復をモードレスのパレットで回す」）で実機に確かめてある:

* JS の `setInterval` から C++ の関数へ、**メインスレッドで**届く（`AddFunctionPromiseSync`）。
* **パレットを隠しても、ページとタイマーは生きたまま**（「隠れたパレットは止まらない」）。

往復では 2 つ目が事故の元だった（見えないところで無人の取り込みが走り続けた）。**ここでは
それが欲しい性質そのもの**なので、そのまま使う。そこで橋の形を「ループ」から「1 回呼ばれて
戻る」に変えた:

```
パレットの JS（250ms ごと） ──vwmcp.serve──▶ 殻（Extensions/ExtMcpPalette）
                                             │ PayloadUse（本体を確保）
                                             ▼
                                   本体 vw_payload_mcp_serve → draw::serveMcpBridge
                                   （スプールを覗いて応え、2 秒に 1 回印を書き直して戻る）
```

戻っている間は Vectorworks が自由に動くので、**人は図面を触ったまま、Claude は読める**。
メニュー「MCP ブリッジを表示…」はパレットを出すだけになった（ユニバーサル名と UUID は
据え置き。ワークスペースが覚えているため）。

## 決めたこと

- **隠れていても受け付ける。** 往復では「隠せるものに、隠れている間の権限を持たせない」と
  決めたが、ここで受け付けるのは**読むだけの道具**で、相手は同じ計算機の同じ利用者だけ
  （スプールは 0700）。**書く道具を足すときは、この判断をやり直すこと。**
- **取り込みの最中は見送る。** 進捗ダイアログの `DoYield` の間にも時計は届く。本体の
  コードがスタックに載っている間（`PayloadInUse`＝入れ子の深さが 0 でない）は本体へ入り
  直さず、「見送っています」とだけ返す——描きかけの図面を読ませないため。印も書き直さない
  ので、取り込みが 15 秒を超えると Python 側からは「動いていない」に見える（取り込みが
  終われば次の刻みで戻る）。
- **本体を入れ替えても橋は途切れない。** 刻みのたびに `PayloadUse` を作るので、自動
  アップデートが置いた新しい本体は次の刻みで読み直される。**このとき前の回の残骸を掃除
  しない**——入れ替えのたびに「開始」が来るので、M24 のように開始時に掃除すると、入れ替えの
  直前に書いた応答や Python が置いたばかりの要求まで消える。掃除するのは**印が古びている
  （＝前の Vectorworks が落ちた）ときだけ**（`core::BridgeSpool::statusIsLive`）。
- **読み込めない本体を刻みごとに読みに行かない。** 時計は 250ms ごとに来るので、読み込みに
  失敗したら 10 秒待つ（読み込みは本体を一時ディレクトリへ複製するので重い）。
- **最初の刻みは 3 秒遅らせる。** Vectorworks の起動直後にパレットが開き直されたとき、
  起動の最中に本体を読みに行かないため（起動中の SDK 呼び出しで落ちた前例がある。M23）。
- **30 分の自動停止と `vw_stop_bridge` は外した。** どちらも「Vectorworks を握り続けない」
  ための歯止めで、握らなくなった今は理由が無い。
- **パレットの HTML は安定版と開発版で 1 つ**（`resources/common.vwr/html/mcp.html`）。
  包む直前に各 `.vwr` の写しへ重ねる（CMakeLists.txt）。2 つへ書き写すと片方だけ直す事故が
  起きる。

## Vectorworks を起こすのは Python サーバ

`vw_launch` は**プラグインではなく Python サーバの道具**である——起こす前にはプラグインが
居ないので、訊く相手が無い。起動の口は OS の作法だけに頼る:

- **macOS は `open -a "Vectorworks 2026"`**。既に動いていれば手前に出すだけで、2 つ目は
  起きない。
- **Windows は既定のインストール先の `.exe`**（`%ProgramFiles%\Vectorworks 2026\`）。
  実行ファイルを直に起こすと 2 つ目が立ちうるので、`tasklist` で動いているのが分かったら
  起こさず「パレットを出してください」と返す。
- どちらも `VW_MCP_APP` で名指しできる（テストの代役もこの経路）。

起こしたあとは**印が現れるまで待つ**（既定 120 秒）。現れたら MCP の
`notifications/tools/list_changed` を送る——起動前の `tools/list` は自前の道具
（`vw_bridge_status` / `vw_launch` / `vw_call`）しか返せないので、Claude に一覧を取り直させる
（`initialize` で `listChanged: true` を宣言した）。

## 実機で分かったこと（1 周目）

- **繋がった。Vectorworks を起動し直してもパレットは開いたまま**で、メニューを押すのは
  最初の 1 回だけでよい。Web パレットの表示状態が起動をまたいで残る、は SDK の挙動なので
  SDK リファレンスの Findings「モードレス（非モーダル）なパレット」へ送ること。
- **ところが Claude からは図面を読む道具が見えなかった。** 見えたのは自前の 2 つ
  （`vw_bridge_status` / `vw_launch`）だけ。Claude のアプリは **`tools/list` を起動したときに
  1 回しか呼ばない**ので、そのとき橋が架かっていなければプラグインの道具は最後まで並ばない。
  `list_changed` の通知は `vw_launch` で起こしたときしか送っておらず、それに応じるかも
  アプリ次第である。**一覧の真実をプラグイン側に置いた（M24）ことの裏面**で、一覧が
  「起動の順序」に左右されていた。
- 直し方は 3 つ重ねた（Python サーバだけで、プラグインは変えない＝再起動は要らない）:
  1. **`vw_call`（名前で呼ぶ汎用の口）を常に並べる。** 一覧が古くても道具に届く。道具の
     名前をサーバへ書き写すことはしない——何を呼べるかは次の 2 が返す。
  2. **`vw_bridge_status` が、動いているときはプラグインの道具の一覧（名前・説明・引数）を
     返す。**
  3. **橋に触れた道具（`vw_bridge_status` と、プラグインの道具の呼び出し）のたびに、まだ
     見せていない一覧が取れたら `list_changed` を 1 度だけ送る。** 同じ一覧で何度も送らない
     （応じないアプリで通知が積み上がらないように）。取れた一覧はキャッシュされるので、
     **次にアプリを起動したときは Vectorworks が落ちていても一覧に並ぶ。**

  直したあとの 2 周目で、**Claude から図面を読めることを実機で確かめた**（`vw_call` 経由）。

## まだ確かめていないこと（実機）

  2 秒に 1 回の小さなファイルの書き換え）。
- 取り込みの最中に「見送っています」になり、終われば戻るか。
