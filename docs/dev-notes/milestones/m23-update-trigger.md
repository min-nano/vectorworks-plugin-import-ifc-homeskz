# プラグインの位置付けと、更新の起こし方（M23）

**プラグイン 1 つには複数のコマンドと PIO を同梱できる。** そこで「1 機能 = 1 プラグイン」を
やめ、構造設計に使う機能をこの 1 つへ収めていくことにした。名前は表示名
**「みんなの構造設計支援」**、ファイル名・フォルダ名 **`min-nano_structure`**（dev は
それぞれ `…Dev` を付ける）。取り込みコマンドの名前は変えない。

判断したこと:

- **ユニバーサル名と拡張機能 UUID は据え置く。** これは**コマンドの同一性そのもの**で、
  ワークスペースはこの名前でコマンドを覚えている。改名の巻き添えで付け替えると、利用者の
  ワークスペースからコマンドが消える（登録し直しになる）。プラグインの名前が変わったから
  といって、コマンドが別物になる理由は無い。同じ理由で PIO のユニバーサル名も据え置き
  ——あちらは**図面に保存された既存オブジェクト**の同一性でもある。

- **ただし PIO のユニバーサル名は安定版と開発版で分ける**（後から直した）。当初は両版とも
  `HomeskzColumnMark` / `HomeskzShearWall` を名乗っており、両方を入れた環境では片方の登録
  しか有効にならなかった。実際に、**安定版で取り込んでも耐力壁が「耐力壁 (Dev)」になる**——
  安定版の取り込みが置いた PIO を開発版の定義（表示名も作図する本体も開発版）が扱っていた。
  メニュー・パレットは最初から版ごとに名前を分けていたのに、PIO だけ漏れていた。据え置く
  理由（図面に保存された既存オブジェクトの同一性）は安定版の側にしか無いので、安定版は
  そのままにして開発版だけ `…Dev` を付けた。開発版で作成した図面の PIO は開発版の新しい
  ビルドからは別物になるが、それは試験用の図面に限られる。

- **C++ の名前空間 `HomeskzIfcImport` も据え置く。** 図面にも配布物にも現れない内部の
  綴りで、書き換えても利用者に何も起きない。200 ファイル超の機械的な差分で、本当の変更を
  読めなくするほうが損である。

- **改名は「きれいな切り替え」にする。** フォルダ名もアセット名も変わるので、古い版の
  アップデータは新しい版を自分の場所へ入れられない。移行を自動でやろうとすると「旧名を
  知っている」コードが要り、それは M22 で廃止した作法そのものになる。1 度だけ手で入れ直す
  （[「アップデート」](../../user-guide/update.md)）。

## 更新の確認を、起動時から 2 つの入口へ

**起動時の自動確認をやめた。** M21 で殻と本体に割って以降、機能追加以外の更新は
**再起動なしでその場で反映される**。だから「起動のたびに問う」必要が無くなった。代わりに:

| 入口 | どう振る舞うか |
| --- | --- |
| メニュー「アップデータを確認 (みんなの構造設計支援)」 | 実行した以上、結果を必ず表示する（更新した／最新／確認できなかった） |
| 取り込みコマンドの頭 | 更新があるときだけ尋ね、取得に失敗したら何も表示せずに取り込みへ進む |

判断したこと:

- **手動で実行したときは結果を必ず表示する。** 起動時のチェックだった頃は「何も表示しない」
  が正しかった——起動を妨げないため。コマンドになった以上、何も起きないのでは「最新だった」のか
  「そもそも動いていない」のかが利用者に区別できない。オフラインもその旨を出す。

- **取り込み時の確認は、本体を確保する前に置く。** そこで新しい本体が入れば `PayloadUse`
  がそれを再読み込みするので、**その 1 回目の取り込みからもう新しいコードが動く**。確保した
  あとでは本体のコードがスタックに載っているぶんアンロードできず、反映が次回に回ってしまう。

- **PIO のリセットからは確認しない。** 取り込み直後には記号・耐力壁が数百個リセットされる
  ので、そのたびに GitHub へ要求を送るわけにはいかない。PIO の更新は、手動の確認か、取り込み時の
  更新に乗って入れ替わるのを待つ。

- **dev の取り込み時確認はブランチ選択を出さない。** 取り込みたいだけの人の前に「どの
  ブランチを使いますか」を挟むのは妨げでしかない。検出するのは**いま動いているのと同じ
  ブランチの、別のコミット**だけ——それだけが「自分のビルドが新しくなった」に当たる。
  そのために `q-dev` の TSV へ 5 列目（ブランチ名）を追加した。リリースの表示名は
  `"Dev: <branch> (<sha>)"` なので照合に使えず、そのままのブランチ名はリリース本文（CI が書く
  `branch=` の行）から読む。**列が無い古い同梱スクリプトでは照合できないので何もしない**
  ——別のブランチのビルドを勝手に入れるよりずっと安全。

## 再起動を SDK に頼めるようになった

M21 の時点では、再起動は**切り離したヘルパープロセス**に任せていた。SDK の
`CloseAllFilesAndQuitVectorworks` を呼ぶと、`bRestart` の有無にかかわらず
「サポートファイルの読み込みに失敗しました」で異常終了したためである
（[「以前は SDK に頼めなかった」](../../development/auto-update/restart.md#以前は-sdk-に頼めなかった実機で確かめた失敗とその前提が消えた経緯)）。

**原因は呼ぶ時機だった。** 当時の確認は**プラグインのロード中**（スプラッシュ表示中）に
走っており、Vectorworks 本体がまだ自分を終了させられる状態になっていなかった。確認が
メニューコマンドと取り込みコマンドへ移り、**Vectorworks が完全に動いている最中にしか
呼ばれなくなった**ので、素直に `CloseAllFilesAndQuitVectorworks(true, true)` に頼める。
未保存ファイルの保存確認も Vectorworks が通常どおり行う。

ヘルパーの一式（`MacRelaunchCommand` / `WinRelaunchCommand` / `PowerShellQuote` /
`MacAppBundleFromExecutable` と、それらが組み立てる shell / PowerShell を検証していた
テスト）はまとめて削除した。**もし将来また起動時に確認したくなったら、この失敗を
思い出すこと**——SDK の終了は「Vectorworks が動いていること」を前提にしている。
