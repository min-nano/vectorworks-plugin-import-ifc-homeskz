# 殻と本体に割ってホットリロードする（M21）

**動機はひとつ。** 「直した → 入れた → 再起動して開き直す」の最後の 2 手が、実機確認の
1 周のうちいちばん長かった。VectorWorks の起動は数十秒かかり、開いていた図面も開き直す
ことになる。**コンパイル済みプラグインは起動時にしか読み込まれない**という SDK の性質
そのものが原因なので、プラグインの側で受け止めるしかない。

**やったこと**は、成果物を 2 つに割って、VectorWorks に読み込ませるものを最小にした
（作法と決めごとは CLAUDE.md「アーキテクチャ: 殻と本体」）。

```
VectorWorks ──読み込む──▶ 殻（登録・更新・読み込み）  … 起動時に 1 度きり。滅多に変わらない
                              │ dlopen / LoadLibrary
                              ▼
                          本体（core / parse / draw）  … いつでも降ろして読み直せる
```

**この道が通ることは SDK リファレンス側で実測済み**だったので、本リポジトリでは調査を
していない（CLAUDE.md「SDK の調査はリファレンス側で行う」）。あちらの
[「プラグインモジュールの読み込みと入れ替え」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)
に、`dlopen` できること・`GS_InitializeVCOM` を自分で呼べば `gSDK` が埋まること・
`dlclose` で本当に消えること・置き換えて読み直すと走るコードが実際に入れ替わることが
実機の数字つきで載っている。**このページはその知見を本プラグインへ当てはめた記録**である。

## 本プラグイン固有の判断

- **本体は載せっぱなしにする。** リファレンスの実機確認プラグインは「メニューを開くたびに
  読み込んで、終わったらアンロードする」作りだが、本プラグインは**PIO のリセットが同じ本体を使う**。
  取り込み直後は記号・耐力壁が数百個リセットされるので、1 回 0.3〜0.4 秒の読み込みを毎回
  払うと現実的な速さにならない。そこで載せたままにし、**入れ替えの判定だけを入口ごとに
  行う**（`src/PayloadSession.cpp`）。判定は同梱ファイルの大きさ・更新時刻で、**中身の
  ハッシュは取らない**——入口のたびに数 MB を読む価値は無く、取りこぼしても次の入口で
  検出されるだけだからである。

- **PIO は「登録は殻・作図は本体」に割る。** `SParametricDef` とパラメータ定義は
  VectorWorks に番地を保持されるので殻に残すほかないが、`Recalculate()` の中身は出せる。
  出したことで、**記号や耐力壁の描画の修正も再起動なしで反映される**ようになった
  （`src/draw/ColumnMarkPio.cpp` / `src/draw/ShearWallPio.cpp`）。

- **PIO のリセットではダイアログを出さない。** 本体を読み込めなかったとき、メニュー
  コマンドは理由をダイアログで表示できるが、リセットは図面の記号の数だけ走るので黙って
  諦めるしかない。`kObjectEventHadError` も返さない——描画できなかったことより、**既に描画して
  ある記号を消さずに残す**ほうが害が少ない。

- **殻の ID で再起動の要否を決める。** `CMakeLists.txt` の `VW_SHELL_INPUTS`（殻に入るもの
  だけ）のハッシュをビルドへ焼き、インストール物にも控える。`do-install` が入れたビルドの
  ID を返し、走っている殻の値と一致すれば**再起動を尋ねない**（`src/UpdaterFlow.cpp` の
  `FinishInstall`）。**この一覧に `draw/` や `parse/` を追加してはいけない**——描画を直した
  だけで毎回再起動が要る仕様に変わってしまう。判断できないときは必ず「要る」へ倒す。

- **`file(SHA256)` だけで ID を出す。** 外部スクリプトを挟むと mac と Windows の CI で
  値が食い違いうる。食い違った瞬間に「毎回再起動が要る」へ変わってしまうので、CMake 組み込みの
  ハッシュだけで完結させた。

## 落とし穴（両方とも実機でしか出ない）

- **殻の記憶域を本体に持たせない。** 境界を越えて渡した構造体のポインタを受け取った側が
  持ち続けると、無効になったポインタから関数ポインタを読んで**VectorWorks ごと落ちる**。
  コンパイルもリンクも CI も通る。複製する側（`src/PayloadHostHolder.h`）と渡す側
  （`Payload::fHost` をメンバに置く）の**両方**で止め、複製していることは無 SDK テストで
  押さえてある（`tests/PayloadHostHolderTests.cpp`）。
- **mac は本体にも個別のアドホック署名が要る。** バンドルの外に置くので `codesign --deep`
  には含まれず、署名が無いと Apple Silicon の検証で `dlopen` に失敗する。

## 実機で確かめたこと（macOS / VW 2026、build 03a175c → 4363d43）

- **本体側からダイアログを開ける。** SDK リファレンスの「まだ確かめていないこと」に唯一
  残っていた項目で、ここが駄目なら設計をやり直すところだった。取り込み設定ダイアログ
  （`VWDialog`）・進捗・完了ダイアログ・VCOM のファイル選択（`IFileChooserDialog`）が、
  すべて本体側から通常どおり開いて動いた。
- **PIO のリセットが境界越しに機能する。** 記号・耐力壁ともリセットが走り、取り込み経路
  だけでなく**伏図の作成中に VW 側が起こしたリセット**も通った。約 100 回のリセットが
  1.6 秒ほどで済んでおり、**「載せっぱなしにする」判断が有効に働いている**（毎回再読み込みする作りなら
  読み込みだけで 30 秒以上になっていた）。
- **本体だけを差し替えれば、再起動せずにコードが入れ替わる。** `.vwpayload` を置き換えて
  同じ VectorWorks のまま取り込み直したところ、ログの見出しの commit が新しい本体のものへ
  変わり、その版でしか直っていない挙動（ログのパス表示）が実際に現れた。**この機能の目的
  そのものが実機で成立している。**
- 描画したものは差し替えの前後で 1174 件が完全に一致し、所要も 1 分 14 秒 → 1 分 15 秒で
  差が無い。

**SDK の挙動として一般化できる分（本体からダイアログを開けること）は
[SDK リファレンスの `Findings/`](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)
へ書き残す**（CLAUDE.md「ドキュメントの分担」）。ここに残すのは本プラグインでの現れ方だけ。

## まだ確かめていないこと

- **Windows での載せ替え**（`LoadLibraryEx` / `FreeLibrary`）。設計上は同じはずだが、
  SDK リファレンス側でも未実測。
- **本体からダイアログを開いたままアンロードする**経路。いまは深さ 0（本体のコードがスタックに
  無い）でしかアンロードしないので安全なはずだが、VectorWorks に本体の番地を持たせたままアンロードする
  操作（イベント登録など）を将来追加するなら、アンロードする前に手放す設計が要る。
- **長時間・多数回の再読み込みでリークしないか。**
