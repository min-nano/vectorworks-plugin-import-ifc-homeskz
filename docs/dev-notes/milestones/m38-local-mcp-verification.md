# 実機確認をローカルの Claude Code から MCP で回す（M38）

**ご要望**: MCP サーバを差し当たり開発版専用にし、Claude Code をローカルセッションで動かして
GitHub の PR コメントを介さずに開発を進めたい。実機確認コマンドが自動でコメントしたり
入れ替えたりする機能は外し、代わりに MCP でログの取得・アップデート・再起動を起こしたい。

**なぜ PR を介すのをやめたか。** M23〜M37 の往復は、Claude が**クラウドのセッション**にいて
利用者の PC に手が届かない前提で組んだものだった——だから結果を公開の PR へ投げ、合図を
PR コメントで返し、PC の側のパレットが 1 分ごとに GitHub を見て新しいビルドを入れていた。
Claude Code が**同じ PC で**動くなら、その遠回りは全部要らない。しかも遠回りが事故の元だった
（自分の案内文を合図と読んで止まる・同じ周を二重に投稿する・隠れたパレットが誰も押して
いないのに取り込みを走らせる・認証なしの API 制限に当たる・閉じた PR へ投稿する。どれも
M24〜M27 で実機で起きた）。

**何を外したか。**

- `vw-feedback.{sh,ps1}`（トークンの登録・PR の特定・投稿・合図の読み取り）とそのテスト。
- 往復の駆動（`src/FeedbackLoop*`）と往復のパレット（`ExtFeedbackPalette`・`html/index.html`）。
- 尋ねずに入れる更新（`UpdateCheckKind::Auto`）と、パレットの周期確認（`PollDevBuildWith`）。
- 実機テストの 1 周目の「PR へ送るか」のダイアログ・伏せ字・宛先の記憶
  （`core::FeedbackSession` の `send` / `repo` / `pr` / `branch` / `anon` / `posted` / `loop`）。
  古い記憶の行は黙って読み飛ばすので、更新しても IFC と設定はそのまま続きの周に使える。
- 報告の匿名化（`parse::redactText` 等）と PR の目印。報告は利用者の PC の中だけで読まれる。

**残したもの。** 実機テストの 1 周（記憶した条件・図面の 3 段の戻し方・前の周との差分・
「図面の状態」の行）はそのまま。ここは M25 で実機を 13 周回して固めたところで、往復の外側
（投稿と入れ替え）とは関係が無い。

**足したもの。**

| 道具 | 誰がやるか | 要点 |
| --- | --- | --- |
| `vw_log` | 本体 | 診断ログを**ファイルから**読む（本体を入れ替えるとメモリの本文は消える） |
| `vw_test_report` | 本体 | 実機テストの報告。記憶の隣の `last-round.md` |
| `vw_run_test` | 本体 | 実機テストの 1 周をダイアログ無しで。1 周目（IFC と設定）は人がメニューから |
| `vw_update` | **殻** | `RemoteDevUpdateWith`（ダイアログ無しで結末を値で返す）。ブランチを名指しできる |
| `vw_restart` | **殻** | `CloseAllFilesAndQuitVectorworks(保存を確認, 再起動)`。Python が架かり直しを見届ける |

## 本体に頼まれたことを殻がやる（ABI 7）

更新と再起動は本体の中ではできない——本体は自分を降ろせない（M21）。かといって殻に
スプールの作法（`core/Bridge`）を持たせると、殻が `core/` をリンクしない決まりが崩れる。
そこで**本体が要求を引き取って、見え方の JSON の `action` に載せて殻へ返す**（応えない）。
殻は本体から戻ったあとでそれを済ませ、結末の JSON を次の `mcp_serve` の `shellReport` に
渡す。そのとき載っている本体——入れ替えたなら**新しい本体**——が応答を書くので、応答の
`payload_commit` を見れば入れ替えが効いたかが分かる。殻はすぐにもう一度本体を呼んで結末を
渡すので、Claude から見れば 1 往復で済む。

再起動は**応答を書いてから**頼む（先に頼むと応える者がいない）。殻まで変わったうえ ABI も
上がったビルドを入れると、古い殻が新しい本体を読めず橋が落ちる——そのときの `vw_restart` は
Python が macOS の作法（AppleScript の quit。保存の確認は通常どおり）で終了させてから起こす。

## 決めたこと

- **MCP ブリッジは開発版だけ。** 取り込み・更新・再起動まで起こせる口を利用者向けの配布物に
  持たせない。安定版はクラスを持つが登録しない（UUID とユニバーサル名は据え置き）。
- **勝手に回る時計を持たない。** 取り込み・更新・再起動は Claude が頼んだときだけ。M24 の
  事故（隠れたパレットが自分の判断で回した）は、権限ではなく**自律**が原因だった。
- **保存の確認は飛ばさない**（ご判断）。再起動で人の応答が要ることがあるので、Claude は
  `vw_restart` の前に一言断る。
- **同じビルドでも取り込む。** M25 の「同じビルドなら取り込まない」は二重投稿の歯止めだった。
- **人がメニューから押した続きの周は 1 度だけ尋ねる**（同じ条件で／選び直す／やめる）。
  M37 までは続きの周を無人のパレットが回すので尋ねられなかったが、いま無人で回すのは MCP で、
  メニューを押すのは人だけ。別の IFC で試すのに記憶のファイルを消させるのは不親切だった。
- **うまく行った周は結果ダイアログを出さない。** モーダルが開いている間は本体がスタックに
  載ったままで、橋が受け付けを見送る＝Claude が報告を読めない。
- **長く走る道具は生存の印に `busy_until` を書いてから走る。** 実機テストの 1 周は 1 分以上
  印を書き直せず、Python が「止まった」と取り違える。
- **トークンの登録口（`vw-feedback.sh login`）も外した**（ご判断）。更新の確認は 1 分ごとに
  回らなくなったので認証なしの 60 回にまず当たらず、要るなら環境変数か `gh` で足りる。
  既にキーチェーン／DPAPI に入っているトークンは引き続き読む。

## 実機で確かめること

- パレットの時計の中から `CloseAllFilesAndQuitVectorworks` を頼んで、再起動し、パレットが
  開き直して橋が架かり直すか（これまではメニューコマンドの中からしか頼んでいない）。
- `vw_run_test` の 1 周を時計の中で走らせて、進捗ダイアログが出て最後まで走り、応答が返るか
  （M24 の往復のパレットでは同じことをしていた）。
- `vw_update` で入れ替えたあと、応答の `payload_commit` が新しいビルドを名乗るか。

分かったことは、SDK の挙動なら SDK リファレンスの `Findings/`、本プラグインの話ならここへ
足す。

## 実機で分かったこと（PR #188 の確認）

- **`vw_run_test` は時計の中で最後まで走る。** 2 周目を MCP から起こし、「取り消し」1 段で
  取り込み前へ戻ってから取り込み直し、報告が応答で返った（220798b。所要 40.9 秒・内訳の
  変化なし）。読むだけの道具（`vw_ping` / `vw_test_report`）も応え、`bridge.json` の
  `served` が増えた。
- **`vw_update` は本体を入れ替え、応答の `payload_commit` が新しいビルドを名乗る。** 殻まで
  変わったビルド（main の取り込みを含む）では `needs_restart` を返したが、本体はその場で
  新しくなっており、再起動の前に回した周は新しい本体で走った。
- **パレットの時計の中から頼んだ再起動（`vw_restart`）は効く。** Vectorworks が落ちて起き
  直し、パレットが開き直して橋が架かり直した（Python 側の見届けが `restarted: true`）。
  そのあとの `vw_update` は `no_new_build`・再起動不要で、殻も新しいビルドになっていた。
  起き直したあとは図面が開いていない（`document_open: false`）。
- **基準を採り直した周が、無関係な図面のレイヤを名指しで消しに行っていた。** 人が空の図面を
  開いてからメニューを押した 1 周目で、前の周のレイヤ名による取り除き（`prepareDrawingForRound`）
  がその図面に対して走っていた（0/34 枚で実害は無し）。本番で取り込んだ図面を開いていれば、
  同じ名前の利用者のレイヤが消えていた。採り直した周では呼ばないようにした。
- **報告の「準備:」が 2 度出て、「取り消しで戻っています」の直後に「人が『取り消し』で
  戻します」と出ていた。** 前置きは `runTestRound` で 1 度だけ付け、取り消しの注記は作業
  ファイルを用意できなかった周（次の周が丸ごと戻せるとは限らない周）だけにした。
- **一時ファイルが溜まり続けていた。** 作業ファイルと退避した図面は一時ディレクトリの直下へ
  置いたきりで、1 つ 1.7 GB のものを含め 3.4 GB を超えていた。**ご要望で、PR が close／merge
  されたらそのブランチの分を消す**ことにした。手元では PR が閉じた瞬間を知れないので、
  **次の実機テストの周の頭**で、ほかのブランチのフォルダについて GitHub に PR の状態を
  尋ねて消す（`core/FeedbackScratch`。[「一時ファイルと片付け」](../../development/live-test/scratch-files.md)）。
  dev プレリリースが消えたことで判じる手は採らなかった——`build.yml` が push のたびに
  消して作り直すので、その間の「無い」を閉じたと取り違える。
