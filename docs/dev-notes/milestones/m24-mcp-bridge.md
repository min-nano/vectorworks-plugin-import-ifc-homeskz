# Claude と図面をつなぐ MCP ブリッジ（M24）

**動機は実機確認の往復である。** このプラグインは実描画をローカルの Vectorworks でしか
確かめられないので（[「実機確認の作法」](../live-verification.md)）、不具合の切り分けはいつも「人が画面を読み、
文章にして伝える」ところで詰まっていた。**Claude が図面を自分で数えられれば**、その往復が
消える——それだけのための道具で、図面を作るためのものではない。

## 形を決めた 3 つの制約

1. **SDK はメインスレッドからしか呼べない。** だから受け口を別スレッドに置けない。
   さらに「常時開けておく口」（アイドルコールバック）も SDK に無い——
   [SDK リファレンス「レイヤ・ストーリ」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Layers%20and%20Stories.md)
   の実測で、`ISDK` にあるのは `RegisterDialogForTimerEvents`（ダイアログのタイマー）
   だけと分かっている。**そこでメニューコマンドの実行そのものを橋の寿命にした**——
   押している間だけ架かり、止めれば消える。ループは進捗ダイアログの `DoYield` で
   Vectorworks へ制御を返す（`draw/ProgressDialog::keepAlive`）ので、再描画も
   ［キャンセル］も機能する。**その代わり、架かっている間は人が図面を編集できない。**
   （**M30 でこの制約を解消した**——往復のパレットで確かめた JS タイマーに載せ替え、橋は
   Vectorworks が動いている間ずっと架かる。[「MCP ブリッジを常駐させる（M30）」](m30-mcp-resident.md)。
   `keepAlive` もそのとき削除した。）
2. **ソケットは開かない。** macOS のファイアウォールが利用者に問い、Winsock と BSD
   ソケットで分岐が増え、非同期の受け口を作れば 1 と衝突する。**ファイルなら
   どれも起きない**——スプール（一時ディレクトリの `min-nano_structure-mcp`）に
   `<id>.req.json` が置かれ、`<id>.res.json` を返す。速さは要らない（人が対話する速度）。

   **置き場所は一時ディレクトリで、探すのは Claude 側。** 中身は正に一時データなので、
   本体の複製や診断ログと同じ場所へ置く（利用者のホームを汚さない）。ただし一時
   ディレクトリは環境変数で決まるので**両側で食い違いうる**——macOS の `$TMPDIR` は
   利用者ごとの `/var/folders/…` で、それを渡されずに起動されたプロセスは `/tmp` に
   フォールバックする（**実機で実際に起きた**。下記「探し方は実機で外した」）。そこでプラグイン側は
   自分の一時ディレクトリへそのまま置き、**Python サーバが候補を順に確認して「稼働中の印
   （`bridge.json`）のある場所」を使う**。加えて `/tmp`
   は同じ計算機の他の利用者からも書けるので、スプールは **0700 で作り、他から書ける
   状態のものは使わない**（要求を投げ込まれれば図面を読まれ、応答を読まれれば中身が
   漏れる）。ホームに置いていたときには要らなかった歯止めである。
3. **MCP そのものはプラグインに持ち込まない。** JSON-RPC・stdio・`initialize` の握手は
   Claude 側の作法であって図面の話ではない。依存の無い Python 1 ファイル
   （`scripts/mcp/vw-mcp-server.py`）へ出し、配布 zip へ同梱した。プロトコルが変わっても
   プラグインを配り直さずに済む。

## 探し方は実機で外した（$TMPDIR が来ない）

**候補を並べる仕組みは正しかったが、肝心の候補が入っていなかった。** 実機で橋を架けた
まま `vw_bridge_status` を呼んだところ、探した場所が `/tmp/…` の 1 つだけで「動いて
いない」と返った。理由は 2 つ重なっている。

- **Claude のデスクトップアプリは MCP サーバを `$TMPDIR` の無い環境で起動する。**
  だから Python の `tempfile.gettempdir()` は `/tmp` にフォールバックする。一方 Vectorworks（GUI
  アプリ）の `std::filesystem::temp_directory_path()` は利用者ごとの
  `/var/folders/…/T/` を返すので、スプールはそちらに在る。
- **その利用者ごとの場所を引く手当ては書いてあったのに、機能していなかった。**
  `if "CS_DARWIN_USER_TEMP_DIR" in os.confstr_names` で守っていたが、
  **この名前は CPython の `os.confstr_names` に載っていない**（あの表は POSIX の名前
  だけで、Darwin 固有のものは入らない）。条件が常に偽になり、候補が 1 つも増えなかった。

直し方は「名前で引けないなら番号で引く」——`_CS_DARWIN_USER_TEMP_DIR` は macOS の
`<unistd.h>` で **65537**。`os.confstr(65537)` を試し、それも失敗したら `getconf(1)` に
訊く（`darwin_user_temp_dir`）。この値は環境変数ではなく**利用者から決まる**ので、
同じ利用者なら両側で必ず一致するのが要点である。

## 当てずっぽうの候補は置かない

直した当座は、保険として **`/tmp` へのフォールバック**と **`/var/folders/*/*/T/` の
総当たり**も追加していた。**どちらも削除した**（実機で繋がったあとの指摘）。理由は「機能しない」
ではなく**「たまたま機能してしまう」**ほうにある。

- **`/tmp` は Vectorworks の一時ディレクトリになり得ない。** GUI アプリは launchd から
  `/var/folders/…/T/` を受け取るので、そこに橋が架かることはまず無い。見つかるとすれば
  **誰かが置いたもの**で、`/tmp` は同じ計算機の誰でも書ける。
- **総当たりは、同じ利用者の「別のセッション」の橋に接続しうる。** 見つかった順（名前順・
  印が新しいもの勝ち）で決まるので、**何処へ繋がったのかが分かりにくい**。決定性を守る
  という本リポジトリの方針とも合わない。

残したのは「プラグイン側が一時ディレクトリを決めるのに使うのと同じ仕組み」だけ——
利用者ごとの場所（confstr）と、環境変数から来る場所（`gettempdir` / `TMPDIR` / `TMP` /
`TEMP`）。加えて **macOS で利用者ごとの場所が引けたときは `/tmp` を候補から除外する**
（`$TMPDIR` 不在で `gettempdir()` が `/tmp` にフォールバックした結果も、ここで消える）。

**場所が知れているなら `VW_MCP_SPOOL` で名指しするほうが確かで、分からないなら繋がらない
ほうが良い**——繋がらなければ `vw_bridge_status` が探した場所を並べるので、そこから
追跡できる。曖昧に繋がるより、はっきり繋がらないほうが直しやすい。

ついでに、**Python 側にも持ち主と権限の確認を入れた**（`spool_is_safe`）。プラグイン側は
自分が作る場所を 0700・自分の持ち物に限っていたが、Claude 側は「稼働中の印があればそこへ
書く」だけだった——誰でも書ける場所に偽の印を置かれれば、要求（レイヤ名などの引数）を
渡してしまい、偽の応答を受け取らされる。候補から `/tmp` を除外した今も残してある。**同じ場所を
両側から参照するのだから、歯止めも両側に要る。**

**教訓は「在るはずの名前を `in` で守らない」。** 守り自体は正しい書き方に見えるのに、
名前が表に無いとその枝は一度も通らず、**失敗が「候補が 1 つ少ない」という静かな形で
しか出ない**。テストは実機で失敗したこの一点を直に押さえてある（`check_spool_search`）。

## 一覧の真実は 1 か所（プラグイン側）

道具の名前・説明・引数の形は **`draw/McpBridge.cpp` の `kTools` ただ 1 つ**が持ち、
Python サーバは起動時に `vw_tools` でそれを取りに行って MCP の `tools/list` に使う。
**だから道具を追加するのに Python 側を直さなくてよい**（プラグインを更新すれば増える）。
取りに行けないとき（Vectorworks が動いていないとき）は前回の一覧を使い、それも無ければ
自前の `vw_bridge_status` だけを返す——「なぜ繋がらないのか」を Claude 自身が調べられる
ようにするため、この 1 つだけはサーバが自分で答える。

## 外から来るものとして扱う

スプールへ書くのは**別プロセス**なので、`core/Bridge` は安全側に倒してある:
id は綴りを検査してからファイル名に使う（`../` でスプールの外へ書かせない）、要求 1 件の
大きさと 1 周で捌く件数に上限を置く、壊れた要求は**消してからエラーで応える**（同じものを
永久に取得し直さない）。ここは無 SDK で閉じているので、全部が単体テストで押さえてある
（`tests/CoreBridgeTests.cpp`）。

## v1 は読むだけ

`vw_ping` / `vw_layers` / `vw_classes` / `vw_layer_objects` / `vw_object_counts` の 5 つで、
**どれも図面を読むだけ**（M24 にあった `vw_stop_bridge` は M30 で削除した。常駐になって止める
理由が無くなったため）。書く道具（作図・修正）を追加するときは
undo の作法（[SDK リファレンス「Undo」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Undo.md)）を
必ず通すこと——半端な記録を取り消すと図面が壊れる。

**オブジェクトの種別番号は名前に変換していない。** `Kernel/API/Objs.TDType.h` の一覧は
本リポジトリでは持たない（SDK の調査はリファレンス側）ので、既に名前の判明しているものだけを
表にして、それ以外は番号のまま返している。**推測で名前を付けない**——嘘の名前は番号より悪い。
