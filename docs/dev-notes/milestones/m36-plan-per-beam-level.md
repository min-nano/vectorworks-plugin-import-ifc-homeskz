# 横架材の高さごとに伏図を作る（M36）

**ご要望**: 伏図は横架材の高さごとに作るのを基本にする。スキップフロアで GL+500・GL+2000・
GL+3500・GL+4200・GL+5500 に横架材があれば、ホームズ君の IFC は GL+500 を土台（1FL）、
GL+2000 と GL+3500 を 2 階（2FL）、GL+4200 と GL+5500 を小屋（RFL）として出すが、伏図は
各高さの梁伏図を描く。取り込み時の設定で複数の高さを同じ伏図にまとめられるようにし、
**まとめるかどうかは設計者が判断する**（高さは 1mm でも違えば別）。登り梁は水下側の高さで
切り分ける。**高さで切り分けるのは横架材だけでなく、柱の断面・伏図記号・耐力壁も**で、
柱のレイヤ名も伏図をまとめる単位で区切る。

フィクスチャ `スキップフロア_サンプル.ifc` の水平な横架材の天端は 1FL=GL+572、2FL=GL+2699 /
GL+3531、RFL=GL+5542 / GL+6010 / GL+6374 で、柱梁伏図は 3 枚から 6 枚になる。ほかの 4 つの
フィクスチャはどの階も高さが 1 つで、**命令セットは 1 バイトも変わらない**（実装時に全
フィールドを書き出して突き合わせた）。スキップフロアも**幾何は 1mm も動かず、変わったのは
配置先のレイヤだけ**（耐力壁の高さはレイヤ平面からの相対値なので、そのぶん取り直した）。

**決め事**（`parse/PlanLevel`）:

- **伏図レベル**＝伏図 1 枚ぶんの横架材の高さのまとまり。高さは各階の横架材レイヤ（横架材
  天端・最上階は軒高）に載る**水平な**横架材の天端を mm に丸めた値。母屋・登り梁の専用レイヤの
  材は見ない（高さがもともと材ごとに違い、母屋伏図が別にある）。水平な横架材の無い階は標準の
  天端 1 つ。
- **傾いた材は水下側**: 低い側の端の天端にいちばん近い伏図レベルへ入れ、レベルを作る材には
  しない（横架材レイヤに載る隅木・登り梁）。母屋は分けない。
- **登り梁は跨ぐ伏図に映し、柱と同じ span レイヤに置く**（ご要望。PR #180）。当初（#183）は
  登り梁を水下側の伏図レベルのレイヤ（`2-登り梁(FL-872)`）へ分け、母屋伏図には一切映さない
  とした（母屋より低い材が母屋と同じ図に並び、高さの関係が直感に反する）が、軒桁より上に
  ある登り梁は母屋伏図に描かれるほうが自然。そこで:
  * 柱梁伏図は、その伏図レベルの高さを**跨ぐ**（下端 ≤ 高さ ≤ 上端）登り梁を映す。
  * 母屋伏図は、**上端がその階のいちばん上の伏図レベルの高さ以上**の登り梁を映す（実機の
    2 階母屋伏図なら 軒高 -238。当初は登り梁が属する伏図レベルの高さで決めたので、軒高
    -1570〜-302 の登り梁が 軒高 -1600 を基準に「跨ぐ」とされ母屋伏図に出た。6abcd67 の実機）。
  * どれにも当たらなければ、低い側の端に近い伏図レベルの柱梁伏図。
  複数の伏図レベルを跨ぐ材があり得るので、柱と同じく**通し番号の範囲の span レイヤ**
  （`{from}to{to}-登り梁`。`parse::noboribariSpan`）へ置き、各伏図は切断（柱梁伏図＝通し
  番号 + 0.25・母屋伏図＝いちばん上 + 0.75）を範囲に含む span を映す（`spanLayersAtCut`）。
  範囲は柱梁伏図 o だけなら `[o, o+0.5]`、母屋伏図にも映すなら to＝いちばん上 + 1、母屋伏図
  だけなら `[いちばん上+0.5, いちばん上+1]`。高さ基準もその span のレベル（種別はレイヤ名
  そのもの。高さは登り梁レベルと同じ）へ付け替える。端がちょうど高さにあれば跨ぐとみなす
  （許容 1mm）。
  * **span レイヤの登り梁は from の階で数える。** レイヤ名に階の接頭辞（"2-"）が無いので、
    接頭辞から階を引いていたところ——データタグの高さの注記（`parse::memberLevelNoteParts`）・
    垂木の桁幅の参照（`parse/Rafter`）——は、from の伏図レベルが属する階（`storyOfOrdinal`）で
    見る。当初これを忘れ、登り梁のタグから高さの注記が消えた（bf500ca の実機）。
  * **実機確認済み**（VW 2026 / macOS。PR #180 の 74fc7cd・`model-9bbf97.ifc`）: 2 階母屋伏図に
    軒高 -238 以上の登り梁だけが映り、軒高 -1570〜-302 の登り梁は 2 階小屋伏図（軒高 -1,600）に
    映った。登り梁のデータタグに高さの注記が付いた。
- **まとめるのは同じ階の中だけ**: レイヤは階（ストーリ）に属するので、別の階の横架材を 1 つの
  レイヤへは置けない。設定の鍵は（階の番号・高さ）の組（`core::PlanLevelKey`）で、IFC を
  読み直しても同じ鍵になる。
- **標準の伏図レベルは名前を変えない**: 各階で標準の天端（`beamTopElevation`）にいちばん近い
  高さを含む伏図レベルは従来のレイヤ（`2-横架材天端` / `R-軒高` / `2-FL` / `2-耐力壁`）。
  それ以外は種別の後ろに高さの印（`core::planLevelTag`。`(FL-872)`）を付けた別のレベル・
  レイヤで、レベルの高さは元のレベルを代表の高さ（いちばん低い天端）のぶんずらしたもの。
  **高さの違う建物でなければレイヤ名は従来と同じ**なので、既存の図面や手順に影響しない。
- **材の高さ基準は元のレベルのまま**: 横架材・床のストーリバウンドは従来どおり `横架材天端` /
  `FL` を指す。レイヤが違っても同じ階のレベルは指せる（柱が span レイヤに居ながら横架材天端へ
  バインドしているのと同じ）。耐力壁だけは高さをレイヤ平面からの相対で持つので、伏図レベルの
  レイヤの高さから取り直した。
- **柱の span の番号は伏図レベルの通し番号**（下から 1, 2, …）。from は柱の下端にいちばん近い
  天端の伏図レベル、to は上端が届く伏図レベル（天端が上端 − 1mm 以上の最も低いもの）。屋根束は
  到達階の最も高い伏図レベル + 0.5。**from は柱が属する IFC の階の中で選ぶ**——フィクスチャには
  RFL に属しながら GL+2699 の横架材に立つ小屋束が 1 本あるが、柱の高さ基準はレイヤの階から
  数える（`StoryBoundCommand::storyOffset`）ので、別の階の番号にすると基準のレベルを失う。
  **どの階も高さが 1 つなら通し番号＝階の番号**で、従来と同じ名前になる。伏図の切断レベル
  （柱梁伏図＝通し番号 + 0.25・母屋伏図＝その階の最も高い通し番号 + 0.75）と伏図記号レイヤの
  選び方（切断の直下）は変えずに、そのまま伏図レベルごとに効く。
- **床・耐力壁・火打**は、下端（床・耐力壁）・配置点の高さ（火打）にいちばん近い伏図レベルの
  レイヤへ置く。仕口は横架材と同じレイヤ。仕口の「同じレイヤの材だけを受ける材とみなす」
  判定と寸法の「標準の天端との差」は、印を外した元のレイヤで見る（`core::stripPlanLevelTag`）
  ので、振り分けで結果が変わらない。重ね順（床は背面・耐力壁は前面）も印を外した種別で効く。
- **タイトル**: 階に伏図が 2 枚以上あるときだけ高さを添える（`2階床伏図（FL-872）`。まとめた
  ものは `（FL-872・FL-771）`）。全部まとめて階に 1 枚なら従来のタイトル。番号は伏図レベルの
  順に 2 から連番で、母屋伏図はその続き。
- **高さの表記は FL・軒高から**（round 1 の後のご要望。GL 基準では分かりにくい）。印・
  タイトル・設定ダイアログの行とも、一般階はその階の FL、最上階は軒高（どちらもストーリの
  高さ）からの差で書く（`FL-872` / `軒高-832` / 差 0 は `軒高±0`）。基準の名前が付くので、
  印を外す判定（`stripPlanLevelTag`）は「FL か軒高＋符号」で始まる括弧だけを剥がす。
  **設定の鍵（`core::PlanLevelKey`）は GL からの高さのまま**——FL を知るには IFC が要り、
  鍵は読み直しても変わらない値でなければならない。そのため診断ログの設定の行だけは GL で書く。
  床のレイヤ（`2-FL(FL-872)`）の印も**伏図レベル（横架材の天端）の高さ**で、床そのものの
  高さではない（同じ伏図レベルのレイヤは同じ印でそろえる）。
- **データタグの高さは常に FL 基準**（round 1 の後のご要望）。タグは断面寸法の後ろに
  構造材の IPZL（挿入点のレイヤからの高さ）を添えていたが、横架材が高さごとのレイヤへ
  分かれると基準がレイヤごとに変わる（GL+2699 の梁は自分のレイヤ上では 0 になり、注記が
  消えた）。そこで**解析側がその階の FL から測った値を階名付きの文字で書き**
  （`core::TagCommand::note`・`parse/Tag` の `memberLevelNote`）、描画側は式の後ろへ
  **二重引用符で囲んだ文字列**として置く（裸で続けたら "(" や "-" が式の演算子と読まれ、
  式全体が評価されずに `#StructuralMember#.#MajorBreadth#…` のまま表示された。実機）。形は `(2FL -872)`、傾斜材は低い端〜高い端で
  `(2FL -872~-40)`、最上階は階名（RFL）ではなく `(軒高 -1,570~-302)`（RFL は図面で使わない。
  round 2 の後のご要望）、数値は 3 桁ごとにコンマ（`core::signedMillimetreText`。伏図レベルの高さの表記も同じ）。
  * **添えるのは階の標準の高さと違う水平な材と、傾斜材**。標準は柱・床版から推した
    横架材天端ではなく**その値にいちばん近い実在の横架材の高さ**
    （`standardBeamHeights`）——グレー本モデルプラン1 は横架材が FL ちょうどで推した値が
    FL−100 なので、推した値で比べると全部の梁に `(1FL ±0)` が付く。母屋は標準より高いので
    従来どおり高さが付く。
  * **隅木・谷木には添えない**（垂木に近い材。ご要望）。ホームズ君は隅木と谷木を 1 つの
    種別（`木梁:隅木・谷木`）で出し、クラスは高さから床梁・母屋へ推定されるので、IFC の
    名前で見分けて命令に持たせた（`MemberCommand::hipOrValley`）。
  * ~~文字なので取り込んだ時点の値で、材を動かしても追随しない（IPZL は追随した）。~~
    → **部材の高さに連動**させた（下記「データタグの高さを部材に連動させる」）。
- **設定ダイアログ**は IFC を選んだ直後に表示するので、**取り込みの前に IFC を 1 度読んで**
  高さの候補を集める（`parse::scanPlanLevelChoices`。解析は 0.3 秒程度）。候補の高さは本番と
  同じ解析（`Context::rawMembers`）から取るので必ず一致する。まとめる相手の居ない高さ（階の
  最も低い高さ）は並べず、同じ階の高さが 1 つしかない建物では欄ごと出ない。行の数が IFC 次第
  なので、チェックはイベントマップに載せず DDX だけで受ける。往復の記憶にも `merge.level=` で
  書く（2 周目以降が同じ条件で走るように）。

**実機確認**（VW 2026 / macOS。PR #172 の 63da6a8・`model-8bc01e.ifc`。設定で 2 階の 3 つの
高さと小屋の 2 つの高さを前の高さとまとめた round 1）: 設定ダイアログの「伏図のまとめ方」が
出てまとめ方が効き、**描画は問題なし**（利用者の確認）。そこで出たご要望が上の「高さの表記は
FL・軒高から」。

**データタグの高さを部材に連動させる**（M36 の後のご要望）。文字の注記は材を動かすと嘘に
なるので、注記の数値をタグの式で部材から読む。式は SDK リファレンス
[Findings「Data Tags」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Data%20Tags.md)
の「傾斜材の両端の天端」の推奨形に、「単位・精度の修飾子」の書式を足したもの:

```
" (2FL "#IPZS##mm_0_0#thsep#sign#"~"@#ZTBBS#<>#IPZS#:""#ZTBBS##mm_0_0#thsep#sign#@#ZTBBS#<>#IPZS#:""")"
```

- **読む高さ**: `#IPZS#`＝始端の天端、`#ZTBBS#`＝外接の上面＝高い端の天端（断面の角は天端より
  上に出ない）。どちらも「絶対Z − 部材の居るレイヤが属する階の高さ」なので、IPZL と違って
  **高さごとに分かれた伏図のレイヤでも基準はその階の FL（最上階は軒高＝その階の高さ）のまま**。
  条件 `"~"@#ZTBBS#<>#IPZS#:""` で両端が同じなら `~高い端` を畳むので、**水平な材と傾斜材で
  式を分けない**（後から材を傾けても注記が追随する）。演算は混ぜない（連結と混ぜると式が
  空になるか括弧が印字される）。
- **書式**: `#mm_0_0#thsep#sign#` で mm の整数・3 桁のコンマ・正に `+`・0 は `±0`——取り込んだ
  時点の文字（`core::signedMillimetreText`）と同じ体裁（round 1 の後のご要望。`#thsep#` は
  単位・精度の修飾子の後ろでだけ効く。単位の修飾子は値を換算するので必ず mm）。
- **始端は低い端**: 始端が高い端だと `#IPZS#` も `#ZTBBS#` も高い端になり、注記が `(2FL -40)`
  に化ける（エラーにならない）。描画側は横架材を作る直前に `core::memberLowEndFirst` で
  端点・天端・高さ基準・端部オフセットを入れ替え、低い端を始端にする（材の形は変わらない。
  高さ基準の ID 0 がパスの始点）。
- **命令**: 解析側は従来の文字（`TagCommand::note`）に加え、注記を添える材に基準の名前
  （`TagCommand::noteDatum`。"2FL" / "軒高"）を持たせる（`parse/Tag` の
  `memberLevelNoteParts`）。どの材に添えるか（標準の高さと違う水平な材・傾斜材。隅木・谷木は
  除く）は取り込んだ時点で決まり、そこは変わらない。
- **階に属さないレイヤでは文字へ倒す**。`#IPZS#` は階に属さないレイヤでは黙って絶対Z を
  返す（Findings の落とし穴）。描画側は関連付け先の横架材のレイヤが階に属すること
  （`GetStoryOfLayer`）を確かめ、だめなら文字で置いて件数を診断へ出す（`draw/Tag` の
  `LinksHeight`）。取り込みの横架材は階のレベルのレイヤに居るので、通常は 0 件。

**実機確認**（PR #182 の 2faa796・`model-8bc01e.ifc`。水平な材だけ `" (2FL "#IPZS#")"` で
連動させた round 1）: 注記が出て、材を動かすと追随し、最上階は軒高基準（利用者の確認）。
ただし `-1236` とコンマが無く、`+` も付かない——そこで出たご要望が上の書式と傾斜材の連動。
上の式（PR #182 の c115be6・`model-9bbf97.ifc`）は round 1 で**ご要望どおりの書式で出た**
（利用者の確認）。高さを連動できずに文字へ倒したタグは 0 件。
