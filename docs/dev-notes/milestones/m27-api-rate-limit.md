# 往復が 1 時間 60 回の壁に当たる（M27）

**症状は「実機テスト中に『ビルドを確認できませんでした（リリース一覧を取得できません
でした。）』が出続ける」。** 直前まで同じ往復が何周も回っていて、心当たりは Mac が一度
スリープしたことだけ——ネットワークが切れたようにしか見えなかった。

**切り分けの決め手は、同じ周の中で PR の確認だけが通っていたこと。** 往復の 1 周期は
`vw-feedback`（PR が open か・止めろの合図が付いたか）→ `vw-update q-dev`（新しいビルドが
出たか）の順に GitHub へ 2 回要求を送る。前者は通り、後者だけが失敗していた。回線が切れているなら
前者から失敗するので、これは**ネットワークの問題ではない**。2 つの違いはただ 1 つ、
**`vw-feedback` はトークンを付けていて、`vw-update` は付けていなかった**ことである。

認証なしの GitHub REST は **IP ごとに 1 時間 60 回**。往復のパレットは **1 分ごと**に
`q-dev` を呼ぶので、これだけで**ちょうど上限**に張り付く——取り込みコマンドの頭の確認・
パレットの「今すぐ確認」・同じ回線のもう 1 台が 1 回でも挟まれば超え、以後その時間内は
403 が返り続ける。スリープは無関係で、単に**上限に達する時刻が来ていた**。

直し方は 2 つとも「当たり前のことをしていなかった」類である。

- **トークンがあるなら必ず付ける。** 投稿に使っているものが既にキーチェーン（Windows は
  DPAPI のファイル）に入っているのだから、読むほうにも同じものを使えばよい。認証ありは
  1 時間 5000 回で、1 分ごとの確認では事実上上限に達しない。**在り処は 1 か所**に置き
  （`scripts/vw-token.sh` / `.ps1`）、`vw-feedback` と `vw-update` の両方が source する
  （`vw-feedback` は M38 で削除し、いまは `vw-update` だけ）
  ——キーチェーンの service 名や探索順を 2 か所に書くと、片方だけ直して行方不明になる。
  **無くても止まらない**（公開リポジトリなので認証なしでも読める）。
- **失敗の理由を必ず言う。** `curl -f` は HTTP の番号も本文も捨てるので、403 も 500 も
  DNS 不達も「取得できませんでした」の 1 種類になり区別されなくなっていた。無人で回る
  往復では**パレットに出る 1 行だけが手掛かり**なので、番号・curl の終了コード・API 制限なら**いつ戻るか**まで
  載せる（`api_get` → `http_reason` / `curl_reason`）。今回は 1 行のせいで「スリープの
  せいか」と疑うところから始めることになった。

**教訓は「無認証の API 呼び出しには、必ず回数の天井がある」。** 周期処理を追加するときは
1 時間あたり何回になるかを数えること——1 分ごとは 60 回で、たいていの無認証の枠は
ちょうどそこにある。
