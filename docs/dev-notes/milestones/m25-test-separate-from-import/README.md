# 実機テストを本番の取り込みから分ける（M25）

（実機テストを本番の取り込みから分ける（M25）は 4 ページに分けてある: **入口を分ける** → [前の周の図を取り除く・取り消す](layer-removal-and-undo.md) → [作業ファイルを開き直す](work-file.md) → [無人の周を勝手に回さない・止めない](unattended-rounds.md)）

**動機は「dev ビルドを改造していると、本番との乖離がバグの入り口になる」という指摘。**
M23〜M24 で往復（実機フィードバック）を積み上げた結果、それが**本番の取り込みコマンドの
中**へ織り込まれていた。しかも `#ifdef VW_DEV_BUILD` の外なので、**安定版にも同じ制御フローが
コンパイルされていた**:

| 本番の経路にあった往復の都合 | どこ |
| --- | --- |
| 記憶を読み、続きの周ならファイル選択と設定ダイアログを飛ばす | `runImportCommand()` の冒頭 |
| 戻り値 `bool` の意味が「次は更新を尋ねずに入れてよいか」 | `runImportCommand()` の型そのもの |
| 投稿できたら結果ダイアログを出さずに返る | `runImportCommand()` の末尾 |
| `sAutoUpdateNextImport` の static・`UpdateCheckKind::Auto`・`ArmFeedbackLoop()` | `ExtMenu::DoInterface()` |

`feedbackAvailable()` が安定版で false を返すので**動きはしなかった**が、分岐は在った。
「開発版だけの機能」と言いながら、実際には本番の入口の形が開発の都合で決まっていた。

**直し方は「入口をもう 1 つ立てる」。** 往復をまとめて dev だけの新しいメニューコマンド
**「実機テストを実行…」**（`Extensions/ExtTestMenu` ＋ 本体の `draw::runTestRound`）へ移し、
本番の取り込みコマンドからは往復の分岐を 1 つ残らず取り除いた。両者が共有するのは**描画を
行うところだけ**（`draw/ImportRun.h` の `runImportRound`）である。

```
            ┌─ Extensions/ExtMenu ──── draw/runImportCommand ─┐
                （本番。往復を知らない）                       │
                                                              ├─ draw/runImportRound
            └─ Extensions/ExtTestMenu ─ draw/runTestRound ────┘   （解析 → 描画 → 集計）
                （dev だけ。往復を知っているのはここだけ）
```

**テストで走るのは本番と同じコードである。** 違うのは「引数を誰が用意するか」だけ——本番は
ファイル選択と設定ダイアログが、テストは記憶が用意する。ダイアログそのものは往復の対象外に
なるが、それらは描画結果に影響しないので実機確認の対象でもない。

## 同じビルドでは取り込まない（round 1 が二重に投稿された）

実機で、**パレットが開いている最中に人がメニューの取り込みを実行**したところ、同じビルド
（`a618af6`）で round 1 がもう一度投稿された。M24 まではそこを「新しいビルドを待っている
あいだに実行した ＝ 新しい 1 周目」と読み、記憶を数え直していたためである。

数字は 1 通目と 1 つも変わらない——**同じビルドで取り込み直せば同じ結果になる**のだから
当然で、その 1 分は最初から無駄だった。M25 では `runTestRound` が手前で折り返す:

- 記憶があり、動いているビルドがそれと**違う** → 続きの周として取り込む
- 記憶があり、**同じ**ビルドが動いている → **取り込まない**。往復を回す（止まっていたら
  回し直す）だけにする
- 記憶が無い → 1 周目として尋ねてから取り込む

2 番目の折り返しは、止めた往復を**取り込みなしで**再開する入口も兼ねる（パレットを閉じた・
「往復を止める」を押した、のあとにメニューを押せばその場でまた回り出す）。
`planFeedbackRound` の `waitingForNewBuild` の枝はこれで用が無くなったので削除した。

**この場合分けは `core::feedbackRoundKind` に出して無 SDK でテストしてある。** SDK も IFC も
知らない純粋な判断であり、しかも**M25 の要点そのもの**なので、描画側に分散させると次に誰かが
「同じビルドでも取り込み直そう」と書き戻したときに気付けない。

（この折り返しは二重投稿の歯止めだったので、PR への投稿を削除した
[M38](../m38-local-mcp-verification.md#決めたこと) で「同じビルドでも取り込む」へ改めた。
場合分けの置き場所は `core::feedbackRoundKind` のまま。）

## 分けたのは言葉のほうまで（結果ダイアログで露見した）

コマンドを分けたあと、実機で**本番の取り込みの完了ダイアログに「PR への投稿: コメントを
投稿できませんでした」が出た**。分けたはずのものが、押した人の目には分かれていなかった。

原因は、実機テストの周が**取り込みコマンドの完了文言を借りて、その後ろへ PR の話を追加して
いた**こと:

```cpp
std::string body = round.body;                    // parse::formatImportResult の文
if (!postError.empty())
    body += "\n\nPR への投稿: " + postError;      // ← 借り物に足していた
showImportResult("ホームズ君 IFC 取り込み", body, log);   // ← タイトルまで本番のもの
```

タイトルを変えるだけでは足りない。**借りている文そのものが取り込みコマンドの持ち物**で、
そこへ往復の話を追加する限り、実装の置き場所は間違っている。実機テストは自分の言葉で結果を
示すべきで、`parse::formatTestRoundResult`（`ImportFailed` / `PostFailed`）を新しく置き、
`round.body` を 1 か所も使わない形にした。

**共有してよいのは表示の仕組み、共有してはいけないのは文言。** `draw/ResultDialog`（短い本文＋
折り畳んだログ欄）は 1 つきりの実装なので両方が使ってよい——`draw/ImportRun` を共有する
のと同じ理屈である。分かれているべきなのは、そこへ何を書くかのほうだった。

## 「打ち切った調査」は、書いてあることについての規則である

利用者から「前の周の図を消すには取り消しコマンドを呼び出せばよいのでは」という指摘を受けて
`Findings/` を調べ直したとき、**その筋は打ち切った調査に含まれていなかった**。#23 が
調べたのは ISDK の undo API とレイヤの直接削除の 2 つで、メニューコマンドの起動は探して
いない。似た話題だからといって「もう調べた」と読むと、**本当はまだ残っている手段を除外してしまう**。
起票した #27 の結論は「できない」だったが、確定したこと自体に意味がある——`Findings/` に
無ければ、それは「調べた結果それが無い」ではなく「調べていない」である。
