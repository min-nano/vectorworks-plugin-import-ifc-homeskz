# 前の周の図を取り除く・取り消す（M25）

（実機テストを本番の取り込みから分ける（M25）は 4 ページに分けてある: [入口を分ける](README.md) → **前の周の図を取り除く・取り消す** → [作業ファイルを開き直す](work-file.md) → [無人の周を勝手に回さない・止めない](unattended-rounds.md)）

## 前の周の図は、プラグインが自分で取り除く

テストの周は同じ文書へ何度も描くので、前の周を戻していないと図が重なる。M23〜M24 では
人が周と周のあいだに手で「取り消し」を実行して回避していたが、往復を自動にした以上
そこだけ人手が残るのは筋が通らない。

**プログラムから「取り消し」を掛ける道は 2 つとも閉じている。**

| 筋 | 結論 |
| --- | --- |
| ISDK の undo 実行 API（`SupportUndoAndRemove` / `UndoAndRemove`） | **できない。** 扱えるのは「まだ `EndUndoEvent` していない、その回のイベント」だけ（[#23](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/23)） |
| メニューコマンドを名前で起動する（VectorScript の `DoMenuTextByName` 相当） | **できない。** その名前が現れるのは `Include/vs.py`（コンパイル対象外のスタブ）だけで、ISDK / VWFC / 実装ソースのどこにも実行系の API が無い（[#27](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/27)） |

残る唯一の道が**レイヤのハンドルを直接 `DeleteObject` する**ことで、これは実機で確認
されている（[#25](https://github.com/min-nano/vectorworks-developer-sdk-reference/pull/25)）。
非アクティブなデザインレイヤも、アクティブレイヤ自身も、落ちずに消える。

**落とし穴が 1 つある。** `DeleteObject(h, useUndo=true)` は、呼び出し時点で undo イベントが
開いていなければ**自分で開き、閉じないまま残す**（実測）。これは「空のイベントや半端な記録を
取り消すと図面が壊れる」という M15 以来の注意点に、`DeleteObject` を呼ぶだけで自分から
踏み込む経路である。だから**呼ぶ側が `SetUndoMethod` ＋ `NameUndoEvent` で開き、
`EndUndoEvent`（1 枚も消せなければ `EndAndRemoveUndoEvent`）まで閉じる**——`ImportUndoScope`
と同じ RAII を削除にも当てる（`draw/DrawUtil` の `RemoveCreatedLayers`）。

**消してよいのは「前の周が自分で作ったレイヤ」だけ。** ここが設計の要点である。
「1 周目に採った基準に無いレイヤ」を消す作りにすると、**利用者が別の用途で足したレイヤまで
巻き込む**——基準は「取り込み前に在って、かつ描き込んだレイヤ」しか並べないので、触って
いないレイヤは基準に載らない。そこで `ImportUndoScope` が**作ったレイヤの名前**を控え、
`DrawCounts::createdLayers` / `createdSheets` として持ち帰り、投稿できた周の終わりに記憶
（`core::FeedbackSession::lastCreatedLayers` / `lastCreatedSheets`）へ移す。次の周はその
名前だけを消す。安全弁は 3 つ——**名前が一致すること・種別が一致すること**（同名の別種別は
消さない）・**消したあとにレイヤが 1 枚も無くならないこと**（全部消した図面は Findings でも
未確認）。

**シートを先に消す。** 「ビューポートが参照しているデザインレイヤを先に消したときの影響」は
Findings で未確認のまま残っている。シート（＝ビューポートが載っている側）を先に消せば
その場面自体が起きないので、順序を `RemoveCreatedLayers` の中で固定して呼ぶ側に委ねない。

**ここは根拠が `Findings/` に追いついていない。** 「ビューポートの載ったシートレイヤを消す」
こと自体が #25 の未確認リストに残っており、順序を固定しても最初の 1 手はその領域に入る。
それでも先に実装したのは、(1) `DeleteObject` をレイヤへ呼ぶこと自体は確認済みでシートか
デザインかで呼び出しが変わらない、(2) 走るのは dev の実機テストだけで対象は開発者が見て
いる試験用の図面、(3) 消す相手を名前で限定し、種別一致と「最後の 1 枚は消さない」の安全弁を
通してある、の 3 つによる。**本来の順序とは逆なので**
[issue #29](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/29) を
立ててあり、「壊れる」という結論が出たらこちらを直す（シートは消さずビューポートだけ
個別に消す等）。

**ただしこれは部分的な復元でしかない。** 取り込みは**テンプレートにもとから在るレイヤにも
描く**（実機の 1 周目で実際に 1 枚あった）。そのレイヤは自分が作ったものではないので消せず、
**上に描いた分だけが残る**——`DrawCounts::undoPartial` はまさにこれを測るフラグで、Findings の
「処理前から在ったレイヤへ描いた分は、そのレイヤごと消すわけにいかないので戻らない」が
そのまま当てはまる。**テンプレート次第で残り方が変わるので、安定した復元にはならない。**

だから PR コメントの末尾は**実測で分岐する**——`undoPartial` が立った周だけ「取り込み前から
在ったレイヤへ描いた分は取り除けません」と言い、そうでない周だけ「取り消しは要りません」と
言い切る。「たぶん大丈夫」を既定にしない。

**丸ごと戻すには undo が要るが、その道は 4 本とも塞がっている。** 順に潰した:

| 筋 | 結論 | 根拠 |
| --- | --- | --- |
| 閉じたイベントへ Undo を掛ける | できない | `UndoAndRemove` の対象は未クローズのイベントだけ（[#23](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/23)） |
| メニューの「取り消し」を名前で起動する | できない | `DoMenuTextByName` 相当が SDK に無い（[#27](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/27)） |
| **イベントを閉じずに返し、次の実行から戻す** | できない | VW がコマンド完了時に代わりに閉じる（[#31](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/31)） |
| **スクリプトエンジン経由で `DoMenuTextByName('Undo', 0)` を呼ぶ** | できない | スクリプトは走る（`VCOMError=0`）のに**取り消しは 1 段も掛からない**。しかも呼ぶと**開いている undo イベントが勝手に終わらされる**（[#39](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/39)。実機確認済み） |

3 つ目は「**その『閉じている』を作っているのはこちらのコード**（`ImportUndoScope` の RAII）
なのだから、意図的に閉じずに返せばよいのでは」という筋で、#23 でも #27 でも調べていなかった
ため #31 として起票した。答えは `GS_EndUndoEvent` 自身の説明文にあった:

> The use of this procedure is not required; VectorWorks will automatically end the event
> **when an external is completed.**

`EndUndoEvent()` を呼ぶこと自体が必須ではなく、**呼ばなくても VW が「外部（＝そのコマンドの
実行）が完了した時点」で自動的に閉じる**。だから「呼ばずに返す」を選んでもイベントは残らず、
次の実行から見れば #23 と同じ「もう閉じたイベント」になる。

**同じ 1 文を、このリポジトリは以前から引用していた**——冒頭の「`GS_EndUndoEvent` の説明に
ある『外部の終了時に自動で閉じる』は『自動で開く』ではない」がそれである。当時は「VW が
勝手にイベントを開くわけではない」という含意だけを読んでいて、「呼ばなくても勝手に閉じる」
という**もう半分の含意**は読み落としていた。**根拠として引いた文は、引いた目的の外側まで
読む**。

したがって「前の周の図を丸ごと戻す」はプラグインには担えない。レイヤ削除（部分復元）で
できるところまでやり、**残る分は利用者に伝える**という運用に落ち着く。

**そして実機では、まだ一度も消していない。** round 1〜3 の「準備:」はどれも
`デザイン 0/23 枚・シート 0/14 枚`——記憶していた名前のレイヤが図面に 1 つも無かった、
つまり毎回まっさらな（または手で取り消した）図面で走っていた、という意味である。
**枚数が 0 のまま成功と読まない**——0 は「消す必要が無かった」であって「消せた」ではなく、
安全弁も削除そのものも通っていない。`RemoveCreatedLayers` を実機で確かめるには
**前の周の図を残した図面**で次の周を走らせるしかなく、issue #29 の危険域（ビューポートの
載ったシートを消す）に触れるのもそのときが初めてになる。

## 「取り消し」は結局こちらから掛けられた（reference #39 の 2 度目の結論）

M23 から M25 まで、この往復は**「プラグインから前回の取り込みを取り消せない」を前提**に
組んできた——レイヤを名指しで消す、作業ファイルを開き直す、という 2 段の控えは、どちらも
その前提の上にある。SDK リファレンス #39 の**2 度目の調査**でその前提が崩れた:
**VectorScript エンジンに `DoMenuTextByName('Undo', 0)` を走らせれば取り消しは実際に効く**
（複数段も可）。1 度目に「効かない」と見えたのは、**測るのに使ったマーカーを C++ が undo
イベントの外で作っていた**からで、取り消しの対象にそもそも入っていなかった。

**このプラグインには当てはまる。** 取り込みは自分で undo イベントを開き、作ったレイヤを
登録している（`ImportUndoScope`）——つまり**取り消しスタックに載っている**。利用者に
「取り消しを押してください」と頼んでいたもの、そのものをこちらから起こせる。

効くと何が変わるか。**取り込み前から在ったレイヤ（テンプレートの「共通」等）へ描いた分まで
戻る**。レイヤ削除は自分が作ったレイヤにしか届かず、作業ファイルの開き直しは図面ごと
差し替えるので前の周の絵は消えるが**開き直しそのものが失敗しうる**——取り消しはそのどちらの
穴も塞ぐ。そこで戻し方を**取り消し → 開き直し → レイヤ削除**の 3 段構えにし、**順序を
入れ替えない**（前が効けば後ろは要らない）。

**押してよい場面を絞ったのは、取り消しが「誰の操作か」を選べないから。** スタックの上に
あるのが自分の取り込みだという根拠を 2 つ揃えたときだけ押す——**いま開いているのが自分の
作業ファイル**であること、**前の周が作ったレイヤが実際に残っている**こと。利用者の図面で
押せば、消えるのは利用者自身の編集である。効いたかどうかも**読み戻して**確かめる
（戻り値は「スクリプトを走らせられたか」しか言わない）。

**実機で効いた**（round 18）。「準備: 前の周の取り込みを取り消しました（**1 段**）。取り込み前
から在ったレイヤへ描いた分も戻っています」——**開き直しは起きず**、「図面の状態」は
「取り込み前の状態へ戻してから実行されています」。所要 76.8 秒はここまでで最速だった
（開き直しの分がまるごと消える）。**1 段で足りた**のは、取り込みがちょうど 1 つの undo
イベントになっているためである。

**これは SDK の側にも返すべき実測である。** リファレンス #39 は「呼び出し元（C++）がした
ことには届かない」で締めているが、正確には**「undo イベントに登録してあれば届く」**——
別のコマンド実行から**前回の取り込みを丸ごと戻せた**のは、この round 18 が初めての実測。
プローブが「届かない」と見えたのは、比較に使ったレイヤをイベントの外で作っていたからで、
本プラグインのように登録していれば話が変わる。

**打ち切った調査は「もう調べない」ではなく「その問いは閉じた」である。** #23 / #27 / #31 /
#39 の 4 本は「ISDK の API から丸ごと戻す」筋を塞いだままで、そこは変わっていない。開いた
のは**別の筋**（スクリプトエンジン越し）で、しかも 1 度目の結論を**実機の足跡で覆した**もの
だった。CLAUDE.md の「打ち切った調査に書いてあることは再調査しない」は**書いてあることに
ついての規則**であって、隣の筋を試さない理由にはならない（M25「『打ち切った調査』は、
書いてあることについての規則である」と同じ話が、今度は結論の側で起きた）。
