## 隠れたパレットは止まらない（往復が勝手に走り出した）

実機で 2 つ続けて出た報告——**「パレットが開いていなくても自動で往復が走り始める」**と
**「閉じるを押しても実機確認のプロセスが死なない」**——は、どちらも同じ 1 つの思い違いから
来ていた: **パレットを隠すことと、パレットの中の時計が止まることは別である。**

`SetWebPaletteVisibility(false)` が消すのは見た目だけで、ページは生きたまま `setInterval` を
刻み続ける。そこへ、駆動が「**本体の記憶が `active` なら回す**」という作りだったのが重なる:

* 「閉じる」は `ShowFeedbackPalette(false)` だけだったので、**隠れたページが 5 秒おきに
  `tick()` を呼び続け**、往復はそのまま回っていた。止める口（パレット）はもう見えない。
* パレットのページが（隠れたまま・前のセッションの続きで）読み込まれていれば、その最初の
  `tick()` が記憶を読み、`active` を見て**誰も押していないのに周を回し始める**。人が押した
  かどうかを、駆動はどこにも記録していなかった。

**直し方は 2 つとも「回してよいのは人が始めた往復だけ」に寄せる。** 駆動は自分が武装したか
（`fArmed`。`Arm` / `BeginRound` で立ち、止まると下りる）だけを見て回し、**記憶が `active`
であることを理由に回さない**——記憶は「続きがある」であって「いま回っている」ではない。
そして「閉じる」は**止めてから隠す**（`FeedbackLoopHide`）。ボタンの文言も「止めて閉じる」に
した——押した結果が名前と違うボタンは、実機で必ず事故になる。

**隠せるものに、隠れている間の権限を持たせない。** 止める口が見えなくなる作りは、その口が
どれだけ立派でも設計として成り立っていない。

**実機で確かめた**（round 15 のあと）。パレットの「止めて閉じる」を押すと往復が止まり、PR へ
`control=ended`（理由「利用者がパレットを閉じました」）が 1 通載った——**閉じても止まらな
かった**以前の振る舞いは消えている。

**ただし、閉じたあと再実行しても往復が始まらなくなった。** 原因は隠す順序である。C++ 側は
「止める → 隠す → 返事」の順で動いていたが、**隠れたページはその返事を受け取れない**。
JS は呼び出し中を `busy` で塞ぐ作りなので、返事が来ないと **`busy` が立ちっぱなし**になり、
以後の `tick()` がすべて捨てられる。ページ自体は生きている（隠しても止まらなかったのがその
証拠）のに時計だけが黙るので、メニューで往復を武装させても誰も動かさない。

直しは 3 つとも「返事に頼らない」方向:

* 順序を**止める → 返事 → 隠す**にする。
* JS は**閉じる呼び出しの返事を待たない**（隠れたあとの見え方に意味は無い）。
* JS の `busy` を**時間で自動的に解く**（30 秒）。返事が来ない場面はほかにも有りうるし、
  パレットには他に回復の手立てが無い。

**「見えなくなるもの」と会話を続けない**——隠す・閉じる・降ろすの直前に投げた問いは、
返ってこないものとして書く。

**なお、この報告の見立ては半分外れていた。** 「再実行しても往復が始まらない」と読まれた
そのあと、パレットは実際には回っていて、新しいビルドを見つけて入れ、殻が変わったことを PR
へ投稿している——時計は動いていたのである。**本当の欠けは「始まったことが何も分からない」
ほう**だった: 同じビルドで押した周は取り込みを行わない（数字が変わらないので走らせないのが
正しい）が、**ダイアログも進捗も出ないので、押した人には何も起きていないように見える**。
手で押した周にだけ結末を返すようにした（`TestRoundOutcome::Rearmed`）。

**「正しく何もしない」ことは、黙っていてよい理由にならない。** 自動の周は黙ってよいが、
**人が押した操作には必ず結末を返す**。

## 図番が重なると Vectorworks が訊いてくる（実機で発覚）

別のモデル（スキップフロア）で本番の取り込みを走らせたところ、軸組図の作成中に
**「その図番は、このシートレイヤの他の図面ですでに使用中です。他の図面に新しい図番を
割り当てますか？」**というモーダルのダイアログが出た。押さない限り先へ進まない。

**これは絵の問題ではなく、無人で回せなくなる問題である。** 往復の周は誰も見ていない
ところで走るので、ダイアログが 1 枚出た時点でその周は止まる（取り込み全体も止まる）。

原因は採番の場所にある。通り名は**方向ごとに**採るので（X通りの切断位置の並び、Y通りの
切断位置の並び）、両方向が同じ綴りを出しうる——とりわけ**名前付きの通り芯が 1 本も拾え
ない図面では、どちらの方向も `1` から始まる連番**になる。軸組図はシートレイヤ 1 枚に
何枚も載るので、そこで図番が衝突する。

直し方は、**両方向を連結した直後に図番を一意にする**（`parse::uniqueSectionNumbers`。
2 つ目以降へ `(2)` … を足し、既にある綴りとぶつからなくなるまで進める）。連結した場所が、
両方向の綴りを突き合わせられる唯一の場所である。**SDK へ渡す前に潰す**のが要点で、
描画側で訊かれてから直す道は無い（訊いてきた時点で人の操作を待っている）。

**M32（図面ラベル）の後、図面によってはまた出るようになった。** 命令の図番は一意のままで
（全フィクスチャで確かめた）、すり替えていたのは**図面ラベル**である。ラベルは作った瞬間に
図番（`Drawing`）へ「そのシートレイヤで使われていない最小の正整数」を自動で持ち、注釈へ
入れた瞬間に**ラベルの値をビューポートへ押し込む**（Title と同じ向き。Findings
「Drawing Labels」）。Title は注釈へ入れた後に書き直していたが図番は書いておらず、
ビューポートの図番がラベルの自動の番号へすり替わって、同じシートの別の軸組図とぶつかって
いた（自動の番号は数として読める図番しか数えないので、当たるかは図面ごとの図番の並びで
変わる）。**注釈へ入れる前と後の両方でラベルの `Drawing` に命令の図番を書く**
（`draw/DrawingLabel` の `drawSectionLabel`）。図番はレイアウトから落としてあるので絵には
出ない。
