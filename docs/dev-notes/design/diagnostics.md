# 診断・完了報告の方針（M15/M19）

進捗ダイアログ・診断ログ・例外境界の SDK 作法は SDK リファレンスの
[進捗・診断](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Progress%20and%20Diagnostics.md)
にある。このプラグインとしての決め事は次のとおり。

- **進捗バーの重みは実測で按分する**（`core::drawWeight`）。1 件あたりの重さは要素で
  **3 桁**違った——仕口 0.1ms/件・アンカーボルト 0.1ms/件に対し、底盤 670ms/件・軸組図
  520ms/枚・伏図 480ms/枚・横架材 130ms/本。件数比で配分すると、シンボル 472 件（全命令の
  4 割超）が 0.05 秒でバーを 4 割進め、17 秒かかる軸組図 33 枚が 3% しか進まない**実態と
  合わない進捗**になる。
- **完了ダイアログは読まれない前提で組む（M19）。** ダイアログは「どのファイルを・
  成功したか・問題はあったか」の 3 つに絞り、内訳・注意・記録はログへ移す。残すのは
  **その場で操作が要ること**だけ——伏図・軸組図の「1 回更新」と、「取り消し」が通常の操作では
  機能しないときの注記。**描画できた件数も所要時間も出さない**（うまくいっているときには読む
  必要が無く、うまくいっていないときはその数だけでは足りない。どちらもログにある）。
  **当たり前のことは書かない**（1 回で戻せるときは何も出さない）。
- **「問題あり」の判定には、平常でも出る説明を混ぜない（M19）。** 異常＝
  `DrawCounts::diagnostics`（完了ダイアログの「問題あり」の根拠）／平常の記録＝
  `DrawCounts::notes`（ログにだけ出る）と行き先を分け、前者だけを結末の判断
  （`parse::importOutcome`）に使う。
- **ログは取り込みのたびに必ず開く（M19）。** 「困ったらログを貼る」を運用の柱にした
  以上、要るときに限って無いのでは意味がない。ログは**ファイルと同時にメモリにも蓄積する**
  （`core::trace::text`）——一時ディレクトリへ書けない環境でもダイアログのログ欄には
  出せるし、表示のためにファイルを読み込み直さずに済む。置き場所はログ自身の見出しに書き、書けなかった
  ときは省略せず「ファイルは無い」と出す。
- **ログの見出しは「どのリビジョンを・いつ・どのファイルに対して動かしたか」（M19）。**
  dev ビルドは PR ごとに中身が違うので、これが無いと「直したはずの不具合」の報告を古い
  ビルドと取り違える。ビルド情報を組み立てるのは SDK 側（`draw/ImportRun` の
  `currentBuildInfo`）——`BuildConfig.h` のマクロを参照できるのはそちらだけで、`parse/Summary`
  は受け取った文字列を並べるだけ。（VW 本体のバージョンは C++ SDK から取れないため、見出しに
  無い。）
- **診断ログへの書き出し口は 2 か所だけ**（`core/Progress` の `beginPhase` と
  `draw/ImportRun`。見出し・区切り・結果・例外）。各要素に `trace::log` を書かず、記録は
  `core::DrawCounts` の diagnostics / notes へ返す。例外は耐力壁 PIO のリセット
  （`draw/ShearWallPio`）だけで、Vectorworks から直に呼ばれる別の入口なので、取り込みの
  最中に限り 1 枚ずつ自身で記録する（リセットの途中で異常終了したときに、どの壁かが最終行に残る）。
- **ログは階層で読む形にする。** 1 行の量より「目的の行へ飛べるか」を優先する。
  * **節**: `=== 準備 ===` → `=== 解析 ===` → `=== 描画 ===` → `=== 結果 ===`。
  * **フェーズ**: 節の下の `[  経過 ms] 見出し…`。経過ミリ秒は 6 桁へ右寄せし、その下の
    詳細（耐力壁のリセットなど）は 2 字下げる——桁が揃わないと字下げが読めない。
  * **耐力壁のリセットは 1 回 1 行**（`耐力壁 (原点 x, y): 内法…・記号の離れ…・高さ…・軸…`）。
    パラメータを書く前のリセットと、同じ取り込みの中で前回と同じ結果になったリセットは
    書かない。全部書いていた頃は 1 回の取り込みで 1600 行のうち 1460 行がこの行だった
    （122 枚 × リセット 4 回 × 3〜4 行）。
  * **結果の「注意:」「記録:」は 1 件 1 行。** 100 字を超える行は `parse/Summary` が
    「見出し:」の下へ項目（` / `・`。`、それでも長ければ `, ` で区切る。括弧の中では
    区切らない）を 1 段下げて並べ直す。描画側は従来どおり 1 件を 1 行で返せばよいが、
    数の「N / M」のように ` / ` を区切り以外で使わない。
  * **描画の内訳（dev の計測）は「分類:項目」の分類ごとに合計を出し**、項目を 1 段下げて
    並べる。1ms に満たない項目は分類ごとに「ほか N 項目」へまとめる（`core::TimingTable::format`）。
- **書いたものを読み戻す検算は開発ビルドだけ（M27）。** ストーリバウンドの record・PIO の
  パラメータ・PIO が持つパスを書いた直後に読み戻して命令と照合する検算は、
  `#if VW_DRAW_VERIFY`（`src/draw/Verify.h`）で dev ビルドにだけコンパイルする。
  **無効になるのは検算だけで、読み戻した結果が描画結果を変えるもの**——実数で入らなければ
  文字列で入れ直す `SetParamRealChecked`、追加した点を設定し直す `NurbsSetPt3D`、データタグの
  レイアウトの取得し直し、シンボルが配置できたことを確認してから数える `draw/Symbol`——
  **は本番でも動作する**（基準は「無効にしたら利用者の描画結果が変わるか」。
  CLAUDE.md「検算は開発ビルドだけに置く」）。**`#if` の中は dev の CI でしか型検査されない**
  ので、両方の分岐が通ることは `ci-debug` の `build`（既定で両チャンネル）で確かめる。
  検算は**実機フィードバックの往復で描画結果の破綻を数値から追跡するための補助の仕組み**で
  ある（「柱が長さ 0 で描かれる（M27）」はこれで解決した）。利用者にとっては**取り込みの
  たびに数百〜数千回パラメータを走査する負担**でしかなく、出てくる文言も開発者にしか意味が
  無い。
