# アーキテクチャの土台

## 2 フェーズ分離が全ての土台

処理を **IFC 解析（`src/parse/`）** と **VW 描画（`src/draw/`）** に完全分離し、両者を
**命令セット（`src/core/Document.h`）だけ**でつなぐ。`parse/` と `core/` は SDK を一切
include しないので、SDK 無し（約 800MB のダウンロード無し）で**コンパイルも単体テストも
できる**——これがこのリポジトリの生産性のほぼ全てを支えている。

- 解析ロジックは**実 IFC に対して CI で常時テストできる**（`tests/`）。
- 描画は実機でしか確かめられないが、**描画へ渡す値は先に確定できる**。だから実機での
  切り分けが「命令セットの値が違うのか／SDK の呼び方が違うのか」の 2 択に絞れる。
- 依存の向きは CI が担保する（`core/` `parse/` を無 SDK でビルド・テストするジョブがある）。

**この分離を崩さないこと。** 「ここだけ SDK の型を使えれば楽」という理由で持ち込むと、
無 SDK テストの前提ごと崩れる。SDK の幾何型が要る計算は `core/Geometry.h` の自前 `Vec2` / `Vec3` /
`Mat4` で書き、`draw/` の入口で変換する。

## 命令セット（Document）の設計則

- **フェーズ間で運べないものを載せない。** SDK ハンドル・STEP エンティティポインタは
  Document に入れない。描画中に必要なハンドルの受け渡しは「命令インデックス → ハンドル」の
  対応表（`draw/ObjectHandles`）で行う（立上り → 壁結合、横架材 → データタグ、柱 → 記号）。
- **同型が並ぶところは 1 つの構造体へまとめる。** アンカーボルト・床束・火打・仕口は中身が
  同じなので `core::SymbolCommand` 1 つで受け、要素の区別は「Document のどのリストか」が
  担う（描画も `draw/Symbol` ただ 1 本）。
- **突き合わせが要る関係は入れ子で持つ。** データタグは `ViewportCommand::tags`、
  グラフィック凡例は `SheetCommand` の中。平らに並べて番号で突き合わせる形にすると、
  突き合わせ自体がバグの温床になる。
- **振り分けは解析側で完結させる。** 「このタグはどのビューポートに載るか」のような判断は
  `parse/` が決め、`draw/` は「渡されたものを置く」だけにする。伏図と軸組図で**描画実装を
  1 つ**にできるのはこのため。ただし**用紙に依るもの**（縮尺・用紙上の位置・軸組図の枚数）は
  描画時にしか決まらないので命令に持たせず、決め方の計算を `core/Layout` に置いて描画側が
  呼ぶ（[用紙の割り付けの決め事](page-layout.md)）。
- スキーマを変えるときは、構造体定義・`validateDocument`・テストを**同時に**更新する。

## レイヤ・クラス・レベルの規約は 1 か所に置く

同じ定数・述語を 2 か所に書かない。IFC 属性インデックス・レベル種別名・基礎のレイヤ名と
許容値・レイヤ名の組み立て・記号レイヤ名・構造クラス名などの唯一の置き場所は、開発ガイドの
[置き場所の一覧](../../development/placement-index.md)にまとめてある（ここには写さない）。
**要素を追加するときに変更する場所が 1 行で済む**形を保つ
（完了ダイアログの要素一覧が `parse/Summary.cpp` の `kElements` 表 1 つなのが典型）。
