# 実機確認の作法

**CI が全て緑でも、実描画（高さ・傾き・スタイル・PIO の挙動）は検証できない。** このリポジトリの
`draw/` に自動テストが無いのはそのためで、代わりに実機（ローカルの VectorWorks）で確かめる。
調査の一般的な作法（読み戻す・測る・正解と差分を取る・setter の戻り値を信じない）は
SDK リファレンスの
「[Investigation Techniques](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Investigation%20Techniques.md)」
にまとめてある。このプラグインでの進め方は次のとおり。

- **切り分けは「完了ダイアログの診断行」と「OIP の値」の読み合わせで進む。** 例えば柱の高さは、
  「鉛直パスが 2 点にならなかった件数」と OIP の 高さ／始端・終端オフセット／スパン・長さの
  組み合わせで、原因が解析側（命令の値）か描画側（パス・パラメータ）かを 1 周ごとに絞り込めた。
- **API の無い設定は「UI で手作業したもの」と見比べて突き止める。** 読み取り専用の
  ダンプを設定の前と後で 2 回取り、diff を見る（選択オブジェクトのパラメトリック
  レコード・付いているレコード・オブジェクト変数・文書内のビューポート一覧を
  [`scripts/vw-dump-pio-fields.py`](../../scripts/vw-dump-pio-fields.py) が書き出す）。
- **実機の出力にはビルドを添える。** M19 以降、診断ログの先頭に `CurrentBuildInfo()` が
  ブランチとコミットを書くので、報告に貼られたログを見ればどのビルドか分かる。
- **役目を終えた計装は消す。** 規約を詰めるための実測コード・一時診断コマンドは、確定と同時に
  外す（履歴に残っているので必要なら作り直せる）。
- **往復はローカルの Claude Code に回させる（M38）。** 開発版の MCP ブリッジ越しに、Claude が
  新しいビルドを入れ（`vw_update`）、要るなら再起動し（`vw_restart`）、同じ条件で取り込み直し
  （`vw_run_test`）、報告と診断ログを読む。1 周目も IFC とリポジトリのテンプレートを名指しして
  Claude が始められる（M40）ので、人がするのは「絵を見て一言書く」だけで、ビルドの入れ直し・
  ファイルの選び直し・ログの貼り付けは無い
  （開発ガイドの[「実機テスト」](../development/live-test/README.md)）。**数字で分かることは向こうが
  見る**ので、所見に書くのは**絵でしか分からないこと**（浮いている・傾いている・重なっている）
  にする。M23〜M37 は同じことを「dev ビルドが PR へ投稿し、パレットが新しいビルドを入れて
  取り込み直す」往復で回していた（[M23](milestones/m23-feedback-loop/README.md) / [M24](milestones/m24-feedback-palette.md) / [M38](milestones/m38-local-mcp-verification.md)）。
- **描画に触れる変更は、実機で確認できるまでマージしない**（[`CLAUDE.md`](../../CLAUDE.md)
  「開発プロセス: PR とマージ」）。未確認の描画が積み上がると、不具合が出たときにどの変更が
  原因か切り分けられなくなる。
- **実機で SDK の挙動として新しく分かったことは、SDK リファレンスの `Findings/` へ足す**
  （この開発メモではなく）。このプラグインの方針・入力データの癖は開発メモへ。
