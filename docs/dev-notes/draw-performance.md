# 描画の高速化（測って初めて場所が分かった）

取り込みの描画に 83〜112 秒かかっていた（測り始めた当時。直したあとの数字は下の各節の
「実機の数字」）。**最適化を始める前に測る**ことにして、区間計測
（`core/DrawTiming` ＋ `draw/Verify.h` の `VW_DRAW_TIMING`）を入れ、実機で 2 周まわした。
**その判断がこのページでいちばん価値のあった部分である**——測る前の仮説はほぼ全部外れていた。

## 測る前に何を予想し、実測がどう答えたか

先に、フェーズ単位の重さ（`core/Progress.cpp` の `kCosts`＝実測の 1 件あたりミリ秒）に
実データの命令数を掛けて見積もると、構造材（横架材＋柱）が 51〜68%、軸組図が 15〜19% と
出た。**「どのフェーズが重いか」までは、この見積もりで合っていた。**

外れたのは**その中の何が重いか**である。当時の推論はこうだった——`ResolveParamName` は
universal 名で一致しないとパラメータ表を先頭から走査するので、そこが重いのだろう、と。

実測（実機・macOS・木造 3 階建て・オブジェクト 1,319 件）の答え:

| 区間 | 合計 | 回数 | 1 回あたり |
| --- | ---: | ---: | ---: |
| `SetObjectClass`（クラスの割り当て） | 6,513ms | 2,025 | 3.22ms |
| `SetFColorsByClass`（面色） | 6,455ms | 1,770 | 3.65ms |
| `SetPColorsByClass`（ペン色） | 6,453ms | 1,770 | 3.65ms |
| `SetOpacityByClass`（不透明度） | 6,437ms | 1,770 | 3.64ms |
| `SetPPatByClass`（線種） | 6,433ms | 1,770 | 3.63ms |

**`SetObjectClass` ＋ 重い属性 6 つで 45.1 秒**——測れた分（69.2 秒）の **65%**、実所要
（83.4 秒）の **54%**。

最優先にしていた名前解決は **1,421 回で 9ms**（0.01%）。プラグインスタイルの関連付けは
463 回で 1ms。**実測が無ければ、全体の半分を素通りして 0.01% を最適化していた。**

## 何が重いのかが正確に分かった

3 つ並べると機構まで見える。

1. **重い 6 つが揃って同額**（6,424〜6,455ms、ばらつき 0.5%）。「どの属性か」は無関係で、
   **呼んだ回数だけ**が影響している。
2. **`SetArrowByClass` だけ 800 倍速い。** 同じ「by-class にする」呼び出しなのにコストがほぼ無い。
   だから**「書き込みそのものが重い」のではなく、「何かを無効化する書き込みだけが重い」**。
   マーカーはこの種のオブジェクトの描画キャッシュに関与しないのだろう。
3. **`AddClass` はコストがほぼ無い**（2,025 回で 4ms）。名前から索引を引くコストではない。

粗い粒度で測った 1 周目では、**同じ 2 関数（`SetClassByName` ＋ `SetAllAttributesByClass`）が
構造材で 82.8ms/回・データタグで 2.4ms/回と 34 倍違った**。実体（3D ソリッド）を持つ
オブジェクトほど高い、という傾向もある。

**したがって有効な対処は「キャッシュ」ではなく「呼ぶ回数を減らす」である。** どう減らせるかは
SDK の側の話なので、リファレンスへ起票した
（[#94](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/94)。文書の既定を
by-class にしてから作れば 7 つとも要らなくなるか／一括の呼び出しがあるか／作成前に反映させる方法が
あるか）。**答えが出るまで手を付けない**——ここで思いつきの順序変更を入れても、再生成の回数は
減らない。

## 1 周の数字で語ってはいけないものがある

2 周のあいだで**構成層（`SetComponents`）が 27.5 秒 → 0.34 秒（81 倍）変動した**。呼び出し回数
（51 回）も対象（立上り 45・スラブ 6）も同じで、コードは区間を割っただけである。実所要も
112.1 秒 → 83.4 秒（差 28.7 秒 ≒ 構成層の差 27.2 秒）と揃って動いているので、**時間の付け替え
ではなく、その仕事が本当に起きなかった**。

原因は分かっていない（文書の状態・VW のキャッシュ・機械の負荷のいずれか）。**分かっている
のは「構成層のコストは 1 周の数字では語れない」ということだけ**で、ここを直す判断をする前に
**同じ条件で複数周まわして再現するかを確認する**こと。逆に、クラスと属性の数字は 2 周とも同じ形で
出ているので、そちらは信頼してよい。

## #94 の答えと、それを受けた直し（構造材のクラスと属性は「作る前に既定で」）

[#94](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/94) の答えが
出た（[Findings「Attributes and Classes」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Attributes%20and%20Classes.md)）。

- **費用は書き込みではなく、それが起こす PIO の再計算**。構造材 PIO では
  `SetObjectClass` と 6 つの `Set*ByClass` が 1 回ごとに再計算を起こす（非 PIO ではコストが
  ほぼ無い。マーカーだけは再計算を起こさない）。上の表の 45 秒はほぼ全部が構造材 517 本 ×
  7 回である（データタグも PIO だが再計算が軽い）。
- **一括の呼び出しは無い。** 減らす方法は「**文書の既定を作る前に立てる**」だけで、そうすれば
  生成された PIO は最初からそのクラスに属し、6 属性も by-class になる。

そこで構造材（横架材・柱・垂木。3 つとも `draw/StructuralMember` の `DrawStructuralMember`
を通る）を次の形にした。

1. `CreateCustomObjectPath` の 1 行だけを `ScopedCreationClass`（`draw/DrawUtil`）で囲む。
   作る前に既定のクラスと既定の by-class を設定し、抜けるときに**設定した既定を元へ戻す**
   （最初の版はクラスと不透明度だけだった。下記「後始末」）。
2. 作った後は `FinishCreatedWithClass` が**既定を継承したかを読み戻し**（読むのは再計算を
   起こさない）、継承していればマーカーだけを by-class にする（コストはほぼ無い）。**継承して
   いなければ従来の `SetClassWithAttributes` で与え直す**——描画結果は変わらず、遅くなるだけ。その本数は開発ビルドの
   診断に「既定のクラスを継がず作った後に与え直した材」として出る。

**見込み**: 構造材 1 本あたり 7 回ぶんの再計算が無くなる。実測の表から 40 秒前後。**所要時間の
計測で確かめること**（区間「クラス:割り当て」と「属性:*」がほぼ 0 になり、代わりに「クラス:既定を
立てる」「クラス:既定を継いだかの読み戻し」が小さく出るはず）。

**後始末（既定を元へ戻す）**: 文書の既定は利用者の図面の設定なので、スコープを抜けるときに
すべて戻す。最初の版はクラスと不透明度しか戻せず、実機で「取り込みの後も既定がクラス
スタイルのまま」になった。ペン色・面色・線の太さ・線種・面パターンの既定の by-class には
解除する API が無いが、**既定の値を書くとそのフラグが解除される**と SDK リファレンスで確定した
（[#102](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/102)）。
そこで作る前に**値とフラグの両方**を退避し、戻すときは値を書き戻してから**元から設定されて
いたフラグだけ**を設定し直す（元から by-class の図面を壊さないため）。マーカーの既定は設定
しない（継承されないので設定する意味が無く、戻し方も未確定）。

**実機の数字（round 1〜2・PR #133）**: 所要 83.4 秒 → 44.3 / 41.3 秒。クラスの割り当てと
属性 6 つは合わせて 45.1 秒 → 約 1.9 秒（残りは非 PIO とデータタグへの per-object の書き込み）。
構造材は 517 本すべてが既定を継承して生成された（与え直し 0）。

**データタグ・スラブ・線などは従来のまま**（per-object で呼ぶ）。非 PIO はコストがほぼ無く、データタグは
531 回で合わせても小さいので、既定を設定する仕組みを広げる理由が無い。

## 横架材の作り直しを 2 回から 1 回へ（`doRegen=false`）

構造材の `ResetObject`（6.5 秒）と `CreateCustomObjectPath`（6.3 秒）がほぼ同額なのは、
**作った時点で 1 回・`ResetObject` で 1 回の計 2 回再計算している**から
（[#81](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/81)）。
`CreateCustomObjectPath(..., doRegen=false)` で作れば作った時点の 1 回が無くなる。

以前はここを「Findings の検証が鉛直のパスだけ」として見送っていたが、
[#109](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/109) の答えで
**部材の向きを問わない**と確定した（[Findings「Parametric Objects」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Parametric%20Objects.md)
の「`doRegen=false` は速い…」）:

- 規則は「0 長のパス」ではなく**「両端の Z の差が 0 のパス」**。Z の差があると 1 回目の
  `ResetObject` が「バウンドの span ＋ 渡した Z の差」を返す。平面上の長さは関わらない。
- 本プラグインの `CreatePath` は M27 から**両端とも同じ Z（`kPathPlaneZ`）**で作っているので、
  横架材・柱・垂木のどれもそのまま条件を満たす。
- 端部オフセットとプラグインスタイルを適用しても結論は変わらない。退化した材の自己修復
  （`SetCustomObjectPath` → もう一度 `ResetObject`）も `doRegen=false` の材で機能する（自己修復は
  のちに撤去した。[M27「自己修復を仕組みごと畳んだ」](milestones/m27-zero-length-column/self-repair.md#自己修復を仕組みごと畳んだ)）。
- 実測（新規の空図面・30 本）は水平材で 1 本 27.1ms → 14.6ms。

そこでまず **横架材だけ**を `doRegen=false` にし（PR #136）、実機で確かめてから**構造材すべて
（横架材・柱・垂木）**へ広げた。3 つとも `draw/StructuralMember` の `DrawStructuralMember` を
通り、パスも同じ `CreatePath` で作るので、切り替えのフラグは持たず `CreateCustomObjectPath` の
呼び出し 1 か所で常に `false` を渡す。

**見込み**: 横架材は構造材 517 本のうち大半なので、「構造材:オブジェクト生成」がほぼ横架材の
本数ぶん減る（6.3 秒の大部分）。「構造材:リセット」の合計は変わらないはず——再計算の
**回数**が減るのは作成のほうで、`ResetObject` 自体は 1 本 1 回のままである。

**実機で確かめること**（速さは所要時間の計測、描画結果は目視）:

- 横架材の高さ（天端）と傾斜梁の勾配が従来どおりか。開発ビルドの検算「両端の絶対 Z」が
  食い違いを数えていないか。
- 横架材の色・線がクラスに従っているか。再計算が既定のクラスを設定している間に走らなく
  なった（`ScopedCreationClass` を抜けた後の `ResetObject` 1 回だけになった）ので、
  オブジェクトが継承した by-class が再計算で保たれるかをここで確認する（Findings の実測では
  per-object の 6 フラグは再計算で解除されていない）。
- 自己修復（パスの再生成）が走った本数が増えていないか（自己修復はのちに撤去した。上記）。

**実機の数字（round 1・PR #136）**: 「構造材:オブジェクト生成」6,337ms → 2,873ms（横架材 266 本 ×
約 13ms＝再計算 1 回ぶんとほぼ一致）、「構造材:リセット」は 6,648ms で不変、所要 41.3〜44.3 秒 →
37.7 秒。検算（潰れ・両端の絶対 Z）の食い違いは 0 で、描画結果（高さ・勾配・クラスの色）も従来どおりと
目視で確認できた。

**実機の数字（PR #138 round 1・`build=a222d81`。柱・垂木まで入ったビルド）**: 「構造材:オブジェクト生成」
6,337ms → **383ms**（517 本すべてで作った時点の再計算が無くなった）、「構造材:リセット」6,776ms で不変、
検算（潰れ・両端の絶対 Z）の食い違い 0。**ただしこの周は前の取り込みが残った図面（取り込み前から
在ったレイヤ 38 枚）に重ねて描画しており、所要（235.8 秒）と描画結果は比較に使えない**——重くなったのは
ラベル（44→3,042ms/回）・通り芯（約 35 秒）・非 PIO の `SetObjectClass`（0.29→11.7ms/回）と、
今回変更していないところばかりで、図面の大きさに影響されたと読める。**時間を比べる周は空の
テンプレートから始めること**（「図面の状態」の枚数が前の周と揃っているかを先に確認する）。

## 打ち切った候補（もう一度やらないこと）

実測で「効果が無い」と分かったもの。**再調査しない。**

- **PIO のパラメータ名の解決をキャッシュする。** 1,421 回で 9ms。
  （SDK リファレンス [#82](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/82)
  は知見としては残るが、速さのためにやる理由は消えた。）
- **クラス名 → 索引（`AddClass`）をキャッシュする。** 2,025 回で 4ms。
- **`B` / `D` の二重書きをやめる。** パラメータ書き全体で 1,421 回・58ms。
- **プラグインスタイルの関連付けを減らす。** 463 回で 1ms。
- **`InsertNewComponentN` の直後の `SetComponentWidth` が二重書きではないかを疑う。**
  幅・名前・クラス・属性はいずれも 57 回で 0ms。構成層で時間を消費するとしたら挿入（240ms）と
  削除（98ms）だけで、しかも上記のとおり周ごとに大きくばらつく。
- **データタグの材料（VCOM の取得・文字スタイルの引き当て・式の組み立て）を共通化する。**
  タグのレイアウト・引出線・実測はいずれも数 ms。重いのは `UpdateDataTag` の方で、これは
  本文を作る本体なので減らせない。
- **レイヤ切替の呼び出しを減らす。** 1,216 回で 172ms。
- **ビューポートのクラス表示・表示レイヤの絞り込みを減らす。** 35 回で 7ms / 5ms。
